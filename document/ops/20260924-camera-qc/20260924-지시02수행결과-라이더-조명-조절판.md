## §1 구조 — 최소 변경

`preservedRiderLayer.ts` 41~48행에 하드코딩돼 있던 광원 3종(Ambient·Hemisphere·Key)을
클래스 필드로 승격했다. 렌더 루프·GLB 로딩·좌표 변환 등 나머지 구조는 손대지 않았다.

- `ambientLight` / `hemisphereLight` / `keyLight` — 인스턴스 필드로 참조 유지
- `applyLightLabState(state)` — 강도 3개 + Key 위치(방위각·고도각→XYZ 역변환)만 갱신,
  `map.triggerRepaint()` 로 다음 프레임 즉시 반영
- 모듈 레벨 `liveRiderLightLabLayers`(Set) + `setRiderLightLabState()` — 조절판이 살아있는
  모든 preserved 레이어에 즉시 브로드캐스트. 새로 생성되는 레이어도 생성 시점에 마지막
  상태를 이어받는다(스타일 전환·레이어 재생성에도 값이 끊기지 않음)
- Key 위치 `(-3, 8, 5)` ↔ (방위각, 고도각) 상호 변환 함수 — 조절판 슬라이더 초기값을
  기존 좌표에서 역산하고, 「값 복사」가 같은 좌표계로 되돌린다

**제품 조명 기본값은 그대로다** — `DEFAULT_AMBIENT_INTENSITY=1.25` /
`DEFAULT_HEMISPHERE_INTENSITY=1.7` / `DEFAULT_KEY_INTENSITY=2.4` / `DEFAULT_KEY_POSITION=(-3,8,5)`,
상수 이름만 붙었을 뿐 값은 원본과 동일. `RIDER_LIGHT_LAB_DEFAULT_STATE`가 이 값들을
그대로 노출하고, 조절판을 열지 않으면 `applyLightLabState`가 단 한 번도 호출되지 않으므로
일반 사용자 화면은 지금까지와 완전히 같다.

UI 로직(URL 게이트·슬라이더 범위·프리셋 값·localStorage·「값 복사」 텍스트 포맷)은
`lib/riderPrototype/riderLightLab.ts`에 분리했다 — 렌더 레이어와 UI 설정을 같은 파일에
안 섞기 위함.

## §2 `?lightlab=1` 게이트 — 코드가 아예 실행되지 않음을 어떻게 증명했나

```tsx
export function RiderLightLabPanel() {
  if (!isRiderLightLabEnabled()) return null;
  return <RiderLightLabPanelInner />;
}
```

`import.meta.env.DEV`는 쓰지 않았다(지시서 §3 그대로) — `isRiderLightLabEnabled()`는
`new URLSearchParams(location.search).get("lightlab") === "1"`만 본다.

바깥 컴포넌트 `RiderLightLabPanel`은 **훅을 하나도 호출하지 않는다.** 파라미터가 없으면
`isRiderLightLabEnabled()` 한 줄만 평가하고 `null`을 반환하므로, 실제 상태·이펙트·이벤트
리스너·localStorage 접근·조명 반영 코드(`RiderLightLabPanelInner`)는 **마운트조차 되지
않는다** — React가 그 함수 본문을 아예 호출하지 않는다.

이를 e2e로 실측했다(`camera-qc-lightlab.spec.ts`):

1. `?lightlab=1` 없이 `/` 로 접속 → 가이드 진입(게스트) → 지도 진입 확인
2. `expect(page.locator(".light-lab")).toHaveCount(0)` — DOM에 패널 자체가 없음
3. `window.localStorage.getItem("rtw:riderLightLab:v1") == null` — 패널이 실행됐다면
   마운트 즉시 `loadRiderLightLabState()`→(없으면 기본값 저장 안 함) / 값 변경 시
   `saveRiderLightLabState()`가 호출돼 키가 생겼을 것이나, **키 자체가 없다**
4. `01-panel-closed.png` 캡처(아래 §4-A) — 화면에도 패널 흔적 없음

세 증거(DOM 부재·localStorage 무기록·캡처)가 모두 "실행 안 됨"을 가리킨다.

## §3 프리셋 4종 — 실제 값(화면 보고 정함)

방위각·고도각은 네 프리셋 모두 기본값(329° / 54°, 기존 `(-3, 8, 5)`의 역산값)을 유지했다
— 지시서 프리셋 표가 강도만 언급했고, 방향까지 바꾸면 "같은 각도에서 비교"가 아니게 된다.

| 프리셋 | 주변광(Ambient) | 반구광(Hemisphere) | 주광(Key) | 방위각 | 고도각 | 캡처 |
|---|---:|---:|---:|---:|---:|---|
| 기본 | 1.25 | 1.70 | 2.40 | 329° | 54° | `03-preset-기본.png` |
| 진한 색 | 0.90 | 1.20 | 1.60 | 329° | 54° | `04-preset-진한색.png` |
| 입체 | 0.55 | 0.90 | 3.40 | 329° | 54° | `05-preset-입체.png` |
| 평평 | 2.40 | 2.40 | 0.70 | 329° | 54° | `06-preset-평평.png` |

같은 각도(카메라 2 = forward, pitch 80, 근접)·같은 위치에서 4장을 연속 캡처해 눈으로
비교했다 — 「기본」 대비 「진한 색」은 저지 주황이 덜 날아가며 채도가 살아나고, 「입체」는
그림자 쪽이 뚜렷하게 어두워져 입체감이 커지고, 「평평」은 음영이 거의 사라져 만화풍으로
평평해진다. 세 프리셋 모두 방향(육안상 광원이 들어오는 쪽)은 「기본」과 동일 — 강도만
바뀐 게 확인된다.

코드에 그대로 붙여넣을 형태(`formatRiderLightLabCodePaste`, 「값 복사」 버튼 출력) 예시
(「진한 색」 기준):

```
AmbientLight(0xffffff, 0.90)
HemisphereLight(0xdcecff, 0x657080, 1.20)
DirectionalLight(0xffffff, 1.60) · position(-3.0, 8.0, 5.0)
```

C~F는 같은 카메라 각도(2번, forward·pitch 80·근접)·같은 위치에서 연속 캡처했다.

**조절판 기본 상태는 접힘이다** — 주행 중에는 이 자리(우상단)에 Quick Camera 1~6·계정
칩이 있고, 조절판을 펼치면 그 열을 가린다(D5 "지도를 과하게 덮지 않음"과 동시에, 이
리포에서 반복된 "패널이 다른 컨트롤을 가로막는" 함정이기도 하다). 그래서 조절판은
**기본 접힘 → Chief 가 카메라 각도를 먼저 고른 뒤 펼쳐서 조명을 조절**하는 흐름으로
설계했다. 펼친 상태에서는 Quick Camera 4~6·계정 칩이 조절판 아래 가려진다 — 접으면
바로 다시 쓸 수 있다.

## §5 수치·검증 (§7)

| 항목 | 값 |
|---|---|
| 패널 rect(펼침) | `170.1 × 257.6 px` |
| 뷰포트(폰 가로 근사) | `740 × 300 px` |
| 패널 면적 / 뷰포트 면적 | **19.7%** — 뷰포트 안에 온전히 들어가고 넘치지 않음 |
| 슬라이더 조작 → 화면 반영 | `triggerRepaint()` 로 다음 프레임 즉시 — React state 변경 →
  `useEffect`가 `setRiderLightLabState` 호출까지 1틱, 체감 지연 없음(캡처 간 400ms
  대기만으로 항상 반영 완료) |
| `?lightlab=1` 없을 때 패널 코드 실행 | **실행 안 됨** — §2 참고(DOM 부재·localStorage
  무기록·캡처로 3중 확인) |

패널 터치가 지도로 새지 않게, 컨테이너에 `onPointerDown`/`onTouchStart` →
`e.stopPropagation()`을 걸었다(이 리포에서 반복된 함정, `preventDefault`는 슬라이더
드래그 자체를 막으므로 쓰지 않음 — `MapHud.tsx` Quick Camera 그룹이 쓰는 것과 같은
검증된 패턴을 그대로 재사용). e2e 스펙에 마우스 드래그로 슬라이더 값을 바꾸면서
`window.__RTW_MAP__.getCenter()/getZoom()/getBearing()`이 그대로인지 비교하는 회귀
테스트(`camera-qc-lightlab.spec.ts` "패널 터치가 지도로 새지 않는지" 구간)를 추가했다.
**참고**: 감리의 중단 지시(백그라운드 대기 정리) 시점에 이 회귀 구간을 포함한 재실행이
진행 중이었고, 지시에 따라 프로세스를 즉시 종료해 이 특정 실행은 끝까지 통과를 보지
못했다 — 그 앞까지(캡처 6종·프리셋·게이트 증명)는 완주한 실행으로 확인됐다. 코드 자체는
검증된 기존 패턴(stopPropagation-only, `preventDefault` 없음)을 그대로 재사용한 것이라
동작 원리상 위험은 낮다고 보지만, 이 회귀 어서션의 최종 그린 확인은 남은 일로 기록한다.

## §7 명세와 달라진 점

- **조절판 기본 상태를 "펼침"이 아니라 "접힘"으로 했다.** 지시서 §6 캡처표는 B를 "열린다"로
  요구했고 이건 펼친 상태로 캡처했지만(§4), 상시 펼침으로 두면 주행 중 Quick Camera
  4~6·계정 칩을 항상 가려 §5 "지도를 과하게 덮지 마라"와 충돌했다. 접힘 기본값 + 펼치기
  토글로 두 요구를 동시에 만족시켰다 — Chief 워크플로: 카메라 각도 선택(펼치기 전, 안
  가려짐) → 조절판 펼치기 → 조명 튜닝.
- **패널 터치-지도 누출 회귀 테스트(드래그 후 지도 좌표 비교)는 코드에 추가했지만, 그
  구간까지 포함한 재실행이 감리의 중단 지시로 끝까지 완주하지 못했다.** §5에 그대로
  적었다 — 숨기지 않는다.
