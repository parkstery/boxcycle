## 1. 답 — **A. 우리 우회 waypoint**

중복은 **`detoured` 에 몰려 있다.** `detourCalls = 0` 인 `exact`·`offered`(= provider 직행 경로를 자른 것)는 거의 0 이다.

| outcome | 표본 | 평균 중복 | 최대 중복 |
|---|---:|---:|---:|
| **detoured** | 8 | **3.7 %** | **17.1 %** |
| exact | 4 | 0.8 % | 3.2 % |
| offered | 12 | 0.4 % | 3.2 % |

그리고 **우회 호출을 많이 쓸수록 중복이 커진다** — 예산(12)을 다 쓴 표본이 최악이다.

| 표본 | detourCalls | 중복 | 지나간 셀 수 |
|---|---:|---:|---:|
| 45°/400m | **12** (예산 소진) | **17.1 %** | 22 |
| 315°/400m | 6 | 8.2 % | 21 |
| 0°/400m | 5 | 3.4 % | 29 |
| 135°/400m | 6 | 0.8 % | 31 |
| 나머지 detoured 4건 | 1–6 | 0.0 % | 28–30 |

셀 수가 같이 떨어지는 것이 핵심이다 — 같은 700 m 를 달리는데 **지나간 땅이 22 셀뿐**이면 나머지는 되밟은 것이다.

**B(provider 가 일방통행 때문에 블록을 돎)도 0 은 아니다.** `135°/600m`(exact)·`225°/600m`(offered) 에서 3.2 %·2.1 % 가 나왔다. 다만 규모가 A 의 1/5 이고, `detourCalls = 0` 이므로 우리가 만든 것이 아니다. **이번 수정의 주 대상은 A** 이고, B 는 후보 선택에서 걸러내는 부수 효과로 처리한다.

### 근거 — 계측 방법

UI 를 거치지 않고 **서버와 같은 코드 경로**를 직접 돌렸다(`g5a-probe.mjs`). `searchDistanceAutoRoute` 에 `functions/src/index.ts:270 fetchDirectionsRoute` 와 동일한 형태의 실제 Mapbox Directions 호출을 물렸다. 무대는 Chief 조건 그대로다 — **강남 논현·역삼 `[127.0347, 37.5051]` · 자동차 · 목표 700 m**, 8방위 × 직선거리 400/600/850 m = **24 표본**.

원자료 `g5a-probe-samples.json`, 판정 출력 `g5a-overlap-report.txt`.

## 2. §4.1 중복 측정 기준 — 정복 셀(z20) **재방문 run**

정복과 같은 기준을 골랐다(§4.1 권장). `conquestCellIdAt` 와 같은 z20 타일(위도 37.5 에서 **약 30 m**)로 경로를 3 m 조각으로 훑어 셀에 귀속시킨다.

**중요 — 첫 시도는 축퇴됐다.** 「이미 본 셀의 미터는 전부 중복」으로 세니 **직선 700 m 가 91.6 % 중복**으로 나왔다. 셀 안에 30 m 를 머무는 정상 주행을 중복으로 센 것이다.

고친 정의: 연속 구간을 **run** 으로 묶고, **떠났다가 다시 들어온 셀의 run** 만 중복으로 센다.

M0 자가 검산을 판정 앞에 세웠고, 통과해야 표본 계산으로 넘어간다.

```
M0 직선 700m   → 0.0 %   (0 % 여야 함)
M0 왕복 350m×2 → 46.2 %  (약 50 % 여야 함)
```

왕복이 50 % 가 아니라 46.2 % 인 것은 반환점 셀이 한 run 으로 합쳐지기 때문이다. 셀 크기(30 m) 대비 오차이며 판정에 영향이 없다.

### 다른 기준과의 차이

선분 근접·방위 반대로 재는 방법도 있다. 셀 기준을 고른 이유는 **HUD 「새 도로 +N km」와 어긋나지 않기 때문**이다. 사용자가 화면에서 보는 손실과 우리가 최적화하는 값이 같은 단위여야 한다. 대신 셀 기준은 **30 m 보다 좁은 되밟기(같은 도로 반대 차선 등)를 잡지 못한다** — 그건 정복도 못 잡으므로 손실도 아니다.

## 3. §2.1 문구 수치 모순 — 산술은 감리가 맞다. 다만 원인은 아직 확정 못 했다

### 감리 산술 확인

`formatDistanceAutoRouteOfferedMessage(directRoadMeters, targetKm)` 는 `directRoadMeters/1000` 과 `targetKm` 를 각각 `toFixed(1)` 로 찍는다. `offered` 는 `directRoadM > D + 150` 에서만 나온다.

**D = 700 m 이면 `offered` ⟹ directRoadM > 850 ⟹ 표시값 ≥ 0.9.** 0.7/0.7 은 불가능하다. 감리 계산이 맞다.

내 24 표본의 `offered` 12건은 전부 directRoad **930–1438 m** 로 계약을 지킨다. 브라우저로 잡은 실제 화면 1건도 내부적으로 일관됐다.

```
[5A] 동 outcome=offered directRoad=3244.5m dist=700.0m detourCalls=0 endMiss=1798.7m
[5A] 동 문구: 클릭 지점까지는 도로로 3.2 km 입니다. 목표 0.7 km 지점에서 종료했습니다.
```

**즉 문구 공식 자체는 정상이다.** 0.7/0.7 을 재현하지 못했다.

### 재현 중 발견한 것 — 슬라이더와 숫자 입력이 어긋난다

브라우저 계측에서 목표 0.7 을 넣었을 때:

```
[5A] 목표 거리 적용값 number=0.7 slider=0.5
```

`DISTANCE_AUTO_ROUTE_KM_STEP = 0.5` 라 **슬라이더는 0.7 을 표현할 수 없다.** 숫자 입력은 0.7 을 받고 서버도 700 m 로 검색하는데(`dist=700.0m` 확인), **슬라이더만 0.5 를 가리킨다.**

Chief 화면의 「슬라이더 0.7」은 실제로는 숫자 입력이었을 가능성이 높고, 이 어긋남이 「화면과 실제가 다르다」의 한 갈래다. 4A ②(거리 조정 후 슬라이더가 옛 값)와 같은 계열이며, **그때 고친 것은 조정 재탐색 경로였고 이 눈금 불일치는 남아 있다.**

### Chief 께 확인 요청

0.7/0.7 을 만들려면 `directRoadM ∈ [650, 750)` 이면서 `offered` 여야 하고, 그건 **D ≤ 550 m** 일 때만 가능하다. 슬라이더가 0.5(=500 m)로 스냅된 상태로 검색됐다면 `directRoad 0.7 km` → `offered` 가 성립하고, 그때 문구는 **「도로로 0.7 km … 목표 0.5 km」** 가 된다.

**화면의 「목표 0.7 km」가 문구 안의 값이었는지, 아니면 슬라이더·숫자 입력 값이었는지**를 알려 주시면 갈립니다. 스크린샷이 있으면 그 한 줄이면 됩니다.

## 4. 다음 단계 (착수 전 · 승인 대기)

원인이 A 로 확정됐으므로 §4.2 는 **Stage 1 우회 후보 선택**을 바꾸는 작업이다.

1. 중복 측정 함수를 제품 코드로 옮긴다(순수 함수 + 시험 3종, §5.1).
2. `trySide` 가 **먼저 수렴한 후보를 즉시 채택**하는 것을 바꾼다 — `f(r) ∈ [D, D+150]` 를 만족하는 후보를 모아 **중복이 낮은 쪽**을 고른다. 거리 hard constraint(±5 m)와 provider 예산(12)은 그대로다. 호출을 더 하지 않고 **이미 뽑은 후보를 다르게 고르는** 것이므로 §4.4 를 지킨다.
3. 응답에 중복 비율을 실어 UI 가 알린다(§4.3). 임계값은 이번 계측 기준 **detoured 평균 3.7 % · 최대 17.1 %** 이므로, 「의미 있게 높음」의 후보는 **10 %** 다(700 m 에서 70 m). 확정 전에 §4.2 적용 후 재계측해 정한다.

**아직 코드를 고치지 않았다.** §2 가 「추정으로 고치지 말고 원인부터 답하라」였으므로 여기서 멈추고 보고한다.

## 5. 감리 지시 중 짚을 것

1. **§2 의 A/B 이분법은 대체로 맞지만 배타적이지 않다.** `exact`(detourCalls 0)에서도 3.2 % 중복이 나왔다 — provider 경로 자체가 조금 돈다. 다만 A 가 지배적(최대 17.1 % vs 3.2 %)이므로 대응 우선순위는 A 다.

2. **§4.1 「같은 셀을 두 번 지나면 두 번째는 새 도로가 아니다」를 그대로 구현하면 축퇴된다.** 직선 주행이 91.6 % 중복으로 나온다. 「셀을 떠났다가 다시 들어온 경우」로 좁혀야 한다. 지시서 문구만 따랐다면 잘못된 임계값을 정할 뻔했다.

3. **§2.2 의 「콘솔에서 찍어 보고」는 `providerCallCount` 를 주지 않는다.** 클라이언트 DEV 로그(`useDistanceAutoRoute.ts:305`)에는 `algorithmVersion`·`endMissMeters`·`directRoadMeters`·`outcome` 만 있고 `providerCallCount`·`detourCalls` 는 서버 로그(`distanceAutoRouteDiagnostics`)에만 있다. 서버 코드를 직접 호출하는 방식으로 둘 다 얻었다.
