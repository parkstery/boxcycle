## 0. 무엇이 바뀌었나 — R1 과의 차이

R1 은 「부족분을 **방향 확장**으로 채운다」였다. Chief 가 **「채우지 말고 안내한다」**로 바꿨다.

> 거리가 짧은 경우 중복된 경로를 탐색하고 표시하기보다는 「N km 가까운 지점을 클릭해 주시기 바랍니다」라는 메시지를 내보내는 게 낫다.

**R1 §3.1(λ̂ 유도 확장)은 구현하지 않는다.** R1 §3.2(우회 3순위 강등)·§3.4(중복 페널티)·§4(폰 fitBounds)는 유효하다.

### 0.1 이 지시서의 범위 — 4건

| # | 내용 | 근거 |
|---|---|---|
| A | 짧은 클릭은 **안내·실패**(Token 환불). 우회로 중복을 만들지 않는다 | Chief |
| B | **도넛**으로 클릭 권장 범위를 표시 | Chief |
| C | **「N km 로 늘려 클릭 지점까지 가기」 버튼 제거** | Chief |
| D | 슬라이더 → **칩 + 예상 시간 + 기본값 5 km** | Chief 승인(우선순위 1·2·3) |

D 의 우선순위 4(구간별 step)·5(상한 축소)는 **칩이 슬라이더를 대체하므로 불필요**해져 범위에서 뺐다.

## 1. A — 짧은 클릭은 안내하고 실패시킨다

### 1.1 판정

```
road(start→click) < D − EXACT_TARGET_DISTANCE_TOLERANCE_M
  → 실패 · Token 환불 · 안내 문구
```

문구는 **실측값으로** 만든다. 「더 멀리」 같은 막연한 말은 쓰지 않는다.

```
너무 가깝습니다 — 도로 1.2 km · 목표 3.0 km. 원 주변이나 바깥을 클릭해 주세요.
```

### 1.2 우회를 이 경로에서 빼라

지금은 이 조건에서 Stage 1 우회가 발동해 중복을 만든다(계측 최대 17.1 %). **`road < D` 에서 우회를 호출하지 않는다.**

우회 코드 자체는 **지우지 마라.** R1 §3.2 대로 다른 폴백 경로에 남긴다. 이 조건에서만 호출하지 않는 것이다.

### 1.3 비대칭은 의도된 것이다

「너무 멂」은 자동 처리(`offered` — D 지점에서 자름)인데 「너무 가까움」은 안내·실패다. 비대칭이지만 근거가 있다.

- **자르기는 중복을 만들지 않는다.** 사용자가 가리킨 방향 안에 머문다.
- **늘리기·우회는 중복을 만든다.** 사용자가 가리키지 않은 영역으로 나간다.

3F-C-R1 의 「실패를 없앤다」 원칙을 일부 되돌리는 것이지만, **그때 실패가 나빴던 이유는 안내가 틀렸기 때문**이다. 이번엔 B 의 도넛이 어디를 클릭할지 정확히 보여주므로 사용자가 시행착오를 하지 않는다.

## 2. B — **원 하나**. 도넛은 그리지 않는다

### 2.1 Chief 결정 (2026-09-05)

> 도넛을 그릴 필요는 없고 전과 같이 **선택한 거리를 반지름으로 하는 원 하나**만 있으면 되겠다.
> 안내 문구: **「{N} km 반경의 원 주변 도로를 선택하세요」**

이전 판의 도넛(`[0.67D, D]` → 정정 후 `[D, 1.5D]`)을 **폐기**한다. 원 하나 + 안내 문구로 간다.

### 2.2 감리 오류 기록 — 권장 구역을 거꾸로 잡았다

최초 판은 도넛을 `[0.67D, D]` 로 잡았다. 그 구간은 **부족분이 발생해 우회·중복을 부르는 구간**이다. Chief 가 화면에서 「도넛을 클릭해도 이전 프로세스가 그대로 반복된다」고 지적한 것이 정확하다.

원인은 목적을 잘못 잡은 것이다 — 감리는 「**클릭 지점에서 끝날 가능성이 있는 구간**」을 권장으로 삼았는데, 권장해야 할 것은 「**중복 없이 목표 거리를 얻는 구간**」이었다. 「늘려」 버튼을 없애기로 한 시점(§3)에 클릭의 역할은 이미 **방향**으로 정해졌으므로, 클릭 지점 도달을 기준으로 삼을 이유가 없었다.

### 2.3 원 = 반지름 D. 그 근거

도로거리는 직선거리보다 항상 크거나 같다(λ ≥ 1). 따라서

> **직선거리 ≥ D ⟹ 도로거리 ≥ D ⟹ 부족분 없음 ⟹ 우회 없음 ⟹ 우리가 만드는 중복 없음**

부등식이므로 반례가 없다. **원의 반지름은 D 로 고정한다.**

### 2.4 「주변」이 안전한 이유 — 살짝 안쪽도 대체로 성공한다

실패 조건은 `직선 < D` 가 아니라 **`도로 < D`** 다. 도로거리가 직선거리보다 크므로, 원 **안쪽으로 조금** 들어간 클릭도 대체로 성공한다.

| 직선거리 | λ=1.0 | λ=1.15 | λ=1.3 |
|---:|---|---|---|
| 0.70 D | 실패 | 실패 | 실패 |
| 0.80 D | 실패 | 실패 | **성공** |
| 0.90 D | 실패 | **성공** | 성공 |
| 0.95 D | 실패 | **성공** | 성공 |
| **1.00 D** | **성공** | **성공** | **성공** |

- 원 **위·바깥**은 보장 성공이다.
- 원 **바로 안쪽**(0.9~1.0 D)은 그 방향의 도로가 조금이라도 굽어 있으면 성공한다. 강남처럼 격자가 아닌 곳에서는 대부분 성공한다.
- 확실한 실패는 **0.8 D 미만**이다.

그래서 「원 주변」이라는 안내가 실무적으로 안전하다. 안쪽 깊이 클릭한 경우만 §1 의 실패·안내로 걸린다.

### 2.5 구현

- 원은 **파선 하나**. 이전 도넛의 두 번째 링·채움을 제거한다.
- 안내 문구는 방향 선택 모드에서 상시 노출: **`{N} km 반경의 원 주변 도로를 선택하세요`** — `{N}` 은 현재 목표 거리를 소수 한 자리로.
- 목표 거리를 바꾸면 원과 문구가 **즉시** 따라간다.
- §1 실패 문구는 유지하되 원과 말이 맞아야 한다: 「너무 가깝습니다 — **원 주변이나 바깥**을 클릭해 주세요」.

### 2.6 provider 중복은 이것으로 안 없어진다

부등식이 막는 것은 **우리가 만드는 우회**뿐이다. 5A-1 계측에서 `exact`·`offered` 에도 0.4~0.8 %(최대 3.2 %) 중복이 있었다 — Mapbox 가 일방통행 때문에 블록을 도는 것이다.

**R1 §3.4 중복 페널티는 그대로 구현한다.** 원은 우회를 없애고, 페널티는 남은 provider 중복을 줄인다. 둘 다 필요하다.

## 3. C — 「N km 로 늘려 클릭 지점까지 가기」 제거

### 3.1 Chief 근거

> 이미 기본 기능으로 start · end · waypoint 를 가지고 있어 user 가 원하는 지점을 선택하는 것은 기본 기능에서 충분히 가능하다.

맞다. 그리고 **이 버튼이 중복 버그를 스스로 만들고 있었다.**

```ts
// useDistanceAutoRoute.ts:404
const rawAdjustedKm = Math.ceil((offered.directKm * 1000) / 100) * 100 / 1000;
```

`directRoadM = 4,340 m` → **올림해서 목표를 4,400 m 로 설정** → 목표가 실측 도로거리보다 60 m 크다 → **부족분 발생 → 우회 발동 → 중복.** 사용자를 도우려던 기능이 스스로 부족분을 만들어 우회를 불렀다.

### 3.2 제거 범위

- 버튼 UI
- `handleDistanceAdjustRetry`·`offeredState.adjustLabel`·`formatDistanceAutoRouteAdjustRetryLabel`
- 「거리 조정 재탐색 1회 무료」 Token 정책과 그 시험 — **재탐색이 없어지므로 함께 제거**
- `offered` 고지 문구 자체는 **유지**한다(고스트 마커·점선 포함). 없애는 것은 버튼뿐이다.

관련 시험이 깨지면 **삭제가 맞는지 판단하고 근거를 남겨라.** 기능이 사라졌으니 시험도 사라지는 것이 정상이다.

## 4. D — 슬라이더를 칩으로 대체한다

### 4.1 지금 문제

```
0.5 ~ 120 km · step 0.5  ⇒  눈금 240개
폰 팝업 슬라이더 폭 ~200 px  ⇒  한 눈금 1 px 미만
```

손가락으로 특정 값을 고르는 것이 물리적으로 불가능하다.

### 4.2 칩으로 **대체**한다 — 추가가 아니다

```
목표 거리   [1] [3] [5] [10] [20]        − 5.0 +
            약 12분 (내 평균 24.3 km/h)
```

- **슬라이더를 없앤다.** 칩이 그 자리를 대신하므로 팝업이 커지지 않는다 — 3D-2 의 공간 최적화를 되돌리지 않는다.
- 미세 조정은 **이미 있는 `±` 버튼과 숫자 입력**이 맡는다. `±` 는 0.5 km 단위를 유지한다.
- 20 km 초과는 숫자 입력으로. 드문 경우에 UI 공간을 쓰지 않는다.
- `DISTANCE_AUTO_ROUTE_KM_MIN/MAX`(0.5~120)는 **그대로 둔다.** 기능적 범위는 유지하고 UI 만 바꾼다.
- 칩 값 `[1, 3, 5, 10, 20]` 은 시작점이다. 더 나은 조합이 있다고 판단하면 근거와 함께 제안하라.

### 4.3 예상 시간 — 본인 평균 속도로 계산한다

일반적인 20~25 km/h 가정 대신 **사용자의 실제 누적 평균**을 쓴다. 이미 갖고 있다.

```
users/{uid}.mileageTotalMeters
users/{uid}.mileageTotalSec        ← useUserTier.ts:31-32
```

- 평균 속도 = `mileageTotalMeters / mileageTotalSec`. 표시 예: `약 12분 (내 평균 24.3 km/h)`
- **누적이 없거나 비정상이면**(0·NaN·비현실적 값) 기본값으로 폴백하고 「내 평균」 표기를 빼라. 신규 사용자가 대부분 여기 해당한다.
- 폴백 기본 속도는 근거를 적어라. 축퇴값(0·상수)이 조용히 통과하지 않도록 방어한다.

### 4.4 기본값 5 km

기존 기본값을 **5 km** 로 바꾼다. 근거는 이 제품의 구조다 — 이어 달리기 루프가 핵심이고, Token 이 경로당 1개이며, 정복은 20 km 한 번보다 5 km 네 번이 더 다양한 새 도로를 얻는다.

## 5. 시험

1. **A 판정** — `road < D − 5m` 에서 실패·Token 환불·문구에 실측값 포함. 우회가 호출되지 않음을 assert.
2. **중복 회귀** — 5A-1 의 24 표본 재측정. `detoured` 평균 중복 **3.7 % → 유의미 감소**. 표본·조건 동일. **이번 작업의 성패다.**
3. **B 경계** — 원 반지름 = **D** 임을 assert. `직선 ≥ D` 인 입력이 「너무 가까움」으로 실패하지 않음을 **전수** assert(부등식이므로 반례가 없어야 한다). 목표 거리를 바꾸면 원 반지름과 안내 문구의 `{N}` 이 함께 갱신되는지도 assert.
4. **B 안내 정직성** — `직선 ≥ D` 클릭에서 **우회가 한 번도 호출되지 않음**을 측정해 보고. 원 바로 안쪽(0.9~1.0 D) 구간의 실제 성공률도 함께 재어 §2.4 표와 대조.
5. **C 제거** — 버튼·핸들러·라벨이 사라지고 `offered` 고지는 남아 있음을 assert.
6. **D 예상 시간** — 누적 없음·0·비정상 입력에서 폴백하고 「내 평균」 표기가 빠지는지 assert.
7. 3E 거리 계약(±5 m) 회귀 유지. `test:distance-auto-route` 112건.
