## 1. 제품 원칙 (이 지시서의 상위 규범)

> **앱이 사용자를 돕는다. 사용자가 앱이 원하는 지점을 시행착오로 찾아 바치지 않는다.**

사용자의 클릭은 「이 도로 위 이 지점에서 끝내고 싶다」는 명확한 의사표시다. 앱의 책임은 두 가지뿐이다.

1. 가능하면 **클릭한 그 지점에서 끝나는** 목표 거리 Route 를 만든다.
2. 불가능하면 **어디까지 갈 수 있는지를 지도 위에 즉시 제시**한다. 「다른 위치를 클릭해 보세요」로 사용자를 되돌려보내지 않는다.

### 2.1 이 표에서 확정되는 사실

1. **사용자는 정확히 도로를 클릭하고 있다.** 6건 전부 클릭→최근접 도로 스냅 거리 **0~5m**. 「클릭 근처에 도로가 없다」는 문제는 존재하지 않는다. 실패는 100% 알고리즘 책임이다.
2. **직선 비율과 도로 거리 사이에 단조 관계조차 없다.** #2 는 비율 0.823 인데 도로 1.03D, #6 은 비율 0.995 인데 도로 1.38D 다. **비율이 더 작은 클릭이 도로로는 더 멀다.** 따라서 직선 비율로 그린 도넛은 튜닝 문제가 아니라 **원리적으로 성립하지 않는다.**
3. **λ(도로/직선)는 목표 거리 스케일에 따라서도 변한다.** 1km 표본에서 1.00~1.39, 5km 표본(전일 48표본)에서 median 1.387·max 3.78. 고정 `0.82 / 1.08` 은 어느 스케일에서도 맞지 않는다.
4. **실패 3건(#3·#4·#5)은 부족분이 각각 149m·268m·139m 에 불과하다.** 우회로 채우면 End 가 클릭에서 4~133m 다. 앱이 못 한 게 아니라 **시도조차 안 한 것**이다.
5. **#4 는 안내가 정반대다.** 「목표거리(1.0 km)까지 도달하려면 바깥 링 쪽을 클릭하세요」라고 했지만, 실제로는 도로거리 732m 로 목표에 **못 미치는** 클릭이며 우회로 1,004m·End miss 4m 라는 **6건 중 최상의 결과**가 나오는 지점이다.
6. **#6 도 안내가 반대다.** 도넛 한가운데(0.995)인데 도로로는 1.38D 라 도달 불가다. 사용자는 더 **안쪽**을 눌러야 하는데 메시지는 방향을 전혀 주지 않는다.
7. **인접한 두 클릭이 정반대 안내를 낸다.** #4 와 #5 는 약 120m 떨어져 있는데 하나는 「바깥을 클릭」, 하나는 「근처에서 못 찾음」이다. 안내가 잡음이다.

### 2.2 화면에서 관측된 UI 결함

- **가이드 링이 화면 밖에 있다.** 4·5·6번 화면에서 도넛은 지도 가장자리 호로만 보이거나 보이지 않는다. 사용자는 눌러야 할 곳을 볼 수도 없는 상태에서 클릭한다.
- **실패해도 수치가 하나도 안 나온다.** 서버는 `directRoadMeters` 를 이미 측정해 놓고 사용자에게 알려주지 않는다.
- **성공(2번 화면) Route 렌더 이상 의심.** 목표 1.00 km 인데 화면 하단으로 길게 뻗은 빨간 선이 함께 보인다. 절단 전 provider geometry 잔여 또는 이전 Route stale 렌더 가능성 — §6.5 에서 확인한다.
- Token 환불은 정상 동작한다(실패 시 3개 유지). 그러나 사용자의 클릭과 시간은 환불되지 않는다.

## 3. 새 계약 — 실패를 없앤다

`clickSnapM > 250m` (클릭 근처에 해당 profile 도로가 실제로 없음) 하나를 제외하면 **모든 클릭은 Route 를 반환한다.**

| 조건 | 동작 | 결과 |
|---|---|---|
| `road(Start→click) ∈ [D, D+150m]` | direct Route 를 D 에서 절단 | End = 클릭 지점. 정상 성공 |
| `road(Start→click) < D` | 우회 waypoint 로 부족분 충족 후 D 에서 절단 | End = 클릭 지점. 정상 성공 |
| `road(Start→click) > D+150m` | **direct Route 를 D 에서 절단해 그대로 제시** | End = 클릭 방향 도로 위 정확히 D 지점. **`offered` 성공** |
| `clickSnapM > 250m` | 실패·Token 환불 | 유일한 실패 |

세 번째 행이 이 지시서의 핵심이다. `road > D` 는 **실패시킬 이유가 없다.** direct Route 를 D 에서 자르면 사용자가 가리킨 방향·그 경로 위의 정확히 D 지점이 나온다. 방향 의도는 지켜지고 거리도 정확하다. 지금까지 이것을 실패로 처리해 사용자를 되돌려보낸 것이 「떠먹여 달라는 앱」의 정체다.

### 3.1 `offered` 응답의 고지 의무

`offered` 로 성공할 때 응답과 UI 는 다음을 **반드시** 포함한다.

- End 가 클릭 지점이 **아니라는** 사실.
- 실측 수치: 「클릭 지점까지는 도로로 **1.57 km** 입니다. 목표 **1.0 km** 지점에서 종료했습니다.」
- **원클릭 거리 조정 제안**: 「**1.6 km 로 늘려 클릭 지점까지 가기**」 버튼. 누르면 거리 slider 를 `ceil(directRoadM / 100) * 100 m` 로 올리고 **같은 클릭 좌표로 즉시 재탐색**한다.
- 이 재탐색은 **Token 을 추가 차감하지 않는다.** 앱이 못 맞춘 것을 사용자가 보정하는 행위이므로 같은 클릭에 대한 거리 조정 재탐색 1회는 무료다.

## 4. 알고리즘 (`searchDistanceAutoRoute` 재작성)

### Stage 0 — direct 측정 (provider 호출 1회, 항상 실행)

```text
route          = Directions(profile, [Start, targetRoadPoint])
clickRoadPoint = waypoints[last].location
clickSnapM     = waypoints[last].distance
directRoadM    = route.distance
```

- `clickSnapM > 250m` → 실패 `NO_ROAD_NEAR_CLICK_MESSAGE`, Token 환불, 추가 호출 없음.
- `directRoadM > D + 150m` → **Stage 2 로 직행**(절단 후 `offered` 반환). 우회는 거리를 늘릴 뿐이므로 **추가 provider 호출 금지**.
- `directRoadM ∈ [D, D+150m]` → Stage 2(절단 후 `exact` 반환).
- `directRoadM < D` → Stage 1.

### Stage 1 — 우회 충족

- `W(r, side) = offset(midpoint(Start, clickRoadPoint), bearing(Start→clickRoadPoint) ± 90°, r)`
- `f(r) = Directions(profile, [Start, W(r,side), clickRoadPoint]).distance`
- 초기 `r0 = (D − directRoadM) / 2`, 수렴 목표 `D ≤ f(r) ≤ D + 150m`.
- `f` 는 대체로 단조증가하나 도로망 불연속으로 튄다. **regula falsi 로 수렴시키고 개선이 없으면 이분으로 fallback** 한다.
- **호출 예산 8회.** `+90°` 쪽을 먼저 시도하고 4회 안에 `f ≥ D` 를 못 만들면 `−90°` 로 전환한다. 실측에서 3~5회 수렴이 다수였다.
- 예산 소진 시 `f ≥ D` 인 후보 중 초과 최소를 채택. 그것도 없으면 Stage 0 의 direct Route 를 `offered` 로 반환한다 — **여기서도 실패로 떨어뜨리지 않는다.**

### Stage 2 — 절단·검증·응답

- 정확히 D 에서 절단(기존 `clipRouteGeometryToTargetMeters`, ±5m 유지).
- `endMissM = distance(clippedEnd, clickRoadPoint)`.
- 응답에 `outcome: "exact" | "detoured" | "offered"`, `directRoadMeters`, `endMissMeters`, `detourCalls`, `providerCallCount`, `algorithmVersion` 을 포함한다.
- **hard gate**: `outcome ≠ "offered"` 인데 `endMissM > 200m` 이면 `offered` 로 강등하고 §3.1 고지를 붙인다. 클릭 지점에서 끝났다고 거짓 보고하지 않는다.
- `MAX_AUTO_ROUTE_PROVIDER_CALLS` 를 35 → **12** (Stage 0 1회 + Stage 1 8회 기준).

### 4.1 제거 대상

- `buildClickBearingReachEndpoints` — 클릭을 지나치는 후보. 삭제.
- `buildClickAxisEndpoints` / `CLICK_INTENT_AXIS_*` — 삭제.
- 자동 Route 경로에서의 `buildAutoRouteCandidates` / `AUTO_ROUTE_DISTANCE_FACTORS` / `AUTO_ROUTE_BEARING_OFFSETS_DEG` 사용.
- `classifyClickIntentFailureMessage` 전체 — 실패 사유가 하나뿐이므로 분기 자체가 사라진다. 직선 비율(`straightM < innerM` / `> outerM`) 분기는 **절대 남기지 않는다.**
- `CLICK_INTENT_END_MISS_FAIL_RATIO` / `CLICK_INTENT_END_MISS_FAIL_MAX_M` 완화치.
- `AUTO_ROUTE_CLICK_ZONE_INNER_RATIO` / `OUTER_RATIO` 및 도넛 geometry(`buildClickZoneDonut`).

### 4.2 provider 계약 확장

`FetchDirectionsFn(profile, start, end)` → `FetchDirectionsFn(profile, waypoints: LngLat[])`. 기존 2점 호출은 `[start, end]` 로 감싼다. harness fake provider 도 다점 입력을 지원해야 한다.

## 5. UI

1. **도넛 삭제.** 2중 링·채움·「바깥 링을 클릭하세요」 안내를 전부 제거한다.
2. **참고 원 1개만 유지**(선택). 반경 = 목표 거리 직선값, 흐린 파선, 문구는 「참고 — 실제 도로 거리는 방향에 따라 다릅니다」. 이것은 금지 구역이 아니라 눈금이다. 정확한 경계는 3F-D(방위별 실측 등도로거리 폴리곤)에서 다룬다.
3. **클릭 안내 문구**: 「도착하고 싶은 도로 위 지점을 클릭하세요」. 「어디를 클릭하라」는 제약 문구를 두지 않는다.
4. **`offered` 결과 표시**: End 마커를 `exact`/`detoured` 와 시각적으로 구분(예: 점선 테두리)하고, 사용자가 클릭한 지점에 회색 고스트 마커 + 두 점을 잇는 점선을 그려 **차이를 눈으로 보여준다**. 팝업에 §3.1 문구와 거리 조정 버튼을 배치한다.
5. **지도 자동 맞춤**: 목표 거리 변경 시 해당 거리 원이 화면 안에 들어오도록 `fitBounds`. 4·5·6번 화면처럼 가이드가 화면 밖에 있는 상태를 허용하지 않는다.
6. **개발용 raw click marker(보라 + 좌표)는 유지**한다. 3F-C-R1 검증에 계속 쓴다.
