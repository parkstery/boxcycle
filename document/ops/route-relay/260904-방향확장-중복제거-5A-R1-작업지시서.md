## 1. 계측 검수 — 원인 A 확정을 승인한다

`DISTANCE_AUTO_ROUTE_KM_STEP = 0.5` 를 감리가 직접 확인했다. 24 표본 계측도 결론이 명확하다.

| outcome | 평균 중복 | 최대 중복 |
|---|---:|---:|
| **detoured** | **3.7 %** | **17.1 %** |
| exact · offered | 0.4~0.8 % | 3.2 % |

**중복은 우회를 넣은 경로에만 몰려 있다.** 그리고 `detourCalls` 가 클수록 중복이 커지고 지나간 셀 수가 줄었다(12회 → 17.1 % · 22셀 vs 1~6회 → 0 % · 28~30셀).

**감리 설계 오류를 기록한다** — 3F-C-R1 §4 Stage 1 에서 우회 예산을 8~12회로 넉넉히 준 것은 「많이 시도할수록 좋다」는 가정이었다. **거리는 맞추지만 경로 품질을 망치는 방향이었다.** 계측이 그 가정을 반증했다.

§2.1 문구 모순(0.7/0.7)은 재현되지 않았고 문구 공식 자체는 정상임을 확인했다. **미해결로 남기되 이번 수정 후 재관찰**한다.

## 2. Chief 설계 결정 — 부족분은 우회가 아니라 방향 확장으로 채운다

> 클릭한 위치가 start 와 가까울 경우 중복이 발생한다. 이 경우 **경로 중복 피하기를 상위 우선순위**로 두고, start 로부터 클릭 위치보다 **더 먼 지점을 가상의 클릭 위치로 지정**해 경로 탐색을 진행한다.

이 결정은 3F-C-R1 이 세운 「클릭 지점에서 끝낸다」보다 **중복 회피를 위에 둔다.** 근거는 이 제품의 핵심이다 — **같은 도로를 두 번 달려도 새 도로는 한 번만 쌓인다.** 클릭 지점에 정확히 닿는 대가로 정복을 17 % 까지 잃는 것은 남는 거래가 아니다.

우회보다 나은 점이 셋이다.

| | 우회(현행) | 방향 확장 |
|---|---|---|
| 중복 | 옆으로 돌았다 와서 **구조적으로 발생** | 한 방향이라 **구조적으로 없음** |
| provider 호출 | 이분 탐색 8~12회 | **1~2회** |
| 예측성 | 도로망 불연속에 따라 튄다 | 안정 |

## 3. 수정

### 3.1 확장 거리는 **실측 λ 에서 유도**한다 — 고정값 금지

Chief 예시의 「3 km 클릭 → 2 km 더」는 **직선거리** 기준이다. 우리가 맞출 것은 **도로거리**다. 직선 5 km 지점까지 도로로 가면 6~7 km 가 되어 목표를 크게 넘고, 그만큼 엉뚱한 방향으로 갔다가 잘라내는 낭비가 생긴다.

**우리는 첫 Directions 호출에서 이미 두 값을 갖고 있으므로 계산으로 정확히 풀린다.**

```
직선거리(start→click)      straightM      ← 알고 있는 값
도로거리(start→click)      directRoadM    ← Stage 0 이 측정한 값
그 방향의 실측 λ           λ̂ = directRoadM / straightM

부족분(도로)               deficit = D − directRoadM
필요한 직선 확장           extendM = deficit / λ̂
가상 클릭                  straightM + extendM 지점 (같은 방위)
```

**λ 를 추정하지 않고 그 방위에서 실제로 잰 값을 쓴다.** 방향마다 λ 가 1.0~1.4 로 흩어지는 문제가 자동으로 해결된다 — 곧은 방향은 조금, 구불구불한 방향은 많이 늘린다.

- 확장 후 route 가 여전히 D 에 못 미치면 **λ̂ 를 갱신해 한 번 더** 확장한다. **총 2회를 넘기지 않는다.**
- 확장 지점의 `clickSnapM` 이 250 m 를 넘으면(도로가 없는 곳) 그 확장은 버린다.

### 3.2 우회는 제거하지 말고 **3순위로 강등**한다

확장으로 안 되는 경우가 있다 — 그 방위가 강·바다·막다른 길이거나 확장 지점 근처에 도로가 없을 때다.

```
① 방향 확장 (기본)
② 안 되면 우회 (5A §4.2 중복 페널티를 적용해 고른다)
③ 그래도 안 되면 shortfall 고지
```

지금 ② 가 1순위인 것을 3순위로 내린다. **우회 코드를 지우지 마라** — 폴백으로 살아 있어야 한다.

### 3.3 End 가 클릭 지점이 아님을 고지한다

이미 만들어 둔 `offered` UI(고스트 마커·점선·고지 문구)를 그대로 쓴다. 문구만 바꾼다.

```
클릭 지점까지는 도로로 3.9 km 로 목표에 모자랍니다.
같은 방향으로 5.0 km 지점에서 종료했습니다.
```

**숨기지 마라.** 4A 에서 배운 「화면과 실제가 다르면 사용자가 앱을 못 믿는다」가 그대로 적용된다. 거리 조정 버튼은 이 경우 의미가 없으므로 띄우지 않는다.

### 3.4 중복 페널티(5A §4.1·4.2)는 그대로 한다

확장이 주 수단이 되어도 ② 우회 폴백과 provider 자체 중복(측정 3.2 %)이 남는다. **정복 셀 기준 중복 측정과 후보 선택 페널티는 예정대로 구현한다.**

## 4. 부수 결함 2건 — 함께 고친다

### 4.1 [폰 전용] 거리 원 자동 축척이 스마트폰에서 안 먹는다

Chief 확인: **PC 에서는 작동하고 스마트폰에서는 작동하지 않는다.**

`MapView.tsx:2542` 의 `fitBounds` 는 `padding: RIDE_HUD_SAFE_PADDING`, `maxZoom: 16` 으로 호출된다. 원인 후보를 **측정으로 가른 뒤** 고쳐라.

- **후보 1 — padding 이 폰 뷰포트를 잡아먹는다.** `RIDE_HUD_SAFE_PADDING` 은 데스크톱 기준이다. 폰 가로에서 CSS 높이가 300 px 대인데 상하 padding 합이 그에 육박하면 `fitBounds` 가 무의미해지거나 Mapbox 가 조용히 무시한다.
- **후보 2 — 팝업이 지도를 덮는다.** 폰에서는 pick popup 이 화면의 큰 부분을 가리는데 padding 이 그것을 반영하지 않는다.
- **후보 3 — `maxZoom: 16` 상한.** 작은 목표 거리에서 원을 채우려면 16 을 넘겨야 하는 경우가 있는지 확인한다.

폰 실측(뷰포트 px · padding · fitBounds 전후 zoom·center)을 찍어 어느 후보인지 답한 뒤 고친다. **추정으로 고치지 마라.**

### 4.2 거리 슬라이더 — 눈금이 아니라 **범위**가 문제다

Chief 판단: **0.5 km 단위는 충분하다.** 실제 라이딩에서 500 m 를 최소 계량 단위로 삼아도 문제없다. 불편한 것은 **슬라이더에서 원하는 거리를 고르기 어렵다**는 것이다.

수치가 이유를 설명한다.

```
DISTANCE_AUTO_ROUTE_KM_MIN = 0.5
DISTANCE_AUTO_ROUTE_KM_MAX = 120        ← 실내 주행에 120 km 는 과하다
step 0.5  ⇒  눈금 240개
```

폰 팝업의 슬라이더 폭이 200 px 남짓이므로 **한 눈금이 1 px 미만**이다. 손가락으로 특정 값을 고르는 것이 물리적으로 불가능하다.

Chief 제안은 **5 km 단위 스냅**이다. 방향은 맞으나 그대로 두면 짧은 거리가 불편해진다 — 5 km 스냅에서 3 km 를 고르려면 5 에서 시작해 `−` 를 네 번 눌러야 한다. Chief 는 지금까지 0.5·0.7·1.0·3.0 km 로 시험해 왔다.

**구간별 스냅을 권한다.**

| 구간 | 스냅 | 눈금 수 |
|---|---:|---:|
| 0.5 ~ 10 km | 0.5 km | 20 |
| 10 ~ 30 km | 5 km | 4 |
| 30 ~ 120 km | 10 km | 9 |
| | | **약 33** |

폰에서 한 눈금이 **6 px** 이 되고, 정밀도는 **실제 주행이 일어나는 짧은 구간에 몰린다.** ± 버튼과 숫자 입력은 지금처럼 0.5 km 단위 미세 조정을 맡는다.

- 균일 5 km 스냅이 더 낫다고 판단하면 그것을 써도 된다. **폰에서 실제로 골라 보고 근거를 REPORT 에 적어라.**
- `DISTANCE_AUTO_ROUTE_KM_MAX = 120` 을 줄이는 것도 검토하라. 120 은 퍼블릭 경로 최대 연장에서 온 값이고 **거리 목표 슬라이더의 상한으로는 근거가 없다.** 줄이면 눈금 문제가 그만큼 완화된다. 바꾸려면 근거와 함께 제안하고 Chief 승인을 받아라.

## 5. 시험

1. **확장 계산 순수 함수** — `λ̂ = directRoadM/straightM`, `extendM = deficit/λ̂` 를 fixture 로 고정. 경계: `deficit ≤ 0`(확장 불필요) · `λ̂` 가 1.0·1.4 인 두 경우 · `straightM = 0` 방어.
2. **중복 회귀** — 5A-1 계측의 24 표본을 다시 돌려 `detoured` 평균 중복 **3.7 % → 유의미하게 감소**함을 수치로 보인다. 표본과 조건을 그대로 쓴다.
3. **거리 계약 회귀** — 3E ±5 m 유지. `test:distance-auto-route` 112건 유지.
4. **provider 호출 수** — 확장 경로가 우회보다 호출이 적은지 표로 확인. 예산 12 를 넘지 않는다.
5. §4.2 슬라이더 — 구간별 스냅 순수 함수 시험(경계 10·30 km 에서 스냅이 바뀌는지).
6. 빠른 회귀만. 브라우저 e2e 는 수용 게이트 1회.

```
npm -w boxcycle-web run test:distance-auto-route
```

- **확장 거리를 고정값(2 km 등)으로 두지 마라.** 실측 λ̂ 에서 유도한다.

- **provider 호출 예산 12 를 늘리지 마라.** 확장은 호출을 줄이는 방향이다.
- End 가 클릭 지점이 아닌 것을 숨기지 마라.
