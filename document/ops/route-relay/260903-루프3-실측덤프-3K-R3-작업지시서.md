## 2. 왜 아직 원인을 모르는가 — 진단 데이터가 버려지고 있다

현재 assert 는 이렇다.

```ts
expect(
  coordsClose(routeStart!, sessionEnd!),
  `루프 ${lap + 1}: Start ≠ sessionEndLngLat`,
).toBe(true)
```

**boolean 을 비교하므로 실패 메시지에 좌표가 남지 않는다.** error-context 에도 `expect(received).toBe(expected)` 와 `Object.is equality` 만 있다. 두 점이 몇 m 떨어졌는지, 3회차 Route 의 Start 가 **어느 Ride 의 종점인지**(2회차 것인지, 1회차 것인지, 전혀 다른 점인지) 알 수 없다.

3K-R2 §2.1 이 요구한 것은 「찍어서 비교하라」였고, 그 덤프가 없어 두 번째 실행도 같은 자리에서 멈췄다. **이번에는 덤프부터 만든다.**

## 3. 이번에 할 일 — 딱 두 가지

### 3.1 실패해도 수치가 남게 만든다

1. `coordsClose(...)` 를 `toBe(true)` 로 검사하지 말고, **좌표와 거리(m)를 메시지에 넣는다.**
   예: `루프 3: Start [127.xxxxxx, 37.xxxxxx] ≠ sessionEnd [127.yyyyyy, 37.yyyyyy] (거리 1234m)`
2. 루프마다 다음을 `console.log` 로 남긴다. Token checkpoint 를 남기는 방식 그대로 하면 된다.
   - 그 시점 `rides` **전체**의 `id` · 정렬키 값 · `sessionEndLngLat`
   - `readLatestRideSessionEnd` 가 고른 값
   - 방금 만든 Route 의 실제 `start`
3. 이 로그는 **성공한 루프 1·2 에도 남긴다.** 3회차만 다른 게 무엇인지 비교하려면 정상 회차의 값이 있어야 한다.

### 3.2 덤프를 보고 판정한다

실행은 **1회**. 로그를 보고 아래로 가른다.

- 3회차 Route 의 Start 가 **2회차 Ride 의 종점**과 같다 → 3회차 주행의 종점이 승계되지 않았다. **제품 결함** — `anchorFixedStartRef` 가 3회차에서 갱신되지 않는지, 「이 지점에서 새 경로」가 직전 값을 재사용하는지 본다.
- 3회차 Route 의 Start 가 **어느 Ride 종점과도 다르다** → anchor 고정이 풀려 일반 Route 로 떨어졌다. **제품 결함** — `App.tsx` 의 `setDistanceDirectionMode(false)`·`anchorFixedStartRef.current = null` 경로가 3회차에서 잘못 발동하는지 본다(`a077293` 이 건드린 자리다).
- `readLatestRideSessionEnd` 가 고른 값이 rides 목록의 진짜 최신과 다르다 → **시험 결함**. 정렬키를 고친다.

### 3.3 예산

**브라우저 실행은 덤프 1회 + 수정 후 확인 1회, 총 2회.** 3K-R2 §2.2 의 예산을 이어서 적용한다. 초과하면 멈추고 **덤프 로그 원문을 그대로 붙여** 보고한다. 원인을 못 찾아도 로그만 있으면 감리가 이어받는다.
