## 1. 증상

같은 퍼블릭 경로를 2명이 달리는데 인원수 표시가 늦다.

| 라이더 | 체감 |
|---|---|
| 라이더1 (먼저 시작) | 10초 이상 뒤 「지금 2명 주행」 |
| 라이더2 (Trail 합류) | **1분 넘게** 「지금 1명 주행」 → 그 뒤 「2명」 |

화면 증거에서 **같은 시각에 두 화면의 숫자가 다르다** — 라이더1 00:30 「2명」 / 라이더2 00:20 「1명」.

4B 로 「다른 라이더 없음」 모순은 사라졌다. 이번 건은 **인원수 갱신 지연**으로 별개다.

## 2. 원인 — 폴링 주기가 60초다

`apps/web/src/lib/rideSyncPolicy.ts`

```ts
export const ACTIVITY_WORLD_POLL_ACTIVE_MS = 60_000;   // 60초
export const ROUTE_ACTIVITY_CACHE_TTL_MS  = ACTIVITY_WORLD_POLL_ACTIVE_MS;
export const COURSE_ACTIVITY_POLL_MS      = ACTIVITY_WORLD_POLL_ACTIVE_MS;
```

「지금 N명 주행」은 `courseActivityHudLine` → 서버 `routeActivity` aggregate 이고, 클라이언트는 **60초 주기 폴링 + 60초 세션 캐시**로 읽는다. 캐시 TTL 은 `c0f2831` 로 폴링 주기와 이미 일치시켰고(불일치 시 throw 하는 가드까지 있다), **주기 자체가 60초라 그 아래로는 못 내려간다.**

### 2.1 두 라이더의 체감이 다른 이유

같은 60초 주기인데 **폴링 위상이 다르다.**

- 라이더1: 주행 시작으로 타이머가 그 시점에 리셋 → 곧 첫 폴이 돈다.
- 라이더2: 이미 폴링 중 → 라이더1 합류 시점이 자기 주기의 어디냐에 따라 **0~60초 대기**. 평균 30초, 최악 60초.

여기에 서버 CF aggregate 집계 지연이 더해진다. 라이더2 가 「지나치게 느리다」고 느낀 것은 **버그가 아니라 폴 직후에 상대가 들어온 경우**다. 재현할 때마다 값이 달라지는 이유도 이것이다.

### 2.2 진짜 문제 — 실시간 소스가 이미 있는데 안 쓴다

4B 가 도입한 `liveRideHudSignal` 은 **구독(onSnapshot) 중인 live ride 행**에서 나온다. 즉 **「다른 라이더가 있다/없다」는 이미 실시간**이다.

그런데 화면에 뜨는 **숫자만** 60초 폴링 aggregate 를 쓴다. 같은 블록 안에서 한 줄은 실시간, 한 줄은 1분 지연이다. 4B 가 고친 모순의 사촌이다.

## 3. 수정

### 3.1 신호를 boolean → 인원수로 확장

`liveRideHudSignal.ts` 는 지금 `__rtwHasOtherLiveRiders: boolean` 만 공유한다. 이를 **내가 아닌 live rider 수**로 확장한다.

- `publishOtherLiveRiderCount(n)` / `getOtherLiveRiderCount()` 로 확장하고, 기존 boolean 은 `count > 0` 파생으로 유지해 4B 동작을 깨지 않는다.
- 발행 지점은 4B 와 같다 — `PublicationSharedPresence` 가 구독 행에서 계산해 publish.

### 3.2 표시값 = 실시간과 aggregate 중 큰 쪽

```text
표시 인원수 = max(aggregate 인원수, 1 + 실시간 다른 라이더 수)
```

- **aggregate 는 권위 있지만 최대 60초 낡았다.** 내 구독 범위 밖 라이더까지 센다.
- **실시간 신호는 즉시지만 내 구독 범위만 본다.** 과소 집계될 수 있다.
- 큰 쪽을 쓰면 **과소 보고가 없고**, 상대가 합류한 순간 화면이 바로 오른다. aggregate 가 따라오면 자연스럽게 그 값으로 수렴한다.
- `1 +` 는 나 자신이다. 주행 중이 아니면 이 보정을 하지 않는다.

**폴링 주기를 60초에서 무작정 줄이지 않는다.** Firestore 읽기 비용이 그만큼 늘고, 이 저장소는 이미 read amplification 을 한 번 겪었다. 실시간 신호로 체감 지연을 없애는 쪽이 비용 0 이다.

### 3.3 그래도 남는 지연 — 주행 중 폴 주기

내 구독 범위 밖(다른 Trail 에서 같은 publication 을 타는 사람)은 여전히 최대 60초 뒤에 보인다. 이건 §3.2 로 안 없어진다.

- **주행 중이고 그 경로에 동행 가능성이 있을 때만** 폴 주기를 짧게 하는 것을 검토한다(예: 15초). idle 은 600초 그대로.
- 다만 이건 **읽기 비용이 4배**다. §3.1·3.2 를 먼저 넣고 폰 2대로 재확인한 뒤, 그래도 체감이 나쁘면 그때 조정한다. **이번 작업에서는 수치를 바꾸지 않는다.**
- `ROUTE_ACTIVITY_CACHE_TTL_MS !== ACTIVITY_WORLD_POLL_ACTIVE_MS` 이면 throw 하는 가드가 있다. 주기를 바꾸게 되면 이 불변식을 반드시 함께 지킨다.

## 4. 판정 기준

| 상황 | 기대 |
|---|---|
| 상대가 같은 경로 주행 시작 | **수 초 내** 내 화면 인원수 증가 (aggregate 안 기다림) |
| 두 화면 동시 비교 | 같은 시각에 **같은 숫자** |
| 상대 이탈 | aggregate 갱신 시점에 감소 — 즉시일 필요 없음 |
| 혼자 주행 | 「1명」 유지, 「다른 라이더 없음」 정상 표시 |

**같은 시각 두 화면의 숫자가 다르면 실패다.** 이것이 단일 수용 기준이다.

## 5. 시험

1. 순수 함수 시험 — `max(aggregate, 1 + realtimeOthers)` 계산을 fixture 로 고정한다. 경계: `aggregate=1, others=1` → **2**, `aggregate=3, others=1` → **3**, `주행 중 아님` → aggregate 그대로.
2. `liveRideHudSignal` 확장 후에도 4B 의 `hasOtherLiveRiders` 동작이 유지되는지 assert (`count > 0` 파생).
3. 빠른 회귀만 (3K-R2 §4 정책).

```text
npm -w boxcycle-web run test:next-ride
npm -w boxcycle-web run test:distance-auto-route
npm --prefix functions run build
npm -w boxcycle-web run build
git diff --check
```

4. 실제 확인은 **2대 동시 접속**이 필요하다. e2e 로 어려우면 사용자 2창 확인으로 대체하고, 그 사실을 보고한다.
