## 1. 증상 — Chief 지적

> 알고리즘에 문제가 있다. 거리를 맞추기 위해 경로 상에 **중복되는 구간**을 만든다.

화면에서 Start 서쪽 구간이 삼각형으로 되돌아온다. 같은 도로를 두 번 지난다.

## 2. 감리가 화면만으로 못 가른 것 — 여기부터 계측한다

원인 후보가 둘이고 **대응이 정반대**다. **추정으로 고치지 마라.**

| 후보 | 주체 | 대응 |
|---|---|---|
| **A. 우회 waypoint** | 3F-C-R1 §4 Stage 1 이 넣은 `W(r, side)` | 우리 알고리즘 수정 |
| **B. provider 경로** | Mapbox driving 이 일방통행 때문에 블록을 돎 | 후보 선택에서 걸러내야 함 |

`outcome` 한 줄이면 갈린다 — `detoured` 면 A, `exact`/`offered` 면 B(우리는 직행 경로를 자른 것뿐).

### 2.1 화면 문구가 수치상 앞뒤가 안 맞는다 — 함께 확인할 것

같은 화면에 이렇게 떠 있다.

```
클릭 지점까지는 도로로 0.7 km 입니다. 목표 0.7 km 지점에서 종료했습니다.
[ 0.7 km 로 늘려 클릭 지점까지 가기 ]
슬라이더 0.7 · HUD 거리 0.70 km
```

`offered` 는 `directRoadM > D + DIRECT_ROAD_EXCESS_TOLERANCE_M(150m)` 일 때만 나온다. `D = 700 m` 면 `directRoadM > 850 m` 여야 하고 그러면 `toFixed(1)` 이 **0.9 이상**이어야 한다. **0.7 이 나올 수 없다.**

- 서버가 보낸 `directRoadMeters` 실값과 `outcome` 을 로그로 확인하라.
- 4A 결함 ③(조정 성공 후 offered 문구 잔존)이 완전히 안 잡혔을 가능성이 있다. `setOfferedState(null)` 은 검색 시작(`:274`)과 조정 재탐색(`:409`)에서 호출되므로 **코드상으로는 정상**이다. 그렇다면 실제 응답이 `offered` 인데 수치가 이상한 것이므로 **서버 쪽**을 봐야 한다.
- 두 문제(중복 구간·문구 모순)가 같은 뿌리인지 다른 뿌리인지도 이 로그로 갈린다.

### 2.2 재현 절차

Chief 화면과 같은 조건으로 재현한다 — **자동차 프로필 · 강남 일방통행 구역 · 목표 0.7 km**. 콘솔에서 다음을 찍어 보고한다.

```
outcome · directRoadMeters · endMissMeters · detourCalls · providerCallCount · algorithmVersion
```

## 3. 더 큰 문제 — 중복 구간은 정복이 안 된다

원인이 A든 B든 **이건 그대로 남는다.** 이 앱에서 중복 구간은 단순히 보기 나쁜 게 아니다.

> **「Ride = Claim」에서 같은 도로를 두 번 달려도 새 도로는 한 번만 쌓인다.**

0.7 km 경로에 0.2 km 가 중복이면

- 사용자는 **Token 1개를 쓰고 0.7 km 를 달린다**
- 그런데 자산으로 남는 **새 도로는 0.5 km** 다
- HUD 「새 도로 +N km」가 주행 거리보다 작게 나와 **사용자가 바로 알아챈다**

토큰을 쓰고 거리를 달렸는데 정복이 덜 되는 것은 화폐가 걸린 손실이다. 4A 의 「토큰 쓰고 원하지 않은 경로」와 같은 계열이다.

### 3.1 지금 판정 기준에 이 항이 없다

`searchDistanceAutoRoute` 는 **거리**만 맞춘다. 중복은 보지 않는다.

- Stage 1 우회 이분 탐색: `f(r)` 이 `[D, D+150m]` 에 들어오면 채택 — 그 경로가 자기 자신과 겹치는지 검사하지 않는다.
- Stage 0/2: 직행 경로를 그대로 절단 — provider 가 블록을 돌아도 그대로 받는다.

## 4. 수정

### 4.1 중복 구간을 수치로 잰다 (먼저)

geometry 자기중첩 비율을 재는 **순수 함수**를 만든다.

- 입력: `LineString`. 출력: 중복 길이(m)와 비율(중복/전체).
- 판정 단위는 **정복 셀 기준**이 자연스럽다 — `conquestTiles` 가 이미 좌표→셀 변환을 갖고 있다. 같은 셀을 두 번 지나면 두 번째는 새 도로가 아니다. **정복 계산과 같은 기준을 쓰면 HUD 「새 도로」와 어긋나지 않는다.**
- 다른 기준(선분 근접·방위 반대)이 더 낫다고 판단하면 그것을 써도 된다. **고른 이유와 두 기준의 차이를 REPORT 에 적어라.**
- 이 함수만으로 Chief 화면의 경로가 실제로 몇 % 중복인지 먼저 보고하라. 체감과 수치가 다를 수 있다.

### 4.2 후보 선택에 중복을 넣는다

`pickBest…` 계열이 거리만 보고 고르는 것을 바꾼다.

- **정확 거리는 hard constraint 로 유지**한다(3E 계약 ±5m). 중복을 줄이려고 거리를 포기하지 않는다.
- 정확 거리를 만족하는 후보가 여럿이면 **중복 비율이 낮은 쪽**을 고른다.
- Stage 1 우회는 `side`(+90°/−90°)와 `r` 조합이 여러 개 나올 수 있다. 지금은 먼저 수렴한 것을 쓰는데, **중복이 낮은 쪽을 고르도록** 바꾼다.
- 후보가 하나뿐이면 그대로 쓰되, 중복 비율을 응답에 실어 UI 가 알릴 수 있게 한다.

### 4.3 사용자에게 알린다

중복 비율이 의미 있게 높으면(임계값은 §4.1 측정 후 정한다) 결과 문구에 넣는다.

```
0.7 km · 새 도로 0.5 km (0.2 km 중복)
```

숨기지 않는다. 4A 에서 배운 것과 같다 — **화면과 실제가 다르면 사용자가 앱을 못 믿는다.**

### 4.4 하지 않는 것

- **거리 정확도를 낮추지 않는다.** 3E 계약(±5m)은 유지한다.
- **provider 호출 예산을 늘리지 않는다.** `MAX_AUTO_ROUTE_PROVIDER_CALLS = 12` 안에서 해결한다. 후보를 더 뽑는 게 아니라 **이미 뽑은 후보를 다르게 고르는** 작업이다.
- 「새 도로 최대화」를 목적 함수로 바꾸는 것은 **이번 범위가 아니다**(§6).

## 5. 시험

1. §4.1 순수 함수 — 겹침 0인 직선, 완전 왕복(중복 100%), Chief 화면의 실제 geometry fixture 세 가지로 assert.
2. §4.2 선택 — 거리가 같고 중복만 다른 후보 2개를 주면 낮은 쪽을 고르는지 assert.
3. 3E 거리 계약 회귀 — `test:distance-auto-route` 112건 유지.
4. 빠른 회귀만(3K-R2 §4 정책). 브라우저 e2e 는 수용 게이트 1회.

```

npm -w boxcycle-web run test:distance-auto-route-replay
npm -w boxcycle-web run test:next-ride
npm --prefix functions run build
npm -w boxcycle-web run build
git diff --check
```

## 6. 범위 밖 — Chief 판단 대기

**「새 도로 최대화」를 자동 경로 생성의 목적 함수로 삼는 것**은 별도 설계다. 지금은 「목표 거리를 맞춘다」가 목적이고, 이번 작업은 거기에 「중복은 피한다」를 더하는 것까지다.

목적 함수를 「목표 거리를 맞추면서 **새 도로를 최대로** 얻는다」로 바꾸면 정복 지도를 읽어 이미 칠한 도로를 피해야 하고, 그건 제품 방향 결정이다. **이번에 손대지 마라.** 5A 결과를 보고 Chief 가 정한다.
