## 1. 개발팀장에게 내리는 지시

**한 번의 Ride가 종료·로컬 기록·서버 저장·Conquest 집계·결과 표시·재개를 거치며 같은 주행으로 식별되고 정확히 표시되는 계약을 확정하라. 필요한 구조 수정과 회귀 검증까지 끝낸 뒤 결과 화면 1단계에 넘겨라.**

사용자는 2026-09-07 자문 검토를 수용했다. 기존 `RIDE-CLAIM-RESULT-1`은 폐기하지 않고 이 작업 뒤로 이동한다. 이번 작업은 전면 리팩토링, 화면 재디자인, 기능 확대가 아니다. 구현 작업량은 0A에서 확정하며 종전 3~5일을 합산 일정으로 사용하지 않는다.

이미 작성된 인벤토리와 거리 카탈로그를 출발점으로 삼는다. 같은 범위의 전수 조사를 다시 만들지 않는다. 상태가 여러 파일에 있거나 FS/RTDB 채널이 둘이라는 이유만으로 통합하지 않는다. 각 원천은 유지하고 **원천 사이의 동일성·변환·수명 계약**을 명확하게 한다.

## 3. 0A — 계약 보완

### 3.1 산출물

새 살아있는 계약 문서를 `document/ops/ride-relay/260907-Ride-결과-데이터계약.md`에 작성한다. 실제 작성일이 달라지면 날짜 접두어도 실제 날짜로 한다. 유형은 `architecture`, 상태는 검토 수준에 맞게 명시하고 색인에 등재한다. 아래 내용은 이 계약 한 곳에만 정의하고 기존 두 조사 문서와 후속 1단계에서는 링크로 참조한다.

1. **생명주기와 실패 분기:** 경로/입력 준비 → Go → running/paused → 종료 스냅샷 → 즉시 결과 표시. 이후 Ride 저장·SavedRoute 진행률 갱신·Conquest 집계를 각각 표시한다. Conquest 완료까지 결과 화면을 대기시키는 직렬 흐름으로 그리지 않는다.
2. **ID 관계표:** 로컬 record ID, 서버 Ride ID, SavedRoute ID, canonical route ID, Publication ID, trace 문서 ID, uid. 각 생성 주체·변경 가능 여부·연결 시점·보존 위치·소비자·해제 시점을 기록한다. legacy 코드 이름은 그 의미와 연결하고 일괄 rename하지 않는다.
3. **필드별 원천 표:** 선언/쓰기 함수/읽기 함수, 단위·좌표 기준, 저장 여부, 낙관값 여부, 비동기 응답 적용 조건. 파일과 심볼을 반드시 연결하고 근거 HEAD를 남긴다.
4. **비동기 상태 전이표:** Ride 저장, 경로 진행률 저장, Conquest 확인은 별도 축. 전이 입력·부수효과·실패 시 보존할 데이터·재시도 가능 범위를 명시한다.
5. **수정 판정표:** 각 후보를 ‘수정 필요/현재 계약 유지/범위 밖’으로 구분하고 재현 시험·근거·수정 파일·예상 작업량을 적는다. 후보 개수만으로 리팩토링을 결정하지 않는다.

기존 조사 문서의 유형 `참조`는 정식 분류가 아니다. 읽기 전용 조사 스냅샷은 `record`로 정리하고 문서 수명 규칙에 맞춰 archive로 이동하면서 들어오는 링크도 수정한다. 지속 관리할 계약 내용은 새 architecture 문서에 이관한다. 조사 완료와 제품 구현 완료를 혼동하지 않는다.

### 3.2 거리 카탈로그에서 반드시 보완할 내용

- `creditMeters`: 서버가 계산한 인정 예산.
- `conquestResult.creditedMeters`: 서버가 실제 소비한 인정분.
- `conquestResult.newMeters`: **해당 Ride의 신규 도로 거리**.
- `conquest/{uid}.totalMeters`: **계정의 누적 내 도로망 거리**.
- 이번 운동 거리, 이번 세션 geometry 길이, 신규 도로 거리가 같다고 가정하지 않는다. 중복·한도·거리 표현 차이를 예시로 설명한다.
- 진행률은 분모를 함께 명시한다. 저장 진행률을 geometry에 곱할 때 필요한 변환과 Route 거리의 출처(Directions/클립/저장 스냅샷)를 구분한다.
- ‘오늘 거리’는 현재 화면의 세션 거리이며 당일 모든 Ride 합계가 아님을 명시한다.
- 같은 이름의 필드를 발견해도 마이그레이션이나 기존 식별자 일괄 치환으로 해결하지 않는다.

### 3.3 결과 모델의 경계

기존 `RideEndResult`를 확장하거나 표시용 모델을 얹는다. 이름이 다른 중복 원본을 새로 만들지 않는다. 구체적인 TypeScript 이름은 0A 계약에서 정하되 아래 의미를 보존한다.

| 부분 | 내용 | 변경 규칙 |
|---|---|---|
| identity | uid, localRecordId, serverRideId(미확정 가능) | 동일 주행으로 연결. 늦은 응답은 owner와 결과 키 일치 시만 적용 |
| session | 시작/끝 거리와 그 기준, 이번 geometry, 실제 종료 anchor | 종료 시 복사·고정. 이후 workspace 변경으로 변하지 않음 |
| exercise | 이번 거리·시간·평속·칼로리 | 종료 사실. 계정 마일리지와 혼합하지 않음 |
| persistence | Ride 저장 상태와 SavedRoute 진행률 저장 상태 | 서로 독립. 한쪽 성공으로 다른 쪽 성공을 주장하지 않음 |
| conquest | 확인 상태와 해당 Ride의 newMeters | 서버 문서 원천. pending/unknown과 0 구분 |
| next action | 재개 또는 종료점에서 새 경로 준비 | 최신 SavedRoute/최근 Ride로 파생. 종료 사실을 덮지 않음 |

**실제 종료점과 재개점은 별도다.** 43%까지 진행한 경로를 처음부터 다시 타다가 20%에서 끝내면 이번 종료점은 20%, 기존 최대 진행 기반 재개점은 43%다. 하나의 mutable anchor로 합치지 않는다. 재개 가능 여부는 경로 삭제·완주 등 최신 상태로 다시 판단한다.

결과 모델은 UI용 통합 표현이지 주행 엔진·서버·프로필·경쟁 전체를 통제하는 새로운 전역 원본이 아니다. UI는 Firestore 문서 구조를 직접 해석하지 않으며 구독·상태 전이는 hook/service가 담당한다. App에는 조립만 남긴다.

### 3.4 0A 게이트

다음 조건을 모두 만족하면 범위 안의 0B로 계속 진행한다. 단순 보고 후 다시 허락을 기다리지 않는다.

- 기존 두 문서의 중복 전수 조사 없이 빠진 ID·변환·수명·실패 계약을 보완했다.
- §6의 핵심 회귀 fixture와 예상값을 정의하고 현행 실패/통과/미실행을 구분했다.
- 필요한 변경 파일과 호환 방식, 수정하지 않을 영역을 정했다.
- 기존 SoT를 바꿔야 하는 사항이 있다면 해당 문서를 먼저 갱신하고 결정 로그에 이유를 남겼다. 제품 인정 정책 자체를 임의로 바꾸지는 않는다.
- 신규 원격 스키마·마이그레이션 없이 가능한 최소 해법을 우선했다. 범위 밖 변경이 필수인 경우 영향과 대안을 구체화하고 그 변경만 분리한다.

## 4. 0B — 필요한 구조 수정

### B1. Ride 동일성 연결

종료 로컬 기록과 서버 응답 ID를 연결하고 최근 기록 병합에서도 사용한다. 결과 시트 안에서만 ID를 알게 하고 히스토리의 중복을 남겨 두지 않는다. 로컬 저장 형식의 선택적 필드 확장과 구형 필드 없는 기록 읽기는 허용한다. 새 원격 ID 체계·서버 필드 변경은 기본 해법이 아니다.

매핑이 입증되지 않은 과거 기록을 시간·거리 유사성만으로 합치거나 삭제하지 않는다. 신규 주행은 연결을 보존하고 legacy의 불확실성은 별도로 다룬다. 서버 목록이 로컬보다 늦게 도착해도 아직 저장 중인 신규 기록이 사라지지 않아야 한다.

현재 `addDoc` 저장의 재호출은 다른 문서를 만들 수 있다. ‘조회 재시도’를 ‘Ride 재생성’으로 구현하지 않는다. 저장 멱등성/백필 전체 재설계는 재현 근거가 있을 때 별도 범위를 산정한다. 계정 전환과 로컬 복원에서 다른 uid 데이터가 합쳐지지 않는지 검사하고, 불확실한 소유 기록을 다른 계정으로 자동 업로드하지 않는다.

### B2. 종료 스냅샷과 거리 변환

workspace 초기화 전에 이번 세션의 시작 offset·종료 위치·geometry·profile·연결 ID를 고정한다. 비동기 처리 중 바뀔 수 있는 refs를 뒤늦게 다시 읽어 다른 Route/Publication을 붙이지 않는다. 종료 순간의 rAF 원본과 throttle된 UI metrics 중 무엇을 사용하는지도 확인하여 손실 여부를 시험한다.

geometry 길이와 routeDistanceMeters가 다른 fixture에서 카드 재개점·실제 Go 이후 위치·종료 anchor·미리보기 구간을 비교한다. 차이가 재현되면 의미가 같은 경계 계산만 공통 순수 함수/adapter로 연결한다. 운동 적분·완주 기준을 geometry 길이로 일괄 교체하지 않는다.

0.97 재개 상한·0.98 완주 기준·서버 max 진행 보존은 유지한다. 상한이 적용되는 구간의 카드 좌표도 실제 준비/시작 지점과 일관되는지 확인한다. 기존 미터·비율을 가진 데이터의 해석을 바꾸는 경우 호환 근거 없이 진행률을 재저장하지 않는다.

### B3. 해당 Ride의 Conquest 결과 연결

`rides/{serverRideId}.conquestResult.newMeters`를 읽는 구독과 순수 상태 모델을 구성한다. 결과 시트가 열려 있는 해당 uid/결과 키에만 적용한다. 기존 누적값−baseline을 결과의 원천에서 제거한다. 누적 계정 통계 구독 자체는 유지한다.

집계 없음, 집계 중, 확정 0, 양수, 조회 오류, 저장 불가를 구분한다. 숫자 유효성 검증을 거치고 문자열을 역파싱하지 않는다. 서버가 일부 payload에서 결과 없이 반환할 수 있으므로 결과 부재를 0이나 거절로 단정하지 않는다.

후속 1단계의 15초 지연 안내/60초 구독 종료 정책은 데이터 상태 모델에서 지원한다. 시트 닫기·새 결과·계정 전환·unmount 시 timer/구독을 해제하고 이전 응답이 시트를 다시 열지 않게 한다. 읽기 재시도는 동일 문서만 대상으로 한다.

### B4. 기존 화면에 연결하고 계약 시험

기존 결과 화면의 배치·지도·색상·CTA 구성은 유지한다. 검증된 모델을 기존 props에 연결하는 adapter를 사용해도 된다. 숫자 원천 변경과 저장/집계 상태를 사실대로 표현하는 최소 문구 변경은 허용한다. 성공하지 않은 저장을 완료라고 표시하지 않는다.

SVG 미리보기·새 hero·레이아웃 개편은 후속 1단계다. 0B는 geometry를 정확히 제공하는 데까지 책임진다. 후속 1단계의 데이터 작업을 중복 구현하지 않도록 API·예제 fixture를 인계한다.

## 5. 수정하지 않을 영역

- 상태관리 라이브러리 신규 도입, App/MapView 전면 분해, 폴더·기존 식별자 일괄 rename.
- FS presence와 RTDB motion 통합, peer 보간/외삽 변경, 센서 프로토콜·속도 정책 변경.
- Trust Tier·정복 인정 수치·무료/유료 정책·토큰 경제·완주/discard 기준 변경.
- 과거 데이터 일괄 삭제·백필·재집계, 원격 배포·마이그레이션.
- 첫 화면·카메라·라이더·공유 기능 개편.

공유 거리 helper 변경이 peer 코드에 영향을 주면 영향 지점을 기록한다. 보간·외삽 등 peerMotion 동작 변경이 불가피해질 때는 [peer-sync 스킬](../../../.agents/skills/peer-sync/SKILL.md)의 replay 절차가 추가로 필요하다. 그런 변경을 결과 모델 정리의 부수 수정으로 섞지 않는다.

## 7. 실행 검증과 보고

착수 전 기준선과 수정 후 결과를 같은 명령으로 비교한다. 루트에서:

```powershell
npm run build
npm --prefix apps/web run test:next-ride
npm --prefix apps/web run test:e2e:ride
npm --prefix apps/web run test:e2e:ride-continuation
```

`apps/web` 작업 디렉터리에서:

```powershell
node scripts/ride-verify/verify-selectors.mjs
```

- [ride-verify 스킬](../../../.agents/skills/ride-verify/SKILL.md)에 따라 selector 계약을 먼저 확인한다. 기존 emulator launcher를 사용하며 실 Firebase로 접속하는 우회 실행은 하지 않는다.
- C1~C14 중 순수 변환/병합/상태 전이는 Node 시험, 실제 저장→서버 ID→집계 수신은 emulator 통합 시험으로 고정한다. 기존 UI에 모델이 연결되는지 실제 종료 흐름으로 최소 1건 확인한다.
- emulator에서 집계 응답 fixture를 주입한 시험과 실제 CF가 결과를 만든 시험은 구분한다. Functions 코드 미변경이라도 대표 유효 Ride 한 건은 저장부터 실제 CF 결과 조회까지 통과시킨다. 다른 CF나 진행률 저장 성공과 묶어서 판단하지 않는다.
- 관련 자동 Route 이어가기 경로를 수정했다면 기존 `test:e2e:ride-continue-phase-c`도 실행한다. 미수정 영역 시험을 관성적으로 확장하지 않는다.
- 5분간 브라우저 검증 진전이 없으면 중단·프로세스/서버/포트/로그 점검 후 headless·단일 worker·기존 서버 재사용 등으로 전환한다. 미실행 필수 검증은 BLOCK이며 skip은 PASS가 아니다.

0A 산출물은 계약 문서·변경 판정표·예상 작업량이다. 0B 완료 보고는 `document/archive/`에 실제 작성일 접두어로 작성하며 다음을 포함한다.

1. 근거 HEAD·변경 파일·기준선 결과와 최종 결과(명령, 종료 코드, 통과/실패/skip 수).
2. C1~C14 PASS/FAIL/BLOCK 표와 fixture/로그/화면 링크.
3. 로컬→서버 ID 연결·거리 변환·상태 전이 설명과 미수정 영역.
4. legacy 호환 범위, 남은 위험, 원격 데이터/정책 변경 여부.
5. 후속 결과 화면이 사용할 타입/hook/adapter·예제 결과 데이터.
6. `RIDE-CLAIM-RESULT-1` 착수 가능 여부와 재산정 작업량.

0B 완료 전 후속 1단계의 신규 미리보기/레이아웃 구현에 들어가지 않는다. 완료 시 후속 지시서 §2·§4의 데이터 구현 지시를 실제 API 소비 지시로 갱신한다. 상태보드는 실제 변경된 기능의 기호만 갱신한다. 문서 작성만으로 코드 완료를 표시하지 않는다.
