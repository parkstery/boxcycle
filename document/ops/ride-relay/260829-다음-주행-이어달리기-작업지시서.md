## 0. 목표와 성공의 정의

사용자는 주행일지를 작성하거나 `MENU → 내 경로 → 선택 → 열기`를 반복하지 않는다. 앱이 마지막 유효 Ride를 해석해 지도 위에 **「다음 주행」**을 먼저 제시한다.

1. 미완주 SavedRoute의 실제 진행 지점에서 **같은 경로 이어 달리기**
2. 마지막 Ride의 실제 종료 지점을 출발점으로 고정해 **새 경로 연결하기**

성공은 기능의 존재가 아니라 다음 문장이 실제로 성립하는 것이다.

> **어제 멈춘 곳이 오늘 앱을 열었을 때 자동으로 다음 출발점이 된다.**

---

## 1. 확정된 제품 결정

1. 최근 주행 목록은 기록 보관용 보조 표면이다. **다음 행동의 주 표면은 지도 위 「다음 주행」 카드**다.
2. 모든 유효 Ride 종료 후 결과 시트를 연다. 도착·ad-hoc 여부로 노출을 제한하지 않는다.
3. 유효 Ride 종료 시 실제 세션 시작·종료 좌표를 자동 저장한다. 일지·메모·이름 입력은 요구하지 않는다.
4. 미완주 SavedRoute가 있으면 기존 경로 재개를 우선 제안한다.
5. 완주·ad-hoc·Publication Ride는 실제 종료점에서 새 Route를 만드는 행동을 제안한다.
6. 「이어 달리기」 CTA는 Route를 불러오고 재개 지점으로 이동해 `ready-to-start`까지만 만든다. 실제 시작은 기존 Go·주행 입력 준비 게이트를 통과한다.
7. SavedRoute geometry는 불변이다. 새 경로 연결 때문에 이전 geometry를 append·mutate하지 않는다.
8. 기존 계산 원칙 **「위치는 누적, 인정은 세션」**은 불변이다.
9. `Journey`는 Ontology상 미확정이다. 이번 UI·신규 코드 식별자·데이터 모델에 사용하지 않는다.
10. 다음 출발점은 사용자 전용 `rides`·`savedRoutes`에서만 해석한다. 실제 종료 좌표를 전역에 공개하지 않는다.

### 1.1 두 종류의 연결

| 종류 | 의미 | 데이터 | 기본 행동 |
|------|------|--------|-----------|
| 같은 경로 재개 | 긴 SavedRoute를 여러 날 나누어 진행 | SavedRoute geometry + `lastProgressRatio` + 최근 Ride | `N%에서 이어 달리기` |
| 새 경로 연결 | 어제 종료점부터 오늘 다른 도로로 확장 | 최근 Ride의 실제 종료 좌표 | `이 지점에서 새 경로` |

첫 번째는 현재 프로토타입이 이미 계산한다. 두 번째는 이번 작업에서 새로 만든다. 두 경험은 같은 카드에서 보이지만 저장 규칙은 분리한다.

## 2. 현재 구현에서 확인된 결함

### 2.1 최근 주행이 읽기 전용 목록

`UserInfoSheet.tsx`는 거리·시각·완주율·계획 지명만 렌더한다. 클릭·지도 이동·재개 액션이 없어 사용자는 다시 MENU와 내 경로를 탐색해야 한다.

### 2.2 이어 달리기 진입이 숨겨짐

```text
MENU → 내 경로 → 행 선택 → 열기 → RouteDock 재개 라디오 → Go
```

진행률 바도 선택한 행에서만 보인다. 기능은 있으나 사용자의 다음 행동으로 제시되지 않는다.

### 2.3 재개 후보가 일회성 state

`resumeCandidateId`는 SavedRoute를 불러올 때 생기고 주행 시작 직후 `null`로 소비된다. 미완주 종료 뒤 진행률은 저장되지만 후보는 복원되지 않는다.

### 2.4 미완주 SavedRoute는 결과 시트가 열리지 않음

현재 `summaryVisible`은 `arrivalToastTick > 0 || lastEndedWasAdhoc !== null`일 때만 참이다. 저장 경로를 31%에서 수동 종료하면 오늘의 진척·다음 출발점을 알려 주는 화면이 없다.

### 2.5 실제 세션 시작·종료 좌표가 없음

`StoredRideSession`은 계획된 전체 Route의 출발·도착 지명만 가진다. 31%에서 시작해 43%에서 끝난 Ride도 전체 Route의 주소로 보이며 정확한 연결점을 복원할 수 없다.

### 2.6 완주 표시 기준 불일치

- 실제 SavedRoute 완주: `completionRatio >= 0.98`
- `UserInfoSheet` 표시: 반올림 백분율 `>= 95`

95~97% Ride가 목록에서는 「완주」지만 SavedRoute에서는 미완주일 수 있다. `isRouteCompletion`을 단일 판정으로 쓴다.

### 2.7 진행률 보존이 클라이언트 상태에 의존

클라이언트가 `max(기존, 신규)`를 계산한 뒤 Firestore를 덮어쓴다. 다른 탭·기기의 늦은 낮은 진행률이 높은 진행률을 되돌릴 수 있다. 서버 문서 기준 단조 증가를 보장해야 한다.

### 2.8 중복 저장이 진행 상태를 0으로 돌려줄 수 있음

`saveRouteToFirestore`의 중복 갱신 분기는 서버 메타만 갱신하면서 반환 객체에 `completed:0`, `lastProgressRatio:0`을 합성한다. 호출부가 state에 병합하면 새로고침 전까지 완료·진행률이 사라질 수 있다.

## 3. 고정 UX 계약

### 3.1 지도 위 「다음 주행」 카드

표시 조건:

- 인증된 User(Guest 포함)가 존재한다.
- `rideStatus === "idle"`이다.
- 최근 Ride와 SavedRoute 로딩이 끝났다.
- 해석 가능한 다음 주행 후보가 있다.
- gate·summary·modal/sheet가 주 화면을 점유하지 않는다.

배치:

- Route가 없는 idle 화면의 **좌하단 기존 RouteDock anchor 자리**를 사용한다.
- 「다음 주행」 카드와 확장된 RouteDock은 동시에 표시하지 않는다.
- CTA로 Route를 준비하면 카드는 사라지고 같은 자리에서 RouteDock이 나타난다.
- 모바일 가로에서는 현재 RouteDock의 안전 영역과 폭 정책을 재사용해 중앙 HUD·우상단 센서/계정·Mapbox control과 겹치지 않게 한다.

미완주 SavedRoute 예시:

```text
다음 주행
한강 북단 · 12.8 / 42.0 km · 31%
어제 멈춘 지점에서 계속합니다
[31%에서 이어 달리기]  [이 지점에서 새 경로]
```

완주·ad-hoc·Publication Ride 예시:

```text
다음 주행
한남대교 북단에서 이어가기
마지막 주행 2026. 8. 29. · 오늘 5.2 km
[이 지점에서 새 경로]  [지도에서 보기]
```

규칙:

- 제목은 고정된 **「다음 주행」**이다.
- 미완주이면 경로명·누적/전체 km·진행률을 보인다.
- 실제 종료 지명이 없으면 좌표를 UI에 노출하지 않고 `마지막 종료 지점`으로 표시한다.
- `처음부터`는 주 CTA와 경쟁시키지 않고 RouteDock 보조 선택으로 유지한다.
- 카드는 이번 앱 세션에서 숨길 수 있다. 숨김은 Ride·SavedRoute를 삭제하지 않는다.
- 사용자가 다른 Route를 명시적으로 불러오면 수동 선택이 우선한다.

### 3.2 「이어 달리기」 동작

1. 후보 SavedRoute가 현재 User 소유이며 `completed !== 1`인지 최신 데이터로 확인한다.
2. 기존 `useSavedRoutesWorkspace` load 경로로 workspace에 불러온다.
3. 최신 `lastProgressRatio`로 재개 offset과 anchor를 계산한다. 최근 Ride의 종료 좌표가 더 뒤이거나 앞이어도 재개 위치의 진실은 SavedRoute의 최대 진행률이다.
4. 지도 카메라를 재개점으로 이동하고 전체 Route를 프레이밍한다.
5. RouteDock을 `ready-to-start`로 만든다.
6. 완료 구간·남은 구간·재개점 마커를 표시한다.
7. 사용자가 입력 준비를 끝내고 Go를 누르면 기존 `handleStartRide(false)`로 시작한다.

후보 해석 뒤 Route가 삭제·완주됐다면 stale 상태를 시작하지 않는다. 최신 상태를 반영하고 재개 CTA를 제거한다.

### 3.3 「이 지점에서 새 경로」 동작

1. 최근 Ride의 `sessionEndLngLat`을 새 Route 출발점으로 설정한다.
2. 이전 Publication·Trail·loaded SavedRoute 결합 상태를 정리한다.
3. 출발점은 `S`로 고정하고 사용자는 도착점·경유지만 선택한다.
4. Directions 응답은 새로운 Route다. 이전 SavedRoute를 수정하지 않는다.
5. 연결 시작 전에 이름 입력이나 저장을 요구하지 않는다.
6. 사용자가 출발점을 직접 바꾸면 일반 Route 생성으로 전환한다.

### 3.4 지도 표현

| 요소 | 표현 |
|------|------|
| 이미 진행한 구간 | 내 도로망과 같은 마젠타 계열 |
| 남은 구간 | 현행 미주행 Route 빨강 |
| 재개점 | 단일 마커 + `31% · 여기서 계속` |
| 전체 Route | 현재 fitBounds 정책 유지 |

완료/남은 구간은 같은 geometry를 진행 거리에서 정확히 둘로 자른다. 경계 틈·중복을 순수 함수 시험으로 막는다. 2026-08-27 결정인 **빨강=아직 안 간 길, 마젠타=달린 길**을 그대로 쓴다.

### 3.5 모든 유효 Ride 결과 시트

`isDiscardableRideRecord`로 폐기되지 않은 모든 Ride는 결과 시트를 연다.

미완주 SavedRoute:

```text
주행 결과
오늘 5.2 km
전체 진행 31% → 43%
다음 출발점이 저장되었습니다
[닫기]  [지금 새 경로 연결]
```

완주:

```text
주행 결과 · 도착
오늘 5.2 km
경로를 완주했습니다
[닫기]  [끝점에서 새 경로]
```

ad-hoc 규칙:

- 결과와 다음 출발점은 SavedRoute 저장 여부와 무관하게 남는다.
- `내 경로로 저장`은 보조 액션으로 유지할 수 있다.
- 저장하지 않으면 다음 출발점까지 잃는다는 경고는 제거한다.

결과 시트를 닫으면 다음 주행 카드가 즉시 갱신된다. Firestore 쓰기 전에는 로컬 record로 낙관 표시하되 실패를 숨기지 않는다.

### 3.6 최근 주행 목록

최근 주행 목록은 1~5단계 완료 뒤 보조 진입점으로 확장한다.

- 행 클릭: 실제 Ride 구간과 종료점을 지도에서 보기.
- 소유 미완주 SavedRoute이면 `이어 달리기`.
- 그 외 실제 종료점이 있으면 `여기서 새 경로`.
- legacy Ride처럼 실제 종료점이 없으면 기록만 표시한다.
- 중첩 button을 만들지 말고 접근 가능한 row action 구조를 사용한다.

## 4. 데이터 계약

### 4.1 `rides/{rideId}` 신규 필드

```ts
type RideContinuationFields = {
  sessionStartLngLat: [number, number] | null;
  sessionEndLngLat: [number, number] | null;
  sessionStartRouteMeters: number;
  sessionEndRouteMeters: number;
  sessionStartProgressRatio: number;
  sessionEndProgressRatio: number;
};
```

규칙:

- start 좌표는 geometry의 `startOffsetMeters` 지점이다.
- end 좌표는 geometry의 실제 종료 누적 거리 지점이다. 계획된 `endLngLat`을 쓰지 않는다.
- meters는 0 이상, end ≥ start다.
- ratio는 0..1 clamp다.
- geometry가 없거나 계산 실패면 좌표는 `null`; Ride 저장은 막지 않는다.
- 현재 `rides`의 본인 전용 read 규칙을 완화하지 않는다.
- 기존 place 필드를 제거·rename하지 않는다. 실제 세션 지명 필드를 추가하고 UI가 이를 우선하되 legacy fallback을 유지한다.

좌표 계산은 `App.tsx`의 `liveForMap`과 같은 경계 함수를 공유한다.

- `rideDistanceAlongRoute`
- `getPointOnRouteByDistance`
- `lineStringLengthMeters`

별도 인덱스 보간을 새로 만들지 않는다.

### 4.2 `StoredRideSession` 확장

로컬 캐시·Firestore loader가 다음을 왕복한다.

- `sessionStartLngLat`, `sessionEndLngLat`
- `sessionStartRouteMeters`, `sessionEndRouteMeters`
- `sessionStartProgressRatio`, `sessionEndProgressRatio`
- 기존 `userRouteId`, Ride id

옛 필드 부재를 허용한다. legacy Ride를 일괄 backfill하지 않는다. SavedRoute가 남아 있으면 표시용 fallback을 계산할 수 있으나 옛 Ride에 다시 쓰지 않는다.

### 4.3 다음 주행 후보는 파생 상태

v1에서는 `users/{uid}.nextRide` 같은 mutable pointer 문서를 만들지 않는다. 최근 Ride와 SavedRoute에서 파생한다.

```ts
type NextRideTarget =
  | {
      kind: "resume_route";
      rideId: string;
      routeId: string;
      progressRatio: number;
      anchorLngLat: LngLat;
    }
  | {
      kind: "extend_from_ride";
      rideId: string;
      anchorLngLat: LngLat;
    };
```

선정 규칙:

1. 유효 Ride를 종료시각 내림차순으로 본다.
2. 최근 Ride가 본인 미완주 SavedRoute와 연결되고 0 < progress < 0.98이면 `resume_route`. 이때 `anchorLngLat`은 최근 Ride 종료 좌표가 아니라 SavedRoute geometry의 `lastProgressRatio` 지점에서 계산한다.
3. 그 외 `sessionEndLngLat`이 있으면 `extend_from_ride`.
4. Route가 삭제됐어도 종료 좌표가 있으면 새 경로 연결은 가능하다.
5. 좌표도 Route도 없으면 후보 없음.
6. 사용자가 카드를 숨기면 다음 Ride가 생길 때까지 다시 강제로 열지 않는다.

resolver는 React 밖 순수 함수로 두고 정렬·legacy fallback을 시험한다.

### 4.4 SavedRoute 진행률 단조 증가

`updateSavedRouteProgressInFirestore`는 transaction으로 현재 문서를 읽는다.

```text
nextProgress = max(server.lastProgressRatio, requestedProgress)
```

- `completed === 1`이면 미완주로 되돌리지 않는다.
- 낮은 stale write는 `lastRideId`도 덮지 않는다.
- 로컬 저장도 같은 규칙을 유지한다.
- 43% 뒤 늦은 31%가 와도 최종 43%다.

### 4.5 중복 SavedRoute 상태 보존

중복 지문 갱신 시 기존 문서의 다음 필드를 보존해 반환한다.

- `completed`, `completedAtIso`, `expiresAtIso`
- `lastRideId`, `lastProgressRatio`
- 최초 `createdAtIso`

존재하는 Route를 새 Route처럼 `completed:0`으로 합성하지 않는다.

## 7. 검증 계약

### 7.1 순수 시험

#### 실제 anchor

- 0% 시작 → 첫 좌표.
- 31% 시작 → geometry 거리 31% 지점.
- 43% 종료 → geometry 거리 43% 지점.
- 100% 종료 → 마지막 좌표.
- routeDistance와 geometry length가 달라도 `rideDistanceAlongRoute`와 동일.
- NaN·음수·초과 clamp.
- geometry 없음 → null이며 Ride 저장 계속.

#### 다음 후보 resolver

- 최근 Ride 없음 → 후보 없음.
- 최근 Ride + 본인 미완주 SavedRoute → `resume_route`.
- completed SavedRoute → `extend_from_ride`.
- 기존 최대 진행률 43%인 Route를 `처음부터` 타고 20%에서 끝내도 `resume_route` anchor는 43%.
- Route 삭제 + anchor 존재 → `extend_from_ride`.
- anchor·Route 없음 → 후보 없음.
- discard Ride는 건너뜀.
- 95~97%는 98% 정책에 따라 미완주.
- 입력이 정렬되지 않아도 `endedAt` 최신 선택.

#### 진행률·중복 저장

- 31→43% = 43%.
- 43→늦은 31% = 43%.
- completed 100→20% = completed 100%.
- 중복 저장 후 기존 completed/progress 유지.

#### Route 분할

- 0%: 완료 선 없음·남은 선 전체.
- 중간: 두 선 경계 좌표 동일.
- 100%: 완료 선 전체·남은 선 없음.
- 두 선 합계 거리가 원본과 허용 오차 내 동일.

### 7.2 `ride-verify` 셀렉터 계약

RouteDock·Go 이전 진입을 바꾸므로 계약을 먼저 갱신한다.

필수 앵커:

- `aria-label="다음 주행"`
- `N%에서 이어 달리기`
- `이 지점에서 새 경로`
- 결과 시트의 오늘 거리·전체 진행
- 기존 `aria-label="주행 시작"`
- 기존 running 판정인 주행 지표·주행 종료

`entry-contract.mjs`와 E2E spec 중 한쪽만 고치지 않는다.

### 7.3 에뮬레이터 E2E — `ride-continuation.spec.ts`

기존 `ride-entry.spec.ts`는 running까지만 검증하므로 신규 spec을 추가한다.

#### C1 — 미완주 SavedRoute 재개

1. Guest 익명 인증.
2. 결정적 fixture SavedRoute 준비.
3. 20%까지 주행하고 종료.
4. 결과 시트에 `전체 진행 0% → 20%`와 다음 출발점 표시.
5. page reload.
6. 다음 주행 카드에 20% 표시.
7. `20%에서 이어 달리기` 클릭.
8. ready-to-start·재개점 20% 확인.
9. Go 후 37%까지 주행하고 종료.
10. 최종 진행률 37%, 두 번째 운동 거리·Claim path는 20~37% 구간만.

#### C2 — stale 진행률 방어

43% write 뒤 늦은 31% write를 보내고 reload 후 카드·Firestore 모두 43%인지 확인한다.

#### C3 — 완주 끝점에서 새 Route

완주 뒤 `끝점에서 새 경로`를 눌러 새 S가 `sessionEndLngLat`과 허용 오차 내 동일하고 이전 SavedRoute가 불변인지 확인한다.

#### C4 — ad-hoc 저장 없이 연결

ad-hoc 종료 뒤 내 경로로 저장하지 않아도 reload 후 종료점에서 새 경로가 가능해야 한다.

#### C5 — legacy 안전성

신규 좌표 필드가 없는 옛 Ride는 목록에 보이되 CTA가 없고 `[0,0]` 이동·crash가 없어야 한다.

명령:

```powershell
cd apps/web
node scripts/ride-verify/verify-selectors.mjs
npm run test:e2e:ride
npm run test:e2e:ride-continuation
```

`RIDE_VERIFY_LIVE=1`을 직접 켜 실 Firebase에 붙이지 않는다. Harness처럼 `firebase emulators:exec`를 사용한다.

### 7.4 전체 게이트

```powershell

node apps/web/scripts/ride-verify/verify-selectors.mjs
npm run build
cd apps/web
```
