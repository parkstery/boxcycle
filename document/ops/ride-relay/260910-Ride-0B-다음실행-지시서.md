## 1. 검수 결과와 실행 원칙

열린 IDE 세션에서 PROBE 자동 수신→ACK→제출 왕복을 확인했다. 해당 SHA의 Windows 격리 시험은 watcher 9건, watchdog 2건 통과했다. 이것은 자동 협업과 짧은 시간 제한 시험의 검증이며 0B 제품 완료 판정이 아니다. 세션 종료 후 자동 재기동은 지원하지 않는다고 보고됐다.

기존 RTW-RESUME-20260910-01 실행을 이어서 아래 순서로 진행한다. 동일 파일을 수정하는 중복 실행을 만들지 않는다. 최신 코드에 이미 구현된 부분은 검증 후 보존하며 재작성하지 않는다. 병합·배포·1단계 구현은 보류한다.

## 2. 다음 작업 순서

### N1. 시간 제한 종료 처리 마무리

- Windows taskkill 실행 자체에도 짧은 timeout을 둬 실패한 정리 명령 때문에 전체 실행이 멈추지 않게 한다.
- 시험 자식·손자 PID가 종료됐는지, 별도로 만든 무관한 시험 sentinel은 살아 있는지 검증한다. 관련 없는 사용자 프로세스를 종료하지 않는다.
- POSIX 지원 코드를 유지한다면 부모 shell 종료와 별개로 남은 process group을 확인·정리한다. 지원 환경별 실행 증거와 미검증 범위를 분리한다.
- 실제로 10분 기다리지 말고 짧은 임시 제한으로 검증한 뒤 기본 600초를 확인한다. 5분 무진전 중단 및 동일 시도 반복 금지는 계속 적용한다.

### N2. 실제 저장·종료·화면 경계 검증

- 실제 useRideEndAndPersistence 또는 그 훅이 실제 호출하는 service에 제어 가능한 저장 Promise를 주입한다. 시험 안에 저장 로직을 복사하지 않는다.
- 저장 reject/null, 저장 성공+진행률 실패, 정상 저장을 실행하여 상태 전이와 실제 결과 시트 문구를 검사한다. type import·상수 비교는 증거가 아니다.
- 종료 원본 샘플과 오래된 UI 샘플을 의도적으로 다르게 두고 실제 종료 경로를 호출한다. 저장된 거리·시간·anchor·세션 geometry가 계약의 동일 종료 샘플을 사용하는지 입증한다.
- 종료 직후 경로 변경/계정 전환과 지연 응답을 시험한다. 결과와 저장 응답이 원래 주행에 귀속돼야 한다. 이번 종료점과 기존 최대 진행률 기반 재개점은 분리한다.
- 구독 controller/hook의 실제 연결, 15/60초 수명 및 stale callback 시험도 최종 증거 목록에 연결한다. 이미 작성한 시험을 활용하되 통과 개수만으로 완료라 하지 않는다.
- 완료 checkpoint: production 호출 위치, 실제 시험명, 관측 상태/좌표, 실행 명령·exit code, 정확한 SHA를 PROGRESS로 제출한다.

### N3. 외부 지도 의존성 격리와 실제 emulator 증거

- 직전 실패는 가짜 Mapbox 토큰에서 map/resume marker 표시가 막힌 상황이다. 실패한 외부 요청을 특정해 고정된 경로/지도 fixture 또는 기존 저장 경로로 검증을 진행한다.
- 시험 전용 외부 의존성 격리는 허용하되 성공 결과·resume marker를 무조건 삽입하거나 주행 상태를 강제로 성공시키는 우회는 금지한다.
- Firebase Auth/Firestore/Functions의 저장→서버 ID→실제 CF 집계→해당 주행 결과 수신은 실제 emulator로 수행한다. CF 결과 주입 시험과 구분한다.
- 원 C13: 결과 닫기→다음 주행→Go를 새로고침 없이 검증한다. 기존 인증·센서 준비 조건을 보존한다.
- 시도 전체는 서버 준비 포함 600초 이내. 실패하면 마지막 성공 단계·정확한 오류·로그를 보존하고 원인 수정 전 동일 시도를 반복하지 않는다.
