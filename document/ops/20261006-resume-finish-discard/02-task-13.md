## 원인 (Supervisor 확정)
- `lib/ride/rideRecordPolicy.ts` `isDiscardableRideRecord`: 이번 세션 거리 ≤ 100m **또는** ≤ 5초 → 기록 폐기(출시 기준 200m·3분 예정).
- `hooks/useRideEndAndPersistence.ts` 의 진행률 낙관 반영(`if (!discardRecord && savedRouteIdAtEnd)`)과 이후 persist 가 **폐기된 주행에서는 진행률·완주를 반영하지 않는다**.
- 이어 달리기는 저장 진행률 지점(상한 97%)에서 출발하므로 남은 구간 = 경로 × (1 − 진행률). 0.45km 경로·95% → 남은 22m → **항상 폐기** → 진행률 95% 고정 → 영원히 완주 불가. 경로가 약 3.3km 미만이면(출시 200m 기준이면 6.7km 미만) 누구든 같은 교착에 빠진다.

## 요구 (원칙: 운동 기록 폐기와 경로 진행 반영을 분리)
1. **짧은 주행이어도 경로 진행은 반영**: 저장 경로 주행에서 이번 세션의 누적 `completionRatio` 가 기존 저장 진행률보다 높으면, 운동 기록(rides 문서·칼로리·거리 통계)은 지금처럼 폐기하더라도 **저장 경로 진행률 갱신·완주 격상은 수행**한다.
   - 완주(≥0.98)면 promote(완주) + 이어달리기 슬롯 해제(기존 완주 경로와 동일 처리).
   - 미완주면 `updateSavedRouteProgressInFirestore`(최대값 유지).
   - 진행이 늘지 않은 짧은 주행(예: 즉시 종료)은 종전대로 아무것도 반영하지 않음.
2. `promote` 의 `rideId` 는 폐기된 주행이라 없을 수 있다 — 빈 문자열/null 처리 방식을 기존 코드 관례에서 찾아 맞추고 결과에 기재.
3. 결과 시트: 폐기된 짧은 주행이어도 경로를 완주했으면 「완주」가, 진행이 늘었으면 진행률 변화가 보이도록(지금은 거리 칸이 통째로 사라진다 — 캡처). 단 `RideSummarySheet.*` 를 바꿔야 하면 최소한으로, 바꾼 이유를 기재.
4. 폐기·반영 판정을 순수 함수로 분리해 단위 테스트: (a) 95%→100%, 세션 22m·15초 → 완주 반영 (b) 0%→3%, 세션 20m → 진행 반영 (c) 진행 증가 없음·즉시 종료 → 반영 없음 (d) 일반 긴 주행 → 종전과 동일. **사보타주**: 「폐기면 반영 안 함」으로 되돌리면 (a) 실패.
5. 저장 경로가 아닌(ad-hoc) 주행의 폐기 동작은 바꾸지 않는다.
