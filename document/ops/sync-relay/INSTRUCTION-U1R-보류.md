## 0. 판정 — **BLOCK**. 다만 네가 멈춘 것은 옳았다

C1 미달을 스스로 밝히고 최소거리를 올려 감추지 않았다. 그건 지시대로다.
**BLOCK 인 이유는 결과가 나빠서가 아니라 자[尺]가 고장 나 아무것도 잴 수 없기 때문이다.**

### 0-1. 자가 고장 났다 — 표본 10 개 전부 bbox 높이가 **정확히 0**

`u1-coords.json` 을 열어 보면 모든 표본에서 두 값이 끝자리까지 같다.

```
c2.after3s   headTopPx 392.35008087215573  ==  wheelBottomPx 392.35008087215573
c1_900       402.96972486267555 == 402.96972486267555   (4 프리셋 전부 동일 패턴)
c1_1200      553.4736004783391  == 553.4736004783391
c4.m4 · m40  동일
```

**세로 높이가 0 인 상자는 어떤 안전 영역에도 들어간다.**
그래서 `inSafeArea: true` 가 자동으로 찍혔고, 화면에서는 헬멧이 잘렸다.

보고서의 「머리·바퀴 y 가 같은 점(≈403~415px)」은 사실 **4 프리셋 사이의 차이**를 적은 것이다.
머리와 바퀴의 차이는 근사적으로 같은 게 아니라 **0** 이다. 이 구분이 중요하다.

원인은 `rideCameraFraming.ts:102-135` 다.

```
지시했던 것   glbModelLayer 가 쓰는 투영 행렬로 project 하라
실제 한 것    map.project(지면) 에 손으로 만든 고도 보정을 더한다
              fov 를 못 읽으면 36.87 을 지어내고, 카메라 거리도 추정값이며
              고도 항이 적용되지 않으면 **조용히 지면 좌표를 그대로 돌려준다**
결과          그 축퇴가 실제로 일어나 머리와 바퀴가 같은 점이 됐다
```

### 0-2. 그래서 C1~C4 가 전부 미확립이다

```
C1  시각적으로 미달 (스크린샷)
C3  「뷰포트 반영」의 근거가 0 높이 bbox 의 inSafeArea:true — 통과로 볼 수 없다
C4  「회귀 통과」도 같은 값에 기댄다 — 통과로 볼 수 없다
C2  「부분」이 아니라 **미측정**이다. snap 의 세 값이 전부 Number.MAX_VALUE(1.797e308) 다
    센티넬은 값이 아니다. 측정 실패로 세라
```

### 0-3. 전고 근거가 좌표계 혼합이다

```
쓴 값    RIDER_DISPLAY_HEIGHT_M = HEAD_C[1] × 1.15 = 1.594 m
문제     HEAD_C 는 절차 리그 공간의 머리 **중심**이다. 헬멧 top 이 아니다
대조     glbModelLayer.ts 주석: GLB AABB 전고 1.263 m → ×1.15 ≈ 1.45 m
         1.594 와 1.45 가 10% 어긋나고, 둘 다 실제 렌더 모델 top 으로 검산되지 않았다
```

생성기가 `riderRig.geometry.mjs` 를 쓴다는 확인 자체는 옳게 했다. 값의 **의미**가 틀렸다.

### 0-4. 살아남은 것

**N1 · N2 는 통과다.** `nametagTexts: ["guest1"]` · `bad: []` · 진단은
`__RTW_PEER_STEP_DIAG__` 로 이동만 됐고 pt7 도 살아 있다. **네임태그는 다시 하지 마라.**

공유 헬퍼도 요구대로다 — `computeRideFollowFraming` 을 `MapView.tsx:2442`(스냅)와
`rideCameraFollow.ts:227`(틱)이 함께 부른다. **이 구조는 유지하라.**

## 1. 이번에 할 일 — 순서를 지켜라

### 1-0. 보존

```

```

### 1-1. **먼저 자를 고쳐라.** 구도는 그 다음이다

```
① 투영을 실제 렌더 경로와 같은 행렬로 바꿔라
   glbModelLayer 가 모델을 그릴 때 쓰는 변환을 그대로 쓰라는 뜻이다
   map.project(지면) + 손계산 보정으로 되돌아가지 마라
   fov 를 못 읽으면 값을 지어내지 말고 **실패로 보고하라**

② 축퇴를 조용히 넘기지 마라
   고도 항이 적용되지 않으면 지면 좌표를 반환하지 말고 **측정 실패**로 표시하라
   Number.MAX_VALUE·0 같은 센티넬을 정상값처럼 JSON 에 적지 마라

③ 자가 검산을 게이트 앞에 세워라  ← 이번 지시의 핵심
   판정 직전에 확인한다:  wheelBottomPx − headTopPx  >  0
   0 이거나 비유한이면 **그 표본은 판정에 쓰지 말고 실패로 기록하라**
   이 검산이 없으면 같은 사고가 또 난다
```

**같은 실수가 두 번째다.** S4-M1 때는 `deferredRunTotal` 이 0 리터럴이라 근거가 허수였고,
이번엔 bbox 높이가 0 이라 게이트가 자동 통과했다. **축퇴값으로 통과할 수 있는 게이트는
반드시 자가 검산을 달아라.** 앞으로 모든 시험에 적용한다.

### 1-2. 전고를 확정하라 — 렌더 모델의 **top**

```
구하라   rider GLB 파일의 AABB 를 실제로 읽어 전고를 산출하라
         (주석의 1.263 m 를 믿지 말고 파일에서 뽑아 검산하라)
         거기에 model-scale 1.15 를 곱한 값이 화면 전고다
쓰지 마라 HEAD_C[1] (머리 **중심**) 을 전고로 쓰는 것
남겨라   산출한 값과 **산출에 쓴 코드/명령**을 증거로 보고서에 적어라
```

`HEAD_C` 는 look-at 높이 계산에는 계속 써도 된다. **전고와 look-at 을 구분하라.**

### 1-3. 그 다음에 구도

계측이 살아난 뒤에 §1-1 의 값으로 zoom·look-at 을 다시 맞춰라.
`computeRideFollowFraming` 한 곳에서만 고쳐라. pitch 80 유지. **최소거리 1 m 를 올리지 마라.**

## 3. 1 m 가 물리적으로 안 되면

계측이 살아난 상태에서 1 m·pitch 80 으로 전신이 안전 영역에 안 들어간다면
**그때는 진짜 결론이다.** 최소거리를 올리지 말고 멈추고, **유효한 실측치와 함께** 보고하라.

```
그 보고에 담을 것
  - 1 m 에서 라이더가 차지하는 실제 세로 픽셀
  - 안전 영역 높이 (뷰포트 − 172)
  - 둘의 비 — 몇 배가 모자란지
```

그 수치를 보고 감리가 안전 영역을 줄일지, pitch 를 예외로 둘지, 구도를 바꿀지 정한다.
**네가 임의로 정하지 마라.**
