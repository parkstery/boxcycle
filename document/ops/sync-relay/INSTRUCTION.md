## 0. S3A-V 판정 — 측정·절차는 채택, **시계 보정만 무효**

전량 보존 · 가드 5건 근거 제시 · `pt3 ok=0` 과 `pt2−pt3` 분리 · 원인 탐색 자제 · `src` 미변경 —
전부 지시대로였다. **한 곳만 무효다.**

### 0-1. 시계 보정이 없는 오차를 만들어 넣었다

두 페이지의 `Date.now()` 를 순차 호출해 얻은 `before 6 ms / after 320 ms` 는 **시계 오프셋이 아니라
호출 간 실행 지연**을 포함한다. 그 314 ms 를 드리프트로 보고 **선형 보간**한 결과 시간축이 휘었고,
`D_eff` · RMSE · max 판정이 전부 무효가 됐다.

**이 측정에서 skew 는 구조적으로 0 이다.** `peer-sync-s3av.spec.ts` 는 Playwright **한 프로세스의
두 브라우저 컨텍스트**이고, 두 페이지의 `Date.now()` 는 **같은 머신의 같은 OS 시계**를 읽는다.
skew 가 존재할 여지가 없다.

### 0-2. 감리 자책 2건

- **가드 ⑤ 설계 결함** — 「드리프트 100 ms 초과 시 선형 보간하고 명시」라고만 적었다.
  **애초에 그 핸드셰이크로 skew 를 잰다는 전제 자체가 틀렸다.** 절차를 지킨 네 잘못이 아니다.
- **「residual 은 skew 불변」이라고 한 것도 틀렸다** — *일정한* 오프셋에만 참이고,
  적용된 것은 **램프**라 잔차에도 실린다.

## 2. skew 처리 교체

```
폐기   순차 Date.now() 핸드셰이크 · 선형 드리프트 보정
정본   skew = 0        근거: 동일 머신 · 동일 OS 시계(두 브라우저 컨텍스트)
```

`clockSkewBefore` · `clockSkewAfter` · `clockSkewInterpolated` 는 **산출물에서 판정 경로에서 제거**하고,
원본 관측치로만 남겨 「실행 지연 포함, 판정 미사용」이라 표기하라.

### 2-1. 전송 비대칭 — **참고값으로만**

양방향이 전부 기록돼 있다(A·B 둘 다 발행·수신). 방향별 `writeStart → 상대 firstSeenAt` 를 각각 내라.

```
A→B p50 ≈ 166 ms      B→A p50 ≈ 155 ms      차이 ≈ 11 ms
```

이 차이는 **전송 경로 비대칭의 참고값**이다. **skew 추정에 쓰지 마라.** skew 는 §2 대로 0 이다.
동일 머신이 아닌 환경으로 확장할 때를 위한 기록일 뿐이다.

## 3. 지연 사슬 — **중복 없이 4 단계로 재정리**

⚠ **`writeRtt` 를 단계로 더하지 마라.** 로그상 B 수신이 write ACK 보다 먼저 일어난다
(`receiveVsAckMs` p50 **−108 ms**). `writeRtt` 는 `writeStart→firstSeenAt` 구간과 **겹쳐 관측된 값**이지
그 뒤에 이어지는 단계가 아니다. 더하면 이중 계산이다. 별도 관측치로만 남겨라.

```
① 샘플링 낡음      (A_auth − A_snap) / 실제속도        pt1 authDist·snapshotDist·appliedKmh
② publishQueue     capturedAt → motionWriteStartAt      pt3 publishQueueMs
③ 전송             motionWriteStartAt → firstSeenAt     pt3(A) ↔ pt4(B, first=1) seq 매칭
                                                        ※ 동일 머신이므로 직접 차분 (보정 없음)
④ 보간 지연        PEER_INTERP_DELAY_MS = 160 (상수)
────────────────────────────────────────────────────────
합계 = ①+②+③+④        서로 인접하고 겹치지 않는다
```

각 단계 **p50 · p95 · n** 과 **m 환산**(그 구간 실제 진행속도 사용, 발행 `speedMps` 금지)을 낸다.

## 4. 재검산 · 수용 게이트

### 4-1. 재검산

`s3av-summarize.mjs` 를 고쳐 `S3AV-chain-events.json` 을 skew = 0 으로 다시 집계한다.
`D_eff` 탐색 조건은 그대로 — `maxDelayMs = 3000` · `minOverlapRatio = 0.7` · 앞 2 s 폐기 ·
케이스 창은 기존 `S3AV-summary.json` 의 `window` 를 그대로 쓴다.

### 4-2. 수용 게이트 — 감리 재검산치를 재현해야 한다

**±5 % 안에 들어와야 한다.** 벗어나면 스크립트가 틀린 것이다.

| case | `D_eff` | RMSE | max | 겹침 |
|---|---:|---:|---:|---:|
| z15-depart | **560 ms** | 0.639 | 2.117 | 1.000 |
| z15-cruise | **540 ms** | 0.751 | 2.746 | 1.000 |

### 4-3. 교차검산 게이트 — §3 합계가 `D_eff` 와 맞아야 한다

| case | ① | ② | ③ | ④ | 합계 | 적합 `D_eff` |
|---|---:|---:|---:|---:|---:|---:|
| z15-depart | 231 | 7 | 155 | 160 | **553** | 560 |
| z15-cruise | 217 | 3 | 151 | 160 | **531** | 540 |

```
게이트   |합계 − D_eff| ≤ 50 ms
         벗어나면 사슬에 중복이나 누락이 있다는 뜻이다 — 맞추려 조정하지 말고 보고하라
```

두 경로(시간축 적합 / 단계 합산)가 독립적으로 같은 값에 도달하는지가 이번 검증의 핵심이다.

## 5. 판정 (재검산 후)

승인된 예산(`HANDOFF` §4)을 **그대로** 적용한다. 예산을 바꾸지도, 도달 가능성을 논하지도 마라.

```
z15-depart   D_eff 560 > 350 ✘ · RMSE ✔ · max ✔
z15-cruise   D_eff 540 > 350 ✘ · RMSE ✔ · max 2.746 > 2.5 ✘
전체         「S3A 대상인 z15 위치 불일치」 — 스케일 PASS · 정확도 미종결
```

⚠ **판정 문구 제약 (S3A-V 와 동일)**

- 「멀티라이더 위치 동기화 결함 종결」이라고 쓰지 마라 — D-1·D-2 / S3B 가 남아 있다
- **「예산이 도달 불가능하다」고 쓰지 마라** — 이번 단계의 결론이 아니다
- **해결책을 제안하지 마라** — 동시 쓰기 확대·보간 지연 조정·샘플링 배선 변경 전부 금지
