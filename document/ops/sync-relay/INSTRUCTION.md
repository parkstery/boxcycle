## 0. 왜 이 라운드가 필요한가

S4-7 은 좋은 답을 냈다. **다만 상한이 합성 시나리오 하나에 매달려 있다.**

```
실측 로그 3 개    speedMps min = max = 1.39 · stdev ≈ 1e-14 · 급변 0 · 정지 없음
                  → 예측 평가에 축퇴. 슬라이더 고정으로 달린 로그다
합성 1 개         5km/h → 1.39 m/s² 감속 → 정지 → 재가속
                  → T=1s 상한을 **이 하나가** 정했다
```

구현에 들어가기 전에 **그 숫자를 실측으로 바꾼다.**

**S4-7 의 결론(예측이 순위 편향·역전을 없앤다)은 유효하다. 되돌리지 마라.**

## 1. Chief 시간을 쓰지 마라 — 먼저 스크립트로 해결하라

Chief 가 직접 달리는 것은 **마지막 수단**이다. 순서를 지켜라.

핵심은 이것이다.

```
필요한 것    RTDB·타이밍·수신이 **실제 파이프라인**을 통과한 로그
필요 없는 것  사람이 페달을 밟았다는 사실
```

**속도 변화는 슬라이더를 스크립트로 움직여 만들면 된다.** 그래도 패킷 경로는 실제다.
S4-7 의 축퇴는 「속도가 고정이었다」는 것이지 「사람이 안 밟았다」가 아니다.

### 1-1. 프로파일

기존 2인 캡처 하네스를 재사용해, peer 쪽 슬라이더를 이 순서로 움직여라.

```
0~10 s    5 km/h 등속            (기준 구간)

```

조건 나머지는 그대로다 — **좌측 카메라 · 16 m · 양쪽 visible · 간격 5 m 이내로 시작.**

## 2. 【필수】 실제로 얼마나 급했는지 재라

**슬라이더가 속도를 즉시 점프시키면 그것은 실주행보다 급하다.** 그러면 T 상한이 또 과소평가된다.

```
2-1  달성된 가속도 분포를 내라 — p50 · p90 · 최대 (m/s²)
2-2  5 → 0 이 몇 초에 걸쳐 일어났는가
2-3  합성이 쓴 1.39 m/s² 와 비교하라 — 더 급한가 완만한가
```

판정해서 적어라.

```
달성 |a| 가 합성보다 완만   → 이 로그가 더 현실적이다. T 상한을 이 로그로 정한다
달성 |a| 가 합성보다 급함    → 슬라이더가 즉시 점프한 것이다.
                              그 사실을 적고 §4 로 가라 (Chief 실주행 요청)
```

**추정하지 말고 로그에서 재라.**
