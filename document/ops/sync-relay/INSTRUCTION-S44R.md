## 1. 핵심 오류 — 감리가 코드에서 확인했다. 다시 조사하지 마라

`apps/web/src/lib/peerMotion/peerJitterCapture.ts:270`

```ts
const alongReverse =
  dy * prevScreenDy < 0 &&
  Math.abs(dy) >= JITTER_SCREEN_REVERSE_PX &&
  Math.abs(prevScreenDy) >= JITTER_SCREEN_REVERSE_PX;
```

**앞뒤를 화면 Y 축으로 고정했다.** 주석에도 「팔로우 카메라에서 앞뒤 ≈ screen Y」라고 적혀 있다.

Chief 가 증상을 본 **좌측 카메라에서는 주행 방향이 화면 X 축에 가깝다.**
그래서 `dy ≈ 0` 이 되어 `alongScreenReverseCount = 0`, `axis: "none"` 이 나왔다.

실제 캡처에는 이것이 들어 있다.

```
2D 반전        6 회 · 최대 42.6 px       ← X 축이라는 이유로 버려졌다
거리 역행      3 회 · 최대 0.257 m       ← 0.5 m 미만이라 버려졌다
```

**`axis: "none"` 은 채택할 수 없다.** 버린 신호를 다시 판정하는 것이 이번 일이다.

## 2. 새 판정기 — 진행축을 프레임마다 구한다

### 2-1. 고정 축 금지

```
쓰지 마라   screen Y 고정 · screen X 고정 · 둘 중 큰 쪽 고르기
써라        그 프레임의 **화면상 진행축** 에 peer 이동을 투영한 부호
```

진행축 û 를 구하는 방법은 네가 정하되, **근거를 적어라.** 권고는 둘 중 하나다.

```
① 경로 접선 투영   그 지점의 경로 진행 방향을 화면으로 투영해 단위벡터로 삼는다 (정확)
② 전진 회귀        displayDistM 이 증가하는 구간에서 Δscreen 을 회귀해 진행 방향을 추정한다
                   (기존 캡처에 lng·lat·screenX·screenY 가 있으므로 재판정이 가능하다)
```

②는 기존 로그만으로 계산되므로 **재판정(§3)에 반드시 쓸 수 있어야 한다.**
û 는 순간값이 아니라 **여러 프레임 창으로 매끄럽게** 구하라 — 튐 자체가 û 를 오염시키면 안 된다.

판정은 투영 부호로 한다.

```
s_i = (Δscreen_i) · û_i        s_i < 0 이면 화면상 후진
```

### 2-2. 카메라 이동과 peer 움직임을 분리하라

같은 프레임에 **로컬 라이더 화면 좌표**를 함께 남겨라. 그러면 셋을 나눠 볼 수 있다.

```
peer 절대 화면좌표        카메라가 움직이면 같이 움직인다
peer − 로컬 상대 좌표     카메라 이동이 상쇄된다 ← 진짜 튐은 여기서 보인다
진행축 상대 변위          위 상대 좌표를 û 에 투영한 값
```

카메라 요·피치·중심도 남길 수 있으면 남겨라. **둘이 같이 움직이면 카메라, peer 만 움직이면 peer 다.**

### 2-3. 임계값 — Chief 합격 기준으로 쓰지 마라

```
금지   0.5 m 미만이라 버리기 · 8 px 미만이라 버리기 · 「임계 이하이므로 정상」
필수   원시 역행량 전수 · 반전 횟수 · 진폭(peak-to-peak) · 지속 구간을 모두 보고
필수   임계값 아래의 **반복 진동**도 버리지 말고 따로 세라
```

`JITTER_SCREEN_REVERSE_PX = 8` 을 유지하려면 **실제 관찰이나 화면 스케일 근거**를 제시하라
(그 카메라 거리에서 1 m 가 몇 px 인지). 근거 없이 남기지 마라.
