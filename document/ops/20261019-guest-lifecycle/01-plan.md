# 실행 계획

## 승인된 범위

Chief가 Guest 유지 + 로그아웃 자동 삭제 철회 + 마지막 활동 30일 서버 정리, 기존 잔여 데이터 최초 정리와 삭제된 Guest 재접속 복구를 요청했다. 제품 의미·수명 정책 변경은 이 요청으로 승인된 것으로 판정한다. Google 사용자 4명 및 관련 개인·공용 데이터를 보호한다.

## 순서·완료 조건

1. 조사: branch/HEAD/기존 dirty 해시 보존. GLM 실제 응답 확인. 운영 Auth 읽기 조회로 Google 4명 확인·보호 UID 고정. users가 없는 데이터까지 귀속을 수집하고 Auth 존재 여부를 대조. 개인정보·키·토큰은 결과에 출력하지 않는다.
2. 구현: 기존 개인 데이터 삭제/공용 익명화 정책 재사용. Guest 서버 활동 시각·30일 판정·일일 제한 배치·실패 재시도·삭제 기록. 활동 갱신과 삭제/Google 연결 사이 경합 방지. 삭제 중 클라이언트 쓰기 재생성 차단을 검증한다. Auth에만 존재하는 Guest와 Auth 없는 데이터도 발견 가능해야 한다. 최초 활동 필드 없는 기존 계정은 안전한 유예 기준을 둔다.
3. 클라이언트: Guest 로그아웃은 계정/데이터 삭제 없이 signOut. 탭 종료는 기존 인증 유지. 복원된 Guest를 서버 검증하기 전에 사용자 데이터 쓰기를 시작하지 않는다. 삭제/disabled 등 확정된 만료에만 해당 UID 캐시를 정리하고 명시 진입 화면으로 복구. 네트워크 실패는 보존·재시도, 전체 localStorage/IndexedDB 초기화 금지. Google 기존 계정 연결 충돌 처리도 보존 우선.
4. 검증: 시간 경계·활동 연장·Google/admin/보호 UID 제외·Auth-only/Firestore-only/RTDB-only·경합·중간 실패 재시도·기존 토큰 재쓰기·네트워크 실패·로그아웃 회귀. functions build/test/lint, web type/build/lint 및 ride-verify 계약. 필요 에뮬레이터, 단일 worker. 5분 진전 없으면 로그·포트 확인 후 경로 전환.
5. 최초 정리: 운영 dry-run 보고·보호 4명 검수 → 정확한 대상 manifest 기반 실행, 실행 직전 Auth 재확인. 실제 개인 데이터만 삭제하고 공용 자료는 현 정책대로 보존/익명화. 전후 Auth UID와 보호 데이터 비교, 잔여 재스캔·실패 보고. 신규 Guest 생성 금지.
6. 운영 적용: 배포할 코드·Rules·스케줄과 비용 범위를 구체화하고 검증된 범위만 반영. 미배포 상태를 완료로 오보고하지 않는다. Chief 테스트 절차와 절대 실행 경로를 제공한다.

## 증거·인계

지시·결과·감리는 별도 파일. 산출물은 evidence, 비밀은 기록 금지. 최초 정리 도구는 기본 dry-run·명시 manifest·프로젝트 확인·최대 처리 수·Google 제외 안전장치 필요. 기존 작업 변경은 덮어쓰지 않으며 커밋/푸시하지 않는다.
