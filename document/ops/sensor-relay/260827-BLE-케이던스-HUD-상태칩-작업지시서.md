## 0. 확정된 제품 결정

실물 `CYCPLUS C3 12695`가 RTW에서 연결되고 페달링으로 주행되는 것은 사용자가 확인했다. 이번 작업은 센서 프로토콜 수정이 아니라 **센서의 위치·상태 확인·상세 설정 진입 UX를 본류에 맞추는 작업**이다.

확정 결정:

1. 센서의 주 표면은 RouteDock이 아니라 **HUD 우측 상단 계정 버튼 왼쪽**이다.
2. 메인 화면은 장치의 긴 이름을 보여 주지 않는다.
3. 메인 센서 칩은 다음 두 정보만 즉시 보여 준다.
   - 주행 전: 흰색/초록색 LED로 미연결/연결 상태
   - 주행 중: LED와 현재 RPM
4. 센서 칩 전체가 버튼이며, 클릭하면 전용 상세 설정을 연다.
5. 장치의 정확한 이름, 연결 오류, 연결/해제, 입력 모드 전환은 상세 설정에서만 보여 준다.
6. 센서 연결 또는 명시적 체험 입력 선택은 **Go 이전에 끝내는 주행 준비 단계**다.
7. RouteDock은 준비가 끝난 라이더가 주행을 실행하는 표면이지 센서·입력 설정 표면이 아니다.
8. 주행 중 센서 상세 설정은 최초 설정이 아니라 단절 복구와 안전한 체험 입력 전환에만 사용한다.

사용자가 해결하려는 문제는 “경로를 만든 뒤 RouteDock 안에서 센서를 찾아야 함”이다. RTW에 들어오자마자 센서 준비 상태를 확인하고, 필요하면 계정 메뉴나 RouteDock을 거치지 않고 설정에 들어갈 수 있어야 한다.

## 1. 고정 UX 계약

### 1.1 배치

`MapHud`의 기존 우상단 영역을 별도 절대 위치 두 개로 겹치지 말고 하나의 액션 행으로 바꾼다.

```text
우측 상단

[ ● CAD / ● 72 rpm ] [ A  a111111 ]
       센서 칩             계정 칩
```

- 데스크톱: 센서 칩이 계정 칩의 **왼쪽**.
- 폭이 좁으면 두 칩이 화면 밖으로 밀리거나 Mapbox 컨트롤과 겹치지 않게 축약 또는 자연스러운 반응형 배치.
- 메인 맵 HUD가 보이는 동안 Guest·등록 사용자 모두 노출한다.
- `gate`와 `summary`에서 숨기는 기존 HUD 정책은 유지한다.
- 계정이 없는 signed-out 맵 모드에서는 로그인 칩 왼쪽에 둘 수 있다. 센서 상태를 계정 데이터에 종속시키지 않는다.
- `setup`, `ready-to-start`에서는 주행 입력 준비 버튼으로 동작한다.
- `riding`, `paused`에서도 상태 확인을 위해 보이지만, 정상적인 최초 센서 설정을 시작하지 않는다. cadence 주행의 단절 복구·연결 해제·명시적 체험 입력 전환만 제공한다.

`MapHud`는 debug/normal 두 경로에서 props를 받는다. `App.tsx`의 두 `mapHud={{...}}` 호출부를 모두 배선한다.

### 1.2 메인 센서 칩 표시

칩의 기본 텍스트는 짧은 `CAD`다. `CYCPLUS C3 12695` 같은 장치명은 칩 DOM에 넣지 않는다.

| 상태 | LED | 칩 텍스트 | 비고 |
|------|-----|-----------|------|
| 미연결 `idle` | 흰색 | `CAD` | 초기 상태 |
| 검색/연결 중 | 흰색 pulse | `CAD` | 텍스트 폭이 흔들리지 않게 유지 |
| 연결됨, 주행 전 | 초록색 | `CAD` | 첫 화면에서 연결 여부 즉시 확인 |
| 연결됨, `riding`/`paused`, 유효 샘플 전 | 초록색 | `-- rpm` | 연결과 데이터 대기를 구분 |
| 연결됨, `riding`/`paused`, 페달 정지 | 초록색 | `0 rpm` | 연결은 살아 있음 |
| 연결됨, `riding`/`paused`, 페달링 | 초록색 | 반올림한 `N rpm` | 예: `72 rpm` |
| 주행 중 단절/오류 | 흰색 | `-- rpm` | 자동 manual fallback 금지 |
| Web Bluetooth 미지원 | 흰색 | `CAD` | 클릭한 상세 설정에서 지원 환경 안내 |

LED는 제품 결정대로 **초록/흰색 두 의미만** 사용한다. 오류를 빨강·주황 LED라는 제3 의미로 메인 칩에 추가하지 않는다. 상세 상태는 `aria-label`, title, 상세 설정의 문구로 전달한다.

필수 접근성:

- 실제 `<button type="button">`.
- `aria-label` 예: `케이던스 센서: 연결됨, 72 rpm`, `케이던스 센서: 연결 안 됨`.
- 상세 설정 열림 상태를 `aria-expanded`로 제공.
- LED만으로 의미를 전달하지 않는다.
- 키보드 focus-visible과 충분한 클릭 영역을 유지한다.

### 1.3 클릭과 주행 전 상세 설정

센서 칩 클릭은 전용 `CadenceSensorSheet` 또는 동일 역할의 전용 상세 패널을 연다. 기존 `RideSettingsSheet` 전체를 여는 방식은 사용하지 않는다. 센서 버튼을 눌렀는데 TTS·BGM 같은 무관한 설정이 먼저 보이면 안 된다.

상세 설정이 소유할 정보와 액션:

- 현재 상태: 미연결 / 검색·연결 중 / 연결됨 / 페달 정지 / 연결 끊김 / 오류.
- 선택된 장치의 전체 표시명. 예: `CYCPLUS C3 12695`.
- 현재 RPM과 `가상 N km/h`.
- 현재 입력 모드: `센서 속도` 또는 `체험 속도`.
- `센서 검색` 또는 `다시 연결`.
- `연결 해제`.
- 명시적 `센서 속도로 전환` / `체험 속도로 전환`.
- Web Bluetooth 미지원 시 Chrome·Edge와 HTTPS/localhost 안내.
- 오류 문구. 토큰, BLE 주소, device id는 표시·저장하지 않는다.
- manual 선택 시 주행 전에 정할 체험 속도. 기존 `SessionSpeedControl`을 이 준비 표면으로 옮겨 재사용할 수 있다.

미연결 상태의 흐름:

1. 센서 칩 클릭 → 상세 설정 열림.
2. 상세 설정의 `센서 검색` 클릭 → 기존 `useBleCrankRpm.connect()` 호출.
3. 브라우저 Web Bluetooth chooser가 스캔·선택 UI를 담당.
4. 사용자가 장치를 선택하면 정확한 장치명을 상세 설정에 표시.
5. 연결 성공 시 LED가 초록색으로 바뀌고 입력 모드는 기존 계약대로 `cadence`가 된다.
6. 실제 크랭크 샘플을 받기 전에는 `페달을 돌려 센서를 확인하세요` 상태다.
7. 사용자가 페달을 돌려 유효 RPM이 한 번 확인돼야 센서 입력 준비가 끝난다.

주의: Web Bluetooth의 `requestDevice()` chooser 대신 임의의 인앱 BLE 스캔 목록을 만들지 않는다. 일반 웹 페이지는 chooser에서 발견된 주변 장치 목록을 수동 열람할 수 없다. `requestDevice()`는 반드시 상세 설정 안의 사용자 클릭 핸들러에서 직접 시작한다.

장치명이 선택 직후에도 보이게 하려면 `requestDevice()`가 resolve된 직후 `device.name`을 상태에 반영하고, GATT 연결 중/실패 시에도 상세 설정에서 선택한 장치를 식별할 수 있게 한다. chooser 취소는 오류로 표시하지 않는다.

### 1.4 주행 전 입력 준비 게이트

정상 순서는 다음으로 고정한다.

```text
Guest/등록 사용자 진입
→ 센서 칩에서 주행 입력 준비
   ├─ 센서 검색 → 연결 → 페달을 돌려 RPM 확인
   └─ 「체험 속도로 준비」 명시 선택 → 속도 설정
→ 경로 선택·확정
→ Go
→ riding
```

앱 시작 시 기존 코드의 `rideInputMode="manual"`만으로 준비 완료로 간주하지 않는다. 사용자가 센서를 연결했거나 체험 입력을 명시적으로 골랐다는 별도 준비 상태가 필요하다.

권장 상태 모델:

```ts
type RideInputReadiness =
  | "choice-required"
  | "manual-ready"
  | "cadence-connecting"
  | "cadence-awaiting-sample"
  | "cadence-ready";
```

준비 완료 판정:

- `manual-ready`: 사용자가 상세 설정에서 `체험 속도로 준비`를 명시적으로 선택하고 속도값을 확인함.
- `cadence-ready`: GATT connected이고 이 앱 세션에서 유효 크랭크 샘플을 최소 한 번 받아 `crankRpm !== null` 상태가 됨. 이후 정지해 `0rpm`이 된 것은 여전히 준비 완료다.
- chooser를 열었거나 GATT만 연결됐지만 크랭크 샘플이 한 번도 없으면 준비 미완료다.
- Go 전에 센서가 단절되면 `cadence-ready`를 해제하고 다시 연결·샘플 확인을 요구한다.

`canStartRide`는 경로 준비뿐 아니라 입력 준비를 포함해야 한다.

```ts
canStartRide = routeReady && inputReadiness in ["manual-ready", "cadence-ready"]
```

준비 미완료 상태에서 Go를 눌러 주행 화면에 들어간 뒤 센서 설정을 시키지 않는다. Go는 시작되지 않아야 하며, 버튼 근처에는 `센서를 연결해 페달을 확인하거나 체험 속도를 선택하세요`처럼 이유를 짧게 보여 준다. 센서의 실제 설정 UI를 RouteDock 안에 다시 넣지는 않는다.

준비 선택은 같은 앱 세션의 다음 경로에서도 유지할 수 있다. 단, cadence 연결이 실제로 끊겼다면 준비 완료를 유지하지 않는다.

### 1.5 RouteDock과 기존 설정의 역할 정리

- `RouteDock`에서 긴 센서 상태 블록과 연결/재연결 버튼을 제거한다.
- `CadenceSensorControl.tsx`가 더 이상 사용되지 않으면 삭제한다.
- `RouteDock.css`의 센서 전용 스타일도 사용처와 함께 정리한다.
- `SessionSpeedControl`과 센서/체험 입력 선택도 RouteDock에서 제거해 주행 전 상세 설정으로 옮긴다.
- 현재 가상 속도는 기존 HUD 주행 지표가 표시한다. RouteDock에 별도 속도 설정·상태 블록을 만들지 않는다.
- manual/cadence 선택과 manual 속도 설정은 Go 전에 새 센서 상세 설정에서 끝낸다.
- `RideSettingsPanel`과 MENU 안에 중복된 BLE 센서 설정도 제거한다. **상단 센서 칩 → 센서 상세 설정**을 단일 주 경로로 만든다.
- 오디오·코칭 등 기존 `RideSettingsSheet` 기능은 그대로 유지한다.

주행 중 상세 설정의 역할은 다음으로 제한한다.

- cadence 주행 중 단절: `다시 연결` 또는 안전한 `체험 속도로 전환`.
- cadence 주행 중 정상 연결: 상태 확인과 연결 해제.
- manual 주행 중: 최초 센서 검색·센서 모드 전환은 제공하지 않고 `다음 주행 전에 센서를 설정하세요`로 안내.
- 주행 중 manual 속도를 다시 튜닝하는 일반 설정 흐름은 만들지 않는다. cadence 단절 후 체험 전환은 주행 전에 정한 manual 속도 또는 기존 안전 기본값을 사용한다.

이 복구 액션은 RouteDock `editLocked`와 무관해야 한다. 경로 삭제·경유지 변경 잠금은 그대로 유지한다.

## 2. 구현 경계와 권장 파일 구조

### 2.1 상태 소유권

- BLE/GATT/CSC: `hooks/useBleCrankRpm.ts`.
- 입력 모드와 목표 속도: 현재처럼 `App.tsx` + `lib/cadenceRideInput.ts`.
- Go 이전 입력 준비 상태: `App.tsx` 또는 의미가 분리된 작은 훅. 연결 상태나 기본 `manual` 값만으로 준비 완료를 추론하지 않는다.
- 메인 칩의 순수 표시: `components/maphud/` 아래 작은 컴포넌트 또는 `MapHud.tsx`의 명확히 분리된 하위 컴포넌트.
- 센서 상세 설정: `components/sensor/` 또는 기존 컴포넌트 규칙에 맞는 전용 컴포넌트.
- 시트 상호 배타 상태: `app/useAppSheetNavigation.ts`에 `cadenceSensorSheetOpen`, setter, opener를 추가한다.

권장 타입은 BLE 훅 객체 전체를 HUD에 넘기지 않고 표시와 액션을 분리한다.

```ts
type CadenceHudState = {
  capable: boolean;
  uiState: BleCrankRpmUiState;
  crankRpm: number | null;
};
```

상세 설정은 여기에 `deviceLabel`, `errorMessage`, `mode`, connect/disconnect/mode callbacks를 추가해 사용한다. 컴포넌트가 CSC 패킷을 해석하거나 속도 공식을 복제하지 않는다.

## 3. 기존 구현에서 함께 닫을 결함

### 3.1 주행 전 준비와 주행 중 복구의 혼합

현재 RouteDock은 `editLocked={routeMenuLockedForProd}`이고 센서 블록에 `disabled={cadence.disabled || editLocked}`를 전달한다. 이 때문에 주행 중 화면에 보이는 `다시 연결`과 `체험 속도로 전환`이 잠긴다.

상단 센서 칩/상세 설정 이관 후 다음이 참이어야 한다.

- 최초 연결·센서 확인·체험 입력 선택은 Go 전에 끝난다.
- 준비 미완료 상태에서는 Go가 주행을 시작하지 않는다.
- 주행 중 센서 단절 → 칩 클릭 가능.
- 상세 설정의 `다시 연결` 가능.
- 같은 주행 세션에서 재연결 후 페달링 재개 가능.
- 사용자가 명시적으로 `체험 속도로 전환` 가능.
- manual로 시작한 주행에서 첫 센서 검색을 시작하지 않음.
- 경로 삭제·경유지 변경은 계속 잠김.

### 3.2 pagehide 후 stale 연결 상태

`useBleCrankRpm`의 현재 `pagehide`는 GATT만 해제하고 `uiState`와 `crankRpm`을 그대로 둔다. BFCache로 복귀하면 실제 GATT는 끊겼는데 UI가 connected/이전 RPM으로 남을 수 있다.

- `pagehide`/복귀 이후 실제 연결과 React 상태가 모순되지 않게 정리한다.
- GATT를 해제했다면 복귀 화면은 연결됨으로 표시하지 않고 RPM도 남기지 않는다.
- 일반 unmount에서 불필요한 상태 업데이트 경고를 만들지 않도록 이벤트 경로와 unmount cleanup을 구분한다.

### 3.3 새 lint 경고 제거

`App.tsx`의 `bleCadencePanel` `useMemo`는 현재 `bleCrankRpm` 누락 dependency 경고가 있다. 새 props 모델을 만들면서 이 경고를 제거한다. 저장소의 기존 react-hooks baseline 전체를 이번 작업에서 광범위하게 고치지는 않지만, **이번 변경이 추가한 error/warning은 0건**이어야 한다.

## 4. 구현 순서

1. 센서 칩 표시 상태와 `RideInputReadiness` 계약을 순수 함수/타입으로 먼저 고정한다.
2. Go 시작 조건에 입력 준비 게이트를 추가하고 selector/e2e 계약을 먼저 갱신한다.
3. `MapHud` 우상단을 센서+계정 액션 행으로 만들고 debug/normal 두 호출부를 배선한다.
4. `useAppSheetNavigation`에 센서 상세 설정을 추가해 다른 시트와 상호 배타로 연다.
5. 전용 센서 상세 설정에 센서 연결·샘플 확인·체험 입력과 속도 준비를 구현한다.
6. RouteDock 및 일반 주행 설정의 중복 센서/속도 준비 UI를 제거한다.
7. 주행 중에는 cadence 단절 복구만 허용하고 최초 센서 설정을 막는다.
8. pagehide 상태 정합성과 새 lint 경고를 수정한다.
9. 자동 검증 후 실물 센서로 아래 수용 시나리오를 확인한다.
10. 코드 사실에 맞춰 결정 로그·상태보드·이 문서 상태를 갱신한다.

## 5. 검증 게이트

### 5.1 자동 검증

최소 명령:

```powershell
npm -w boxcycle-web run test:sensor-cadence
node apps/web/scripts/ride-verify/verify-selectors.mjs
npm run build
```

실주행 진입 E2E:

```powershell
cd apps/web
npm run test:e2e:ride
```

5000 포트가 다른 dev 서버에 사용 중이면 하네스 문서대로 `RTW_DEV_PORT=5001`로 실행한다. 에뮬레이터 없이 `RIDE_VERIFY_LIVE=1`만 직접 켜서 실 Firebase에 붙이지 않는다.

RouteDock/HUD 앵커를 바꿔 기존 6단계 셀렉터 계약이 영향을 받으면 `entry-contract.mjs`와 `ride-entry.spec.ts`를 함께 수정한다. 검증기를 삭제·약화하지 않는다.

이번 작업은 Go의 사전조건을 바꾸므로 ride-entry E2E도 반드시 새 순서를 따라야 한다. 자동 E2E에는 BLE 장치가 없으므로 Guest 진입 후 센서 상세 설정에서 `체험 속도로 준비`를 명시적으로 선택한 뒤 경로 로드→Go→running으로 진행한다. 기존 테스트가 기본 `manual` 상태만 믿고 바로 Go를 누르게 두지 않는다. 셀렉터 계약에도 `주행 입력 준비` 단계를 추가한다.

추가 시험 또는 정적 계약으로 최소 다음을 고정한다.

- 미연결: 흰 LED + `CAD`.
- 연결/주행 전: 초록 LED + `CAD`.
- 연결/주행 중: 초록 LED + 반올림 RPM.
- 연결/주행 중 최초 샘플 전: `-- rpm`.
- 연결/주행 중 정지: `0 rpm`.
- 단절/주행 중: 흰 LED + `-- rpm`.
- 메인 칩에 전체 장치명이 렌더되지 않음.
- 칩의 접근성 이름에는 연결 상태와 RPM이 포함됨.
- 기본 `manual` 값만으로는 Go 준비 완료가 되지 않음.
- 명시적 `체험 속도로 준비` 후 Go 가능.
- cadence는 connected만으로 부족하고 유효 RPM 샘플 확인 후 Go 가능.
- cadence가 Go 전에 단절되면 Go가 다시 잠김.

### 5.2 실물 수용 시나리오

| 번호 | 절차 | PASS |
|------|------|------|
| H1 | RTW 메인 맵 진입 | 계정 왼쪽에 흰 LED `CAD` 칩 표시 |
| H2 | 센서 칩 클릭 | 센서 전용 상세 설정 열림 |
| H3 | `센서 검색` 클릭 | 브라우저 chooser가 사용자 클릭으로 열림 |
| H4 | `CYCPLUS C3 12695` 선택 | 전체 장치명은 상세 설정에만 표시, 메인 칩은 짧게 유지 |
| H5 | 연결 성공, 페달을 아직 돌리지 않음 | 초록 LED지만 `페달을 돌려 확인` 상태, Go 준비 미완료 |
| H6 | 주행 전에 페달을 돌려 유효 RPM 확인 | `cadence-ready`, 경로까지 준비되면 Go 가능 |
| H7 | 새 앱 세션에서 센서 없이 경로만 로드 | 기본 manual 값만으로 Go 불가, 준비 이유 표시 |
| H8 | 상세 설정에서 `체험 속도로 준비`와 속도 선택 | `manual-ready`, Go 가능 |

| H10 | 페달 정지 | `0 rpm`, 기존 램핑 후 거리 정지 |
| H11 | 주행 중 센서 단절→칩→`다시 연결` | 감속 정지, 자동 manual fallback 없음, 같은 세션에서 복구 가능 |

실물 로그에는 장치 표시명과 PASS/FAIL만 남긴다. BLE 주소·device id·Firebase/Mapbox 토큰은 기록하지 않는다.

## 7. 하지 말 것

- 센서 칩을 계정 메뉴 안에 넣지 않는다.
- 메인 칩에 `CYCPLUS C3 12695` 같은 긴 이름을 노출하지 않는다.
- 인앱 BLE 스캔 목록을 새로 만들지 않는다.
- 앱 시작과 동시에 chooser를 자동으로 열지 않는다.
- 기본 `manual` 초기값을 사용자의 명시적 체험 입력 선택으로 간주하지 않는다.
- Go 후에 최초 센서 설정을 요구하거나 manual 주행 중 센서 검색을 시작하지 않는다.
- RouteDock에 센서/체험 입력 선택, manual 속도 설정, 현재 가상 속도 블록을 두지 않는다.
- 센서 단절을 manual 자동 전환 신호로 사용하지 않는다.
- 센서 액션을 RouteDock `editLocked`에 묶지 않는다.
- FTMS·파워·심박·저항 제어를 함께 추가하지 않는다.
- CSC 파서, 0.32 매핑, 30km/h 상한, Conquest 서버 정책을 이번 UI 작업과 함께 재설계하지 않는다.
- 기존 react-hooks baseline 전체를 범위 없이 수리하지 않는다.
- 물리 검증 없이 상태보드를 ✅로 올리지 않는다.
