## 0. 사용자 요청과 성공의 정의

사용자는 PC에서 Web Bluetooth 선택기를 열어 **`CYCPLUS C3 12695`가 검색·페어링되는 것**까지 확인했다.

그러나 사용자가 원하는 결과는 브라우저 페어링 자체가 아니다.

1. RTW 안에서 센서를 연결한다.
2. 페달을 돌리면 현재 케이던스가 즉시 보인다.
3. 주행을 시작한 뒤 페달을 돌린 만큼 라이더가 실제 경로를 전진한다.
4. 페달을 멈추면 라이더도 감속해 멈춘다.
5. 센서 연결이 끊겼는데 슬라이더 속도로 몰래 계속 달리지 않는다.

즉 이번 작업의 성공 기준은 **“BLE 연결됨”이 아니라 “페달링이 주행을 지배함”**이다.

## 1. 현재 코드의 진실

### 1.1 이미 있는 것

- `apps/web/src/hooks/useBleCrankRpm.ts`
  - 표준 BLE CSC 서비스 `0x1816`과 CSC Measurement `0x2A5B`를 사용한다.
  - 누적 크랭크 회전수와 1/1024초 이벤트 시간을 파싱한다.
  - `uint16` rollover와 RPM EMA를 처리한다.
- `apps/web/src/components/ride/RideSettingsPanel.tsx`
  - 주행 설정 시트에 센서 연결/해제와 RPM 표시가 있다.
- `apps/web/src/App.tsx`
  - RPM을 Conquest의 `pedalSec`와 라이더 페달 애니메이션에 전달한다.
- `apps/web/src/hooks/useVirtualRideSession.ts`
  - 실제 경로 전진은 `speedKmh` 목표값과 `rideSpeedRamp.ts`가 결정한다.
- `apps/web/src/components/route-dock/SessionSpeedControl.tsx`
  - 현재 주행 속도의 실질적인 입력은 5~50km/h 슬라이더다.

### 1.2 현재 사용자 흐름이 실패하는 이유

1. `useBleCrankRpm({ sessionActive: rideStatus !== "idle" })`이므로 **주행 전 연결을 유지할 수 없다.**
2. BLE RPM은 정복 판정과 애니메이션에만 쓰이며 **가상 거리 적분 속도를 바꾸지 않는다.**
3. 센서 연결은 MENU → 주행 설정 안에 숨어 있어, 시작 전 센서 확인 흐름이 없다.
4. RPM 이벤트가 stale이면 `null`이 되지만, 이를 단순히 슬라이더 fallback 조건으로 사용하면 페달을 멈춘 순간 가짜 속도로 다시 달릴 위험이 있다.
5. 상태보드의 “BLE 케이던스 ✅”는 프로토콜 수신 관점일 뿐, 사용자 관점의 “센서로 주행”은 아직 완료되지 않았다.

## 2. 이번 작업에서 확정하는 제품 규칙

### 2.1 입력 모드는 명시적으로 분리한다

```ts
type RideInputMode = "cadence" | "manual";
```

- `manual`: 기존 속도 슬라이더를 사용하는 **체험 입력(T0)**.
- `cadence`: BLE CSC 크랭크 RPM이 가상 속도를 결정하는 **센서 입력(T1)**.
- 센서 연결 성공 시 `cadence`로 전환한다.
- 센서가 끊기거나 RPM이 stale이어도 자동으로 `manual`로 돌아가지 않는다.
- `manual` 복귀는 사용자가 명시적으로 선택해야 한다.
- 연결이 끊긴 `cadence` 모드의 목표 속도는 `0`이다.

이 규칙은 “페달링 없이 계속 전진”하는 가장 위험한 실패를 막는다.

### 2.2 케이던스→가상 속도 MVP 모델

파워·저항·기어 정보가 없는 케이던스 센서이므로 현실 속도를 측정한다고 표현하지 않는다. 이번 단계에서는 고정 가상 기어를 사용한다.

```ts
CADENCE_DEADZONE_RPM = 8
CADENCE_TO_KMH = 0.32
CADENCE_SPEED_MAX_KMH = 30

rpm < 8        -> 0 km/h
otherwise      -> min(30, rpm * 0.32)
```

체감 기준:

| 케이던스 | 목표 가상 속도 |
|---------:|---------------:|
| 40 rpm | 12.8 km/h |
| 60 rpm | 19.2 km/h |
| 80 rpm | 25.6 km/h |
| 94 rpm 이상 | 30 km/h 상한 |

- 내부 계산은 소수값을 유지하고 UI에서만 반올림한다.
- 기존 `stepRideSpeedKmh` 램핑은 유지해 시작·정지가 순간이동하지 않게 한다.
- 이 수치는 튜닝 가능한 상수로 한 파일에 둔다. 컴포넌트에 흩뿌리지 않는다.
- 30km/h는 현행 T1 정복 인정 상한과 의도적으로 맞춘 초기값이다. 이것을 실제 도로 속도나 경쟁 기록으로 홍보하지 않는다.

### 2.3 RPM 상태의 의미를 분리한다

- `null`: 아직 유효한 크랭크 샘플을 한 번도 계산하지 못함 또는 센서 데이터가 유효하지 않음.
- `0`: 연결은 살아 있지만 페달링이 멈춤.
- `> 0`: 유효 케이던스.
- 연결 상태는 RPM 유무가 아니라 별도 연결 상태로 판정한다.

현재 stale 처리처럼 무조건 `null`만 쓰지 말고, 연결 중 정지 상태는 `0`으로 표현할 수 있게 한다. 마지막 유효 크랭크 변화 후 약 2.5초 동안 새 회전이 없으면 `0rpm`으로 전환한다. 전체 감속이 너무 느려지지 않도록 실제 센서에서 “페달 정지 → 화면 속도 0”이 7초 안에 끝나는지 확인한다.

### 2.4 Web Bluetooth 권한 규칙

- 최초 `requestDevice()`는 반드시 사용자 클릭에서 호출한다.
- 첨부 증거의 `file://` 페어링 권한은 RTW의 `localhost` 또는 배포 HTTPS 출처 권한을 대신하지 않는다. RTW에서 최초 1회 다시 선택하는 것이 정상이다.
- 장치 선택 필터는 표준 CSC를 우선하되, CSC UUID를 광고하지 않는 CYCPLUS 대응을 위해 아래 OR 필터를 사용한다.

```ts
filters: [
  { services: [CSC_SERVICE_UUID] },
  { namePrefix: "CYCPLUS" },
],
optionalServices: [CSC_SERVICE_UUID]
```

- `acceptAllDevices: true`를 기본 경로로 사용하지 않는다. 주변 모든 기기를 보여 주어 사용자가 잘못 고르기 쉽다.
- 선택 장치에 CSC 서비스 또는 크랭크 데이터가 없으면 “센서가 CSC 케이던스 모드인지 확인해 주세요”라는 제품 문구를 보여 준다.
- 자동 재연결·`navigator.bluetooth.getDevices()`는 이번 완료를 막는 필수 범위가 아니다. 물리 센서 수직 흐름이 통과한 뒤 별도 후속 작업으로 둔다.

참고:

- [Web Bluetooth specification](https://webbluetoothcg.github.io/web-bluetooth/)
- [Chrome Developers — Communicating with Bluetooth devices](https://developer.chrome.com/docs/capabilities/bluetooth)

## 3. 목표 사용자 흐름

### 3.1 주행 전

1. Guest 또는 등록 사용자가 입문 경로를 불러온다.
2. RouteDock에서 속도 입력 영역을 본다.
3. 기본은 `체험 속도`이며 근처에 `센서 연결` 액션이 직접 보인다.
4. `센서 연결`을 누르고 브라우저 선택기에서 `CYCPLUS C3 12695`를 고른다.
5. 성공하면 다음 상태가 보인다.
   - 장치명
   - `연결됨 · 페달을 돌려 확인하세요`
6. 페달을 돌리면 `NN rpm · 가상 NN km/h`로 바뀐다.
7. 이 상태에서 주행을 시작한다.

### 3.2 주행 중

1. 연결된 상태에서 페달을 돌리지 않으면 라이더는 움직이지 않는다.
2. 페달을 돌리면 RPM→목표 속도→기존 램핑→거리 적분 순서로 전진한다.
3. HUD 속도, 경로상 이동, 라이더 페달 애니메이션, presence publish가 같은 적용 속도를 기준으로 움직인다.
4. 페달을 멈추면 RPM 0 판정 후 감속해 멈춘다.
5. 연결이 끊기면 경고와 `다시 연결`을 표시하고 감속해 멈춘다.
6. 사용자가 `체험 속도로 전환`을 누르기 전에는 슬라이더로 자동 복귀하지 않는다.

### 3.3 종료 후

- 주행 종료가 센서 연결을 즉시 강제로 끊지 않게 한다. 같은 앱 세션에서 다음 경로를 바로 탈 수 있어야 한다.
- 명시적 연결 해제, 앱 unmount, 페이지 종료에서는 GATT와 notification listener를 정리한다.

## 4. 구현 구조

### 4.1 데이터 흐름

```text
CSC Measurement
  -> CSC packet parser
  -> crank delta / event-time delta
  -> smoothed crankRpm
  -> explicit RideInputMode
  -> cadenceRpmToVirtualSpeedKmh()
  -> rideTargetSpeedKmh
  -> useVirtualRideSession / stepRideSpeedKmh
  -> appliedSpeedKmh
  -> distance + HUD + map rider + presence + coaching
```

### 4.2 권장 파일 경계

새 파일명은 Claude가 코드 구조에 맞게 미세 조정할 수 있으나 책임은 아래처럼 분리한다.

| 파일 | 책임 |
|------|------|
| `apps/web/src/lib/bleCscCadence.ts` | CSC 상수·패킷 파싱·rollover·RPM 계산 같은 순수 로직 |
| `apps/web/src/lib/cadenceRideInput.ts` | 입력 모드 타입·RPM→가상 속도 상수와 순수 함수 |
| `apps/web/src/hooks/useBleCrankRpm.ts` | Web Bluetooth 권한·GATT·notification·disconnect·stale 생명주기 |
| `apps/web/src/App.tsx` | 입력 모드와 manual speed를 합쳐 `rideTargetSpeedKmh` 결정 |
| `apps/web/src/components/route-dock/RouteDock.tsx` | 주행 전 센서 연결/확인 UI를 사용자 본류에 노출 |
| `apps/web/src/components/route-dock/SessionSpeedControl.tsx` | manual 전용임을 명확히 하고 cadence 모드에서는 숨김 또는 비활성 |
| `apps/web/src/components/ride/RideSettingsPanel.tsx` | 상세 연결 상태·다시 연결·명시적 manual 전환 보조 UI |
| `apps/web/src/hooks/useVirtualRideSession.ts` | 목표 속도 수신과 적용 속도 적분. BLE 자체를 알지 않음 |

컴포넌트가 BLE 패킷을 해석하거나 훅이 RouteDock 문구를 소유하지 않게 한다.

### 4.3 속도 값의 역할을 혼동하지 않는다

현재 `App.tsx`의 `speedKmh`는 계획 속도·슬라이더·실제 이동 속도처럼 여러 의미로 사용된다. 이번에 아래 의미를 코드에서 분리한다.

```ts
manualSpeedKmh       // 사용자가 체험 모드에서 정한 값
rideTargetSpeedKmh   // 현재 입력 모드가 만든 목표값
appliedSpeedKmh      // 램핑 후 실제 거리 적분에 쓰는 값
```

- `RouteDock`의 예상 시간 계산은 기존 manual/planning 값을 유지해도 된다.
- 주행 중 HUD, live presence, Mapillary, 코칭처럼 “현재 실제 움직임”을 나타내는 소비자는 가능하면 `appliedSpeedKmh`를 사용한다.
- 모든 `speedKmh` 사용처를 무조건 일괄 치환하지 말고 의미를 확인한다.

## 5. 실행 순서

### 단계 A — 안전한 작업선

1. `git status --short --branch`로 `main2`가 깨끗한지 확인한다.
2. 별도 worktree 없이 `git switch -c feat/ble-cadence-drive`.
3. `AGENTS.md`, Ontology, Conquest §3.2, 상태보드 §3.1, `ride-verify` skill을 읽는다.
4. 기준 빌드와 ride selector 검증을 먼저 실행한다.

### 단계 B — 순수 로직 분리와 회귀 시험

1. CSC 파서·rollover·RPM 계산을 훅에서 순수 모듈로 분리한다.
2. cadence→speed 함수를 별도 모듈에 만든다.
3. 새 Node test를 만든다. 새 테스트 프레임워크는 추가하지 않는다.
4. 최소 시험 케이스:
   - crank-only 패킷
   - wheel+crank 패킷 오프셋
   - crank flag 없음
   - 짧은 패킷
   - revolution/event-time `uint16` rollover
   - 60rpm, 80rpm 계산
   - 0/NaN/비정상 고RPM 거부
   - deadzone과 30km/h cap
   - 연결된 정지 상태가 manual 속도로 fallback하지 않음

권장 스크립트: `npm -w boxcycle-web run test:sensor-cadence`.

### 단계 C — BLE 생명주기 수정

1. `sessionActive` 때문에 idle에서 끊기는 구조를 제거하거나 의미를 앱 생명주기로 바꾼다.
2. 주행 전 연결이 유지되고 주행 종료 후에도 같은 연결을 재사용하게 한다.
3. device/characteristic/disconnect listener의 중복 등록과 cleanup을 점검한다.
4. CYCPLUS 이름 필터 fallback과 CSC 서비스 오류 문구를 추가한다.
5. 최초 샘플 전 `null`, 유효 페달링 `>0`, 페달 정지 `0`을 구분한다.
6. 연결이 끊겼을 때 `error` 또는 `disconnected` 의미가 UI에서 분명해야 한다.

### 단계 D — 입력 모드와 실제 주행 연결

1. `manualSpeedKmh`, `rideInputMode`, `rideTargetSpeedKmh`를 분리한다.
2. cadence 모드에서는 `rpm ?? 0`을 속도 변환 함수에 넣는다.
3. 센서 연결 성공은 cadence 모드로 전환한다.
4. disconnect/stale은 목표 속도 0이며 manual로 자동 전환하지 않는다.
5. `useVirtualRideSession`에는 `rideTargetSpeedKmh`를 전달한다.
6. 주행 중 publish/HUD/coaching/Mapillary의 속도 의미를 감사하고 `appliedSpeedKmh`로 통일할 곳을 고친다.
7. 기존 Conquest `pedalSec`는 유효 RPM 기준을 유지하되 0rpm 시간은 증가시키지 않는다.

### 단계 E — 본류 UI

1. 센서 액션을 주행 설정에만 숨겨 두지 말고 RouteDock의 속도 입력 근처에 노출한다.
2. 상태를 최소한 다음처럼 구별한다.
   - 지원 안 됨
   - 센서 연결
   - 연결 중
   - 연결됨/페달 확인 대기
   - RPM 수신 중
   - 페달 정지
   - 연결 끊김/다시 연결
3. cadence 모드에서는 manual slider를 숨기거나 명시적으로 비활성화한다.
4. `체험 속도로 전환`은 명시적인 보조 액션으로 둔다.
5. 모바일 폭에서도 Go 버튼·경로 조작을 밀어내지 않는지 확인한다.
6. 제품 문구는 `RPM 센서`보다 `케이던스 센서`를 우선한다.

### 단계 F — 문서 동기화

물리 센서 검증까지 통과한 뒤에만 문서를 완료로 바꾼다.

1. [결정 로그](../../260707-RTW-결정-로그.md) 최상단에 `[Product] [Sensor]` 한 줄 추가:
   - 케이던스 센서가 가상 속도의 직접 입력이 됨
   - manual은 T0 체험 입력으로 남음
   - 센서 단절 시 자동 manual fallback 금지
2. [Conquest 설계 OQ-9](../../260703-Conquest-정복-레이어-설계.md)의 “도입 여부”를 채택 결정과 초기 매핑값으로 갱신한다.
3. [기능 상태보드](../../260707-RTW-기능-인벤토리-상태보드.md):
   - BLE 프로토콜 수신과 센서 직접 주행을 구분해 실제 상태를 표시한다.
   - 물리 센서 검증 전에는 ✅로 올리지 않는다.
4. 이 지시서 상태를 `코드 반영 완료(2026-08-27)` 또는 실제 완료일로 바꾼다.

## 6. 검증 게이트

### 6.1 자동 검증

아래를 모두 통과해야 한다.

```powershell
npm -w boxcycle-web run test:sensor-cadence
npm run lint
npm run build
node apps/web/scripts/ride-verify/verify-selectors.mjs
```

`RouteDock`, HUD 셀렉터, 주행 시작 흐름을 바꾸므로 `ride-verify` 계약이 깨지면 코드와 검증기를 함께 맞춘다. 검증기를 삭제하거나 약화하지 않는다.

### 6.2 물리 센서 검증 — CYCPLUS C3 필수

환경: PC Chrome 또는 Edge, RTW `localhost` 또는 HTTPS.

| 번호 | 절차 | PASS |
|------|------|------|
| P1 | RTW에서 `센서 연결` 클릭 | 브라우저 chooser가 사용자 클릭으로 열림 |
| P2 | `CYCPLUS C3 12695` 선택 | 장치명이 RTW UI에 표시되고 connected 상태 |
| P3 | 주행 전 페달 5회 이상 회전 | 2개 유효 샘플 이내 RPM 표시, 값이 계속 갱신 |
| P4 | 센서 모드로 입문 경로 주행 시작, 페달 정지 | 거리·라이더 위치가 증가하지 않음 |
| P5 | 40~80rpm로 페달링 | HUD 속도·거리·라이더 애니메이션이 함께 증가 |
| P6 | 페달 정지 | RPM 0 판정 후 7초 이내 적용 속도 0, 거리 증가 정지 |
| P7 | 다시 페달링 | 새 RPM으로 주행 재개 |
| P8 | 주행 중 센서 전원/연결 끊기 | 경고 표시·감속 정지, manual 속도로 자동 진행하지 않음 |
| P9 | `다시 연결` | chooser 또는 재연결 후 동일 세션에서 페달 주행 재개 |
| P10 | 일시정지→재개 | 일시정지 중 거리 고정, 재개 후 페달링할 때만 전진 |
| P11 | 주행 종료 후 다음 경로 준비 | 센서 연결이 불필요하게 즉시 해제되지 않음 |
| P12 | 명시적 `체험 속도로 전환` | manual slider가 다시 활성화되고 그때만 manual 주행 가능 |

물리 검증 로그에는 Mapbox/Firebase 토큰, BLE 주소 같은 민감 식별자를 남기지 않는다. 장치 표시명과 PASS/FAIL만 기록한다.

## 7. 수용 기준

다음이 모두 참이어야 완료다.

- [ ] RTW 출처에서 CYCPLUS C3를 사용자가 직접 선택할 수 있다.
- [ ] 주행 전에 연결 상태와 RPM을 확인할 수 있다.
- [ ] cadence 모드의 거리 적분은 센서 RPM이 만든 목표 속도로 동작한다.
- [ ] 페달을 돌리지 않으면 전진하지 않는다.
- [ ] 페달 정지와 연결 단절이 manual fallback을 일으키지 않는다.
- [ ] HUD·거리·라이더 애니메이션이 하나의 적용 속도와 모순되지 않는다.
- [ ] 기존 manual 체험 주행은 명시적 manual 모드에서 회귀 없이 작동한다.
- [ ] 기존 Conquest `pedalSec`와 T0/T1 구분이 깨지지 않는다.
- [ ] 자동 시험, lint, build, ride selector 검증이 통과한다.
- [ ] CYCPLUS C3 물리 검증 P1~P12가 통과한다.
- [ ] 결정 로그·Conquest OQ-9·상태보드가 코드 사실과 동기화된다.

## 8. 하지 말 것

- FTMS 스마트 트레이너, 파워, 심박, 저항 제어를 이번 작업에 넣지 않는다.
- 케이던스를 실제 파워나 현실 속도로 포장하지 않는다.
- 장치 ID나 BLE 주소를 Firestore에 저장하지 않는다.
- `acceptAllDevices`를 기본 chooser로 만들어 주변 모든 기기를 노출하지 않는다.
- 센서 stale/disconnect를 manual fallback 신호로 사용하지 않는다.
- 기존 속도 변수들을 의미 확인 없이 일괄 rename하지 않는다.
- 동행 sync 알고리즘, 라이더 GLB 형태, Conquest 서버 수치를 함께 리팩터링하지 않는다.
- 새 worktree를 만들지 않는다.
- 물리 센서 검증 없이 상태보드를 ✅로 올리지 않는다.
