## 최신 판정 요약

**Standard 낮·실제 3D 지형·라이더 추적을 유지하면서 최소 24FPS를 충족한 최종 해법은 아직 확보하지 못했다.** 여러 실험으로 성능 해법에서 제외할 조정과 추가 조사할 렌더링 경로를 구분했다.

- 지형 ON/OFF에서 가장 큰 성능 차이가 관찰됐다. 지형을 사용하는 렌더 경로가 핵심 조사 대상이다.
- 높이 배율 1.3/1.0/0.1, 300m 밖 표면 간소화, 배경 장식 생략에서는 목표에 유효한 개선이 확인되지 않았다.
- 최신 사용자 화면은 공식 고도 선 8개가 실제 적용된 Standard 낮·Mercator·지형 1배 ON 상태에서 6.8FPS다. **공식 고도 선 단독 해법은 최소 24FPS 기준 불합격**이다.
- 지형 기복에 따른 카메라 움직임과 저FPS의 동반 발생이 관찰됐다. 다만 카메라 계산·고도 조회·지도 표면 합성·최종 GPU 렌더링 중 어느 비용이 주된 병목인지는 미확정이다.
- 다음 단계는 설정값의 추가 미세 조정보다 프레임 비용의 계측과 원인 분리다. 이 계측은 아직 실행하지 않았다.

이번 갱신은 기존 실험 기록과 최신 사용자 검수의 정리다. 새 성능 시험·제품 코드 변경·커밋·푸시·배포는 수행하지 않았다. 운영 지형 기본 배율은 1배다.

목표는 Standard 낮·실제 지형·라이더 추적을 유지하면서 최소24FPS를 확보하는 것이다. 평균뿐 아니라 최저1초24FPS와 프레임 간격p95≤41.7ms를10초 표본의 기준으로 쓴다. 이 기준의 통과도 장시간 발열·실폰 성능 보장은 아니다. 아래 수치는 서로 다른 스타일·해상도·구간·기기 조건이 섞여 있으므로 행 사이를 정밀 A/B로 비교하지 않는다.

## 이번 후보: Mapbox 공식 고도 선

Chief가 승인한 전용 5218 비교다. 기존 동적 선의 layout에 `line-elevation-reference: ground`, `line-z-offset: 0.15`를 적용했다. 지면 위 15cm에서 SDK가 선을 그리는 공식 기능이다. 지형 표면 배치 경로와의 분리는 개발 브라우저에서 확인했으나, 최신 사용자 검수 6.8FPS로 최소 24FPS 단독 해법은 불합격이다. 캐시 재사용률과 정확한 전후 효과량은 현재 Standard 조건에서 미계측이다. [Mapbox 공식 설명](https://docs.mapbox.com/help/troubleshooting/layer-rendering-order/), [고도 속성 사양](https://docs.mapbox.com/style-spec/reference/layers/#line-elevation-reference).

대상은 내 이번주행/최근신규선, 활동pulse/heat선, 관전경로의 본선·glow(최대10개)다. 실제있는앱GeoJSON line만수정한다. 정적선택경로·내누적도로망·Standard내부도로·건물·가로수·라벨·라이더는대상외다. 데이터·색·선폭·glow paint·레이어순서를바꾸지않는다. 고도선자체의렌더차이로가림/외관이달라질수있으므로직접검수한다.

카메라/지형안전보정은그대로실행한다. 캐시강제보존·카메라정지·무효화차단·자체WebGL렌더러는사용하지않는다. 기본복귀는기존layout값을복원한다. Standard/day·Mercator·지형ON에서만적용하고지형OFF/다른스타일에서는해제한다. 새지도/레이어에는새기본값을저장한다. 적용거부/실패는복원하고측정을차단한다。

실제Standard는globe 투영설정으로시작했다. 공식고도선의지원조건을맞추기위해전용비교판은Standard/day에서 **기본/공식두모드모두Mercator** 로맞춘다. 다른스타일/맵으로전환시저장한투영을복원한다. 따라서이전globe기반시험수치와이번후보수치를직접효과량으로비교하지않고, 이번페이지의Mercator기본을새기준으로쓴다. 운영앱투영설정은미변경이다.

- 증거: `tmp/elevated-lines-on.json`, `tmp/elevated-lines-on.png`, `tmp/elevated-lines-restored.json`, `tmp/elevated-lines-tests.log`。

초기 브라우저 검증에서 globe 지원 조건 불일치와 공개 getLayer의 새 객체 반환 때문에 반복 속성 쓰기가 발생했다。수정 후 재검증했으며 실패 중 측정값을 성능 증거로 쓰지 않는다。레이어 재생성 식별을 위해 설치3.23.1의 style.getLayer 객체 정체성을 읽는다。설정 변경은 공개 setLayoutProperty/setProjection만 사용하고 렌더러・지형 캐시는 변경하지 않는다。

미실행/한계: 공식 선과 UI 수정은 ops JS에 한정돼 당시 제품 tsc/생산 재빌드/전체 map 시험을 반복하지 않았다. Ego 브라우저는 약 1Hz로 제한돼 10초 표본 0.9FPS는 성능 결론에서 제외한다. 최신 사용자 직접 화면 6.8FPS는 별도의 유효한 관측이다. 실폰·센서·발열·급커브/능선/고가/터널·장시간 시각 품질은 미검증이다. 정지 PNG 하나로 선 외관 동등성이나 지형 정지 결함 부재를 보증하지 않는다. 서로 중복되는 회귀 집합의 수를 전체 고유 시험 수로 합산하지 않는다. 미커밋·미배포.

## 남은 조사와 의사결정 기준

카메라가 움직이면 최종 화면은 달라져야 한다. 이것이 DEM·지형 메시·지도 표면 텍스처를 매번 모두 새로 생성해야 한다는 뜻은 아니다. 다음 비용을 분리해 현재 Standard 조건에서 측정하는 것이 우선이다.

| 측정 대상 | 확인할 내용 | 비용이 클 때 검토할 방향 |
|---|---|---|
| CPU 카메라·고도 조회 | 지면 샘플, 충돌 회피, 위치·각도 보정의 실행 시간 | 중복 조회 제거, 계산 재사용, 안전 조건을 유지한 보정 개선 |
| 지도 표면 재합성 | 지형에 입힐 도로·면·선 텍스처의 재그리기와 무효화 원인 | 정적·동적 표시 분리, 실제 캐시 무효화 원인 수정 |
| 최종 지형 렌더링·GPU | 현재 시점의 투영·가림·픽셀 처리 비용 | 실제 메시·표면 해상도나 렌더 구조 변경 검토 |

6.8FPS는 대략 프레임당 147ms, 24FPS는 41.7ms 이하다. 큰 비용을 제거해야 하는 상황이다. CPU와 GPU 작업은 겹칠 수 있어 각각의 시간을 단순 합산하지 않는다.

1. 동일 코스·속도·카메라·해상도에서 위 비용을 계측한다. 현재는 미실행이다.
2. 필요하면 같은 카메라 궤적에서 앱 추가 지형 오버레이 유무를 진단 비교한다. 표시를 뺀 FPS를 제품 FPS로 보고하지 않는다.
3. 확인된 큰 비용만 대상으로 다음 후보를 만든다. 더 단순한 지도 표면, 별도 지형 메시, 네이티브 이전은 검토 가능한 방향이지만 성능을 보장하지 않으며 제품·개발 범위 결정이 필요하다.
4. 후보가 회복되면 급커브·능선·하강·지형 결측·자동 평면 복귀 및 실폰 장시간 발열을 함께 검증한다.

실험 Firebase는 로컬 에뮬레이터에 연결하고 지도는 실제 Mapbox 서비스에서 받는 구조다. 운영 Firestore 트래픽 부재를 지도 렌더 비용 부재로 해석하지 않는다.
