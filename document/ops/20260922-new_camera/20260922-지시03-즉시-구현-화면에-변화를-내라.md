## §0 왜 이 지시가 나왔나

Chief 가 방금 앱을 열어 확인했다. **바뀐 것이 하나도 없다.**

> 「새로운 카메라 버튼이 생기지도 않았고 기존 카메라의 기능이나 UI 어떤 것도 변화가 없다」

감리가 `git status` 로 확인한 사실: `apps/web/src` **변경 0줄**. 화면의
카메라 칩은 `상공·북향·후방·전방·좌측·우측` 그대로, 거리 `40.0m` 그대로다.

**이것은 개발팀장만의 문제가 아니다.** 감리가 조사 단계와 승인 단계를 문서로만
연달아 돌려 두 라운드 동안 픽셀을 한 개도 못 움직였다. 그 책임은 감리에 있다.
그래서 **단계를 합친다.**

## §1 이번 보고에서 화면이 바뀌어 있어야 한다

지시01 의 STEP 2·3·4·5 를 **한 번에** 수행한다. 순서는 아래대로 하되,
**중간에 감리 승인을 기다리지 마라.** 이번 한 번은 끝까지 가서 그림으로 보고하라.

1. **명칭 정정** — 지시01 §2 확정안. `rear30→forward`(전방) · `front30→backward`(후방) ·
   `leftFlat→left` · `rightFlat→right`. MapViewSheet 칩 라벨도 구도와 일치시킨다
2. **거리 범위** — 상한 `RIDE_CAMERA_DISTANCE_MAX_AT_BASE_M` 40→60.
   하한은 숫자를 내리지 말고 밀착 4방향 pitch 를 **67°** 로 내려 5m 를 연다
   (`defaultM = maxM` 이라 기본 거리가 60 이 되는데, **기본값은 40 에 고정**하라 —
   기존 주행 첫 화면을 바꾸지 않기 위해서다. 이 한 줄은 감리가 지금 정한다)
3. **Quick Camera UI** — 주행 중에만 `MapHud` 의 Account 칩 **왼쪽**에 `1~6`.
   ride state 기준 렌더(CSS 숨김 금지). 폰 가로에서 겹침·잘림 없을 것
4. **1~6 동작** — 1번 Route Fit ↔ Aerial 60m 토글(`fitBounds` 는 클릭 순간 1회),
   2~5번은 정정된 모드 + 5m, 6번은 `baseHeading=0` 고정 forward 구도 + 5m

**줌 비간섭(원안 §10)은 이번 범위에서 제외한다** — 그것만 따로 마지막에 한다.
대신 지시02 §3 B1(사용자 역산 거리에는 floor 보호를 적용하지 않는다)의 **자리만**
주석으로 남겨라.

## §2 【증거 계약】 이것이 없으면 보고를 반려한다

수행결과 파일 §0 에 **반드시** 넣어라. 하나라도 빠지면 읽지 않고 `수행결과02` 를 요구한다.

| 증거 | 형식 |
|---|---|
| **코드가 실제로 바뀌었다** | `git diff --stat -- apps/web/src` 출력을 그대로 붙여라. 0줄이면 그 보고는 실패다 |
| **주행 중 화면** | Quick Camera `1~6` 이 Account 왼쪽에 보이는 캡처 1장 |
| **1~6 각각** | 6장. 라이더가 화면 안에 실제로 보이는지가 판정 기준이다 |
| **명칭 정정 전/후** | 같은 지점의 「전방」·「후방」 쌍 |
| **좌/우 실측** | 「좌측」·「우측」 캡처. 코드 판독(좌=좌)이 그림에서도 맞는가. 반대면 매핑 바꾸지 말고 반증 보고 |
| **pitch 80° vs 67°** | 같은 지점 비교 2장 — Chief 가 밀착감을 보고 판단한다 |
| **회귀** | `npm run lint` · `npm run typecheck` · e2e `u5-render-phase.spec.ts` 결과 |

캡처는 **폴더 경로를 통째로** 적어라(`.out` 은 gitignore 라 파일 링크가 안 열린다).

## §3 막히면 막혔다고 즉시 써라

끝까지 못 갔으면 **간 데까지의 코드 변경과 캡처를 그대로 내고**, 어디서 왜 막혔는지
써라. 부분 성공을 성공으로 포장하지 마라. **문서만 있고 코드 diff 가 없는 보고는
「작업하지 않은 것」과 같다** — 이번 라운드에서 실제로 그런 일이 있었다.

커밋·푸시는 여전히 금지. assert 완화·허용치 조정으로 통과시키지 마라.

## §4 【필수】 검증 예산 — 시간을 쓰는 방식도 지시 대상이다

Chief 지시(2026-09-23): 주행 검증이 길어지고 같은 수정을 반복하는 데 시간이 샌다.

### 4-1. 한 번의 주행 검증은 **5분 이내**

- 캡처에 필요한 만큼만 달린다. 1~6 을 **한 세션 안에서 연속으로 눌러** 6장을 얻어라 —
  버튼마다 주행을 새로 시작하지 마라
- 5분 안에 필요한 그림을 못 얻으면 **더 달리지 말고 멈춰라.** 무엇이 부족했는지 적고,
  짧은 경로·정지 상태·오프스크린 등 **다른 경로**로 같은 것을 보여라
- 주행 시간은 증거가 아니다. **필요한 그림이 증거다**

### 4-2. 같은 수정 **3회**면 접근을 바꾼다 (3-strike)

동일한 증상에 대해 같은 성격의 수정을 3회 시도했는데 그림이 안 바뀌면,
**4회째를 하지 마라.** 그 자리에서 멈추고 수행결과에 이렇게 적어라:

```
3-strike 발동: <증상>
  시도 1: <무엇을 바꿨나> → <그림이 어떻게 됐나>
  시도 2: …
  시도 3: …
  → 내 진단이 틀렸을 가능성: <무엇을 잘못 가정했나>
  → 다른 접근 후보 2개와 권고
```

감리가 진단을 다시 세운다. **같은 가정으로 네 번째를 시도하는 것이 가장 비싼 실패다.**

### 4-3. 대기·반복 금지

브라우저·Playwright 단계가 5분간 진전이 없으면 같은 시도를 반복하지 말고 즉시
중단해 프로세스·포트·로그를 확인하고 headless·단일 worker·기존 서버 재사용으로 전환한다
(CLAUDE.md 「자율 진행 및 질문 정책」). 전환 후에도 불가능할 때만 BLOCK 으로 보고한다
