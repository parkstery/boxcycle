## 판정

**기존 비용 절감은 효과가 있지만, 출시 규모에 대응한 구조는 아직 아니다.** 현재 read 문제는 (1) 개인의 누적 도로망 전체 재조회, (2) 매일 운영 데이터 전체를 훑는 게스트 정리, (3) 다인 위치 데이터의 다대다 전달로 나뉜다. 자동 시험의 운영 연결 가능성은 실제 결함이지만 오늘의 급증 전체를 자동 시험으로 귀속할 증거는 없다.

무료 5만을 넘었다는 사실과 서비스 원가가 감당 불가능하다는 결론은 별개다. 그러나 누적 데이터와 동시 라이더 수에 따라 비용이 커지는 구조는 지금 고쳐야 한다. 지난 11월의 총액 추정치를 현재 단가·사용 시나리오 대조 없이 재사용하지 않는다.

## 1. 운영에서 확인한 수치

프로젝트 `boxcycle-dc2df`, `(default)` DB, Standard/Native, 서울 `asia-northeast3`, freeTier=true를 관리 API로 확인했다.

`firestore.googleapis.com/document/read_count`를 60초 단위로 전 페이지 수집하고 **각 point의 endTime 직전 시각**으로 한국 날짜와 태평양 날짜를 각각 계산했다. 수집 2026-11-19 20:45 KST. 아래는 LOOKUP + QUERY + NOT_FOUND 합계인 **운영 지표**다. 실제 청구서 합계가 아니다.

| 한국 날짜/기간 | read 지표 | 해석 |
|---|---:|---|
| 10/20~11/6 | 평균 41,005/일, 범위 11,695~75,815 | 18일 중 4일이 지표상 5만 초과 |
| 11/7~11/18 | 평균 5,516/일, 범위 3,308~10,858 | 앞 기간 평균보다 약 86.5% 감소 |
| 11/17 | 3,308 | 낮은 사용일 |
| 11/18 | 10,858 | 기존 자문 수치 3,500~7,700 범위보다 큼 |
| 11/19 00:00~수집 시점 | 24,208 | QUERY 22,405, LOOKUP 1,341, NOT_FOUND 462 |

무료 할당량은 **태평양 자정**에 리셋된다. 현재 11월에는 한국 **17시**이며, 일광절약시간 적용 시에는 16시다. 같은 원시 지표를 해당 날짜로 나누면 PT 11/18은 26,712, PT 11/19 부분일은 2,785다. 한국 날짜 합계를 무료 할당량의 하루와 바로 비교하지 않는다.

사용량 대시보드/Monitoring은 청구와 다를 수 있다. 빈 쿼리 최소 1 read, 색인 집계 읽기 등은 지표에 그대로 드러나지 않을 수 있다. Rules 의존 읽기도 별도 원가 항목이다. 따라서 **지표 5만 미만 → 청구도 반드시 5만 미만**이라고 보장하지 않는다.

근거: [과금·무료 한도](https://firebase.google.com/docs/firestore/pricing), [지표와 청구의 차이](https://firebase.google.com/docs/firestore/monitor-usage). 원시 결과 `evidence/read-series.json.gz`(gzip 무손실 압축), `read-summary.json`, 날짜 재집계 `period-summary.json`, 공식 metric 설명 `metric-descriptors.json`.

기존 절감 배포와 감소 시점은 부합하지만 사용자 활동량도 달라졌다. 총량 감소 전체를 특정 배포의 인과 효과로 확정하지 않는다. 관련 서버 함수는 관리 API상 11/6 배포이며 현재 ACTIVE다.

## 2. 개인 도로망 — 현재 앱 진입 폭증의 가장 강한 코드상 원인

`apps/web/src/App.tsx:273`에서 `useConquest(user, configured)`를 항상 사용한다. `hooks/useConquest.ts:58~76`은 uid가 생기면 다음 두 조회를 실행하고, `totalMeters`가 바뀔 때 똑같이 실행한다.

- `lib/conquest/repo/firestoreConquest.ts:108`: `conquest/{uid}/chunks` 전체 getDocs.
- 같은 파일 `:213`: `conquest/{uid}/traces` 전체 getDocs.

두 조회 모두 limit·변경분 조건·지속 캐시·in-flight 공유가 이 저장소 경로에 없다. 초기 summary는 null이므로 totalMeters=0이다. 요약 구독에서 실제 누적 거리(0보다 큼)를 받으면 의존성이 바뀌어 전체 읽기를 다시 요청한다. cleanup의 cancelled 플래그는 결과 적용을 막지만 이미 요청한 조회를 취소하지 않는다. 새 도로를 얻어 서버 누적 거리가 바뀔 때에도 전체를 재조회한다.

| 운영 계정(식별정보 생략) | traces | chunks | 전체 1회 | rides | savedRoutes |
|---|---:|---:|---:|---:|---:|
| A: 가장 큰 계정 | 342 | 69 | **411** | 696 | 165 |
| B: 두 번째 | 98 | 29 | **127** | 247 | 29 |
| C | 18 | 11 | 29 | 185 | 15 |

코드상 첫 진입의 0→실제 값 변화는 **두 번 호출될 수 있는 근거**다. 하지만 SDK가 겹친 요청/캐시를 공유할 수 있어 **411×2=822가 매번 청구된다**고 확정하지 않는다. React StrictMode가 있는 개발 서버도 운영 빌드와 분리해서 측정해야 한다.

오늘 분 단위 spike는 14:58 695, 08:51 666, 16:49 653, 08:07 620, 19:07 604 등이다. 전체 도로망 411 + 최근 기록 최대 50 + 저장 경로 최대 50 + 공개 요약 약 39 및 기타 조회는 수백 read를 충분히 설명할 수 있는 **용량 모델**이다. 개별 분의 호출 경로·계정을 추적한 것은 아니므로 해당 합계를 실측 귀속으로 표시하지 않는다.

규모 문제: A와 같은 누적량의 사용자 100명이 한 번씩 전체를 받으면 해당 두 조회만 41,100 문서, 200명이면 82,200 문서다. 신규 Guest가 모두 같은 비용을 내는 것은 아니다. 읽기 비용이 운동 이력에 비례하므로 오래 쓰는 사용자가 더 비싸지는 것이 핵심이다.

대책 후보:

1. uid별 summary 준비 상태를 구분해 첫 전체 조회의 중복 요청부터 제거하고 in-flight 공유를 검토한다.
2. uid별 지속 캐시와 서버 변경 버전을 설계해 재방문은 변경분만 받는다. 계정 전환 격리, 삭제·수정 반영, 캐시 유실 시 복구가 필요하다.
3. 누적 도로망 전체를 보여 주는 기능은 보존하면서 공간/지도 범위별 로딩 또는 버전 있는 정적 산출물을 검토한다. 단순 limit으로 오래된 도로를 감추는 안은 해결책으로 채택하지 않는다.

1은 좁은 클라이언트 수정 후보, 2~3은 서버 데이터/지도 계약과 Chief 결정 필요성을 먼저 검토할 설계 과제다. 중복만 제거해도 전체 이력에 비례하는 근본 비용은 남는다.

## 3. 게스트 정리 — 약 3,300 read를 매일 만드는 확정 경로

`functions/src/guestLifecycleScheduled.ts`는 매일 KST 03:15에 실행된다. `guestLifecycleAdmin.ts:353`의 listProfileUids는 users·userPrivate·livePresence·conquest·rides·savedRoutes·routeAutoRouteCache·routeTokenLedger·nicknames·publicRouteRequests·routePublications와 members/livePublicationRides/chunks/traces/openTrailListings group을 전부 훑는다. `.select()`는 내려받는 필드를 줄일 뿐 문서별 read를 없애지 않는다. 등록 사용자 자료도 후보 발견을 위해 읽는다.

현재 해당 스캔 범위의 문서 합계는 **3,290개**다. 주행 1,245, 경로 계산 캐시 573, 궤적 487, 토큰 원장 393 등이 크다. 빈 조회 최소 비용·설정 1건·프로필 확인·재시도/실삭제는 별도다. count는 순차 수집한 현재치이며 새 공개 등록 등이 진행 중이어서 03:15 당시의 동일 스냅샷은 아니다.

운영 로그: **03:15:07 완료, scanned=13, registered 6명, fresh 7명, deleted=0, failed=0**. Monitoring의 03:16 분에는 **3,277 read**가 집중된다(로그/지표의 표본 시각 차이 포함). 코드·문서 수·시각이 일치해 이 급증의 주원인은 게스트 정리로 강하게 확인된다. 로그의 scanned는 후보 uid 수이며 읽은 문서 수가 아니다.

이 지출은 라이딩하지 않는 날에도 생긴다. 주행 기록 등이 10만 문서가 되면 매일 후보 발견 스캔 자체가 10만 read를 넘을 수 있다. 삭제 최대 20명 cap은 앞단 전체 스캔 비용의 상한이 아니다.

대책: 만료 예정 Guest를 별도 인덱스/작업 큐에서 기한·상태로 제한 조회하는 일상 경로와, 고아 데이터 복구를 위한 전체 감사 경로를 분리한다. 전체 감사에는 커서·회차 문서 예산·실행 주기를 둔다. **현재 고아 발견·삭제 재시도·최근 활동 재확인·등록 사용자 보호를 보존하는 설계가 전제**다. 정리 함수를 무작정 끄거나 고아 검사를 없애는 방식은 채택하지 않는다. 정책·데이터 모델 변경은 Chief 결정 대상이다.

원시 근거: `evidence/counts.json`, `evidence/sweep-logs.json`. Auth listUsers와 Firestore read는 서로 다른 서비스이므로 Auth 사용자 13명을 Firestore 13 read로 계산하지 않는다.

## 4. 자동 시험 — 운영 연결 위험 확정, 오늘 사용량 귀속은 미확정

`apps/web/playwright.config.ts`는 FIRESTORE_EMULATOR_HOST가 없으면 일반 `dev:localhost`를 실행하며, 일반 모드에서는 기존 서버 재사용도 허용한다. `lib/firebase/app.ts`는 **VITE_USE_EMULATOR=1일 때만** Auth/Firestore/RTDB를 에뮬레이터로 연결한다. 기본 `test:e2e`, `test:e2e:smoke` 등에 운영 연결을 거부하는 공통 장치가 없다.

반면 `test:e2e:ride`, camera 계열 등 다수 npm 명령은 Functions 에뮬레이터 래퍼를 사용하고, sensor-dock/정적 시안 등 일부 시험은 실앱을 마운트하지 않는다. **자동 시험 전체가 운영 DB를 사용한다는 설명은 틀리다.** 현재 `.env.emulator`의 projectId는 운영과 같은 문자열이나 emulator 플래그가 켜져 있다. 프로젝트명만으로 운영 연결 여부를 판정할 수도 없다.

오늘 01~08시 스파이크가 자동 시험이었다는 결론은 시간대 추정뿐이다. 운영 지표에는 브라우저/시험명/코드 경로 라벨이 없다. 현재 Auth에 남은 사용자 13명 중 오늘 생성된 계정은 0명이다. 이미 삭제된 계정의 이력까지 부정하는 자료는 아니지만 “오늘 시험마다 새 Guest 생성”을 뒷받침하지도 않는다.

대책: 일반 시험의 기본값은 독립 demo 프로젝트+에뮬레이터로 하고, 서비스별 연결 목적지를 검증한 뒤 시험을 시작한다. 기존 운영 dev 서버 재사용도 거부한다. 에뮬레이터 연결 실패 시 운영으로 되돌아가지 않아야 한다. Functions·Auth·Firestore·양 지역 RTDB·외부 HTTP 목적지까지 함께 확인한다. 운영 확인은 별도 명령/고정 시나리오/실행 예산을 둔다. 기존 운영 쓰기 시험을 이번 조사에서 실행하지 않았다.

| 계정 통계 | UserInfoSheet 열릴 때 최대 400 | A는 최대 400문서. recentSessionsTipId 변화에도 재요청 |
| Rules | guestLifecycle·Trail·publication 등 get/exists | 의존 문서 read 별도. 동일 요청의 동일 문서 반복 참조를 모두 별도 read로 곱하면 안 됨 |

공개 카탈로그는 전 사용자 공통 데이터이므로 배포/변경 버전 기반 CDN 캐시·번들 후보가 된다. 개인 도로망과 동일한 보안/캐시 정책을 적용하면 안 된다. 통계는 이미 있는 누적 요약을 활용하되 기간·지역 통계의 의미와 정확성을 먼저 맞춰야 한다.

기존 계측은 listener open/close, one-shot 호출 또는 docChanges 수 중심이며 일부는 DEV 전용이다. **이 값을 billable read와 같다고 보고 절감률을 계산하지 않는다.** 현재 빈틈인 Conquest 전체 조회·백필·서버 스캔에 반환 문서 수/실제 요청/캐시 적중 계측을 추가하는 것이 후속 검증 과제다.

## 6. 다인 주행 — 출시 전 별도 해결이 필요한 가장 큰 확장 위험

`firestoreTrailLivePublicationRides.ts:80`은 타인 위치 문서를 계속 구독한다. hub는 같은 viewer 내부 중복 구독을 합치고 자기 uid는 서버에서 제외하지만, 서로 다른 사람 사이의 전달은 남는다.

현행 `lib/ride/rideSyncPolicy.ts`: RTDB 정상 steady heartbeat **12초**, 비정상 **4초**. 정상 상태의 큰 속도 변화 쓰기는 최소 6초, 그 외 burst도 있으므로 300회/시간은 steady 가정이다. 옛 문서의 항상 4초/900회 모델을 현재 정상 동작의 실측치로 제시하지 않는다.

같은 Trail의 N명이 한 시간 동안 서로를 모두 구독한다고 가정하면 위치 문서 변경 전달만 **300×N×(N−1)** read다.

| 동시 라이더 | 정상 steady 12초 | RTDB 비정상 steady 4초 |
|---:|---:|---:|
| 2 | 600/시간 | 1,800/시간 |
| 10 | 27,000/시간 | 81,000/시간 |
| 20 | 114,000/시간 | 342,000/시간 |

이는 운영 청구 실측이 아닌 전원 상호 구독 가정의 비용 모델이다. 초기 조회·관전자·Rules·서버 집계·속도 변경·재연결을 제외했다. 구독 범위가 작으면 줄지만 현재 Trail 인원에 대한 읽기 상한으로 입증된 것은 없다. 세계 지도 Trail 8개 제한은 Trail마다 라이더 수를 제한하는 장치가 아니다.

대책 후보는 낮은 빈도의 공용 백업 스냅샷을 묶어 제공하거나, 수신 범위/백업 전달 계약을 바꾸는 것이다. **정상 RTDB 중 Firestore 백업을 단순 해제하는 안은 기존 복구 지연 우려가 있어 재채택하지 않는다.** 원본 표본시각·정지/완주·삭제/재합류·RTDB 단독 장애·수신자만 장애를 보존해야 한다. 서버 쓰기/호출 비용·문서 크기·hot document·장애 독립성까지 총원가로 비교한다. 동기화 구조 변경은 Chief 결정 대상이다.

## 7. 권고 순서와 다음 검증

1. **시험 격리 먼저**: 일반 시험에서 운영 서비스 요청 0을 목적지 검사/에뮬레이터 실패 시 중단으로 증명한다. 오늘 총량의 절감률은 아직 계산하지 않는다.

   → 2026-11-19 후속: 중계기(릴레이) 방식의 정량 비교·권고안·함정·결정 항목은 [10-multi-rider-relay-design.md](10-multi-rider-relay-design.md) 에 있다. 핵심은 **RTDB motion 채널은 이미 스타(중계) 구조**이고, 남은 n:n 은 Firestore 백업 컬렉션 구독이며, 백업을 「읽지 않는 쓰기」로 두고 관전자는 보드 1개만 구독하면 읽기가 n²에서 선형이 된다는 점이다.
