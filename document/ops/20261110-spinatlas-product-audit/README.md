## 진단할 질문

### A. 제품 방향과 사용자 가치

- 누구의 어떤 상황을 해결하는지, 핵심 타겟과 약속이 한 문장으로 분명한가?
- Ride = Claim과 Local First가 실제 첫 사용 흐름과 현재 기능 우선순위를 이끄는가, 아니면 기능 축적에 밀렸는가?
- 사용자가 왜 다시 타야 하는지 경험 안에서 설명되는가? 가설과 실제 사용자 증거를 구분한다.
- 무료 코어, 센서·체험 입력, 정복 보상, 순위·개척자 정의, 토큰/저장 한도에 제품 원칙과 미결정 충돌이 있는가?
- 제품이 아직 검증하지 않은 가정(시장·가격·유지율 등)을 코드 완성도로 대체해 평가하고 있지 않은가?

### B. 사용자 여정과 실제 경험

신규 사용자부터 반복 사용자까지 다음 흐름을 단계별로 추적한다: 첫 방문·로그인/Guest → 지역·Ready Ride 발견 → 센서 연결 또는 체험 → 경로 준비 → 시작·일시정지·재개 → 종료·기록·Claim → 다음 주행 → Trail 동행/계정/지역 통계.

각 단계에서 성공 조건, 실패·취소·재시도, 권한·네트워크·센서 단절, 저장 중 앱 종료, 잘못된/늦은 응답, 기존 사용자의 이어 달리기를 확인한다. “화면이 있다”와 “사용자가 실제 기기에서 완료했다”를 구분한다. 폰 가로·터치·BLE·화면 잠금·음성은 실기기 검증 여부를 별도 표시한다.

### C. 시스템 구조와 변경 안전성

- UI, 도메인 규칙, 저장소, Firebase Functions/Rules, 외부 지도·센서 경계가 이해되고 한 곳에서 바꿀 수 있는가?
- 핵심 불변조건(주행 기록, 거리·진행률, 이어 달리기, Claim, 순위, 동행 위치, Guest 삭제)이 웹·서버·규칙·문서 사이에서 일치하는가?
- 코드 크기·결합·중복은 실제 변경 위험이나 이해 비용으로 이어지는가? 파일이 크다는 사실만으로 분할을 권하지 않는다.
- 기존 시험이 사용자 계약을 보호하는가? 무엇이 단위/계약/에뮬레이터/E2E/수동 실기기 검증에만 남아 있는가?
- 의존성 업데이트, 데이터 호환성, 장애·재연결, 중복 이벤트, 부분 성공·재시도에서 위험이 있는가?

### D. 데이터·보안·비용·운영

- 계정·주행·위치·지역 데이터의 접근 경계, 보존·삭제·복구, Rules 및 서버 신뢰 경계가 명확한가?
- Firebase·Mapbox 등 외부 서비스에 대한 키·환경·비용 상한·호출량·비용 귀속이 관측 가능한가?
- 오류를 발견하고 원인을 추적하며 안전하게 복구할 수 있는가? 로그·경보·운영 점검·롤백·백업 복구의 실제 근거를 찾는다.
- 사용자 데이터 손실·중복·부분 장애·계정 삭제·지역 판정 실패가 사용자에게 어떻게 드러나고 운영자가 어떻게 확인하는가?
- 법률·개인정보 적합성은 코드만으로 판정하지 않는다. 필요한 정책·검토·결정이 보이지 않으면 미확인 질문으로 남긴다.

### E. 출시와 검증 준비

- 배포된 것, 로컬 검증만 된 것, 미완료·미결정인 것을 분리한다.
- 출시 전 완화값·테스트 계정·센서 전용 순위 등 되돌려야 할 설정, 데이터 마이그레이션과 롤백 계획이 빠짐없이 추적되는가?
- 실폰·실센서·인증 사용자·다른 네트워크·장애 복구·비용 검증 중 실제로 해 본 것과 남은 것이 무엇인가?
- 첫 주행 완료율, 72시간 내 재주행 등 제품 가설을 판별할 지표가 정의되고, 실제 사용자 데이터가 들어오는가?
- 출시 판정에서 누가 무엇을 승인해야 하는가? 필요한 Chief 결정과 외부(법무·스토어·결제 등) 검증은 코드 작업과 분리한다.

### F. 개발·문서·AI 협업 방식

- 요구→결정→지시→구현→독립 검수→배포→실사용 확인의 인계가 추적되는가?
- 문서의 단일 진실이 정해져 있고, HANDOFF·현황판·상태보드·옵시디언·코드가 실제와 일치하는가?
- 바이브코딩에서 반복 수정·되돌림·기능 누적이 발생하는 원인을 요구 불명확, 시각 검수, 공유 상태, 테스트 환경, 미결정 정책 중 어디서 찾을 수 있는가?
- 테스트·문서·스크립트·운영 절차가 제품 코드와 같은 속도로 갱신되는가?
- 현재 지침이 좋은 판단을 돕는가, 아니면 기록·승인 비용 때문에 개발을 막는가? 병목과 잘 작동하는 관행을 둘 다 기록한다.

## 증거와 결론 형식

발견마다 아래를 적는다.

`ID | 주제 | 관찰/근거(경로:줄 또는 명령·결과) | 사용자·사업·운영 영향 | 확신(확인/추정/미확인) | 우선도(지금/출시 전/나중) | 제안과 의존 결정`

- 한 주장을 코드 한 곳이나 문서 한 줄만 보고 일반화하지 않는다. 반대 증거·예외가 있으면 함께 적는다.
- 수치 점수로 건강도를 꾸며내지 않는다. 가능한 경우 사용자 영향, 발생 가능성, 탐지 가능성, 수정 비용을 설명하고 순서를 정한다.
- “없음” 대신 조사 범위와 못 본 부분을 적는다. 저장소에서 발견하지 못한 것은 서비스 전체에 없다고 단정하지 않는다.
- 총평은 `방향은 타당/불명확`, `핵심 경험은 구현/미검증`, `운영 준비는 충분/부분/불명확`처럼 근거와 함께 조건부로 쓴다. 한 단어 점수나 막연한 안심·경고는 금지한다.

## 단계와 실행 경계

### 1단계 — 기준 상태와 증거 수집

읽기 전용으로 현황·문서 충돌·dirty 상태를 기록한다. 기존의 안전한 정적 분석 및 관련 시험을 활용하되, 명령 실행이 생성물·운영 데이터·공유 서버에 영향을 줄 수 있으면 먼저 부작용을 확인한다. 아직 기준선 명령을 새로 늘리거나 전체 시험을 무조건 실행하지 않는다. 실행한 명령, 통과, 실패, 미실행 이유를 분리한다.

### 2단계 — 전체 진단과 개선안

산출물에 경영 요약(Chief가 읽는 1~2쪽), 사용자 여정·시스템 경계 요약, 증거 기반 발견 목록, 미결정/미검증 목록, 3단계 우선순위(당장 위험 제거 / 출시 전 검증 / 제품 관측 후 결정), 리팩터링 제안 순서와 예상 범위를 담는다.

리팩터링 후보마다 다음을 명시한다: 해결할 실제 문제, 바뀔 코드·문서 범위, 동작·데이터 계약 영향, 선행 특성화 검증, 완료 증거, 롤백 방법, Chief 결정 필요 여부. 위험한 구조·정책·데이터 변경은 코드 정리로 포장하지 않고 별도 결정으로 올린다.

**여기서 멈춰 Chief에게 진단과 실행 순서를 보여 준다.** 이 단계에서는 앱 동작·데이터·화면·공용 문서의 지속 계약을 바꾸지 않는다. 발견을 감추기 위해 정련 기준을 완화하지 않는다.

### 3단계 — 지시된 항목의 리팩터링

Chief가 선택·승인한 항목만 한 번에 하나씩 수행한다. 우선 사용자 동작을 고정할 검증을 확인하고, 없으면 검증을 먼저 제안한다. 구조 변경과 기능 변경을 분리한다. 변경 후 관련 시험·타입·빌드·의존성·문서 게이트를 필요한 범위로 실행하고 실제 결과를 보고한다. 시험을 통과시키기 위해 시험을 삭제·완화하지 않는다. 공유 작업 트리의 미커밋 변경은 건드리지 않는다.

아키텍처·Rules·데이터 형식·외부 API·비용·동기화·제품 의미가 영향을 받으면 구현 전에 Chief 결정으로 되돌린다. 커밋·푸시·배포는 별도 명시 지시가 있기 전엔 하지 않는다.
