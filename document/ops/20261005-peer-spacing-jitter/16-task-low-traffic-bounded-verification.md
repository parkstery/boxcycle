# 추가 지시 — 낮은 트래픽과 제한된 검증 시간

Codex Supervisor · 2026-10-05. Chief의 최신 요구를 우선한다. 구현·시험은 Cursor CLI가 담당한다.

## 목표와 범위

신호 주기를 짧게 하는 해법은 제외한다. 기존 트래픽 절감 설정을 보존하면서 두 창의 상대 위치/순서를 같은 시간축에서 표시하고 앞뒤 튐을 없애는 것이 목표다. 기존 600ms 안은 확정 요구가 아닌 후보다. 사용자는 특정 지연값이나 wire/Rules 변경을 아직 선택하지 않았다. 이번 단계는 기존 증거를 활용한 제한된 조사와 재생 비교 및 구체 실행안 작성이다. 제품 코드·송신 설정·Rules는 이번 지시에서 변경하지 않는다.

현재 README, 15 검수, 14 결과, peer-sync SKILL과 HARNESS를 읽고 시작한다. 이전 작업을 재조사하거나 전체 테스트를 반복하지 않는다. 다른 작업의 변경을 되돌리거나 커밋하지 않는다.

## 수행

1. `20261002-public-trail-traffic-followup`의 배포된 절감 기준과 현재 실제 코드를 대조한다. RTDB motion 200ms와 Firestore heartbeat 4초를 분리해 기록한다. 사진 당시 선택 채널은 미계측임을 유지한다. FS 1초→4초 절감을 되돌리거나 FS 구독/read/write를 추가하는 안은 제외한다.
2. 기존 two-view 모델을 재사용하여 현재 빈도 유지와 낮은 RTDB 빈도 후보(1초)를 비교한다. 같은 물리 입력, 비대칭 지연, 등속/가감속, stall, 근접 순서, 시계 오차 조건에서 공통 과거 시점과 예측 방식의 실제 한계를 비교한다. 미래 패킷을 미리 읽지 않는다. 1초 후보를 현행 adaptive peer-only 표시 실패만으로 제외하지 말고 self/peer 공통 시간축 모델로 평가한다. 필요하면 비교 하네스만 수정하며 새 제품 구현은 하지 않는다.
3. 각 후보의 메시지 수, 실제 직렬화 payload bytes(가능한 기존 encode), FS 작업 증분, 상대 간격 오차·순서 반대 비율·튐·자기 표시 지연을 표로 제시한다. bytes 추정과 측정을 구별한다. 기존 timestamp 재사용 가능성을 먼저 확인하고 optional 필드가 필요한 이유/최소 비용을 구체화한다. 임의의 오차 tolerance로 FAIL을 PASS로 바꾸지 않는다. 신호 공백 동안 정확한 현재 순서 보장이 불가능하면 이를 분명히 쓰고 공통 시각/불확실 표시로 어떻게 처리할지 제안한다.
4. 비용 증가를 최소화하는 권고안 하나와 구현 대상 파일, 필요한 Chief 결정, 실제 제품 경로의 합격 조건을 작성한다. 기존 수신 수정의 한계와 모델 증거를 분리한다. 브라우저 실주행이나 추가 비용 측정이 필수이면 다음 단계의 짧고 구체적인 측정 절차만 제안한다.

## 시간 제한

- 이번 단계는 오프라인 결정적 재생을 사용하며 브라우저 실주행을 시작하지 않는다. 가상 수십 초를 실제로 기다리지 않는다.
- 새 비교 명령은 각각 wall-clock 120초 상한으로 실행한다. 결과 없는 대기는 60초 이내 진단으로 전환하며 같은 실패 경로는 최대 한 번만 재시도한다. 재생은 바뀐 비교만 돌린다.
- 후속 브라우저 관측안은 정상 주행 30~60초, 전체 명령 180초 hard timeout, 단일 worker/headless/기존 서버 재사용을 원칙으로 한다. 근거 없이 몇 분 주행하며 기다리는 방법을 제안하지 않는다.
