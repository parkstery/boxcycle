# PLAN 두 창 표시 일치 — Chief 승인용

담당: Cursor CLI · 지시: [04](04-task-fix-and-two-view-plan.md) · 시각: 2026-10-05  
상태: **계획만** (이 단계에서 카메라/HUD/표시 정책 코드 변경 없음)

## 1. 문제 재구성 (코드 근거)

두 창(라이더 A·B)에서 「누가 앞인가」가 서로 다르게 보이거나 순서가 뒤집혀 보이는 현상은, **dual-stamp 도착축 결함(이번 TASK-02로 수정)** 과는 별층이다. stamp 복구 후에도 아래 구조적 비대칭은 남는다.

### 1.1 self = 즉시, peer = 과거 보간

| 역할 | 위치 결정 | 코드 |
|------|-----------|------|
| self | 로컬 `virtualDistanceMeters` → 경로 선상 점 **즉시** | `App.tsx` `liveForMap` → `getPointOnRouteByDistance` |
| peer | 수신 버퍼를 `now - delay` 시점으로 **보간** | `integrator.ts` `peerRenderTimeMs` / `stepPeerMotionEntity` · 지연 = max(160ms, gap×2.2) ≤ 3000ms (`peerSyncPolicy.ts`) |

실측 하한(기존): 편도 ~70ms + 적응 지연 ~0.25–0.44s → 20km/h에서 **약 1.4–2.4m** peer가 뒤로 보임([260927-RTW-동행-지연과-경쟁-판정](../20260927-peer-competition/260927-RTW-동행-지연과-경쟁-판정.md)).

### 1.2 두 창 재생으로 생기는 착시

오프라인 두 뷰 모델(동일 등속, RTT·시계만 다름):

```text
진실: A.dist = B.dist = v·t
창 A: self_A = v·t ,  peer_B = v·(t - D_A)     → A가 D_A·v 만큼 앞서 보임
창 B: self_B = v·t ,  peer_A = v·(t - D_B)     → B가 D_B·v 만큼 앞서 보임
```

- **거리 격차:** 각 창에서 「내가 앞」으로 보임(대칭 착시).
- **역순 구간:** `D_A ≠ D_B`(비대칭 RTT·지터·적응 지연)이면 창마다 앞뒤가 다름. **공통 지연 상수를 양쪽 UI에 넣어도**, 지연이 창마다 독립이면 순서 일치를 보장하지 못한다.
- **속도 반영 지연:** 상대가 속도를 바꿔도 peer 쪽은 버퍼+delay 뒤에야 보임. self는 즉시.

이것은 「현실의 망 지연」이지, stamp가 도착축이던 **큰 역행/텔레포트**와 혼동하면 안 된다. 후자는 TASK-02로 제거 대상이었고, 전자는 설계 선택이다.

### 1.3 카메라·geometry 동일성 (구분)

| 가설 | 판정 | 근거 |
|------|------|------|
| self/peer가 다른 좌표 변환을 쓴다 | **낮음** | 둘 다 `getPointOnRouteByDistance(routeGeometry, distM)` (`App.tsx` · `PeerMotionRegistry.buildRenderFeatures`) |
| publication geometry가 창마다 다르다 | **가능·별도** | 각 클라이언트가 로컬 `routeGeometry`를 씀. 토큰/허브 불일치 시 같은 distM도 lngLat이 어긋남 → 이름표·uid·**경로 거리(distM)** 로 비교할 것(색은 self/peer라 창마다 바뀜) |
| 카메라 framing이 순서를 뒤집는다 | **낮음(보조)** | Quick Camera는 self를 따라감(`rideCameraFraming`). 상대적 앞뒤 인식은 지도 위 마커/라이더 간격이 본진 |

비교 키: **uid · 이름표 · displayDistM/경로 거리**. 색상·카메라 각도만으로 판정하지 않는다.

## 2. 선택지

### 옵션 P — 공통 과거 시점 (권고)

양쪽(또는 peer가 있을 때 self 포함)을 **같은 재생 시각** `T = now - D_display` 로 그린다.

- peer: 이미 이 모델.
- self: 로컬 궤적 버퍼(또는 최근 dist 샘플)를 같은 D만큼 늦춰 표시.
- D_display: 고정(예 300ms) 또는 `max(localPeerDelay, minDelay)`.

| 항목 | 내용 |
|------|------|
| 장점 | 창 안에서 self–peer 상대 순서가 송신 Δt에 수렴. 예측 없음 → 튐 재발 위험 낮음. TASK-02와 정합 |
| 단점 | 화면 전체가 D만큼 「과거」。혼자 탈 때는 D=0 유지 가능 |
| 한계 | 창 A의 D_A와 창 B의 D_B가 다르면 **창 간** 절대 시각 일치는 안 됨. 순서 일치에는 서버 공통 시계+동일 D 정책 또는 사후 판정(문서 ①) 필요 |

### 옵션 Q — 현재 위치 예측

peer를 `now`에 가깝게 외삽(속도×미도착시간).

| 항목 | 내용 |
|------|------|
| 장점 | 나란히 느낌·뒤처짐 감소 |
| 단점 | 가속/감속·stall에서 오차→다시 튐. 지금 고친 smoothness와 충돌 위험 큼 |
| 한계 | 양방향 RTT가 다르면 예측해도 창 간 순서 보장 못 함 |

### 옵션 R — 현상 유지 + 승부만 분리

표시는 현행(self 즉시 / peer 과거). 경쟁 순위는 화면이 아니라 통과 시각 기록([260927] ①).

| 항목 | 내용 |
|------|------|
| 장점 | 구현 최소. 「뒤처짐=물리」 메시지와 일치 |
| 단점 | Chief가 제보한 **두 창 육안 역순**은 남음 |

## 3. 권고안

**옵션 P(공통 과거 시점)를 채택할 것을 권고한다.**  
근거: (1) 이미 peer 경로의 계약과 같고, (2) 예측(Q)은 회귀 비용이 크며, (3) R(현상 유지)은 육안 역순을 해소하지 못한다.  
다만 **창 간 절대 일치**까지 필요하면 P만으로는 부족하고, 서버 공통 시계+동일 D 또는 경쟁 판정 분리(R의 판정 부분)를 후속으로 묶는다.

현실 지연(~0.25s)과 stamp 역행 오류를 혼동하지 말 것. P의 목표는 「창 안 상대 순서의 안정」이지 「지연 0」이 아니다.

## 4. 구체 변경 범위 (승인 후 구현 시)

제품 코드는 **미적용**. 승인 시 예상 터치:

| 영역 | 파일(예상) | 변경 |
|------|------------|------|
| self 표시 지연 | `App.tsx` (`liveForMap`) 또는 MapView self rider 경로 | peer 존재 시 self dist를 D만큼 과거 샘플로 |
| self 궤적 버퍼 | 신규 소형 모듈 예: `peerMotion/selfDisplayClock.ts` 또는 `ride/` 쪽 링버퍼 | (t, distM) 수 초치 · Date.now 주입 가능하게 |
| 지연 예산 SoT | `peerSyncPolicy.ts` | `PEER_COVIEW_DELAY_MS` 또는 peer 적응 지연과 공유하는 getter |
| peer (변경 최소) | `integrator.ts` | 가능하면 그대로; D를 self와 맞출 때만 읽기 |
| HUD 거리/갭 | `peerHud.ts` / DEV `peerSyncDebug` | 표시 거리도 같은 시계 쓰는 지 명시 |
| 카메라 | `rideCameraFraming` 등 | self 지연 표시를 따라가도록(카메라만 현재 self를 보면 어긋남) |
| 제외 | RTDB/FS wire, Rules, 송신 주기, 색상 의미 | 변경하지 않음 |

## 5. 지연 예산

| 항목 | 제안 | 비고 |
|------|------|------|
| 목표 D_display | **300ms** (초기) | 편도~70 + 5Hz 한 간격 여유. 20km/h≈1.7m |
| 상한 | ≤ peer `PEER_INTERP_DELAY_MAX_MS`(3000)과 분리해 **≤500ms** 권장 | 나란히 느낌이 깨지기 전 |
| 적응 | peer `arrivalGap×2.2` 의 EMA를 읽어 self D를 따라가게 할지 / 고정 300ms 할지 — 승인 때 선택 | 고정이 검증·설명 단순 |
| 혼자 주행 | D=0 | 지도 반응성 유지 |

## 6. 서버 공통 시계

| 용도 | 방법 | 트래픽 |
|------|------|--------|
| 표시(P) | **클라이언트 로컬 now + 동일 D 정책**으로 충분(창 안 상대 순서). 서버 시계 필수 아님 | 증분 0 |
| 창 간 절대 시각·경쟁 | RTDB `t`는 송신 `Date.now()`라 ±수십 초 왜곡 가능. FS `serverTimestamp`는 서버축 | 표시용으로 FS를 늘리지 말 것(4s steady 유지) |
| 확보안(승인 시) | (a) 모션 패킷에 서버 수신 offset 1회 측정(RTT/2) 캐시 · (b) 경쟁만 Cloud Function 통과시각 | (a) 연결 시 1회성 · (b) 이벤트성 |

기기 시계 조작이 보상과 연결되면 표시(P)와 판정(서버)을 **반드시 분리**(문서 ①).

## 7. 네트워크 stall 한계

- peer stall > `PEER_INTERP_MAX_EXTRAP_MS`(1200ms) 이후 hold — self를 같은 D로 늦춰도 **상대가 멈추면 간격이 벌어져 보임**(진실).
- 한 방향만 stall이면 공통 D로도 순서 착시가 남음 → UI은 「신호 약함」정도만, 순서로 단정하지 않음.
- 15s liveness 소멸은 현행 유지(TASK-30C).

## 8. 트래픽 증분

| 방안 | 증분 |
|------|------|
| P (self 로컬 지연) | **0** (송신·구독 불변) |
| Q (더 짧은 간격/예측 보정 패킷) | 송신 주기 축소 시에만 증가 — **비권고** |
| 서버 시계 샘플 | 세션당 수 회 이하 |

## 9. 오프라인 전후 비교 (예측 vs 공통 과거)

동일 입력(200ms, RTT 140±sin, 20km/h)을 두 뷰로 재생하는 사고 실험:

| 지표 | 현행(self now / peer past) | P 공통 과거 D=300ms | Q 외삽 to now |
|------|---------------------------|---------------------|---------------|
| 창 안 \|self−peer\| 평균 | ~v·D_peer (1.5–2.5m) | ~0 (±지터) | ~0이나 가속 시 오차 |
| 창 안 순서 뒤집힘(등속) | D_A≠D_B일 때 가능 | 동일 D면 거의 없음 | 예측 오차 시 발생 |
| 화면 속도 폭(peer) | TASK-02 후 5–6.1 | 동일(peer 경로 유지) | stall/가속에서 악화 위험 |
| 창 간 「같은 순간 누가 앞」 | 불일치 | D 정책 공유 시에만 개선 | 불일치 잔존 |

수치 재현 하네스(미구현): 두 Registry+두 self 버퍼에 대칭/비대칭 RTT를 넣고 순서 불일치 프레임 수를 센다 → 승인 후 `scripts/peer-sync/two-view-order-harness.mjs` 후보.

## 10. 검증 완료 조건 (승인·구현 후)

1. 두 뷰 하네스: 등속·대칭 RTT에서 창 안 순서 불일치 프레임 = 0 (또는 ≪ 현행).
2. 비대칭 RTT(±50ms)에서도 창 안 상대 순서는 유지; 창 간 절대 일치는 별 게이트로 명시.
3. 기존 게이트 회귀: `peer-spacing-jitter-harness`, `replay --check`, smoothness/liveness, `rtdb-fs-fallback` 전체.
4. 가속/감속·stall 시 Q 대비 P가 속도 폭·역행에서 덜 나쁨을 그래프로 남김.
5. 혼자 주행 시 self 지연 0 (맵 반응 회귀 없음).
6. Chief 육안: 두 창에서 이름표·경로 거리 기준 앞뒤가 일치하는 느낌(색 무시).

## 11. Chief에 물을 것

1. 표시 정책: **P 공통 과거 / Q 예측 / R 현상유지(+판정 분리)** 중 선택.
2. P 선택 시 D_display 고정 300ms vs peer 적응 지연 추종.
3. 창 간 절대 일치·경쟁 보상이 필요한지(필요 시 서버 시계·판정 분리 범위 확대 → 별도 승인).
