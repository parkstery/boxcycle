# 지시 03 — 퍼블릭 신청 「원본 저장 경로와 일치하지 않습니다」 오거절 수정

- 담당: Developer(Cursor CLI) · 보고: `03-result-03.md` · 커밋·푸시·배포 **금지**
- 병행: 지시 04가 `apps/web` 을 동시에 고친다. **이 지시는 `functions/` 만** 수정한다.

## 원인 (Supervisor 확정)
`functions/src/autoReviewPublicRouteRequest.ts` §3c(~185–210): 신청 좌표로 **지금 규칙**의 지문을 계산한 뒤, `savedRoutes/{id}.routeFingerprint`(**저장된 값**)과 비교한다. 지문 규칙이 바뀌기 전(좌표열 전체 해시)에 저장된 경로는 저장값이 옛 규칙이라 **항상 불일치 → 거절**된다. 「새로고침 후 다시 시도」로는 절대 풀리지 않는다.
- 클라이언트 쪽 `findExistingSavedRouteByFingerprint`(`apps/web/src/lib/route/repo/firestoreSavedRoutes.ts`) 주석이 같은 함정을 이미 기록하고 「저장값을 믿지 말고 geometry 로 재계산」하는 방식으로 풀었다. 서버도 같은 원칙을 따른다.

## 요구
1. 저장 경로 대조를 **저장 경로 문서의 geometry 로 지금 규칙의 지문을 재계산**해서 비교하도록 바꾼다.
   - geometry: `geometryCoordsJson`(JSON 문자열) 우선, 없으면 옛 `geometry.coordinates`. profile: 문서 `profile`(`resolveRouteProfile`).
   - 재계산 지문 == 신청 지문 → 통과. 이때 저장 문서의 `routeFingerprint` 가 다르면 **새 값으로 백필**(admin update, `routeFingerprint` 필드 하나만).
   - geometry 를 읽을 수 없는 문서 → 저장값이 64자이고 일치하면 통과, 아니면 거절.
   - 재계산해도 다르면(정말 다른 경로) 거절 — 문구를 원인에 맞게: 「저장된 경로와 신청한 경로의 모양이 다릅니다. 내 경로에서 다시 선택해 신청하세요.」
2. 신청 자체의 지문(신청 좌표 vs 신청 `routeFingerprint`) 검사는 **그대로** 둔다.
3. 순수 판정 로직은 테스트 가능한 함수로 분리(예: `functions/src/savedRouteFingerprintMatch.ts`), Firestore 접근은 기존 파일에 남긴다.
4. `functions/` 안에서 **저장된 `routeFingerprint` 를 재계산 없이 비교하는 다른 곳**이 있는지 grep 해 결과에 목록으로 보고(수정은 하지 말 것).

## 테스트
- `functions/src/savedRouteFingerprintMatch.test.ts` 신설(node:test, 기존 `*.test.ts` 와 같은 방식) 후 `functions/package.json` 의 `test` 목록에 추가.
- 케이스: (a) 옛 규칙 저장값 + 같은 geometry → 통과·백필 필요 true (b) 새 규칙 저장값 일치 → 통과·백필 false (c) geometry 다름 → 거절 (d) geometry 없음 + 저장값 일치/불일치 → 통과/거절.
- **사보타주 확인**: 판정 함수를 「저장값 직접 비교」로 잠시 되돌리면 (a) 가 실패하는지 확인하고 원복 — 결과에 기록.
