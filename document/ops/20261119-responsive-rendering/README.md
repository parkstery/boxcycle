## 1. 현재 구조와 확인된 문제

### 1.1 800×360 고정 여부

앱 전체를800×360으로 고정하는 width/height 또는 그 크기로 축소하는 transform은 제품 소스에서 발견하지 못했다. `App.css:10`의 map-first 셸은100dvh, 지도 stage는absolute/inset0, 지도는100%×100%다. **전체 화면은 유동적이지만 그 위 HUD의 배치가 가로폰 중심**이다.

800×360은 주로 주석·시험 조건·`scripts/ui-800x360` 검수 화면 명칭으로 쓰인다. 실제800 리터럴 예외는 `lib/map/appIntroMapView.ts:13`의 유효하지 않은 화면 너비 fallback으로, 앱 전체 고정 폭이 아니다. 초기 줌에도800×360 기준이라는 주석이 있다. 각종360 각도값·800ms·font-weight800은 화면 고정과 무관하다.

### 1.3 세로·태블릿·폴더블

`RotateOverlay.css:17`은 **portrait AND width≤900px** 전체를 가리는 회전 안내를 띄운다. 실제 로컬 앱 DOM에서360×800,768×1024는display:flex,900×700은none을 확인했다. 주석은 스마트폰 전용이라고 하지만 CSS는768px 태블릿도 막는다.

`public/manifest.webmanifest`의orientation은landscape다. 설치형 앱에서 실제 강제 여부는브라우저별 확인이 필요하지만 세로 지원을 하려면 CSS 차단뿐 아니라 이 설정 정책도 검토해야 한다. 이번에는 바꾸지 않았다.

`index.html`에viewport-fit=cover, HUD/조작부/하단스택 등에safe-area-inset 적용은 있다. **safe-area 미지원 앱은 아니지만 모든 팝업·모달에 적용된 것도 아니다.** 모달 중에는100vw−고정여백만 쓰는 곳이 있다.

제품 코드에viewport-segment 관련CSS/JS/화면분할 검출은 발견하지 못했다. 일반900×700 단일 화면과중앙 힌지가 있는두 화면을 구별하지 못한다. safe-area는힌지 간격을 대신하지 않는다.

## 2. 레이아웃 설계 제안

### 2.1 원칙과 분류

지도전체배경, 기존색·글꼴·윤곽선·아이콘·버튼기능/순서·접기동작을유지한다. 화면전체를800×360 비율로축소하거나버튼/글자를일괄축소하는방식은사용하지않는안을제안한다.

기기명대신 **실제가용너비/높이·컨텐츠최소폭·분할영역**으로구분한다. 아래수치는설계시작후보이며새고정해상도가아니다.

- 좁은영역: 안전여백을뺀가용폭약600px 미만. 메뉴/RPM/계정과지표를줄분리한다.5개지표는같은순서로3+2줄을허용하는안. 현재한행고정39/81의예외라승인이필요하다.
- 낮은영역: 높이약420px 이하.800×360·844×390의현행밀도/배치를보존한다. 기존340px등의작은높이예외도회귀검증후정리한다.
- 여유있는영역: 가용폭600px 이상·높이560px 초과. 기존코너앵커를유지하되패널은최소/최대폭·최대높이를가져지도에남는공간을돌려준다.
-421~560px 높이같은중간조건도기본규칙을가지며누락된분기로남기지않는다. 좁음/낮음은서로배타적인기기분류가아니라독립제약이다.

화면영역의소유자를정한다: 상단메뉴/RPM/계정·지표, 왼쪽인터벌/보조패널, 오른쪽2×4조작부, 하단표고/저작권/시계, 중앙지도. **예약영역은서로공유하고패널이숨었다고매순간위치가튀지않게한다.** 카메라도같은예약영역에서가려지지않는지도영역을기준으로프레이밍한다.

전체배치는media query, 각패널내부의열/행은할당된컨테이너폭에따라container query를점진적으로적용하는안을제안한다. 폴백은기본flex/grid. containment는크기계산에영향을주므로상단영역/패널의명확한wrapper부터적용하고,지도canvas와height:auto 패널전체에무작정size containment를걸지않는다. [MDN container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/container-type)

### 2.3 safe-area·폴더블·키보드

공통안전영역계산으로노치/제스처막대/저작권공간을예약한다. 팝업·메뉴·모달도같은가용영역안에서최대크기를정하고내부스크롤을허용한다. 키보드가뜬동안입력과닫기버튼이보이도록visualViewport를활용하되주행상태·경로·3D설정은재시작하지않는다.

Viewport Segments 기능이지원되는경우만힌지/분할영역을검출하고그영역을피한다. 지원하지않으면단일화면반응형으로폴백한다. 이기능은브라우저지원이제한적이므로필수실행조건으로만들지않는다. 힌지가있는양쪽화면에서는주지도하나를연속된주영역에두고기존보조패널을다른영역에배치하는안을검토한다. 두번째WebGL지도를추가하지않으며,이분할안자체는추가디자인승인대상이다. [MDN viewport segments](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/horizontal-viewport-segments)

## 3. maxdpr 적용 구조와 개선 제안

### 3.1 현행과 실제 버퍼

`src/lib/map/rtwMapConfig.ts`의 현재 기본상한은1.5(11-22 코드 대조), 쿼리maxdpr는1~4 범위,페이지당1회읽는다. `MapView.tsx:1014`에서Mapbox생성전에window.devicePixelRatio접근자를min(실제DPR,상한)으로감싼다. 설치실패시기존DPR로진행한다. 공식Mapbox DPR setter를사용하는구조는아니며,설치된mapbox-gl3.23.1에는그setter가없다.

지도캔버스CSS크기가W×H라면요청백버퍼는대략(W×r)×(H×r)이며정수반올림/구현제한이있다. 최종값은canvas.width/height와GL drawingBufferWidth/Height로확인해야한다. 라이더three.js도같은캔버스/컨텍스트를공유한다. DOM계기판글자의CSS크기를낮추는설정은아니다. 다만지도내지명·선·라이더는선명도변화가있다.

초기 비교 당시 실측: CSS800×360·PC에서원래DPR3 지정시DPR2→1600×720,1.5→1200×540,1→800×360으로실제GL버퍼가바뀌었다. 이는스마트폰성능실측과구분한다. [선행조사](../20261119-mobile-3d-investigation/README.md)

| 전체지도CSS크기 | DPR1.5 픽셀수 | DPR2 픽셀수 |
|---|---:|---:|
|360×800 / 800×360|648,000|1,152,000|
|844×390|740,610|1,316,640|
|768×1024 / 1024×768|1,769,472|3,145,728|
|900×700|1,417,500|2,520,000|

같은 DPR 2에서도 1024×768은 800×360보다 약 2.73배 많은 픽셀을 그린다. 2→1.5는 픽셀 수 43.75% 감소, 2→1은 75% 감소다. CPU 계산이나 총 처리 시간도 같은 비율로 줄어든다는 뜻은 아니다. [MDN smaller back buffer](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

### 3.3 성능판정·상하향 안정화

UI분류와품질등급을분리한다. UA/화면너비/메모리용량/GPU명은참고정보이며품질결정의충분조건이아니다. 기본목표는지속가능한30fps로제안하되,이번조사가실제렌더루프를30fps로바꾸는작업은아니다. 추후30/60fps제품목표를먼저확정한다.

기존perflab의실제지도렌더간격·CPU시간·지원시GPU시간을활용하고,연속측정은가벼운별도운영정책으로분리한다. perflab전체패널/상세프로파일링을상시켤필요는없다.

- 프레임p50/p95,50ms초과비율,Mapbox실제render횟수,지도CPU,라이더CPU,지원시GPU시간을같이기록한다. rAF콜백횟수만으로실제지도렌더fps라고간주하지않는다.
- 초기타일/GLB로딩,스타일전환,화면회전/리사이즈,탭백그라운드,키보드/입력,일시정지/장면정지는등급판정에서구분/제외한다. API/타일지연으로자동2D가된것을GPU저하로오판하지않는다.
- **튜닝시작예시**: 정상주행에서5초창3회연속p95>45ms 또는50ms초과프레임>10%이면한단계하향. 한번변경후최소30초유지. 순간프레임하나로변경하지않는다.
- 상향은60초이상안정(p95약36ms이내)에더해CPU/GPU렌더시간여유가있을때만1단계시도. 시험상향10초내악화하면복귀하고일정시간재시도금지.30fps안정만으로60fps급여유가있다고판정하지않는다.
- GPU timer 미지원이면원시GPU시간을만들지않는다. CPU와실제표시지연을보고보수적으로하향하며,자동2.0승급은보류하거나별도제한시험으로확인한다. CPU병목인데DPR만계속내리는루프는중단한다.
- 열을직접측정할수없는브라우저에서는온도값을추정해표시하지않고10~20분지속성능추세로검증한다. Context Loss는발생시각/복구이벤트를기록하되원인이반드시메모리라고단정하지않는다.

위 임계값은 채택된 규격이 아니라 실기기에서 조정할 설계 후보다. GPU 타이머는 확장 지원을 확인하고 disjoint 결과를 제외해야 한다. [Khronos GPU timer](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/)

### 3.4 구현 시 제약

현행 maxdpr는 쿼리를 캐시하므로 URL 업데이트만으로 실행 중 화질은 바뀌지 않는다. 구현한다면 수동 쿼리 상한과 적응형 정책을 분리하고, 한 곳에서 실행 중 상한을 갱신한 뒤 map.resize() 경로로 버퍼를 다시 할당하는 구조를 검증한다. private painter나 canvas.width만 직접 바꾸는 방식은 피한다.

전역 DPR shim은 페이지 전체 JS의 관측값을 바꾸는 부작용이 있다. 이 제약을 함께 검증하고 여러 곳에서 독립적으로 DPR을 덮어쓰지 않는다. 지도 재생성보다 같은 인스턴스와 GL 컨텍스트를 유지해 라이더·경로·카메라·센서 연결을 보존하는 방향을 우선한다.

지형 health에 따른 자동 2D와 품질 정책은 별개다. 화질 조정이 사용자 3D 선택을 임의로 끄거나, 수동 OFF를 성능 회복 시 다시 켜서는 안 된다. 백그라운드에서는 품질 판단을 멈추고 복귀·화면 확장 후 다시 안정 구간을 관측한다. [MDN background behavior](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)
