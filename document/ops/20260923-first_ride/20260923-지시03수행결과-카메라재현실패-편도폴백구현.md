### A-3. 배제된 가설 목록 (다음 사람이 다시 파지 않도록)

이번 라운드에서 **직접 계측·재현을 시도해 반증한** 것들이다. "가능성이 낮다"가 아니라 "이 조건
아래서는 증상이 재현되지 않았다"는 뜻이다.

1. **역지오코딩 응답 지연(1.5s)만으로 인한 경합** — C1~C4 정상 완주. 반증.
2. **`getCurrentPosition` 콜백 자체의 지연(2.5s, 권한 프롬프트 체감 지연 흉내)** — 반증.
3. **권한 프롬프트가 `document.visibilityState` 를 hidden 으로 바꾸고, 그 동안 rAF 가 멈춰 `flyTo`
   가 중간에 끊긴다** — `visibilitychange` 이벤트를 강제로 흉내 냈으나 반증. (단, 이건 **이벤트만
   흉내 낸 것**이다 — 실제 브라우저가 백그라운드 탭에서 rAF 콜백을 몇 프레임이나 건너뛰는지, 혹은
   Mapbox 내부 애니메이션 루프가 그 상황에서 어떻게 반응하는지는 headless Chromium 으로 정확히
   재현할 수 없었다. 완전히 배제된 것은 아니다 — §A-3-부기 참고)
4. **`prefers-reduced-motion` → `flyTo({ duration: 0 })` 경로의 잠복 버그(0-duration 애니메이션이
   조용히 무시된다는 가설)** — `reducedMotion: "reduce"` 컨텍스트로 재현했으나 반증. `duration: 0`
   이어도 `moveend` 가 정상 발화하고 center 가 target 과 일치했다.
5. **`localFirstFramedAtRef` 가드에 의한 억제** — 코드를 다시 읽어 확인: `applyLocalFirstRegion` 은
   `setLocalFirstRegion` 호출 *전에* `localFirstFramedAtRef.current = region.at` 를 먼저 쓰기 때문에,
   재개 복원 effect(App.tsx:2014-2027)가 나중에 같은 렌더에서 실행돼도 가드가 이미 일치해 스킵된다
   (중복 디스패치가 아니라 **정상 설계**임을 코드 검토로 확인). 재현 시나리오에 따로 넣지 않았다 —
   구조상 이 라운드의 클릭 경로(`onConfirmRegion` → `applyLocalFirstRegion` 단독 호출)에서는 애초에
   관여하지 않는다.
6. **`mapLoaded` 가 클릭 시점에 아직 false 였다가 늦게 true 로 바뀌는 경합** — 모든 재현에서
   클릭 이전에 이미 `mapLoaded: true` 로 3회 로그가 찍혀 있었다(맵이 카드보다 먼저 뜬다). 이 경합이
   실제로 열릴 조건(카드는 보이는데 맵이 아직 로드 전) 자체를 만들지 못해 시험하지 못했다 — **미확인**
   으로 남긴다(배제가 아니다).
7. **다른 카메라 주체(팔로우·QuickCamera·NextRide 앵커)가 `followMode` 를 가로챔** — 코드 검토로
   `tickRideCameraFollow` 가 `followMode === "free"` 일 때 즉시 return 함을 확인(`rideCameraFollow.ts:240`).
   `applyLocalFirstRegion` 이 `setFollowMode("free")` 를 먼저 호출하므로 구조적으로 막힌다 — 코드
   경로 검토로 배제(재현 시나리오에 넣지 않음).

### A-3-부기. 완전히 배제하지 못한 것 (다음 시도 우선순위)

- **모바일 실기(iOS Safari / Android Chrome)의 네이티브 권한 다이얼로그가 만드는 진짜 백그라운드
  전환과, 그 동안 Mapbox GL 내부 `requestAnimationFrame` 루프가 몇 프레임이나 씹히는지**는 desktop
  headless Chromium 으로 근본적으로 재현할 수 없다. `essential: true` 옵션이 reduced-motion 취소는
  막지만 탭 백그라운드 자체의 rAF 스로틀링까지 막아 주는지는 Mapbox GL 문서로도 확정하지 못했다.
- **최초 1회 권한 부여 시 브라우저별 "새로고침 없이는 좌표가 안 잡히는" quirk**(일부 구형 브라우저
  구현에 보고된 적 있는 종류) — Playwright 의 `grantPermissions` 는 API 로 권한을 즉시 부여하므로 이
  "최초 부여" 경로 자체를 재현하지 못한다(실제 권한 프롬프트 UI 를 거치지 않는다).

     Mapbox 내부에서 애니메이션이 취소됨(§A-3-부기 rAF 가설과 일치할 가능성).
   - `movestart` 는 찍히는데 `moveend` 가 없다 → 애니메이션이 중간에 끊김(가장 유력한 다음 단서).

   문제**(예: 탭이 백그라운드라 화면 자체가 갱신 안 됨)일 가능성이 커진다 — 이 경우 화면 녹화가 더
   유용하다.

## B. 폐합 실패가 막다른 골목이다 — 편도 폴백 구현 (지시02 §2 E4 정정 반영)

### B-1. 한 줄

`searchReadyLoopRoute` 가 실패(`no_loop`)하면, 그 실패 중 **가장 오차가 작았던 후보의 시작 방위**로
기존 `searchDistanceAutoRoute` 를 1회 더 호출해 편도 대안을 만든다(§B3 — 새 알고리즘 금지, 재사용만).
`closed: boolean` 플래그로 순환/편도를 구분해 클라이언트에 넘기고, 카드는 두 경우 다 **같은 버튼
셋**(경로가 이미 있으면 「다른 경로」 1개, 없으면 「Ready Ride 시작」·「다른 경로」·「다시 고르기」)을
보여준다. 편도조차 못 만들면(`no_road`/`budget_exceeded`, 후보 자체가 없었을 때) 그때만 기존 실패
문구를 쓴다.

### B-7. 명세와 달라진 점 — 카드 UI 구조 변경(구조적 발견, 이견 아님)

§B3 의 목업은 「Ready Ride 시작」·「다른 경로」·「다시 고르기」 3버튼을 **성공/편도 상태 둘 다** 보여
준다. 그런데 Ready Ride 생성이 성공하는 순간 `onApplyRoute` 가 실제 Route 를 적용하고, 그 순간
`stage` 가 `idle` → `ready-to-start` 로 바뀌어 **`LocalFirstEntryCard` 자체가 통째로 사라진다**
(`firstRideIntroVisible` 가 `stage === "idle"` 을 요구하기 때문 — 지시02 캡처 09-go-gate.png 가 이미
이 상태를 보여준다: 카드 없이 RouteDock 의 Go 버튼만 남는다). 목업이 요구하는 "경로가 이미 그려진
채로 카드가 3버튼과 함께 남아 있는 화면"은 **기존 구조에서는 존재할 수 없었다.**

**대응**: `App.tsx` 에 `readyRideGeneratedActive`(`stage === "ready-to-start" && localFirstRegion &&
readyRide.lastResult`) 를 추가해 이 경우에도 카드를 유지하되, 좌하단 스택(`MapBottomLeftStack` —
RouteDock 과 카드가 이미 같은 스택을 공유하도록 설계돼 있었다, 2026-09-16 주석 참고)에 RouteDock 과
나란히 쌓았다. 다만 이 상태에서는 **3버튼이 아니라 「다른 경로」 1개만** 남긴다 — 「Ready Ride 시작」
은 이미 아래 RouteDock 의 실제 「주행 시작」과, 「다시 고르기」는 RouteDock 의 경로 지우기와 각각
의미가 겹쳐 동시에 두면 사용자가 어느 쪽을 눌러야 하는지 헷갈리고 회귀 위험(경로 지우기 두 경로가
서로 다른 정리 작업을 하면 상태 불일치)이 생긴다고 판단했다. 핵심 요구(§B2 "결과 없이 되묻지 않는다"
· "다른 경로를 선택할 기회를 동시에 준다" · "사실을 말해 준다")는 그대로 충족한다.

이 판단은 **근거 있는 이견**으로 분류한다 — 승인 전 3버튼 그대로 재구현이 필요하면 알려 달라
(RouteDock 쪽에 별도로 배선해야 한다).
