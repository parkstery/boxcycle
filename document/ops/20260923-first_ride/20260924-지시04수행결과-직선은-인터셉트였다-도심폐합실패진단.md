## §2 진짜 증상 — 도심 폐합(closeLoop) 성공률 진단

### 방법

Cloud Function 엔드포인트는 실패 시 진단 필드(방위별 오차·자기중복 등)를 클라이언트에 내려주지
않고, `firebase functions:log` 는 gen2 함수의 최근 로그를 사실상 조회하지 못했다(재현: `-n 500`
줘도 12시간 이상 지난 로그 2~15줄만 반환, 최신 호출 로그가 잡히지 않음 — **알려진 제약으로 기록만
남긴다**, 별도 라운드 필요 시 Cloud Logging API 직접 조회로 전환 권고). 그래서 **실제 컴파일된
`functions/lib/distanceAutoRouteCore.js`(빌드 산출물, synthetic 아님)의 `searchReadyLoopRoute`를
그대로 로컬에서 호출하되, Directions 요청은 실 Mapbox API 를 직접 때렸다** — 오케스트레이션 코드는
100% 실물, provider 호출도 100% 실물이며, 우회한 것은 Cloud Functions 의 HTTP 레이어(인증·캐시·
토큰) 뿐이다. **엔드투엔드 검증은 §0-4 의 실 백엔드 직접 호출로 별도로 확인**했다(그건 진짜
Cloud Function 을 거쳤다).

### 원인 — 수치로

- 모든 실패 사유가 `no_loop` 이고, `selfOverlapRatio`(왕복 자기중복 판정)는 대부분
  0~9.6%로 기각 기준(60%)에 한참 못 미친다 — **자기중복이 원인이 아니다.**
- 실패 케이스의 `errorRatio`(거리 오차 비율)는 **0.20~1.00** 분포로, 허용 기준
  `MAX_DISTANCE_ERROR_RATIO = 0.2` 를 거의 항상 초과한다.
- `READY_LOOP_BEARING_SAMPLES_DEG = [0, 72, 144, 216, 288]` 는 **지리·도로망과 무관하게 고정된
  5개 방위**다. 삼각 폐합 다리 반경(`R ≈ 0.258·D`, 목표 3km 면 다리 반경 ~774m)을 직선거리로
  역산해 두지만, 실제 도로는 격자·일방통행·곡률 때문에 이 반경에서 크게 벗어난 실거리가 나온다 —
  좁은 도심 격자에서는 5개 표본 중 어느 것도 ±20% 안에 들어오지 못하는 일이 흔하다(위 데이터에서
  errorRatio 0.2~1.0, 즉 목표보다 20~100% 벗어남).
- **결론(한 줄)**: 폐합 실패의 지배적 원인은 **고정 5방위 표본 + ±20% 거리오차 허용치**의 조합이
  도심 도로망의 실제 거리 분산을 따라가지 못하기 때문이다. selfOverlap·예산 소진은 부차적이다.

**⚠ 이 라운드에서 고치지 않았다** — 정정 지시 §3 이 "고치는 것은 이번 라운드 범위가 아니다"라고
명시했다. 개선 후보(참고용, 결정은 감리 다음 라운드):
1. 거리 오차 허용치를 방위 표본 수·지역 밀도에 따라 완화(예: 도심에서 ±20% → ±30%),
2. 고정 5방위 대신 클릭 기반처럼 반경을 이분탐색(regula falsi)으로 조정,
3. 방위 표본 수를 늘려(예산 안에서) 명중 확률을 높임.

## §3 STEP 2 — 불변식(V1~V3) 구현 (그대로 유지)

`functions/src/distanceAutoRouteCore.ts` 에 `validateRouteGeometryPlausibility()` 를 추가하고,
`searchDistanceAutoRoute`(클릭 기반 + closeLoop 편도 폴백 공용)의 모든 최종 반환 지점과
`searchReadyLoopRoute`(폐합)의 `eligible` 후보 필터에 배선했다. 두 함수가 클릭 기반·Ready Ride
폐합·Ready Ride 편도 폴백 **세 경로 전부**의 공통 반환 지점이므로, **한 곳에 넣는 것으로 세 경로
전부가 같은 검사를 받는다**(지시서 "기존 클릭 기반 경로에도 같은 검사를 적용하라" 충족).

### 기준값과 실측 근거

실 Mapbox Directions cycling 응답 7건(`​.out/jisi04/stats-real-routes.mjs` — 도심 밀집 4곳 + 교외
간선도로 1곳 + 강변 자전거도로 1곳 + 여의도 폐합형 1곳)을 재서 정했다.

| 검사 | 기준값 | 실측 분포 | 근거 |
|---|---|---|---|
| **V1** 점 밀도 | `points/km < 5` → 거부 | 실측 22.37 ~ 40.72 | 최솟값(22.37)의 **4배 이상 여유**. 교외 저밀도 도로 대비 |
| **V2** 최장 구간 비율 | `최장 구간 / 전체 길이 > 0.35` → 거부 | 실측 0.029 ~ 0.0997(교외 김포 간선도로 포함) | 최댓값(0.0997)의 **3.5배 이상 여유** |
| **V3** 출발점 정합 | `geometry[0]` ↔ 요청 `start` 거리 `> 300m` → 거부 | 기존 클릭 스냅 실패 기준(`CLICK_SNAP_FAIL_M=250m`) 참고 | 기존 게이트를 다시 걸지 않도록 살짝 더 넉넉하게 |

절대값(점 개수·구간 길이) 대신 **밀도·비율**로 잡은 이유: 목표거리가 500m~120km 로 넓어 절대
임계값 하나로는 짧은 경로에서 과잉 차단, 긴 경로에서 과소 차단이 난다. 비율 기준은 스케일에
무관하다.

### 배선 지점

- `searchDistanceAutoRoute` — `assembleFromClipped`·`assembleShortfall` 최종 반환 직전. 위반 시
  `status:"failed"`, `message: "경로 절단에 실패했습니다.(<reason>)"`.
- `searchReadyLoopRoute` — `eligible` 필터에 `validateRouteGeometryPlausibility(...).ok` 조건 추가.
  위반 후보는 조용히 버려지고 다른 방위 표본으로 넘어간다(다른 표본이 전부 걸리면 기존
  `no_loop` 실패 경로를 그대로 탄다 — "모든 후보가 걸리면 정직하게 실패"를 기존 실패 경로가 이미
  만족한다).

   이상 지난 로그만 2~15줄 반환). Cloud Logging API 직접 조회(다른 인증·툴)가 필요할 수 있다 —

   명시). 개선 후보 3가지를 §2 말미에 남겼다.
4. **클릭 기반 경로의 실 백엔드 회귀 확인 생략** — §5-2 참고. 단위 시험의 공유 함수 검증으로
   대체했다.
