## 2. 【핵심】 원인 재규명 — **"두 층이 다른 IK를 쓴다"는 틀렸다**

F9 보고서 §3-2와 이전 F10 §3-1은 원인을 *"`solveIk3D` vs `aim_bone` 의 해가 다르다"* 로
봤다. **그 진단은 틀렸다.** 감리0801이 F9 보고서의 실측 좌표만으로 역산해 확인했다.

### 2-1. `aim_bone` 은 정상 작동했다. 다리가 **물리적으로 짧아서 못 닿았다**

`aim_bone` 은 본 길이를 유지한 채 방향만 돌린다. 즉 **오차 없이 조준했더라도, 본이
목표까지 닿지 않으면 그만큼 남는다.** 실제로 그 일이 벌어졌다.

좌측(BDC, 무릎 10°) 기준 — 전부 F9 보고서 §3-2 표의 수치다:

| 구간 | joints 가정 | Blender 실제 | 차이 |
|---|---|---|---|
| HIP → 무릎 | **378.40** (=430×0.88) | **349.29** | **−29.11** |
| 무릎 → 발목 (SHIN) | 352.00 | 352.00 | 0 ✔ |
| **HIP 에서 도달 가능 거리** | 730.40 | **701.29** | **−29.11** |
| 필요한 HIP → 발목 | 727.63 | 727.63 | — |
| **여유** | +2.77 (무릎 10°) | **−26.34 (도달 불가)** | |

### 2-2. 이 가설로 **좌·우 오차를 0.06mm 이내로 재현했다**

`ratio = 349.29 / 378.40 = 0.92307` 을 써서 무릎을 그 비율만큼 당긴 뒤 SHIN 을 발목으로
조준했을 때의 잔여 오차를 계산하면:

| 다리 | 예측 오차 | **F9 실측** | 차이 |
|---|---|---|---|
| 좌 (BDC, 무릎 10°) | **29.14mm** | 29.2mm | 0.06 |
| 우 (TDC, 무릎 116.9°) | **12.26mm** | 12.2mm | 0.06 |

**두 다리가 서로 다른 각도인데도 하나의 상수로 둘 다 맞는다.** 우연이 아니다.
좌우 오차가 달랐던 이유도 이걸로 설명된다 — 같은 29mm 부족분이 폈을 때(BDC)는 그대로
드러나고 접었을 때(TDC)는 부분 상쇄되기 때문이다.

### 2-3. joints 자체는 결백하다 — 감리가 직접 검산했다

`20260801-F9-AFTER/input-ik-joints-v2.json` 을 열어 전 phase·좌우를 검사했다.

```
|hip-knee| = 378.40  (thigh 378.40, diff  0.00)
|knee-foot| = 352.00 (shin  352.00, diff  0.00)
```

**joints 는 자기 본 길이와 완벽히 일치한다.** solver 를 바꿀 이유가 없다.
따라서 이전 F10 의 선택지 (A)(B)(C) 는 **전부 이 문제를 못 고친다.** (A)는 이미
하고 있는 일이고(`aim_bone("THIGH_"+side, g2b(d["knee"+side]))` — `fit_ik.py:369`),
(B)(C)는 닿지 않는 다리를 다른 방법으로 못 닿게 할 뿐이다.

### 2-4. 진짜 원인: **THIGH 만 연장이 빠졌다**

`fit_ik.py:139-166` 에 `extend_shin()` 이 있다. 주석이 이 사고를 정확히 예고해 뒀다:

> *"실제 GLB 메시 SHIN 뼈가 rest 350mm 라 그대로면 발이 목표에 못 닿는다"*
> → GLB SHIN 을 json 이 가정한 rest 길이로 늘려 두 층 정합

**SHIN 에는 이 처리가 있고 THIGH 에는 없다.** `export-ik-joints-v2.mjs:27` 은
`thigh: 0.430 * SCALE` 을 그냥 가정하는데, 실제 GLB 의 THIGH 구간(THIGH head →
SHIN head)은 rest **396.92mm** (=349.29/0.88)다. 33mm 짧다.

즉 **정강이에 이미 적용된 처리를 허벅지에 안 한 것**이 유일한 원인이다.

## 3. F10-R1 지시

### 3-1. 【먼저】 계측하고 보고하라 — 코드 고치기 전에

내 결론은 F9 보고서의 수치만으로 역산한 것이다. **Blender 에서 직접 재서 확인하라.**
rest 자세(`pose_position="REST"`)에서:

| 재야 할 것 | 감리 예측 |
|---|---|
| `THIGH_L/R` 의 `bone.length` (rest, 스케일 전) | ? |
| **`THIGH_L/R` head → `SHIN_L/R` head 거리** (rest) | **396.92mm** |
| THIGH tail 과 SHIN head 사이 간격(붙어 있나) | ? |
| 같은 항목을 `SHIN` 연장 **전/후** 로 각각 | — |

**THIGH tail 과 SHIN head 가 떨어져 있는지가 갈림길이다:**

- **붙어 있으면** → THIGH 본 자체가 짧다 → `extend_thigh()` 로 해결
- **떨어져 있으면** → THIGH 는 378.4 인데 SHIN 이 29mm 위에 붙어 있다 → 연장이 아니라
  **SHIN head 를 THIGH tail 에 재부착**해야 한다

어느 쪽이든 **결과 불변식은 같다**:

```
|THIGH head → SHIN head| (world, scale 후) == v2Bones.thigh == 378.40mm
```

내 예측이 틀렸으면 **틀렸다고 보고하라.** 감리는 F6~F8 에서 혼합좌표로 크게 틀린 적이 있다.

### 3-2. 그 다음 고쳐라

`extend_shin()` 과 **똑같은 방식**으로 THIGH 를 처리한다. 새 설계를 하지 마라 —
바로 위 30줄에 검증된 패턴이 있다.

```
THIGH_REST_TARGET = JD["v2Bones"]["thigh"] / JD["scale"]     # 0.4300 m
def extend_thigh():   # extend_shin 과 동일 구조
    tail 을 head→tail 방향으로 THIGH_REST_TARGET 까지 연장
    delta 만큼 자식(SHIN)과 그 하위(FOOT·TOE) 전부 재부착
extend_thigh()        # extend_shin() 보다 먼저 — 부모가 먼저다
```

- **호출 순서 주의**: THIGH 를 먼저 연장해야 SHIN 의 head 가 옳은 자리에서 시작한다
- 두 함수를 하나로 합쳐 일반화해도 좋다(판단은 당신 몫). 다만 **SHIN 처리의 동작은
  바뀌면 안 된다** — 지금 SHIN 은 정상이다
- `fit_ik.py` 는 OneDrive 자산이다. **수정 전 원본을 `.bak` 으로 남겨라**

### 3-3. 합격 기준

| 항목 | 기준 |
|---|---|
| **`footContactAssertions`** | **좌·우 모두 5mm 이내 PASS** ← 이것이 합격 판정 |
| `frameAssertions` · `crankPhaseAssertions` · `jointsFreshness` | 전부 PASS |
| BDC 무릎 실측 | **10°** 목표 |
| `v2Bones` · 프레임 · scale | 불변 |

예측: 이 수정만으로 발 오차가 **좌·우 모두 1mm 미만**으로 떨어진다. 그렇게 안 되면
남은 오차가 얼마인지 그대로 보고하라.
