### 1-3. 반증 ② — 그런데 수정 방향은 옳았다. 근거는 감리 것보다 강하다

팔꿈치 170.01°(굽힘 10°)는 얼핏 "거의 잠김"이라 나쁜 값 같지만, **역산해보면 설계값이다**:

```

riderRig.geometry.mjs:104 주석: "상완은 F13-B 에서 팔꿈치 10° 굽힘을 만들려고 연장한 값"
UPPER_ARM_LEN = 0.33483                                        ← 오차 0
```

즉 **상완 334.83 은 GLB 실측 어깨에서 실제 후드까지 굽힘 10° 가 되도록 F13-B 가 역산한
값**이다. 어깨를 V2 실측으로 옮기는 것이 옳다는 증거가 감리 계산보다 오히려 강했다.
그래서 반증을 보고하되 **§2-2 는 지시대로 이행**했다.

### 1-4. 반증 ③ 【중대】 — **사지 길이 "차이 0.00 ✔" 이 틀렸다. 노드 scale 을 빼먹었다**

감리 표(§1-2 · HANDOFF §7-3)는 자식 오프셋만 보고 "사지 길이 4개 차이 0.00 ✔" 이라 했다.
**그 노드들에는 `scale: 1.13636` 이 걸려 있다.**

| | 앱 IK | 자식 오프셋 | **× scale 1.13636 = 실제 렌더 길이** | 오차 |
|---|---|---|---|---|
| THIGH | 378.40 | 378.40 | **430.00** | **+13.64%** |
| SHIN | 352.00 | 352.00 | **400.00** | +13.64% |
| UPPER_ARM | 334.83 | 334.83 | **380.49** | +13.64% |
| FOREARM | 212.84 | 212.84 | **241.86** | +13.64% |

`1.13636 = 정확히 1/0.88`. 430 · 400 · 380.49 · 241.86 은 **전부 rest 원본값**이다 —
즉 이 GLB 는 **scale 0.88 이 취소된 크기로 렌더된다.** 앱 IK 는 0.88 적용값으로 각을
푸는데 렌더는 13.64% 긴 사지로 그린다. 그림에서 라이더가 과대해 보이는 것이 이것이다.

## 3. 【핵심】 ②③ 실패의 진짜 원인 — F19 산출물의 앱 계약 위반 2건

감리 진단(어깨 106.70mm)은 사실이지만 **그것만으로는 ②가 서지 않는다.** 더 큰 원인이 있다.

### 3-1. 무엇이 다른가 — F18 산출물과 대조하면 즉시 드러난다

| 노드 | `.pre-F19.bak` (**F18 산출**) | **현재 (F19 산출)** |
|---|---|---|
| `arm_l`·`arm_r`·`leg_*`·`torso` | `rotation: null` · `scale: null` | **`rotation [0,−0.7071,0,0.7071]`** (y축 −90°) |
| | | **`scale 1.13636`** (= 1/0.88) |

**F18 산출물은 계약을 지켰고, F19 산출물만 이 둘을 들고 왔다.**

### 3-2. 왜 이것이 치명적인가

`glbModelLayer.ts:34` 의 `model-rotation` 은 노드 회전을 feature-state 값으로 **대체**한다
(누적이 아니다). `pose.mjs:10` 의 계약 *"Solver root 는 GLB node root 와 반드시 동일"* 은
**위치뿐 아니라 rest 자세에도** 적용된다.

```
rotation −90°y  → 앱이 [0,0,0] 등으로 덮어써 지워진다 → 메시가 축 둘레로 90° 돌아간다
                  torso 가 [0,0,0] 으로 덮이므로 몸통이 자전거와 90° 어긋난다  ← 그림 그대로
scale 1.13636   → feature-state 로 덮이지 않아 그대로 적용된다 → 사지 13.64% 과대
```

즉 **어깨 106.70mm 는 이 위에 얹힌 2차 오차**였다. 어깨만 고쳐서는 ②가 설 수 없었다.

## 6. 이견 · 선택지 (사용자에게 직접 묻지 않고 감리를 거친다)

### 이견 1 — 「메시 재굽기 금지」의 경계를 다시 그어야 한다

§3 의 원인은 **앱 코드로는 고칠 수 없다.** GLB 노드의 rest 를 손대야 한다.
지시서 §4 는 "필요하다고 판단되면 먼저 근거를 보고하고 승인받아라" 라 했으므로 여기서 멈췄다.
**근거는 §1-4·§3 에 전부 있다.**

### 이견 2 — 감리 진단표의 "차이 0.00 ✔" 판정 방식

자식 오프셋만 보고 `scale` 을 보지 않았다. HANDOFF §7-3 표도 같은 실수를 담고 있으니
**정정이 필요하다**(내 첫 검산도 같은 함정에 빠질 뻔했다).
