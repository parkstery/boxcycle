## 1. 감리 진단 검산 — **3건 전부 일치. 반증 없음**

### 1-1. 「Mapbox 는 대체가 아니라 누적이다」 — **감리가 옳고 내 F20 §3-2 가 틀렸다**

`mapbox-gl-dev.js:36067~36073` 를 직접 열어 확인했다.

```js
multiply$5(node.globalMatrix, parentMatrix, node.localMatrix);
const nodeOverride = this.nodeOverrides.get(node.name);
if (nodeOverride !== void 0) {
  rotationYZX(m, nodeOverride.orientation);
  multiply$5(node.globalMatrix, node.globalMatrix, m);   // ← post-multiply = 누적
}
```

`:36431~36432` 도 확인: `node.name = nodeDesc.name`(glTF 노드명 그대로) ·
`node.localMatrix = fromRotationTranslationScale(rotation, translation, scale)`
→ **rest 회전·배율이 localMatrix 에 살아 있고 지워지지 않는다.** 감리 판정 그대로다.

### 1-2. 「정점은 이미 올바르다」 — **일치**

| torso 메시 로컬 AABB (mm) | x | z | 판정 |
|---|---|---|---|
| **현재 제품** | **−141.9 … 466.2** (전후) | **±193.6** (좌우 폭) | 자전거와 같은 축 배치 ✔ |
| F20 정규화 시험판 | ±193.6 | −141.9 … 466.2 | 90° 틀어짐 ✔ |

감리 수치와 소수점까지 일치한다. **내 F20 시험판이 오히려 오차를 정점으로 옮겼다는
판정도 맞다.** 폐기했다.

> 사소한 정정: 감리 표는 *"장축=x"* 라 했으나 torso 실제 장축은 **y(765.7mm)** 다
> (x 608.2 · z 387.2). x/z 관계는 옳으므로 결론에 영향 없다.

### 1-3. 「정점이 0.88 스케일로 저장돼 있는가」 — **일치. 다만 판정 근거를 바꿨다**

감리가 제시한 "메시 AABB 도 같은 스케일" 은 **판정 근거로 못 쓴다** — 메시 AABB 는
뼈 길이가 아니라 살덩이 범위라 지표별로 0.82~1.57 로 흩어진다(전완 AABB 380.0mm 는
손까지 포함한 값이다). **더 결정적인 지표로 확인했다:**

```
키 삭제 후 전고 = torso.T.y 802.21 + 메시 y최대 645.8 = 1448.0mm
glbModelLayer.ts:30 기준  라이딩 자세 실제치 ~1450mm    → 오차 0.1%  ✔
scale 을 살리면            802.21 + 645.8×1.13636 = 1536.1mm (+6%)  ✘
```

**정점은 0.88 스케일이 맞다. scale 삭제가 옳다.**

## 3. 【핵심】 ②③ 실패의 새 원인 — 노드 구조가 옛 라이더와 다르다

앱 IK 계측은 여전히 `handErr 0.000mm · footErr 0.000mm` 인데 화면은 무회전이다.
**계측과 렌더가 다른 장면을 보고 있다**(HANDOFF §4-1b 와 같은 종류, 세 번째다).

### 3-1. override 메커니즘 자체는 정상이다 — 세 가지로 확인

1. `evaluateFeatureStateForNodeOverrides`(`:88231`)가 `part` = 노드명으로 `model-rotation`
   을 평가해 `nodeOverrides` 에 넣는다. 우리 `match` expression 과 규약이 맞다
2. **콘솔 에러 0 · 라이더 관련 경고 0** (주행 중 187 메시지). `setFeatureState` 는
   throw 하지 않았다
3. **옛 절차적 라이더는 같은 앱 코드에서 손이 후드에, 발이 페달에 정확히 붙는다**(F20 촬영)

### 3-2. 그렇다면 남는 차이 — **노드가 메시를 직접 소유하는가**

| | **옛 절차적 라이더** (앱에서 정상) | **V2 강체 분해** (무회전) |
|---|---|---|
| `arm_l` | `mesh` **없음** · `t` **null** · children 4개 | `mesh=1` **직접 소유** · `t=[92.78, 1137.35, 180.40]` |
| `leg_l` | `mesh` 없음 · `t` null · children 4개 | `mesh=66` 직접 소유 · `t=[−211.28, …]` |
| `torso` | `mesh` 없음 · `t` null · children 8개 | `mesh=157` 직접 소유 · `t=[−205.17, …]` |
| 구조 | **순수 그룹 노드**(회전 핸들) + 메시는 자식에 | **메시 노드 = 회전 노드** |

옛 라이더는 `arm_l` 이 **빈 그룹**이고 메시가 자식에 달려 있다. V2 는 `arm_l` 자신이
메시를 들고 translation 도 갖는다. **F19 강체 분해가 만든 구조 차이**이며, F18 산출물
(`.pre-F19.bak`)도 V2 와 같은 형태다 — 즉 **V2 를 앱에 올린 F18 이후 줄곧 이 상태였다.**

### 3-3. 확정하지 못한 것 — 정직하게 쓴다

**이 구조 차이가 무회전의 원인이라고 단정할 근거는 아직 없다.** 번들 코드상
`globalMatrix = (parent × local) × R_override` 는 translation 이 있어도 노드 원점 기준
회전이 되어야 정상이다. 그런데 화면은 무회전이다.

**남은 검증 후보**(다음 지시가 정해야 한다):
- `syncRiderGlbModels` 가 `s.pedalPose` 를 실제로 넘기는지 — `if (s.pedalPose)` 가
  false 면 `setFeatureState` 자체가 호출되지 않는다(에러도 안 난다)
- `restToDirRotationDeg` 의 three 'XYZ' 분해 ↔ Mapbox `rotationYZX` **오일러 순서 불일치**
  — 옛 라이더에서 우연히 맞아떨어졌을 가능성
- `RIDER_GLB_NODE_OVERRIDE_NAMES` 가 실제로 model spec 에 전달되는지

**§3-1 중지 조건은 해당되지 않는다**(몸통 90° 는 해소됐다). 그러나 지시 범위가
"노드 9개에서 키 2개 삭제" 였고 그것은 끝났으므로, **앱 배선 조사는 감리 지시를 받고
하는 것이 옳다고 판단해 여기서 멈췄다.**
