## 0. 왜 이 문서가 존재하는가 — 전략 진단

### 0.1 역사적 사실

- pre-version은 **구글 스트리트뷰 기반 실내 사이클 시뮬레이터**였다. 거리뷰가 앱의 전부였고, 거리뷰 비용이 앱을 죽였다.
- Mapbox + Mapillary로 피벗한 것이 현재 앱이다. Mapillary는 품질·연속성이 낮아 **더 이상 핵심 매력이 될 수 없다**(보조 기능으로 강등).
- 현재 피치 "경로를 직접 만들어 전 세계를 달린다"는 **도구(tool)의 언어**다. 도구는 창작자(사용자의 1~5%)에게만 어필하고, 대부분의 사용자는 "타는 것"에만 관심이 있다.

### 0.2 전장 분석 — 어디서 싸우면 안 되고, 어디가 비어 있는가

| 진영 | 콘텐츠 모델 | 강점 | 구조적 한계 |
|------|------------|------|------------|
| Zwift · MyWhoosh | 스튜디오 제작 3D 가상 세계 | 게임급 그래픽·레이스 | 세계가 **미리 만든 몇 개의 섬**. 지구 전체 불가 |
| Rouvy · Kinomap | 실사 촬영/업로드 영상 | 실사 몰입감 | **촬영된 경로만**. 촬영·라이선스 경제 필요 |
| **RTW** | 벡터 지도(Mapbox) | **행성 전체·한계비용 ~0** | 사진적 리얼리즘 없음 |

결론 두 가지:

1. **그래픽 충실도 전장은 회피한다.** 자본 구조상 이길 수 없고, 이기지 않아도 된다(Strava·GeoGuessr·Wordle — 그래픽 없이 이긴 선례들의 공통점은 "화려함"이 아니라 다른 가치를 팔았다는 것).
2. 경쟁자 누구도 콘텐츠 모델상 **"지구 전체"를 제공할 수 없다.** 이것이 RTW의 유일한 구조적 해자다. 단, "어디든 갈 수 있다"는 그 자체로는 안 팔린다 — **빈 지구는 지루하다.** 이 해자를 의미 있게 만드는 장치가 본 문서의 정복 레이어다.

### 0.3 증명된 심리, 비어 있는 자리

실외에는 "현실 도로의 완주·수집"을 게임으로 만든 선례가 이미 있다: **Wandrer.earth, CityStrides, Squadrats**(달린 도로/타일의 완성도를 채우는 게임 — 열성 유저층 보유). 전부 **실외 GPS 전용**이다. **실내 라이더가 현실 지구를 정복·수집하는 앱은 (조사 시점 기준) 없다.** Zwift 유저는 가상 섬을 돌고, Rouvy 유저는 남이 찍은 길을 탄다.

### 0.4 현재 앱의 결정적 결함 — 흔적의 증발

red dot은 24시간이면 사라지고([presence 설계](260523-World-Activity-Presence-설계.md)), 주행은 통계 숫자로만 남는다. **활동이 자산으로 축적되지 않으면 러닝머신이고, 축적되면 게임이다.** 고칠 것은 그래픽이 아니라 **영속성**이다.

> **피치 전환:** "경로를 만들어 어디든 갈 수 있어요"(기능) → **"실내에서 페달을 밟을수록, 현실 지구 위에 당신의 영토가 영구히 늘어납니다"**(판타지). Ride The World라는 이름이 문자 그대로가 된다.

## 1. 핵심 루프

```
달린다 → 지나간 블록이 영구히 칠해진다 → 지도가 변한다 → 더 칠하고 싶다
```

- 휘발성 레이어(red dot·liveNow — "지금/최근 누가")와 영구 레이어(정복 — "역사적으로 누가")는 **공존·보완**한다. red dot 파이프라인은 그대로 두고 그 옆에 영구 축적을 추가한다.
- 신규 탐험 동기가 내장된다: 이미 칠한 블록의 재주행은 새 영토를 주지 않으므로, 루프 자체가 "안 가 본 곳"으로 유도한다.

## 2. 3대 메커닉

| # | 메커닉 | 내용 | 콜드스타트 의존 |
|---|--------|------|----------------|
| M1 | **개인 정복(블록)** | 지나간 블록이 내 것으로 영구 기록. 총 블록 수·도시별 집계 | **없음 — 혼자여도 성립** (Phase A 1순위 근거) |
| M2 | **개척자 크레딧** | 그 블록에서 **자격 조건(§3.4)을 최초로 충족한** 사용자의 닉네임이 영구히 남음(write-once). Phase A는 **기록 전부·노출 최소**(§3.4) | 없음 — 오히려 유저가 적을수록 개척지가 많아 **빈 지도가 매력으로 반전** |
| M3 | **집단 페인트** | 블록별 누적 열기(heat)·클럽/국가 색 — 세계지도가 라이더들의 캔버스가 됨 | **있음 — 밀도 필요 → Phase B/C**, 시즌 도시로 해결 |

## 3. 정복 판정 규칙

### 3.1 정복 단위 — **도로 셀(z20, ~30m)** 로 전환 (2026-07-03 PM 결정)

> ~~z16 타일(면)~~ → **도로 셀(선)**. 사이클리스트의 자산은 면적이 아니라 **달린 도로**다.
> 타일 방식의 결함(PM 지적): 자산의 시각 언어가 도로가 아니라 면이라 라이딩 컨셉과 어긋나고,
> 상행 500m 스침과 타일 내 전 도로 5,000m 완주가 같은 1블록이 되는 노력-보상 불비례.

**타일→도로 전환이 가능해진 근거:** 애초에 도로 세그먼트를 기각한 이유는 맵매칭·GPS 노이즈였는데, RTW는 시뮬레이터라 **경로가 Mapbox Directions 산출 = 태생부터 도로에 맵매칭**돼 있다. 실외 앱(Wandrer)이 못 푸는 문제가 RTW에는 없다.

| 요소 | 값 |
|------|-----|
| 정복 단위 | **z20 슬리피 타일 = "도로 셀"**(서울 위도 ~30m) — 경로를 ~12m 간격 보간해 셀 집합으로 변환 |
| 자산·표시 | **「내 도로망」** — 주행 궤적(단순화 폴리라인) 영구 렌더. 지표 = **신규 도로 km**(셀 중복 제거 → 노력 정비례) |
| 상·하행 | 물리적으로 분리된 도로(이격 >30m)는 자연히 구분, 같은 도로 왕복은 1회 — 중간값이 자동 성립 |
| 줌아웃 LOD | 원거리에서 궤적을 타일 채우기로 집계 표현 — Phase B(v1 타일 렌더 재활용 후보) |

- 중도 종료 시 실제 진행 구간까지만. 셀 줌(z20)은 축적 데이터 단위 — **확정 후 변경 불가에 준함**(OQ-1).
- v1(z16 타일) 테스트 데이터는 유휴 잔재로 남김(출시 전이라 무해) — `conquest/{uid}/chunks` 의 z10 문서·`pioneerChunks`.

**도로 "ID" 문제에 대한 명확화(2026-07-03 외부 자문 반영):** Directions 는 geometry 를 줄 뿐 영구 도로 ID를 주지 않는다 — 맞는 지적이다. 그래서 v2 는 **도로를 식별하지 않는다.** 원자 단위는 여전히 **z/x/y(z20) — 타일과 동일한 영구 ID 체계**이고, "도로"라는 성질은 (a) 경로가 지나는 셀만 마킹된다는 사실과 (b) 표시를 궤적(선)으로 한다는 데서 나온다. 같은 도로를 두 번 달리면 같은 centerline → 같은 셀이 나오는 **기하학적 수렴**에 기대는 것이지, 도로 ID 매칭이 아니다. 잔여 리스크: ① Mapbox/OSM 도로 데이터 갱신으로 centerline 이 수 m 이동하면 경계 셀 일부가 달라져 **경미한 중복 인정**(신규 km 과대) 가능 — 관찰 대상(OQ-12). ② 30m 내 평행 이면도로가 셀을 공유해 신규 인정이 누락될 수 있음 — 수용. ③ **안정적 "구간 ID" 설계가 정말 필요한 곳은 구간 챌린지(Pioneer)** — OSM way 기반 + 버저닝 전략이 Phase B 의 선행 설계 과제(OQ-13).

### 3.2 입력 신뢰 등급(Trust Tier) — 정복의 화폐는 "검증된 페달링" (2026-07-03 개정)

**전제 수정(PM):** 속도 슬라이더는 **개발 편의로 유지되는 장치**이며 제품의 코어 입력이 아니다. **주요 타겟 = 센서 보유 실내 라이더**(마스터 §1.3 타겟 재정의와 동시 개정). 슬라이더만으로 정복이 쌓이면 페달 한 번 밟지 않고 도시를 칠할 수 있고, 그 순간 페달링 라이더의 성취가 무의미해진다 — 정복은 **검증된 노력에만** 지급한다.

원칙: **주행 자체는 모든 티어에서 자유**(탐험·경로 생성·red dot·동행은 제한 없음). 제한은 오직 "정복 인정"에만 건다 — 페달링 라이더에게는 어떤 불이익도 없다.

| Trust Tier | 입력 | 정복 인정 속도 상한 | 1일 정복 한도 | 비고 |
|---|---|---|---|---|
| **T0 no-sensor** | 속도 슬라이더만 | **15 km/h** | **5 km/일** (≈ z16 10~12블록) | 체험 티어 — 루프를 맛보게 하고 센서 전환 유도 |
| **T1 케이던스** | BLE CSC 크랭크 — **이미 지원**(`useBleCrankRpm`, Chromium) | 30 km/h | 시간 기준 §3.3 | **케이던스 > 0인 시간만** 정복 시간으로 인정 |
| **T2 트레이너/파워** (향후) | FTMS 등 | 측정값 | §3.3 동일 | 중독 방지 캡은 T1과 동일(캡의 목적이 다르므로) |

- 정복 인정 거리 = `min(실주행 거리, 티어 속도 상한 × 인정 시간, 잔여 1일 한도)`. 블록은 **경로 순서대로 예산 소진까지** 인정.
- **개척자 크레딧도 인정된 블록에만 발생** — 슬라이더 개척 land-grab 차단.
- 슬라이더 UI는 유지(개발·체험용). 시뮬 주행 속도는 자유 — 정복 **계산**만 상한으로 클램프.
- Trust Tier는 [tier·진입 정책](260519-사용자-tier-및-진입-정책.md)의 **계정 tier와 독립 축**이다(계정 tier × 입력 신뢰의 곱집합).
- 유효 주행 게이트 재사용: `isDiscardableRideRecord`(200m·출시 기준 3분 — [출시 전 확인사항](출시%20전%20확인사항.md)의 5초→3분 복원과 연동) 통과 주행만 정복 인정.

### 3.3 1일 한도 — cheat 차단과 게임 중독 방지는 같은 장치

센서가 있어도 "하루 종일 주행한 기록"이 그대로 영토가 되는 것은 과하다(PM). 공정성(cheat claim 차단)과 건강(중독 방지)을 한 장치로 해결한다:

- **T1/T2 일일 인정 시간(제안, config):** 첫 **2h 전액** → 이후 **2h 절반** → **4h 정지**(soft cap → hard cap).
  - 근거: 실내 세션 대다수는 30~90분, 더블 세션까지 4h로 커버. 그 이상은 게임이 보상하지 않는 것이 건강·공정 양면에 맞다.
  - 한도 도달 시 부드러운 안내: "오늘의 정복 한도에 도달했어요 — 주행은 계속할 수 있습니다."
- 블록 상한 병행: 인정 블록 ≤ `ceil(인정 시간(초) / 30)` — §3.1의 규칙을 유지하되 "시간"의 정의가 **검증된 페달링 시간**으로 바뀐다(T0은 슬라이더 시간이되 §3.2 한도가 지배).
- **모든 수치는 config**([tierQuotas 시드](config-tierQuotas.seed.json)와 같은 방식)로 두고 Phase A 실데이터로 튜닝(OQ-7). 지금 숫자에 매달리지 않는다.

### 3.4 Claim은 관대하게, Pioneer는 **구간 챌린지로** (2026-07-03 도로 전환과 함께 개정)

**개정(도로 전환과 동시):** 셀/타일 단위 pioneer 는 폐기한다. Pioneer 는 **구간 챌린지**로 재정의(PM 안 채택):
- **도심**: 교차로~교차로 구간, **외곽·고속화도로**: IC~JC 구간을 **완주**한 최초의 라이더가 개척자.
- **완주 무결성 규칙**: 구간을 끝까지 + 장거리 구간은 정지 시간 상한(예: 200km 구간 정지 30분 이내) — 수치는 config.
- 구간 정의에는 OSM 도로 그래프가 필요 → **Phase B 설계 과제**(마스터 §4.2 `challenge` 타입과 통합). Strava 세그먼트의 "와트 없는" 버전.
- Phase A 는 Claim(내 도로망)만 운영. 아래 v1(타일 pioneer) 논의는 **구간 챌린지 설계 시 참고용 기록**으로 보존:

<details>
<summary>(보존) v1 타일 Pioneer 규칙 — 폐기됨</summary>

타일은 **정확성을 포기하고 단순성을 얻는 근사 구조**다(Squadrats·포켓몬GO 셀과 동일 철학). 이 전제 위에서 두 판정을 **비대칭**으로 설계한다:

| 판정 | 규칙 | 이유 |
|------|------|------|
| **Claim(내 영토)** | 타일에 **닿기만 하면** 획득(관대) | 개인 레이어 — 배타성이 없으므로 후하게 줄수록 좋다 |
| **Pioneer(개척자)** | **타일 내부 경로 길이 ≥ P_MIN(가설 100m, config)** 을 **최초로** 충족(엄격·write-once) | 유일하게 배타적인 자원 — "모서리 5m 스침 개척자"만 막으면 된다 |

- **P_MIN은 자기 주행 경로 geometry만으로 계산한다**(폴리라인을 타일 bbox로 클리핑 → 길이 합산). 도로 그래프·맵매칭 **불필요**. 반면 "블록 내 도로의 몇 %를 탐험했나"류(탐험도·비율) 판정은 도로망 데이터가 필요하므로 **도입 금지** — 조건의 목적은 "충분한 탐험 측정"이 아니라 **"스침 방지"** 다(OQ-4 장기 봉인과 일관).
- **철학(등기 원칙):** Pioneer는 공정 제도가 아니라 **역사 기록**이다. 같은 블록을 더 길게 달린 후발 주자보다 조건을 먼저 충족한 사람이 임자다(부동산 등기·에베레스트 초등의 규칙). 도로 길이·통과 횟수·탐험도는 전부 무시한다 — 경계 사례의 억울함은 수용하고, 대신 규칙은 누구나 한 문장으로 이해한다.
- **무주지(無主地) 허용:** 도로가 모서리만 스치는 타일은 누구도 P_MIN을 못 채워 **영구히 개척자 없음** — 버그가 아니라 "정복 불가능한 봉우리"로 수용(Claim은 가능하므로 완주는 막히지 않음).
- **데이터 비가역성 — 기록은 Phase A 첫날부터:** pioneer는 write-once라 **첫 주행부터 기록하지 않으면 영원히 복원 불가**다(초기 유저 = 건국 공신 보상이라는 메커닉의 존재 이유가 소급 불가). 따라서 Phase A는 **기록은 전부, 노출은 영토 탭 팝업만**. 대대적 노출(상시 레이어·리더보드)과 **지역 단위 개척 업적**("이 도시 첫 100영토"·"이 국가 첫 라이더" — 타일 경계의 미세 불공정을 큰 단위로 희석) 승격 여부는 Phase B에서 결정(OQ-11).

</details>

## 4. 데이터 모델 (Firestore · Phase A) — v2 도로 셀 (2026-07-03)

기존 `ride 생성 → CF(routeActivityOnRideCreated) → routeActivity` 파이프라인과 같은 패턴으로 **CF `conquestOnRideCreated`** 를 병렬 추가한다.

```
rides/{rideId}.conquest            ← 클라 페이로드 v2: { v:2, z:20, cells:[{id,m}...],
                                      path:[[lng,lat]...](단순화 궤적), pedalSec }
conquest/{uid}                     ← 요약(1문서): totalMeters(신규 도로 m), totalCells,
                                      daily{day, usedSec, usedMeters}, updatedAt
conquest/{uid}/chunks/{z12Id}      ← 청크: { cells: { "<z20Id>": firstAtDay } } (중복 제거 인덱스)
conquest/{uid}/traces/{rideId}     ← 「내 도로망」 궤적: { path, newMeters, day } (신규 도로 있을 때만)
rides/{rideId}.conquestResult      ← CF 회신: { newMeters, newCells, creditedMeters, tier, day }
```

- **청크 = z10 타일**(z16 4,096개 커버, 서울 위도 ~31km 사각). 사용자의 활동 도시 하나가 문서 몇 개에 담긴다.
  - 문서 크기: 최악 4,096키 × ~24B ≈ 100KB < 1MB 한도. 실사용은 청크당 수십~수백 키.
- **뷰포트 조회 = z10 청크 ID 몇 개의 point-get** — 2차원 범위 쿼리 불필요(타일 ID를 범위 검색하는 대신 상위 타일로 묶는 설계 이유).
- 개척자 표시는 Phase A에선 **블록 탭 시에만**(레이어 상시 렌더는 후순위) — 읽기 비용 절감.
- 클라이언트 캐시: 자기 청크는 세션 캐시(+ 여유 시 IndexedDB) — 재읽기 최소화.
- **geometry 접근 방식(확인 완료 2026-07-03):** ride 문서에 geometry 는 없고, ad-hoc 주행은 서버 어디에도 geometry 가 없다 → **클라이언트가 주행 종료 시 진행 구간을 타일로 변환해 `rides.conquest` 페이로드로 첨부**하고, CF(`conquestOnRideCreated`)는 검증·한도 적용·집계만 한다. 페이로드 신뢰 수준은 기존 rides 파이프라인(클라이언트 작성 distanceMeters 등)과 동일 — 캐주얼 스테이크로 수용(OQ-8 계열), 경쟁 요소 도입 전 재평가.

### 4.1 Oracle DB와의 관계

준비 중인 Oracle 연동의 **1순위 이관 후보 = 전역 레이어**(`pioneerChunks`, Phase B의 heat 집계). 사용자별 정복(`conquest/{uid}`)은 Firestore 유지(권한 규칙·실시간 구독 이점). 인프라가 전략을 앞서지 않도록 Phase A는 Firestore만으로 출시한다.

## 5. 비용 추정 (Phase A)

가정: DAU 100 · 1인 1일 2주행 · 평균 10km(≈25블록, 신규 60%).

| 항목 | 계산 | 일간 |
|------|------|------|
| writes | 주행당 자기 청크 1~3 + pioneerChunks 1~2 + 요약 1 ≈ 5 × 200주행 | ~1,000 |
| reads | 지도 열람 세션당 청크 ~5 + 요약 1 ≈ 6 × 200세션 | ~1,200 |
| storage | 유저당 청크 ~10개 × 10KB = 100KB → 1만 유저 ≈ 1GB | — |

Firestore 무료 한도(write 2만/일·read 5만/일) 대비 **한 자릿수 %**. 초당 갱신되는 presence 계열보다 훨씬 싸다 — 이 레이어는 비용이 아니라 리텐션에 베팅하는 기능이다. [비용 체크리스트](260523-Firebase-비용-운영-체크리스트.md)에 관측 항목 추가할 것.

## 9.5 주행 인정·Route 진행률·미완료 쿼터 (2026-07-07 자문 3연속 → 확정)

**핵심 원칙:** "달린 것은 모두 축적된다"와 정합. **운동·Claim·Pioneer는 실제 달린 만큼 즉시 인정**(변경 없음). 제한은 오직 **미완료 Route 저장 슬롯 개수**에만 둔다(최소 인정 거리 임계는 **폐기** — 철학과 충돌하고, 개수 쿼터가 행동을 더 잘 유도).

### 9.5.1 인정 분리 (무엇을 언제 인정하나)

| 대상 | 인정 시점·기준 | 현재 코드 |
|---|---|---|
| 운동 거리·칼로리·누적 | 즉시. `isDiscardableRideRecord`(100m·5초 폐기 필터)만 | ✅ 이미 일치 |
| Conquest(Claim)·Pioneer | 즉시, **실제 주행 구간(0..virtualDistance)만** | ✅ 이미 일치 |
| **Route 완주 격상(`completed:1`)** | **완주율 ≥ 98%** 일 때만 | ⚠️ 現버그: 완주율 무관하게 격상 → **게이트 추가** |
| Route 진행률(이어 달리기) | `lastProgressRatio` 저장. 미완료도 저장 | ❌ 신규 |
| "이 Route 최초 완주" 타이틀·뱃지 | 100% 완주에만 | ❌ 신규(미션 붙일 때) |

### 9.5.2 미완료 Route 쿼터 (악용 차단의 본체)

- **미완료(`completed=0`) 슬롯 상한**: **무료 5 / 유료 10**. 이 상한은 기존 **보유 총량(`saveRouteMaxActive`: 무료 30·유료 100) 범위 내**의 하위 제약이다(별도 +알파 아님).
- 새 Route 생성 시 미완료가 꽉 차면 → **"이어서 주행 / 삭제" 선택 강제**(둘 중 하나 없이는 새 Route 불가).
- 최소 인정 거리 임계는 두지 않는다 — 개수 쿼터로 대체.

### 9.5.3 미완료 자동 정리

- **미완료 TTL 7일 → 90일 연장**([firestoreSavedRoutes.ts](../apps/web/src/lib/firestoreSavedRoutes.ts) `SAVED_ROUTE_EXPIRY_MS`). 장거리 프로젝트를 몇 달 보관 가능.
- ⚠️ **불변 원칙**: Route 삭제·만료돼도 **누적 거리·Claim·Pioneer·칼로리는 유지**. 사라지는 것은 Route 문서뿐.

### 9.5.4 UI (장기 프로젝트화)

- 저장 목록에 진행률 바(`████████░░ 80%`) + ⭐프로젝트 표기("서울 한 바퀴 42%").
- 재로드 시 "80% 지점부터 이어가기" 옵션.

### 9.5.5 구현 단위

1. ✅ 완주 게이트 — `completionRatio >= 0.98` 일 때만 격상, 미완주는 `updateSavedRouteProgressInFirestore`로 진행률만 (07-12 `ce3d006`)
2. ✅ `lastProgressRatio` 필드 — Firestore 파서(clamp01)·로컬 3곳 (07-12 `ce3d006`)
3. ✅ 미완료 쿼터(무료5/유료10) 검사 — `tierQuotaCore` 서버검사 + `details.reason` (07-12 배포)
4. ✅ 초과 유도 UI — 저장 진입점 3곳 → 「내 경로」 대기 탭 유도 배너 (07-12 `ce3d006`)
5. ✅ `SAVED_ROUTE_EXPIRY_MS` 7일 → 90일 (07-12 `ce3d006`)
6. ✅ 진행률 바 UI(SavedRoutesPanel) (07-12 `957159e`)
7. ✅ **이어 달리기 재개** — 설계 확정·구현 완료(07-13 `6e5647a`, Playwright 실주행 E2E 검증: 20% 저장→재개 UI→누적 HUD→37% 갱신→처음부터 probe max 유지). **원칙: 위치는 누적, 인정은 세션.**
   - `useVirtualRideSession.resetDistances(startOffsetMeters)` — virtualDistance를 offset(= `min(lastProgressRatio, 0.97) × routeDistance`)으로 시드. 위치·도착판정·completionRatio(누적)는 무수정 작동
   - **운동 인정 분리**: `record.distanceMeters`·칼로리·평속 = `virtualDistance − offset`(이번 세션만). completionRatio는 누적 유지
   - **Claim 분리**: `buildConquestCellsFromRoute`/`buildTraveledPathForTrace`에 `fromMeters` 추가 → **[offset, virtualDistance] 구간만** 페이로드. (순진한 offset 시드는 0..offset 셀·trace·크레딧 예산을 오염 — §9.5 인정 분리 원칙 위반)
   - HUD = **누적 위치**(예: 338.4km/540km — 여정 몰입), 종료 요약·기록 = 「오늘 N km」 병기
   - 진행률 저장 = **max(기존, 신규)** — "처음부터 다시" 후 중간 종료해도 최대 도달점 유지
   - UI = 미완료 경로 로드 시 RouteDock Go 영역에서 「N%부터 이어달리기(기본) / 처음부터」 선택
   - 수정 지점 5곳: `useVirtualRideSession.ts` · `useSavedRoutesWorkspace.ts`(로드 시 offset 후보) · `conquestTiles.ts`(from-to) · `useRideEndAndPersistence.ts`(세션 거리) · `RouteDock.tsx`(선택 UI)
