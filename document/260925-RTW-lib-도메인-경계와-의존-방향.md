## 1. 이 문서가 존재하는 이유

구조 감사 보고서 §8 은 도메인 분할안을 제시하면서 **「순환 4쌍은 이 분할 과정에서 자연 해소된다」** 고 적었다.
실측 결과 **그것은 사실이 아니다.** 분할은 순환을 **드러낼 뿐 끊어주지 않는다.**

| 감사의 전제 | 실측 |
|---|---|
| 순환 4쌍 | **3쌍**(1쌍은 Phase 3 에서 이미 해소) |
| 평면 구조가 순환의 원인 | 3쌍 중 **2쌍이 `firestore*` 를 한쪽 끝에** 둔다 — 원인은 평면성이 아니라 **층의 오분류** |
| `lib/firebase/` 로 모으면 됨 | `firestore*.ts` 25개는 인프라가 아니라 **도메인을 아는 저장소**다 |

그러므로 **파일을 옮기기 전에 방향을 선언**하고, 그 선언을 기계가 지키게 한다.

## 2. 제품 개념 관계와 코드 의존 방향은 다르다

이것이 Phase 5 의 가장 중요한 설계 원칙이다. 둘을 같은 그림으로 그리려 하면
**제품의 실제 개념을 코드 구조에 맞추는 역전**이 일어난다.

### 제품 개념 관계

```
                         GEO
                    지리 기반·계산
                          │
              ┌───────────┴───────────┐
              ↓                       ↓
            ROUTE                    MAP
         「달릴 길」              「보여주는 것」
              │
              ↓
            RIDE
          「실제 주행」
              │
       ┌──────┴──────┐
       ↓             ↓
     TRAIL        CONQUEST
   공유 맥락        Claim·누적
```

이 그림은 **개념의 순서**다. Route 가 만들어지고 → 제시되고 → Ride 가 발생한다.
Route 는 만들어졌으나 Ride 가 발생하지 않을 수도 있다 — 그래서 Route 와 Ride 를 합치면 안 된다.

### 코드 의존 방향

```
geo · debug            ← 전 도메인이 볼 수 있다(기반·계측 말단)

trail  ──→ trail/repo  ──→ firebase       Ride 를 import 하지 않는다
conquest ─→ conquest/repo ─→ firebase
route/core ─────────────────────────────  Conquest 를 모른다
route/http ──→ ClaimReader ←── conquest   포트로 연결한다
ride   ──→ route · conquest · activity · sensor · identity
map    ──→ 전 도메인(표현 계층)
```

**개념 그림에 있는 화살표가 코드에 그대로 있어서는 안 된다.**
`Trail → Ride` 와 `Conquest → Route` 가 그 예다 — 개념으로는 존재하고, 코드로는 금지한다.

## 3. 도메인 책임

책임·허용 목록의 **값**은 [`dep-layers.json`](../apps/web/dep-layers.json) 이 갖는다. 여기서는 판단 근거만 적는다.

| 도메인 | 왜 이 경계인가 |
|---|---|
| `geo` | 자문이 말한 「가장 아래쪽 순수 기반」. 다른 도메인을 알아서는 안 된다. **전 도메인이 볼 수 있다**(선언의 `universallyImportable`) |
| `route` | 「어떤 길을 달릴 것인가」. `routeFingerprint` 는 **경로 동일성 판단**이므로 `geo` 가 아니라 여기다(감사 §8 의 착오를 정정) |
| `ride` | 「실제 주행이라는 행위」. Route 를 **사용할 수 있지만** Route 와 동일하지 않다 |
| `trail` | 공유 주행 맥락 — Trailhead·접근권·표시번호. **Ride 의 하위가 아니다** (§4) |
| `conquest` | Claim·점유 셀·누적. **Route 의 하위가 아니다** (§5) |
| `firebase` | **순수 인프라** — 초기화·경로·변환기·에뮬레이터 배선. 도메인을 모른다 (§6) |
| `<도메인>/repo` | 도메인을 아는 저장소. `firebase` 와 자기 도메인만 본다 |
| `map` | 표현 계층이므로 전 도메인을 본다. 대신 아무도 `map` 을 보지 않는다 |
| `peerMotion` | Ride 의 하위 **전송** 계층. Trail 저장소를 직접 찌르지 않는다 (§7) |
| `debug` | 계측 말단. 방향 판정에서 제외한다(빌드 플래그 게이팅은 별건 — 감사 R11) |
| `weather` | 1파일 도메인이지만 **되살릴 제품 개념**이다(2026-08-27 표시 제거, 상태보드 §날씨). 포괄 폴더에 넣지 않는다 |
| `identity` `account` `sensor` `storage` `terms` `coach` `activity` `camera` `rider` | 종전 `lib/` 평면에서 이름 없이 섞여 있던 것들. **포괄 폴더(`shared`·`common`·`utils`)를 만들지 않는다** — 만들면 지금의 평면 `lib/` 이 이름만 바꿔 영구화된다 |

### 파일 이름이 도메인을 정하지 않는다

| 파일 | 이름이 말하는 곳 | 실제 소속 | 왜 |
|---|---|---|---|
| `rideCameraFraming.ts` | ride | **camera** | 카메라 프레이밍이다 |
| `routeWaypoints.ts` | route | **geo** | waypoint 는 지리 개념이다 |
| `rideConquestResult.ts` | conquest | **ride** | 주행 종료 결과의 표현이다 |
| `rideConquestSubscription.ts` | conquest | **ride** | 주행 쪽 구독이다 |

## 4. Trail 은 Ride 의 하위가 아니다

**결정적 증거: `trail/` → `ride/` 직접 import 는 0건이다.**

Trail 은 주행보다 **먼저** 존재한다 — Trailhead 에 있다가 주행을 시작한다
(`atTrailheadIdle = sanitizedTrailId === DEFAULT_TRAIL_ID && !isRideSessionActive`).
Trail 은 Ride 를 **담는 맥락**이지 결과가 아니다.

Trail 이 주행을 알아야 할 때(「이 Trail 에 지금 누가 달리는가」)는 `trail/repo` 의 조회로만 안다.

> **다만 조건이 있다.** `trail/repo` 가 Ride 의 정책·스키마 모듈을 import 하면
> 화살표가 `trail/` 에서 `trail/repo/` 로 **옮겨간 것**일 뿐 결합은 그대로다.
> 그래서 `trail/repo` 는 **Trail 이 소유한 좁은 읽기 모델만** 정의하고 반환한다.
> 게이트가 `trail/repo → ride/**` 도 위반으로 센다 — 규칙이 축퇴로 통과하지 않게.

## 5. Conquest 는 Route 의 하위가 아니다 — 포트로 잇는다

경로 생성이 Claim 을 읽는 것은 **제품 요구 그 자체**다.
`distanceAutoRouteHttp.ts:503` 이 「출발점 주변 Claim만 읽어 신규도로·자기중복으로 순위(탈락 아님)」라고 적고 있다.
「의존이 역방향이니 끊자」고 하면 **기능을 제거하는 결과**가 된다.

대신 **코어는 Claim 을 모른다.**

```
route/core   ─ ClaimReader 인터페이스만 안다 (Firestore 없이 단위 시험 가능)
route/http   ─ 조립 지점(composition root). 여기서 conquest 구현을 주입한다
conquest     ─ ClaimReader 를 구현해 제공한다
```

이 seam 은 **경로 생성 3갈래(클릭 A→B · 거리 자동 · Ready Ride)의 공통 코어**를 만들 때 그대로 계약이 된다.

### 집행 결과 (2026-09-25, P5-3)

**실측하니 코어는 이미 `claimedCellIds` 를 입력으로 받고 있었다.** 진짜 위험은 의존 방향이 아니었다.

> **셀 ID 계산이 세 곳에 복제돼 있었다.**
> `conquestClaimRead`(읽는 쪽, 상수 사용) · `distanceAutoRouteCore`(재는 쪽, `zoom = 20` **리터럴**) ·
> `apps/web/src/lib/conquestTiles`(**쓰는 쪽**)

어긋나면 `claimedCellIds.has(...)` 가 영영 실패한다. 그런데 그 결과(비율 전부 1.0)는
**「Claim 이 없는 사용자」와 구분되지 않는다** — 가산 항이 모든 후보에 같아져 순위 효과만 사라지고
에러도 로그 이상도 없다. **이것이 R10 의 실체다.**

**네 번째 사본이 시험 안에 있었다.** `distanceAutoRouteCore.test.ts` 가 타일 계산을 자기가 다시
구현해 자기를 검증했다 — 읽는 쪽이 어긋나도 통과하는 구조다. 공유 함수를 쓰게 고쳤다.

| 한 일 | 내용 |
|---|---|
| `functions/src/geoTiles.ts` 신설 | 서버 안의 두 벌을 **실제 통합**(순수·import 0) |
| `ClaimReader` 포트 | 코어가 선언, `conquestClaimRead` 가 구현, `…Http` 가 조립. 기존 `fetchDirections` 주입 패턴을 그대로 따라 **동작 무변경**(기본값이 Firestore 구현) |
| 고정 벡터 | 빌드가 나뉘어 코드를 공유할 수 없는 클라이언트와는 **양쪽에 같은 값**을 박았다(`20_894282_406315` 등). **바꿀 땐 두 파일을 함께** |
| 리터럴 제거 | 리더의 `"20_"` 접두어를 줌 상수 파생으로 |

**게이트 G3 계약 19건. 네 방향으로 깨뜨려 확인했다.**

| 파괴 | 결과 |
|---|---|
| 코어에 타일 계산 사본 부활 | 사본 탐지 실패 |
| 코어가 conquest 모듈 import | 구조 검사 실패 |
| **컴파일은 통과하면서 매핑만 z19 로 어긋남** | 배선 검사 실패 — **가장 중요하다.** 앞의 둘은 `tsc` 가 먼저 잡지만 이건 잡지 못한다 |
| 클라이언트 줌 상수만 변경 | 클라이언트 고정 벡터 3건 실패 |

탐지식을 `Math.log(Math.tan(` 로 잡으면 **Mercator 미터 투영 2곳(정당한 코드)** 을 오탐한다 —
타일 고유형(`tan(φ) + 1/cos(φ)`)으로 좁혔다. **오탐하는 탐지는 결국 꺼진다.**

## 6. Firebase 는 도메인 안도 밖도 아니다 — 두 층이다

`lib/firebase/` 에 전부 몰면 도메인 분할이 무의미해지고, 도메인 안에 두면 Firebase 교체 시 전 도메인이 흔들린다.
**양자택일이 틀렸다.** `firestore*.ts` 는 이미 도메인 로직을 **수입**하고 있다.

```
firestoreRides.ts         → rideRecordPolicy · rideDocFields · rideSessionsStorage
firestoreTrailInstance.ts → trailAccessPolicy · trailDisplayNumber
firestoreCourses.ts       → routeFingerprint · basicIntroHubRouteGeometries
firestoreRouteActivity.ts → activityWorldTraceStyle
```

이건 「Firebase 층」이 아니라 **Repository** 다. 인프라로 취급해 아래에 깔았기 때문에
위 도메인을 되짚어 올라가는 화살표가 30건 넘게 생겼고, 순환 2쌍이 그 결과다.

```
lib/firebase/            순수 인프라. 도메인을 import 하지 않는다
   app.ts · paths.ts · converters.ts · emulator.ts

lib/<도메인>/repo/        도메인을 아는 저장소. firebase 와 자기 도메인만 본다
```

층이 갈리면 순환 ②③은 **선언으로 끊는 것이 아니라 구조적으로 끊긴다** —
`trailAccessPolicy`(정책)가 아래, `trailInstanceRepo`(저장소)가 위로 정렬된다.

### 집행 결과 (2026-09-25, P5-5)

**파일을 폴더로 옮기는 것만으로는 순환이 하나도 끊기지 않았다.** 감사 §8 의 「자연 해소」가
틀렸다는 것을 여기서 다시 확인했다 — 이동 직후 순환은 3쌍 그대로였다.

끊은 것은 **타입의 위치**였다. 세 순환 모두 한쪽은 **타입만**, 반대쪽은 **함수**를 가져갔다.

```
trailAccessPolicy → firestoreTrailInstance (타입)          정책이 저장소를 올려다본다
firestoreTrailInstance·…OpenTrailListings → trailAccessPolicy (함수)

rtdbTrailMotion → firestoreTrailLivePublicationRides (타입)  저장소끼리 타입을 주고받는다
firestoreTrailLivePublicationRides → rtdbTrailMotion (함수)
```

`lib/trail/trailTypes.ts`(도메인 층, import 0)로 타입 4개를 내리자 **순환 3쌍 → 1쌍**이 됐다.
저장소는 종전 이름으로 re-export 해 소비자 약 30곳을 건드리지 않았다. 단, **`lib/` 안의
소비자는 타입 모듈을 직접 보게** 했다 — 호환 re-export 를 경유하면 순환이 그대로 살아남는다.

남은 1쌍은 `activityWorldLod ↔ rideSyncPolicy`(R9)이고 P5-4 의 몫이다.

부수 효과로 **`peerMotion/types.ts` 가 저장소를 import 하지 않게 됐다**(§7 의 「가장 아래여야
할 타입 모듈이 가장 위를 본다」). 다만 Trail **도메인** 타입을 보는 것은 남아 있어
`peerMotion → trail` 1건으로 계상된다 — D6 에서 갚을 빚이다.

| `lib/` 평면 파일 | 145 | **126** |

**P5-4 까지 누적: 방향 위반 59 → 58 · 순환 3쌍 → 0쌍.**

## 7. peerMotion 은 「모범」이면서 최대 위반자다

감사 §8 은 `lib/peerMotion/`(14파일)을 모듈화의 **본보기**로 꼽았다. 폴더 **내부** 응집도만 보면 맞다.
그런데 **밖으로 나가는 화살표**를 재면 2층 구조의 최대 위반자다.

```
peerMotion → trail/repo  12건   (rtdbTrailMotion · firestoreTrail · …Instance · …Paths · …LivePublicationRides)
peerMotion → firebase     2건
peerMotion → rider        2건
```

특히 **`peerMotion/types.ts` 가 `firestoreTrailLivePublicationRides` 를 import 한다** —
구조상 가장 아래여야 할 타입 선언 모듈이 가장 위를 보고 있다.

peerMotion 은 Ride 의 하위 **전송** 계층이다. Trail 저장소를 직접 찔러서는 안 된다.

### 집행 결과 (2026-09-25, D6) — 위반 58 → 41

**방향을 뒤집었다.** 종전 선언은 `peerMotion.mayImport ∋ ride` 였다(전송이 주행 위).
전송은 Ride 가 **쓰는 기계**이므로 아래여야 한다 → `ride.mayImport ∋ peerMotion`.

뒤집으니 「peerMotion 이 ride 를 본다」가 드러났고, 그 실체는 전부 **오배치**였다.

| 무엇이 | 어디 있었나 | 어디로 | 없앤 위반 |
|---|---|---|---|
| `PEER_INTERP_*` · `*_FLIGHT_DRAIN_TIMEOUT_MS` · `SPECTATOR_MAX_EXTRAP_MS` | `rideSyncPolicy` | **`peerMotion/peerSyncPolicy`** | peerMotion → ride |
| `rtdbTrailMotion`(5Hz peer motion 채널) | `trail/repo` | **`peerMotion/repo`** | peerMotion ↔ trail/repo |
| `sanitizeTrailId` · `DEFAULT_TRAIL_ID` | `trail/repo/firestoreTrail` | **`trail/trailId`** | peerMotion·ride → trail/repo |
| `lastFrom SeenAtToMillis`(Timestamp → ms) | `trail/repo/firestoreTrail` | **`firebase/converters`** | ride/repo·activity/repo·route/repo → trail/repo |
| `ACTIVITY_WORLD_POLL_*` · `ROUTE_ACTIVITY_CACHE_TTL_MS` | `rideSyncPolicy` | **`activityWorldPollConstants`** | activity → ride |

`firebase/converters.ts` 는 감사 §8 의 목표 구조가 적어 둔 자리다 — Timestamp 를 밀리초로
바꾸는 일에 Trail 은 아무 상관이 없는데, 그 함수가 Trail 저장소에 있었기 때문에 **네 도메인의
저장소가 Trail 저장소를 import** 하고 있었다.

> ⚠️ **옮기는 일에 재작성을 섞을 뻔했다.** `lastSeenAtToMillis` 를 「깔끔하게」 다시 쓴 초안은
> 원본의 **nanoseconds 합산**과 **`< 1e12` 는 초 단위** 해석을 빠뜨렸다. presence 시각이 조용히
> 달라질 뻔했다. 원본을 **그대로** 옮겼다.

### 「식별자를 안다」와 「DB 를 읽는다」는 다르다 — `mayImportRepoOf`

peerMotion 은 RTDB 경로 `/trails/{trailId}/motion/{uid}` 때문에 **Trail ID 를 알아야** 하지만
Trail 문서를 읽을 이유는 없다. 그런데 종전 규칙은 「X 가 Y 를 볼 수 있으면 Y/repo 도 본다」였다
— 그러면 D1 의 「Trail 이 소유한 읽기 모델만」이 말이 되지 않는다.

그래서 **남의 도메인 저장소 접근을 별도 허가(`mayImportRepoOf`)로 분리**했다. 이 조항은 규칙을
넓히는 것이 아니라 **한 차원 더 좁힌다** — 도입하자 숨어 있던 위반이 55 → 57 로 **늘었다**.
정당한 것만(`ride → route/repo`, `account`·`route → identity/repo`) 명시하고 나머지는 빚으로 남겼다.
`mayImportRepoOf` 도 규칙 지문에 넣었다. 실제로 `peerMotion.mayImportRepoOf = ["trail"]` 로
넓히면 위반이 41 → 35 로 줄지만 **지문 불일치로 막힌다**(파괴 검산으로 확인).
