## 1. 목적

- 문서가 **개발 진행과 따로 노는 것**을 줄이고, PM·기획·개발이 **같은 기준**으로 상태를 공유한다.
- 문서가 많아져도 **찾기·갱신·연결** 비용이 통제 가능하게 유지된다.

---

## 2. 문서 네 덩어리(역할 고정)

새 문서를 만들 때 **아래 넷 중 하나**에만 속하도록 분류한다. 애매하면 **가장 좁은 범위**부터 선택한다.

| 구분 | 코드(파일·폴더 태그용) | 담는 내용 | 예시 |
|------|------------------------|-----------|------|
| **제품·범위** | `product` | MVP/기능 정의, 우선순위, KPI, 무료·유료 정책 | 기능 명세, 로드맵(주차 단위가 아닌 제품 목표) |
| **아키텍처·데이터** | `architecture` | DB 스키마, API 설계, 인프라·스택, 보안·마이그레이션 원칙 | Postgres 설계, API 초안, Firestore→Postgres 가이드 |
| **실행** | `execution` | 당장 할 일, 체크리스트, 리팩터링 Phase, 스프린트 단위 작업 | `app.js` 분리 Phase 1-A~D |
| **기록** | `record` | 특정 시점 스냅샷, 중간 보고, 의사결정 로그 | “2026-05-08까지 코드 기준” 중간 보고 |

**원칙:** 같은 사실(예: “MVP에 코인이 포함되는가”)은 **한 문서를 진실(source of truth)으로 정하고**, 다른 문서에서는 **링크 + 한 줄 요약**만 둔다. 복붙으로 이중 기술하지 않는다.

## 3. 파일명·접두어 규칙

### 3.1 필수 접두어

- **모든** 프로젝트 문서 파일명은 아래 형식을 따른다.  
  `YYMMDD-` + 본문 슬러그  
  - `YYMMDD`: 문서가 **처음 작성된 날짜**(6자리, 예: `260509`). 이후 내용을 대폭 수정해도 **접두어는 바꾸지 않는다**(이력은 Git·본문 “개정”으로 남긴다).
  - 본문 슬러그: 한글·영문 혼용 가능. 공백 대신 하이픈(`-`)을 쓴다.

**예:** `260509-BOXCYCLE-문서-생성-및-수정-지침.md`, `260509-app-js-프론트백엔드-분리-1차리팩터링.md`

### 3.2 예외(접두어 생략 가능)

- 루트 `README.md`만 예외로 둔다(저장소 관례·GitHub 표시용).  
  단, **제품 요약·실행 방법**은 README에 두고, **상세 설계·장기 로드맵**은 `document/`에 두며 README에서 링크한다.

### 3.3 선택: 폴더로 네 덩어리 구분할 때

문서 수가 늘면 `document/product/` 등 하위 폴더를 둘 수 있다. 이 경우에도 **파일명 접두어 `YYMMDD-`는 유지**한다.

## 4. 문서 상단 메타 블록(필수)

새 문서 첫머리에 아래 표를 둔다(이 지침 문서와 동일 형식 권장).

| 항목 | 설명 |
|------|------|
| 문서 유형 | 네 덩어리 중 하나 + 부가 설명 |
| 최초 작성 | `YYYY-MM-DD` |
| **상태** | `초안` / `검토됨` / `코드 반영 중` / `코드 반영 완료(YYYY-MM-DD)` 중 하나 |
| 연결 문서 | 관련 문서 링크(상대 경로, 아래 §5) |

**상태**는 PM이 코드를 읽지 않고도 “이 문서를 의사결정에 써도 되는지” 판단할 수 있게 한다.

## 5. 문서 간 연결(링크)

### 5.1 언제 링크를 단다

- 한 문서의 전제가 **다른 문서의 결론**일 때(예: 리팩터링이 DB 필드명에 의존).
- **진실은 한 곳**에만 두고, 나머지는 링크로 참조할 때.
- 백엔드가 늘면서 **같은 도메인**(예: 주행 `rides`, 코스 `courses`)이 여러 파일에 흩어질 때 — **개요 1편**을 두고 세부는 링크로 나눈다.

### 5.2 링크 쓰는 방법

- 저장소 기준 **상대 경로**를 쓴다.  
  예: 같은 폴더 `document/` 안이면 `[아키텍처](260509-아키텍쳐-DB설계.md)`처럼 **공백 없는** 파일명으로 링크한다.
- 링크 문구는 **파일명이 아니라 의미**(예: “MVP DB 스키마 초안”)로 적는다.

### 5.3 중복·갈래

- 내용이 **갈라졌다면**(예: A안 폐기, B안 채택) 기록 문서에 **한 줄 결정 사유**를 남기고, 구버전 문서 상단에 `상태: 폐기됨 → 대체: … 링크`를 적는다.

---

## 6. 생성·수정 워크플로

1. **새 주제**가 생기면 네 덩어리 중 어디에 넣을지 먼저 정한 뒤, `YYMMDD-` 파일을 만든다.
2. **코드/배포가 바뀌어** 문서와 어긋나면, **실행·기록** 문서를 우선 갱신하거나 상태를 `코드 반영 중`으로 바꾼다.
3. **범위·스키마·API 계약**이 바뀌면 **제품** 또는 **아키텍처** 문서를 먼저 고치고, 그에 의존하는 **실행** 체크리스트·**기록**을 맞춘다.
4. PR·이슈·커밋에 **변경한 문서 경로**를 한 줄이라도 적어, 개발과 문서가 같은 단위로 추적되게 한다.
