# Spinatlas 3D 주행 FPS 원인 분석과 개선 대안

11-22 추가 직접 검수: 커스텀 후보에서29.6FPS 표시에도 지형이 일시 정지하고 라이더만 움직이는 현상을 Chief가 관찰했다. **현재 후보는 UX 불합격**이며 제품 이식은 계속 보류한다. 고정하는 코드와 관찰된 정지 현상의 원인은 구분하며, 원인은 아직 미확정이다. [직접 검수 기록](../../ops/20261119-camera-terrain-follow/20261122-reuse-approach.md#v2-직접-주행-검수).

## 요약

**현재 가장 큰 비용은 Mapbox가 도로·경로선 등의 레이어를 3D 지형 위에 다시 그리는 작업이다.** 라벨 충돌 배치를 매 프레임 처음부터 반복하는 앱 동작도 발견해 수정했다. 제자리 레이어 이동 수정 후 로컬 생산 빌드 두 회차에서 라벨 배치 평균은 기존 34.1 ms에서 3.0 / 5.2 ms로 줄었으나 지형 다시 그리기에 평균 52.6 / 67.9 ms가 남았고, 화면은 8.79 / 6.58 FPS였다.

사용자 GTX 1660 실주행에서 3D 지형과 건물을 켰을 때 10.5 FPS였고, 건물을 숨기고 3D 지형을 유지해도 약 10 FPS였다. 하드웨어 가속은 정상으로 확인했다. 같은 기종의 로컬 검수도 지형과 지도 처리 비용을 주요 병목으로 지목하지만, 사용자의 실센서 주행을 그대로 재현한 결과는 없다.

**현재 우선순위는 Outdoors에서 실제로 그려지는 선과 타일 재그리기 비용을 구분하는 것이다.** 11월 22일 계측에서 이 호출은 프레임당 4,058회, CPU 경과 시간 25.4 ms였다. 3D 지형을 유지하는 평균 30 FPS 목표와 휴대폰 프리뷰 제공은 남아 있다.

## 측정 기준과 주요 수치

### 사용자 실주행 초기 관측

실제 Edge, GTX 1660에서 전달받은 수치다. 프레임 p95와 GPU 시간은 이 관측에 포함되지 않았다.

| 조건 | 평균 FPS | 지도 렌더 호출 평균 |
|---|---:|---:|
| 3D 지형과 건물 표시 | 10.5 | 66.7 ms |
| 건물 숨김, 3D 지형 유지 | 약 10 | 69.6 ms |
| 앱에서 3D 뷰 끄기 | 57.1 | — |
| `mapcut=terrain`으로 자동 평면에 머문 상태 | 63.1 | — |

`mapcut=terrain` 회차에서는 지형과 건물이 함께 빠졌다. 건물의 영향은 건물만 숨긴 회차에서 판단한다. 이 조건에서 건물 숨김으로 FPS가 개선된 증거는 없었다.

### 제자리 레이어 이동 수정 전후

서울 남산공원길 시작 구간, 수동 5 km/h, QC2, Edge·GTX 1660, 가로 800×360 CSS 화면과 1200×540 렌더 버퍼, Outdoors, 지형 1.3배에서 계측했다. 라벨·도로·건물을 표시했고, 코스 선택 후 7초 뒤 출발해 10초 창을 비교했다. 이전 작업에서 활동 데이터 중복 전달을 제거한 상태에서 제자리 레이어 이동 생략 전후를 비교했다.

| 회차 | 평균 FPS | 프레임 p95 | 지도 호출 평균 / p95 | GPU 평균 / p95 | 라벨 배치 평균 | 지형 다시 그리기 평균 |
|---|---:|---:|---:|---:|---:|---:|
| 레이어 수정 전 | 5.06 | 269.9 ms | 158.1 / 212.4 ms | 68.6 / 151.6 ms | 34.1 ms | 78.4 ms |
| 레이어 수정 후 1 | 8.79 | 169.9 ms | 88.5 / 126.2 ms | 43.3 / 57.6 ms | 3.0 ms | 52.6 ms |
| 레이어 수정 후 2 | 6.58 | 200.1 ms | 116.0 / 154.7 ms | 49.9 / 78.6 ms | 5.2 ms | 67.9 ms |

프레임 p95는 프레임 간격의 95번째 백분위수로, 평균 FPS가 가릴 수 있는 끊김을 보여 준다. 지도 호출 시간은 메인 스레드의 벽시계 시간이고 GPU 시간과 일부 겹칠 수 있다. 두 시간을 더해 프레임 시간을 계산하지 않는다. 평균 30 FPS에는 평균 프레임 간격 약 33.3 ms가 필요하다. 각 비교의 환경과 계측 방식이 다르므로 실주행·독립 지도·개발 빌드·생산 빌드의 절대 수치를 하나의 전후 비교로 합치지 않는다. ## 확인한 원인

### 1. 화면에 필요한 지형 타일을 반복해서 다시 그린다

Mapbox는 도로·진행선 등 지도 레이어를 타일 텍스처에 먼저 그린 뒤 지형 표면에 합성한다. 800×360 생산 빌드 추적 기준에서 프레임당 고려한 지형 타일은 평균 40.7개였고 전부 다시 그렸다. 검수에서 카메라를 고정해도 38개 전부를 다시 그렸다. 따라서 카메라 이동이 없어도 앱의 스타일·소스 갱신이 계속되면 재그리기 비용이 남는다.

재사용을 방해하는 두 경로를 구분했다.

- **전체 캐시 무효화.** 순서가 변하지 않는 `moveLayer`도 Mapbox에 스타일 변경을 알린다. 또 직렬화한 스타일의 레이어 목록에는 라이더·이정표 같은 커스텀 레이어가 빠져, 활동 점과 라이더가 서로 최상단을 다시 요청할 수 있었다. 실제 순서를 기준으로 중복 이동을 생략한 검수에서 전체 무효화가 84/84프레임에서 3/95프레임으로 줄었다. 개별 타일 갱신이 남아 이 회차의 타일 재사용은 0이었다.
- **개별 타일 무효화.** 추적 카메라의 `moveend`는 줌에 따라 달라지는 선의 캐시를 갱신할 수 있다. 앱의 GeoJSON 소스 갱신과 Mapbox의 타일 로드 이벤트도 같은 경로에 들어온다. 동적 GeoJSON `updateData`는 두 주행선의 워커 데이터 응답을 689~731회에서 101회로 줄였지만 화면에서는 약 41개 타일을 계속 다시 그렸다. 워커가 바뀐 데이터 없이 부분 응답을 끝낸 경우에도 타일 이벤트로 지형 캐시를 무효화하는 것을 별도로 확인했다.

### 2. 불필요한 레이어 이동이 라벨 전체 배치를 반복시켰다

지도가 `idle`에 도달하기 전에는 Mapbox가 초기 로드용 배치를 사용한다. 초기 로드 또는 레이어 순서 변경이 반복되면 라벨을 화면에 놓고 겹침을 검사하는 일이 한 프레임에 집중된다. 수정 전 기준 99프레임은 전부 초기 로드 상태였고, 라벨 충돌 계산만 평균 31.8~35.5 ms였다. 타일 간 심볼 인덱싱은 약 0.5 ms로 작았다.

실제 레이어 순서를 기준으로 제자리 이동을 생략한 뒤, 출발 전 `idle`과 주행 중 정상 라벨 배치를 확인했다. 제품 빌드 두 회차에서 강제 전체 배치와 실제 레이어 이동 호출은 각각 0회였고, 새 라벨 배치가 13회 / 5회 완료됐다. 지도에 표시할 라벨과 경로선의 정책은 그대로 유지했다.

### 3. 초기 의심 항목의 영향은 조건에 따라 제한적이었다

- **카메라 추적.** 강제 렌더 독립 장면에서 지형 카메라 고정은 지도 호출 4.5~5.3 ms, 주행 추적은 36.2~36.6 ms, 제자리에서 추적만 갱신한 경우 29.8 ms였다. 평면 주행 추적은 4.9 ms였다. 추적 함수 자체는 약 0.7 ms였고, 두 카메라 호출이 예약한 지도 갱신은 같은 렌더에 합쳐질 수 있었다. 이 실험은 카메라 변화가 지도의 후속 처리를 키운다는 근거이며, 사용자 화면 FPS는 측정하지 않았다.
- **건물과 라이더.** 사용자 GTX 1660 회차에서 건물을 숨겨도 FPS가 오르지 않았다. 800×360 별도 계측에서 커스텀 레이어 그리기에는 라이더와 이정표를 합쳐 평균 1.7~1.8 ms가 걸렸다. 다른 기기·지도 스타일·씬에서는 비용이 달라질 수 있다.
- **렌더 해상도.** DPR 1.5에서 1로 낮춰 버퍼 픽셀 수를 55.6% 줄여도, 같은 생산 빌드의 FPS는 8.59 → 9.07에 그쳤고 지형 재그리기는 약 41개로 유지됐다. 이 비교에서 해상도 조정의 효과는 작았다. [타일·라벨·GPU 계측](../../ops/20261119-camera-terrain-follow/README.md)

| 3D 뷰 끄기 | 사용자 관측 57.1 FPS. | 기존 수동 선택 및 지형 이상 보호의 용도 유지 |

제품 반영 파일은 `mapLiveOverlayLayers.ts`, `layerOrder.ts`, `routeConquestLayers.ts`다. 레이어 개선은 설치된 Mapbox GL JS 3.23.1의 `style._order`를 읽으며, 실제 순서 배열을 읽을 수 없으면 스타일 목록을 사용한다. 배치 인수와 지형 캐시 내부 동작을 바꾸는 후보는 브라우저 검수에만 적용했다. 두 성능 개선은 로컬 실행 기준이며 커밋·푸시·배포는 이뤄지지 않았다.

## 운영본 PC 주행 비교

사용자 제공 성능 Lab 결과. 2026-11-22 01:06~01:08 KST, 빌드 `CGsscEeh`, Windows Edge·GTX 1660, 화면 렌더 버퍼 1608×818, 실효 DPR 1.25. 두 회차 모두 지형 1.3배와 주행 라벨 숨김 설정이 확인됐다. 수치는 각 회차 마지막 10초이며, 30초 전체 평균은 아니다.

Outdoors의 평균 FPS가 더 높았으며 두 회차 모두 모든 표본이 50 ms를 넘었다. Standard 낮의 지도 호출 평균은 21.4 ms 길었고 GPU 평균은 비슷했다. 라이더 렌더는 두 회차 모두 약 0.6 ms였다. 두 회차의 줌과 지도 구성이 달라 스타일 자체의 효과량은 확정할 수 없다. 사용자 관찰상 Standard 낮과 해질녘의 체감 차이는 없었으며 해질녘의 계측값은 없다. 휴대폰 실측도 남아 있다.

### 빈 베이스맵 선 호출 생략 검수

별도 로컬 Edge 검수에서 기준 선 호출의 73%에 그릴 데이터가 없었다. 빈 호출에 프레임당 약 5.4 ms, 확인 자체에 약 2.0 ms가 들었다. 후보는 빈 호출 421,611건을 생략했다. 기준 → 후보는 12.94 → 14.29 FPS, 프레임 p95 110 → 100 ms, 지도 평균 64.9 → 58.4 ms, GPU 평균 42.9 → 38.5 ms였다. 조건별 1회, 브라우저 2/2 통과. 픽셀 비교·QC3·실센서·휴대폰은 미검수이며 제품과 프리뷰에는 반영하지 않았다. ## 남은 작업과 배포 판단

1. **다음 담당 Codex**는 Outdoors를 기준으로 실제 데이터가 있는 선 호출과 스텐실·타일 재그리기 비용을 분리한다. 큰 비용부터 줄이면서 동일 카메라 자세의 픽셀과 반복 실행의 FPS·프레임 p95·지도·GPU 시간을 비교한다.
2. 개선이 반복되면 QC2·QC3 구도, 카메라 이동 간격과 체감 끊김, 지면 간섭 방지, 사용자 줌, 자동 3D 복귀, 수동 3D OFF, 라벨·건물·주행선 표시를 확인한다. 센서 입력과 라이더 애니메이션 주기도 유지한다.
3. 검증한 변경만 분리해 휴대폰용 Hosting 프리뷰로 제공한다. 실제 가로 화면 스마트폰과 센서에서 평균 FPS·프레임 p95·카메라 움직임을 따로 확인한다. 현재 새 프리뷰는 없다.

11월 22일 타일·텍스처·레이어별 계측 브라우저 시험 5/5, 관련 계약 시험 51/51 통과. 새 후보의 제품 반영과 커밋·푸시·배포는 없었다. 실제 휴대폰·센서 주행과 눈으로 보는 카메라 부드러움은 남아 있다.

## 검증 상태와 근거

- 최근 레이어 수정의 관련 계약 시험 51건, TypeScript, ESLint 및 생산 빌드 주행 확인 2건이 통과했다. 첫 생산 빌드 확인은 Functions 에뮬레이터의 시작 시간 초과와 브라우저 fetch 오류로 실패했고, 함수 탐색 허용 시간을 늘린 재실행에서 통과했다.
- 앞선 800×360 WebGL 능선 검수에서 QC2·QC3의 지상고, 라이더 기준점, 자동 3D 복귀를 확인했다. 전체 앱에서 수동 OFF 후 다시 켜는 클릭 시험은 당시 시간 제한에 걸렸다. 즉시 출발은 후속 로컬 시험에서 검증했다. 실제 폰 GPU와 실센서 입력은 후속 시험에도 포함되지 않았다.
- 저장소의 상세 기록과 재현 명령은 카메라 검수 README에 있다. 원시 자료는 저장소 기준 `tmp/terrain-perf/`의 `controlled-render.json`, `camera-candidates-edge.json`, `prod-tiles-*-product.json`, `prod-tiles-*-conquest-event.json`, `prod-tiles-*-placement-product-confirm.json`에 있다. 사용자 실주행 초기 수치는 사용자 제공 계측을 인용했다.
