## 1. 핵심 결론

현재 거리·방향 방식은 **출발점에서 사용자가 클릭한 지점까지 Mapbox 도로 경로를 구한 뒤, 목표 거리 지점에서 잘라 적용하는 기능**이다. 출발·도착 방식은 **사용자가 지정한 두 지점과 선택 경유지를 연결하는 도로 경로 전체를 적용**한다.

따라서 동일 출발점·동일 클릭점·동일 이동수단·동일 Mapbox 응답을 전제하면, 거리·방향 결과는 출발·도착 결과의 앞부분이 된다. 목표 거리가 클릭 지점까지의 도로거리보다 부족하면 클릭 지점 전에 끝난다. 목표가 더 길면 현재 일반 클릭 흐름은 우회해 채우지 않고 「너무 가깝습니다」로 실패한다.

두 방식은 같은 도로 경로 공급자와 주행·저장 체계를 쓴다. 생성 방법이 다르다는 이유로 자동 경로에 별도 주행 속도나 정복 보상이 붙지는 않는다. 경로 모양·실제 길이·도로 중복 여부가 달라지면 실제 주행 결과도 달라질 수 있다.

서버 제한시간은 실행 상한 설정이며 실제 지연 측정값이 아니다. 현재 일반 클릭 자동 경로가 여러 후보를 매번 수십 회 요청한다는 설명은 실행 코드와 맞지 않는다.

## 3. 자동 경로 실행 흐름

1. 사용자가 출발점을 정하고 거리·방향 탭에 진입한다. 신규 세션에서는 자동차가 기본이다.
2. 목표 거리를 정한다. 출발점 중심으로 **반지름 D의 원 하나**를 표시한다. 원은 도로거리 등고선이 아니라 직선거리 참고선이다.
3. 지도에서 지점을 클릭하면 `targetRoadPoint`로 서버에 전달한다. 방위각도 계산하지만 실제 공급자 호출의 목적지는 이 좌표다.
4. 서버는 인증·요청 검증 후 동일 사용자/requestId 캐시를 확인한다. 신규 요청은 경제 설정에 따른 생성 토큰 처리를 한다.
5. Mapbox에 `[start, targetRoadPoint]`로 도로 경로를 한 번 요청한다.
6. 클릭 지점에서 해당 이동수단의 도로로 맞춘 거리가 250m를 초과하면 실패한다.
7. 도로거리와 목표거리 D를 비교하고 아래 표에 따라 처리한다.
8. 성공 결과를 기하 검증 후 반환한다. 프런트는 기존 경유지를 지우고 실제 종점·기하·거리·예상 시간을 공통 경로 상태에 적용한다.
9. 지도에는 생성된 경로가 준비된다. 사용자가 주행 시작 버튼을 눌러야 달리기 시작한다.

| 공급자 도로거리 L과 목표 D의 관계 | 처리 | 사용자 관점 |
|---|---|---|
| L < D−5m | `failed` | 클릭이 너무 가까움. 실제 도로거리·목표거리와 재선택 안내 |
| D−5m ≤ L ≤ D+150m | 우선 `exact`로 조립 | D까지 절단하거나, 기하 길이가 D보다 약간 짧아도 ±5m이면 원본 채택 |
| L > D+150m | `offered` | 클릭 지점까지 가지 않고 D 지점에서 종료하는 경로 제안·적용 |
| `exact` 조립 후 실제 끝과 스냅된 클릭점이 200m 초과 차이 | `offered`로 전환 | 목표거리를 맞췄어도 클릭점 도착으로 표현하지 않음 |
| 공급자 L은 조건을 만족하지만 기하 길이가 D−5m보다 짧음 | `shortfall` 가능 | 부족 거리 안내와 함께 짧은 실제 경로 적용 |
| 빈/한 점 기하, 절단 오류, 기하 검증 불통과 등 | `failed` | 경로 생성 실패 |

여기서 L은 Mapbox 응답의 `distance`, 절단·최종 자동 거리 계산은 좌표열의 구면 거리 합이다. 서로 다른 수치이므로 불일치 예외가 있다. `detoured`라는 응답 타입과 우회 코드는 남아 있지만, 현재 일반 클릭의 거리 판정이 모든 경우를 먼저 반환하므로 그 우회 분기는 도달하지 않는다.

### 기하 검증

자동 경로 최종 반환 전 다음 휴리스틱을 확인한다.

- 1km당 좌표 5개 이상.
- 가장 긴 좌표 사이 구간이 전체 길이의 35% 이하.
- 첫 좌표가 요청 출발점에서 300m 이하.

직선 가짜 경로 등을 막으려는 검사다. 실제 도로 데이터와 대조하는 검증은 아니므로 도로의 존재·안전성 전체를 보증하지 않는다. 출발·도착 서버에는 같은 검사가 없다.

## 4. 같은 조건으로 실행하면 어떻게 다른가

아래는 실제 지명 측정이 아닌, 코드 분기를 설명하기 위한 수치 예다. 두 방식의 이동수단과 공급자 응답은 같다고 가정한다.

| 조건 | 거리·방향: 목표 5km | Start/End: 클릭점을 End로 지정 |
|---|---|---|
| 클릭점까지 도로 8km | 앞 5km에서 끝나는 경로. 클릭점 도착 아님 | 클릭점까지 8km 전체 |
| 클릭점까지 도로 3km | 너무 가까움으로 실패. 2km 우회해서 채우지 않음 | 클릭점까지 3km 경로 |
| 클릭점까지 도로 5.10km | 대체로 앞 5km. 실제 종점과 클릭점 거리 등에 따라 결과 분류 달라짐 | 5.10km 전체 |
| 같은 동쪽 방향, 가까운 A·먼 B 클릭 | A는 실패하고 B는 성공할 수 있음. 도로 분기 때문에 앞부분도 달라질 수 있음 | A까지 경로와 B까지 경로를 각각 생성 |
| 기존 경유지 2개가 설정된 상태 | 자동 성공 시 경유지 제거, 두 점 기반으로 새 경로 적용 | 경유지 2개를 순서대로 통과하도록 요청 |

**체감 차이를 비교할 때는 반드시 이동수단을 동일하게 맞춰야 한다.** 거리·방향은 자동차, Start/End는 자전거로 계산하면 길이 절단 이외에 도로 선택부터 달라질 수 있다.

## 5. 토큰·서버 비용·실패 처리

### 사용자 토큰

두 방식 모두 `spendRouteGenerateToken`과 같은 경제 설정을 사용한다. **항상 1개 차감이라고 단정할 수 없다.** 코드 기본 `generateCostBase`는 현재 0이며, 실제 값은 Firestore `config/routeTokenEconomy` 설정으로 덮어쓸 수 있다. 운영 값을 이번에 읽지 않았으므로 실제 현재 요금은 미확인이다.

일반 자동 탐색이 처리된 실패(`searched.status === "failed"`)를 반환하면, 차감 비용이 양수인 경우 환불한다. Start/End도 공급자 응답 오류 등 명시된 실패 분기에 환불 처리가 있다. 서버 강제 종료·네트워크 예외·캐시 기록 실패까지 포함한 모든 실패에 무조건 환불된다고 보장하는 구조는 아니다. 특히 일반 Start/End의 실 Mapbox `fetch` 네트워크 예외는 개별 환불 블록을 거치지 않고 바깥 예외 처리로 넘어갈 수 있다.

자동 경로는 같은 사용자/requestId의 처리 결과를 `routeAutoRouteCache`에 저장해 재사용한다. 하지만 사용자가 다른 방향을 클릭하는 새 탐색은 새 requestId이므로 이전 성공의 무료 재요청이 아니다. Start/End도 차감 원장의 멱등 처리는 있으나 경로 응답 자체를 캐시하지는 않는다.

### 운영 비용

일반 지도 클릭 자동과 Start/End는 모두 통상 Directions 1회다. 자동은 결과 캐시 읽기·쓰기와 절단·검증·진단이 추가된다. 실제 과금 차이는 서버 실행 시간·캐시 적중·경제 설정 등에 달렸고 이번에 청구나 지연을 측정하지 않았다. Ready Ride의 후보 탐색 비용을 일반 거리·방향 클릭 비용으로 계산하면 과장된다.

## 6. 주행·저장에 미치는 영향

두 방식은 공통 `routeGeometry`·`routeDistanceMeters`·`profile` 상태에 합류하며 같은 `useVirtualRideSession`으로 주행한다. 경로 수단은 공급자 도로 탐색 옵션이고, 주행 속도 입력은 센서/체험 목표 속도에서 온다. 자동차 경로를 골랐다는 이유로 자동차 속도로 가상 주행하지 않는다.

자동 결과의 `duration`은 공급자 전체 예상 시간을 절단 비율만큼 줄인 값이다. Start/End는 공급자 전체 시간을 그대로 쓴다. 따라서 경로 요약의 예상 시간은 실제 센서 속도에 따른 운동 완료 시간 보장이 아니다.

저장 로직은 두 방식 모두 실제 기하·출발·도착·거리·예상 시간·수단·경유지 배열을 받는다. 목표 km·방향 클릭점·자동 outcome을 사용자 경로의 재생성 조건으로 따로 저장하지 않는다. 나중에 불러오면 생성된 기하를 불러오는 구조이며, 원래 목표와 방향을 다시 탐색하는 구조가 아니다. 자동은 실제 잘린 종점이 저장되고 경유지 배열은 비어 있다.

새 도로 적립은 실제 주행 구간에 좌우된다. 일반 자동이 이미 달린 길을 특별히 피해 주거나 중복을 모두 제거하지 않는다. 우회로 거리 채우기를 꺼 둔 것은 추가 중복을 줄이는 선택이며 신규 도로 최적화와는 구분해야 한다.

## 7. Ready Ride·간편 인터벌과의 구분

같은 `getDistanceAutoRoute` API 안에도 서로 다른 경로가 있다.

| 흐름 | 클릭점 | 방향 결정 | 특징 |
|---|---|---|---|
| 이번 조사 중심: 일반 거리·방향 | 사용자가 지정 | 그 클릭점까지 도로 요청 | 1회 Directions 후 절단/실패. Claim 후보 순위 없음 |
| Ready Ride 기본 편도 | 생략 | 서버가 방위 표본 탐색 | 출발 주변 Claim을 읽고 신규 도로·자기중복 등을 후보 순위에 반영. 호출 예산 13회인 별도 알고리즘 |
| `closeLoop: true` 요청 | 생략 | 서버 폐합 후보 탐색 | 루프 탐색·편도 대안 처리가 있는 별도 분기. 일반 거리·방향의 기본 동작이 아님 |
| 간편 인터벌 | 클라이언트가 가상 클릭점 생성 | 무작위 방향 최대 3회 시도 | 일반 `searchTowardPoint` 재사용. 사용자 지도 클릭 흐름과 진입 조건·목표거리 산정이 다름 |

알고리즘 버전 문자열 `5A-claim-score`는 API가 공유한다. 그 문자열만 보고 일반 클릭 경로에도 Claim 순위가 적용된다고 판단하면 안 된다.

## 8. 조사에서 확인한 한계·불일치

1. **「방향만 사용」이라는 옛 문구와 실행 계약의 차이.** `DISTANCE_AUTO_ROUTE_DIRECTION_HINT`에는 클릭 거리를 사용하지 않는다고 적혀 있지만 실제 코드는 클릭 좌표까지의 도로거리로 성공/실패를 판단한다. 현재 팝업의 활성 안내는 「N km 반경의 원 주변 도로를 선택하세요」다. 같은 방위의 어느 지점을 눌러도 동일 결과를 보장하는 기능이 아니다.
2. **±30°·±20%·35개 후보 상수를 현재 클릭 계약으로 읽으면 안 됨.** 웹/서버에 이전 후보 생성·선택 함수와 상수가 남아 있다. 일반 클릭은 그 후보 루프를 쓰지 않는다. ±20% 규칙과 Claim 순위는 Ready Ride 등 해당 호출 분기에 한정해 해석해야 한다.
3. **Start/End의 120km 상한 주석과 서버 구현 불일치.** 웹은 start→경유→end 직선 합 >120km를 차단한다. `routeLimits.ts`는 실제 거리 상한도 서버가 강제한다고 설명하지만, 현재 `getMapboxDirections`에는 공급자 실제 거리 >120km 응답을 거부하는 검사가 없다. 직선 100km·도로 140km 같은 경우가 제품 상한으로 확실히 막힌다고 볼 수 없다. 자동 API는 목표 입력 0.5~120km를 검증한다.
4. **성공 뒤 자동 재탐색 실패는 오류 안내가 약해질 수 있음.** `hasSuccessfulRoute`가 참이면 훅은 실패 상세 대신 재탐색 안내를 상태 문구로 유지한다. 호출자에게는 실패 메시지를 돌려주므로 실제 표시는 호출자 처리까지 구분해야 한다. 이전 성공 경로가 계속 남을 수 있다는 점을 함께 이해해야 한다.
5. **안전·풍경·고도·미주행 도로의 전역 최적화는 일반 클릭에 없음.** 공급자 도로 경로를 거리로 자르는 기능이며, 이런 추가 최적화를 수행한다고 볼 코드 근거가 없다.

위 사항은 조사 결과다. 이번에는 제품 동작·정책·설정을 수정하지 않았다.
