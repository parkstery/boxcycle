# Part A — Chief용 요약

## 문제

같은 Public Trail에서 두 창이 비슷한 속도로 달릴 때:

1. **창 간 순서 역전** — 한쪽 창에서는 A가 앞인데, 다른 창에서는 B가 앞처럼 보임.
2. **초당 서브미터 상대간격 진동** — 앞뒤 간격이 초당 여러 번 약 0.05–0.15m 폭으로 「툭툭」 흔들림(드문 수 m snap과 별개).

송신 주기를 올려 해결하지 말 것 · 기존 트래픽 정책(RTDB ~200ms · Firestore heartbeat 4s)을 지킬 것 · 같은 시각에 양쪽 창의 위치·순서가 맞을 것이 요구였다.

## 결론 (말할 수 있는 것 / 없는 것)

| 말할 수 있음 | 말할 수 없음 |
|---|---|
| 수신 시각으로 송신 축을 덮어쓰거나 창별 지연이 갈리면 **창 간 순서**가 깨진다. 공통 표시 시각(추정 서버 now − D=600ms)으로 self·peer·카메라가 맞으면 순서 불일치는 해소된다(제품 구현 + 하네스 + **사용자 실주행 PASS**). | stall·미도착·큰 clock jump 구간까지 「항상 완벽 동기」라고 말할 수 없다. |
| 실측 paired JSON에서 running 구간 **1s gap peak-to-peak ≈ 0.05–0.15m**, wire 거리 **0.1m 격자**. 합성 등속 재생에서 quantum **0.1→0.01m** 시 1s-pp **0.100→0.008m**(−92%). | 합성 수치를 실측 전후 체감 숫자로 대체할 수 없다. 원본 0.1m 반올림 전 거리는 복구 불가. |
| 송신 횟수·주기 불변. encode JSON UTF-8 평균 **+0.888 B/패킷**, 5Hz·1rider·1h **+15 984 B ≈ 16 KB/h**(JSON only). | 네트워크 overhead·수신자 fanout·Firebase billed 달러는 미측정. |
| **Chief/사용자 실주행 PASS**(2026-10-05 진술). 상세 통합·main2/main 반영은 TASK-39. | Firebase/Vercel **수동 배포는 범위 밖**. push 연동 자동배포 여부는 환경에 따름. |

## 적용한 핵심 변경

1. **송신 시각축 보존** — 도착 시각으로 ingest stamp를 덮지 않고, 단일·이중 소스 정규화축을 통일.
2. **공통 표시 시계** — companion에서 self·peer·카메라가 추정 서버 시각의 **D=600ms** 과거를 공유. solo는 D=0. HUD 속도/거리·Claim은 **즉시 실제값**.
3. **optional `tSrv`** — 캡처 순간 추정 서버 시각. 기존 `t` 유지. Rules optional number.
4. **RTDB↔FS estimated bridge** — FS fallback을 `quality=estimated`로 구분, 권위 anchor 오염 방지.
5. **wire 거리 양자 0.1→0.01m** — encode와 selfDisplayBuffer가 동일 canonical. 송신 주기·D600·FS4s **불변**.
6. **진단 capture** — 20초 표본 보존·완료 export·40ms 저장 간격(프레임 dt와 분리).

## 2. 시간축 / receive 재기준화 · tSrv · common 600ms

### 2.1 실패했던 축

- 패킷이 도착한 **로컬 시각**으로 송신 시각을 덮으면, 같은 물리 구간이 창마다 다른 타임라인에 붙는다.
- self를 즉시, peer만 과거로 그리면 창마다 「누가 앞」이 갈라진다.
- 창별 EMA로 D를 고르면 두 창의 표시 시각이 더 벌어진다.

### 2.2 채택 모델 (**C** + **S**)

```text
commonNow ≈ localNow + serverTimeOffset   (.info/serverTimeOffset)
renderTime = commonNow − D                (companion D=600ms, solo D=0)
self · peer · camera 가 같은 frame renderTime 소비
HUD / Claim = 즉시 실제값 (이 시계 밖)
optional tSrv = 캡처 순간의 estimateServerNowMs (encode 재샘플 금지)
기존 client t 유지 (B안: t 의미 변경 거부)
```

핵심 파일:

- `apps/web/src/lib/peerMotion/commonDisplayClock.ts` — `COMMON_COMPANION_DISPLAY_DELAY_MS = 600`
- `apps/web/src/lib/peerMotion/repo/serverClockOffset.ts`
- `apps/web/src/lib/peerMotion/selfDisplayBuffer.ts`
- `apps/web/src/lib/peerMotion/PeerMotionRegistry.ts` — frame 공통 시각
- `apps/web/src/lib/peerMotion/syncFromPresence.ts` — ingest 축·diag
- `apps/web/src/lib/ride/publishLiveLocationFanout.ts` · `liveLocationSnapshot.ts` — tSrv 캡처·self 표본

### 2.3 트래픽 정책 유지

| 정책 | 값 | 비고 |
|------|-----|------|
| RTDB motion 목표 | ~200ms (5Hz) | 송신 횟수 증분 없음 |
| Firestore live heartbeat | 4s | fallback 품질 검증 후 유지 |
| Rules | `tSrv` optional number | schema 대변경 없음 |

## 3. RTDB ↔ FS estimated bridge · authority

- RTDB가 권위 motion. FS는 공백·장애 시 보조.
- FS 추정 시각은 내부 `quality=estimated` — capture/diag와 권위 anchor를 섞지 않음.
- RTDB→FS 전환 시 버퍼 clear로 생기던 frame jump는 residual 작업에서 **3.181→0.058m**, axisFlip **2→0** (합성/하네스, 30).
- publication\|uid 경계·late anchor 방어 유지.
- **전체 residual pp**(등속 공백 1.238m · 정지 2.136m · 가속 10.965m)는 **미해결 정확도 한계**로 남음 — 「소스 전환 결함 수정」과 「전 구간 smoothness」를 혼동하지 말 것.

## 4. 양자화 0.1 → 0.01m

### 4.1 실측 (**P**)

- 원본 복사(UID 익명화): `document/ops/20261005-peer-spacing-jitter/evidence/real-paired-20261005/rider_{A,B}.json`
- running `relativeGapM` 1s-pp ≈ **0.05–0.15m**; 창 간 Agap+Bgap≈0 유지.
- wire dist 전부 **0.1m 격자**. dGap 주기 중앙값 ~250–300ms ≈ RTDB 발행.
- 당시 capture meta는 idle(legacy ring240) — 완료 20s 아님. 종료/hold 구간은 주행 진동과 분리.

### 4.2 합성 (**S**) — 제품 encode/self/Registry

| | quantum 0.1 | quantum 0.01 |
|--|-------------|--------------|
| mean 1s-pp | **0.1000 m** | **0.0080 m** |
| reduction | — | **0.92** |

- phase∈{0,40,80,120,160}ms × speed∈{5,6,20}km/h: after 1s-pp ≤ before (악화 없음).
- PNG: `evidence/.../graphs/quantize-beat-synthetic-compare.png` · `observed-running-gap.png`

## 9. 재발 시 20초 진단 절차

1. 양쪽 창 hard refresh · 동일 Trail · 독립 UID · 약 5–6 km/h · 20초.
2. 각 창: `await window.__rtwPeerIngestDiag.capture(20)` → `download()` (`payloadSource=last-completed` 확인).
3. 분리해서 볼 것: **UID** · **phase**(running/hold) · **source**(rtdb/fs) · **quality**(estimated?) · **wire dist 격자** · **relativeGapM 시계열**.
4. **raw vs rendered**: raw gap/jump가 매끄러운데 화면만 튀면 GLB/camera; raw가 톱니면 wire/integrator/clock.
5. 시각맞춤: 두 JSON의 atMs를 다운로드 시각으로 억지 정렬하지 말 것 — 중첩 구간·server offset·tSrv를 본다.
6. 회귀: `test:peer-spacing` + quantize mutation + common-display. 송신 주기부터 올리지 말 것.
