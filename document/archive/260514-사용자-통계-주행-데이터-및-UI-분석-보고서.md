## 1. 목적과 범위

### 1.1 목적

- 앱에서 **사용자에게 노출되는 주행 통계**(주간·월간·연간)가 **어떤 데이터**를 근거로 하고, **어떤 규칙**으로 집계되는지 한곳에 정리한다.
- 이후 **Oracle Cloud PostgreSQL** 등 백엔드 통계 API로 이전할 때, **동일 지표를 재현**하기 위한 기준 문서로 쓴다.

### 1.2 범위

| 포함 | 제외 |
|------|------|
| 클라이언트 `StoredRideSession` 모델 | 서버 측 집계 API(아직 없음) |
| Firestore `rides` 저장·조회(통계용 400건) | `savedRoutes`, `courses` 등 다른 컬렉션 통계 |
| `rideStatsAggregate` 기간·집계 수식 | `RideHistoryPanel` 전용 화면(메뉴 내 목록) 상세 UX |
| `UserInfoSheet` 내 통계 탭·로딩·폴백 | 닉네임·프로필(`users` 문서) 통계 |

## 2. 사용자에게 보이는 통계 UI

### 2.1 진입 경로

- **맵 HUD** 우상단 계정 영역 → 사용자 정보 시트(`UserInfoSheet`) 슬라이드 인.
- 라이딩 잠금 시 시트는 열리지 않음(`App.tsx`에서 `open={userInfoSheetOpen && !rideLocked}`).

### 2.2 UI 구성(통계 구간)

| 요소 | 설명 |
|------|------|
| 탭 | **주간** / **월간** / **연간** (`RideStatsPeriod`: `week` \| `month` \| `year`) |
| 기간 라벨 | 선택 탭에 대응하는 한국어 날짜 범위 문구(`periodStats.range.labelKo`) |
| 지표 4칸 | **주행**(건수), **거리**(km), **시간**(h/m), **평속**(km/h) |
| 칼로리 | 별도 한 줄: 기간 내 `caloriesEstimate` 합의 반올림(kcal) |
| 안내 문구 | 데이터 소스 한계·폴백 시 노란색 계열 노트(`statsLoadNote`) |

### 2.3 “최근 주행” 블록과의 관계

- 시트 하단 **최근 주행**은 부모가 넘기는 `recentSessions`만 사용한다(최대 8줄 표시).
- **통계 탭**은 별도 상태 `statsSessions`로 집계한다.
- 따라서 **통계에 쓰인 건수**와 **목록에 표시되는 건수·출처**가 다를 수 있다(아래 4절).

## 3. 원천 데이터 모델

### 3.1 클라이언트 공통 타입 — `StoredRideSession`

파일: `apps/web/src/lib/rideSessionsStorage.ts`

| 필드 | 타입 | 통계에서의 역할 |
|------|------|------------------|
| `id` | `string` | 식별. Firestore 문서 ID 또는 로컬 생성 ID |
| `endedAt` | ISO 문자열 | **기간 필터의 기준 시각**(주/월/년 경계와 비교) |
| `elapsedSec` | `number` | 시간 합산, 평속 분모(초) |
| `distanceMeters` | `number` | 거리 합산, 평속 분자(km 환산) |
| `avgSpeedKmh` | `number` | **통계 평속에는 미사용**(기간 합산으로 재계산) |
| `caloriesEstimate` | `number` | 칼로리 합산 |
| `routeDistanceMeters` | `number` | 통계 집계 미사용(경로 메타) |
| `routeDurationSec` | `number` | 통계 집계 미사용 |
| `userRouteId` | `string \| null` | 통계 집계 미사용 |
| `routeName` | `string \| null` | 통계 집계 미사용 |
| `completionRatio` | `number` (0~1) | 통계 집계 미사용(완주율은 목록·격상 로직에서 사용) |

### 3.2 Firestore 문서 — `rides` 컬렉션

파일: `apps/web/src/lib/firestoreRides.ts` 내부 `RideDoc`

클라이언트 세션에 더해 서버 메타가 있다.

| 필드 | 비고 |
|------|------|
| `userId` | 쿼리 키 |
| `roomId`, `courseId` | 현재 저장 시 `courseId`는 null 고정 |
| `profile` | `cycling` \| `driving` \| `walking` — 저장되나 **통계 UI에서는 프로필별 분리 없음** |
| `startedAt` | 현재 null로 저장 |
| `source`, `status` | `web`, `completed` |
| `createdAt`, `updatedAt` | 서버 타임스탬프 |

통계 집계는 **`endedAt` 기준**이며, Firestore에서 읽어온 뒤 `StoredRideSession`으로 정규화된다.

### 3.3 칼로리 산출(주행 종료 시점)

파일: `apps/web/src/App.tsx` (주행 종료 처리부)

- 세션에 넣는 값: `Math.round((virtualDistanceKm) * 30)` 형태의 **추정치**(거리 km × 30).
- 통계 화면에서는 기간 내 세션의 **`caloriesEstimate` 합**을 표시한다.
- 의학·대사 모델이 아닌 **단순 휴리스틱**임을 제품 설명 시 명시하는 것이 좋다.

## 4. 데이터 적재·로딩 경로

### 4.1 저장(클라우드)

- 로그인(또는 Firebase 익명) 사용자 + Firebase 설정이 있을 때, 주행 종료 시 `saveRideSessionToFirestore`로 `rides`에 `addDoc`.
- 동시에 로컬 `localStorage`에도 최근 50건까지 유지(`rideSessionsStorage`).

### 4.2 통계 전용 로드 — `loadRideSessionsForStatsFromFirestore`

- 쿼리: `where("userId", "==", uid)` + `orderBy("endedAt", "desc")` + `limit(기본 400)`.
- **최근 400건**만 통계 집계에 사용한다.
- `loadRecentRideSessionsFromFirestore(limit)`는 내부적으로 동일 쿼리에 **다른 limit**(기본 50)만 적용한다.

### 4.3 `UserInfoSheet`에서의 `statsSessions` 채우기

시트가 열릴 때(`open === true`) `user.uid`가 있으면:

1. **Firebase 미설정** → `statsSessions = recentSessions`, 노트: 클라우드 미설정.
2. **설정됨** → Firestore에서 최대 400건 로드 시도.
   - 성공 시: 400건이 꽉 차면 “400건까지만” 노트.
   - 실패 시: `recentSessions`로 폴백 + 실패 노트.

의존성: `recentSessions[0]?.id`가 바뀌면 재조회(새 주행 반영 목적).

### 4.4 한계(현재 설계에서 반드시 알려야 할 점)

| 한계 | 영향 |
|------|------|
| **상한 400건** | 누적 주행이 많으면 **올해·이번 달 통계가 과소**일 수 있음 |
| **기간 경계 = 기기 로컬** | `rideStatsAggregate`는 `Date`의 로컬 getter 사용. **IANA 타임존 문자열**은 아직 반영하지 않음 |
| **연간 라벨** | “올해 1/1~12/31” 문구이나 실제 필터는 **올해 1월 1일 00:00 ~ 내년 1월 1일 00:00 미만** |
| **주 시작 요일** | **월요일 00:00** 기준(일요일이면 전주 월요일로 이동) |
| **프로필 혼합** | 자전거·도보·운전 세션이 한 사용자에 섞이면 **한 버킷에 합산**됨 |

## 5. 집계 로직 상세 — `rideStatsAggregate.ts`

### 5.1 기간 경계 정의

모두 **`now` 인자의 기본값 = `new Date()`**(호출부에서 넘기지 않음) → **사용자 기기 로컬 타임존**에서 연·월·일·요일이 해석된다.

| 기간 | 시작 | 끝(배타) |
|------|------|-----------|
| 주간 | 해당 주 **월요일** 00:00:00.000 | 그로부터 **7일 뒤** 00:00:00.000 |
| 월간 | 해당 달 1일 00:00:00.000 | **다음 달** 1일 00:00:00.000 |
| 연간 | 해당 연도 1월 1일 00:00:00.000 | **다음 해** 1월 1일 00:00:00.000 |

세션 포함 조건:

`endedAt` 파싱 타임스탬프 `t`에 대해 `start <= t < endExclusive` (반개구간).

### 5.2 집계 지표 수식

입력: 기간에 포함된 세션 집합 `filtered`.

| 지표 | 수식 |
|------|------|
| `rides` | `filtered.length` |
| `distanceMeters` | `sum(distanceMeters)` |
| `elapsedSec` | `sum(elapsedSec)` |
| `caloriesEstimate` | `sum(Number(caloriesEstimate ?? 0))` |
| `avgSpeedKmh` | `(sum(distanceMeters)/1000) / (sum(elapsedSec)/3600)` — 합계 거리·합계 시간으로 **전체 평균 속도** 재계산. `elapsedSec === 0`이면 0 |

**주의:** 개별 세션의 `avgSpeedKmh` 평균이 아니다. “그 기간 전체를 한 번에 탄 것처럼” 본 평균 속도다.

### 5.3 라벨 문자열(`labelKo`)

- **주간**: 시작·끝 날짜를 `toLocaleDateString("ko-KR", { month: "numeric", day: "numeric" })`로 표시.
- **월간**: `N년 M월 (시작일 ~ 말일)` 형태.
- **연간**: `N년 1월 1일 ~ 12월 31일` 고정 문구(실제 필터는 연도 경계와 일치).

## 6. 파일·컴포넌트 의존 그래프(요약)

```
App.tsx
  └─ recentSessions (최대 50 로컬 + Firestore 동기)
       └─ UserInfoSheet props.recentSessions  ── 폴백·최근 주행 목록

UserInfoSheet.tsx
  └─ statsSessions ← loadRideSessionsForStatsFromFirestore(uid, 400)
       └─ aggregateRideStatsForPeriod(statsSessions, statsPeriod)
            └─ rideStatsAggregate.ts

firestoreRides.ts
  └─ rides 컬렉션 read/write

rideSessionsStorage.ts
  └─ StoredRideSession 타입 + localStorage
```

## 7. 다른 화면과의 비교

| 화면·기능 | 데이터 소스 | 상한 |
|-----------|--------------|------|
| `UserInfoSheet` 통계 | `statsSessions`(Firestore 우선 400) | 400 |
| `UserInfoSheet` 최근 주행 목록 | `recentSessions` | 부모가 유지(앱에서는 50) |
| `RideHistoryPanel`(메뉴) | Firestore `loadRecent…(50)` 또는 로컬 | 50 |

통계와 “전체 기록”을 동일하게 보여주려면 **백엔드 페이지네이션 또는 일별 롤업 테이블**이 필요하다.

## 8. 향후 개선 방향(요약)

아래는 [Firestore Postgres 이전 체크리스트](260509-Firestore-Postgres-이전-체크리스트.md) 및 기존 아키텍처 논의와 정합되도록 정리한 권고다.

1. **상한 제거 또는 롤업**: `ride_daily_rollup` 등으로 서버에서 주·월·년을 미리 합산하고, 클라이언트는 API만 호출.
2. **타임존**: 제품 정책대로 `Intl`의 IANA 타임존을 쿼리 파라미터로 넘겨 서버에서 `AT TIME ZONE` 처리.
3. **프로필 분리**: `profile === "cycling"`만 통계에 넣을지, 탭으로 나눌지 정책 결정.
4. **완주율·코스 차원**: `completionRatio`, `userRouteId`를 활용한 “완주 비율”“자주 탄 코스” 등 2차 지표.
5. **칼로리**: 식별 가능한 모델명·공식을 문서화하거나 서버에서 일관 산출.
