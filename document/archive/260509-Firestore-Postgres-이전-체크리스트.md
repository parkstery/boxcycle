# Firestore → Postgres 이전이 힘들어지는 스키마 피하기

본 프로젝트는 **초기에 Firebase로 서비스를 검증**한 뒤 PostgreSQL 등으로 분리할 계획이다. Firestore에 두었다가 나중에 옮길 때 **특히 꼬이기 쉬운 패턴**만 체크리스트로 정리했다. 아래를 지키면 이전 스크립트·스키마 설계 부담이 줄어든다.

---

## 문서 구조·크기

- [ ] **한 문서에 배열이 무한정 쌓이게 설계하지 않기**  
  예: `ride.samples[]`에 초 단위 포인트를 전부 넣음 → 문서 크기 한계에 가깝고, Postgres로는 행 단위로 쪼개야 해서 이전 스크립트가 무거워진다.  
  → 샘플은 **서브컬렉션 `rides/{id}/samples`** 또는 처음부터 **별도 컬렉션 + `rideId`**로 분리한다.

- [ ] **깊은 중첩 객체(map 안의 map 안의 map)**로 비즈니스 데이터를 넣지 않기  
  Postgres는 **평탄한 테이블 + 조인**이 자연스럽다. 3단 이상 중첩은 `JSONB`로 몰리기 쉽고, 쿼리·인덱스·마이그레이션이 불편해진다.

- [ ] **“문서 하나 = 여러 엔티티”**로 합치지 않기  
  예: `user` 문서 안에 `courses[]`, `sessions[]`, `coinsLedger[]`를 모두 넣기.  
  → 이후 `users`, `courses`, `rides`, `ledger` 테이블로 쪼개는 비용이 커진다.

---

## ID·참조·정합성

- [ ] **비즈니스 키를 문서 ID로만 쓰지 않기** (또는 반드시 문서 내부 `id` 필드에도 동일 값을 둔다)  
  예: 이메일을 docId로 사용한 뒤 이메일 변경이 가능해지는 경우.  
  → **불변 UUID**를 `userId`로 두고, 이메일은 일반 필드로 둔다.

- [ ] **다른 문서를 가리킬 때는 항상 `userId`, `courseId` 같은 명시적 FK 필드**를 둔다  
  컬렉션 경로만으로 관계를 추론하게 만들지 않는다 (이전 스크립트가 경로 파싱에 의존하면 깨지기 쉽다).

- [ ] **“어디가 진실(source of truth)인지” 한 곳만 정한다**  
  같은 값을 여러 문서에 중복 저장할 경우, 업데이트 규칙을 문서화해 두지 않으면 Postgres 이전 후 정합성 정리가 필요해진다.

---

## 쓰기 패턴·비용·이전 난이도

- [ ] **단일 문서에 고빈도 업데이트**를 넣지 않기  
  예: `presence/{courseId}` 한 장에 `positions` 맵을 1초마다 패치.  
  → Postgres에서는 보통 **세션 행 + 최근 위치** 또는 **캐시 계층(Redis 등)** 설계가 자연스럽다. Firestore에만 두면 비용·보안 규칙·이전 경로가 모두 애매해진다.

- [ ] **전역 카운터 한 문서** (`stats/totalRides` 등)에 트래픽이 몰리게 설계하지 않기  
  → 핫스팟이 되고, 이전 후에도 단일 행 병목이 된다. 집계는 **배치·서버·함수**로 분리하는 편이 낫다.

---

## 지리·경로 데이터

- [ ] **GeoJSON 전체를 “의미 없는 문자열 한 방”에만 넣고 끝내지 않기** (길이·검색·검증이 필요하면)  
  Firestore `GeoPoint`는 **점** 위주다. **LineString** 길이·스냅·PostGIS 이전 시 다시 파싱·검증이 필요해진다.  
  → 최소한 **`geometry`는 구조화된 GeoJSON 객체**로 두고, **`distanceM`, `bounds`** 같은 요약 필드를 같이 둔다.

- [ ] **좌표 배열의 순서가 경로 의미**라면, 순서 보존이 명확한 필드명·스키마로 둔다 (인덱스 전략과 함께 문서화).

---

## 쿼리·인덱스 전제

- [ ] **Firestore 복합 인덱스에만 의존하는 독특한 쿼리 패턴**을 제품 핵심으로만 고정하지 않기  
  Postgres에서는 인덱스·뷰 표현이 달라질 수 있다. **도메인 필터**는 명시적 필드로 (`courseType`, `regionCode`, `publishedAt` 등).

- [ ] **“배열 contains + range + orderBy” 같은 복잡 조합**만으로 핵심 목록 조회를 설계하지 않기  
  SQL로 옮길 때 인덱스 설계가 달라진다.

---

## 보안 규칙에만 녹인 비즈니스 로직

- [ ] **코인 차감·구독 상태 같은 경제 로직을 “클라이언트 + 규칙”만으로 끝내지 않기**  
  이전 시 **서버 트랜잭션**으로 반드시 다시 짜야 한다. 가능하면 처음부터 **Cloud Functions / 백엔드**에서만 잔액을 변경한다.

---

## 서브컬렉션·export

- [ ] **나중에 “전체 스캔·백필”이 필요한 데이터를 깊은 서브컬렉션에만 두지 않기**  
  예: `users/{uid}/rides/{rideId}`만 있고 목록용 top-level이 없음 → export·이전 시 전 사용자 순회 비용이 커진다.  
  → 운영·리스트에 필요하면 **`rides` top-level + `userId`**를 고려한다.

---

## 타입·시간

- [ ] **날짜는 `Timestamp` 타입으로 통일**한다 (문자열 ISO와 혼용 최소화).  
  → Postgres `timestamptz` 매핑이 단순해진다.

- [ ] **금액·코인은 정수 최소 단위**로 저장한다 (부동소수 `double`로 코인 저장은 지양).

---

## 한 줄 요약

**큰 배열·깊은 중첩·한 문서 고빈도 패치·규칙만 믿는 경제 로직·경로 전체를 구조 없이 한 필드에만** 두는 패턴을 피하면 Firestore → Postgres 이전이 훨씬 수월하다.
