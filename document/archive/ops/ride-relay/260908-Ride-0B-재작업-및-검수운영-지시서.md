## 1. 실행 명령

Grok 개발팀장은 아래 제품 결함과 원지시서의 미충족 게이트를 직접 구현·시험하고 같은 PR에 제출한다. placeholder 정리는 종료된 항목이다. 함수 추출이나 시험 개수 증가를 계약 충족으로 보고하지 않는다. 현재 판정은 PARTIAL이며 PR Draft, main2 병합 및 1단계 착수 보류를 유지한다. 원지시서 §6 C1~C14 번호·의미를 변경하거나 범위 밖으로 제외하지 않는다.

## 2. 다음 구현 순서와 수용 조건

### R1 — F2 종료·저장·재개 거리 변환

`useRideEndAndPersistence`의 진행률 분모는 routeDistanceMeters이고 App의 재개 offset은 geometry 길이를 곱한다. 운동 적분 기준과 geometry 좌표 기준을 구분한 adapter로 전체 왕복을 일치시켜라. 단순히 모든 계산을 geometry 길이로 바꾸지 말고 기존 저장 진행률 호환 및 운동·완주 정책을 유지한다.

- 재현: routeDistance=1000, geometry=1200, 종료 운동 offset=500이면 저장 비율 0.5를 운동 offset 600으로 재개해서는 안 된다. geometry상의 대응 위치와 운동 offset의 단위 차이는 명시한다.
- 실제 종료→저장→로드→카드→준비→Go 경계를 호출하는 시험으로 980/1000 및 반대 관계, 정상 길이를 검증한다. 기대값은 독립적인 거리/좌표 계산으로 산정한다.
- 31%→43% 세션 구간, 처음부터 20% 종료와 기존 최대 43% 재개 분리, 0.97/0.98 정책, 삭제/geometry 없음도 원 C4~C7대로 검증한다.

### R2 — F4 저장 상태와 화면

- Ride 저장의 반환 실패와 throw/reject를 모두 처리하여 pending이 영구히 남지 않게 한다. 어느 작업에서 발생한 예외인지 분리하고 해당 상태축만 정확히 변경한다.
- Ride 저장 성공+경로 진행률 실패, Ride 저장 실패, 경로 진행률 n/a를 실제 persistence 경로에 실패 주입하여 시험한다. 재시도 가능 여부와 기록 보존을 입증한다.
- `RideSummarySheet`의 저장 완료 문구를 실제 저장 상태에 연결한다. 미확정·실패를 성공으로 표시하지 않는다.
- `isDiscardableRideRecord`/`isRouteCompletion` 호출만으로 F4/C10 시험을 대체하지 않는다. production hook/service와 소비 UI까지 상태 전이를 확인한다.

### R3 — F5 스냅샷과 비동기 결과 소유권

- uid/localRecordId/serverRideId와 결과 세대 또는 동등한 식별자를 사용해 활성 결과만 갱신한다. closure의 구독 ID와 그 구독 문서 ID 비교만으로 활성 결과 검사를 대체하지 않는다.
- A→B 전환 직후 B 응답 전에도 A 값이 B에 표시되지 않도록 결과를 키와 묶거나 초기화한다. unsubscribe와 별도로 늦은 성공/오류 콜백과 저장 응답 적용 조건을 검증한다.
- 종료 시 session geometry/profile/anchor/지명/연결 ID를 복사·고정하고 이후 Route 변경과 계정 전환에 영향받지 않게 한다. 종료 원본 샘플과 UI throttle 사이의 C14도 입증한다.
- 실제 hook/service에 제어 가능한 지연 응답을 주입해 A→B, 계정 A→B, 닫기, unmount 및 반복 열기/닫기를 시험한다. 단순 문자열 equality 시험으로 C11/C12를 대체하지 않는다.

### R4 — F3 Conquest 상태 계약 잔여

- newMeters 없음과 확정 0을 구분한다. 숫자 타입·유한성·음수를 검사하며 null/boolean/문자열을 Number로 강제 변환하여 확정 결과로 만들지 않는다.
- 원지시서의 15초 지연/60초 구독 종료, timer 정리, 동일 문서 조회 재시도를 검증한다. 조회 재시도에서 Ride를 다시 생성하지 않는다.
- C8/C9/C12를 실제 parser·구독 수명에 연결한다. 다른 Ride의 누적 계정 증가가 현재 결과에 영향을 주지 않게 한다.

### R5 — F1 회귀 및 emulator 증거

- 이미 보완한 legacy 동일 ID 및 신규 serverRideId 병합을 유지한다. 실제 서버 조회 형태와 저장 대기 중 다음 Ride를 포함해 C1~C3 회귀를 실행한다.
- 원지시서 §7 및 ride-verify 스킬의 기존 하네스를 사용한다. Guest 진입 timeout은 인증·서버·포트·로그·selector 원인을 좁혀 수정하고 인증 우회나 실 Firebase 접속으로 통과시키지 않는다.
- 대표 유효 Ride의 저장→서버 ID→실제 Cloud Function 집계→해당 문서 결과 수신을 emulator에서 입증한다. fixture 주입 시험은 실제 CF 시험과 별도 표기한다.
- C13 결과 닫기→다음 주행→Go를 reload 없이 검증한다. 5분 무진전이면 기존 지침대로 진단 후 검증 경로를 전환한다.

## 3. 제출 형식

최종 HEAD, 변경 파일/심볼, 실행 명령·종료 코드·PASS/FAIL/SKIP 수, 재현 fixture와 실제 관측값, C1~C14 원번호별 시험 위치와 로그를 제출한다. 관련 build/next-ride/selectors/주행·continuation 검증도 포함한다. emulator 프로젝트·호스트와 실행 로그를 식별 가능하게 남기되 자격증명은 기록하지 않는다. 보고서는 실제 날짜 접두어로 document/archive에 작성한다.

테스트 파일에 production 함수를 import했다는 사실과 해당 계약을 검증했다는 사실을 분리한다. 인라인 모사·무관한 leaf 시험·skip·미실행은 필수 게이트 PASS의 근거가 아니다. root lockfile 및 관계없는 변경을 섞지 않는다.

## 4. 자동 협업 운영

- Grok: 구현·자체 시험·같은 PR 제출 담당. Codex: HEAD 고정·독립 검수·다음 재작업 지시 담당. 사용자를 반복 지시 전달자로 삼지 않는다.
- 직접 전송 채널이 확인된 뒤 supervisor는 이 범위의 재작업 지시를 추가 허락 없이 전달한다. 전송 성공과 수신 대상은 확인하고 기록한다. 채널이 연결되지 않았다면 문서 작성과 실제 전달을 혼동하지 않는다.
- supervisor는 새 HEAD 또는 새 증거가 있을 때 재검수하고 미통과 항목을 같은 지시서 기준으로 돌려준다. 변화 없는 상태에서 동일 지시를 반복 발송하지 않는다.
- 자동 재검수는 0B에 한정한다. C1~C14 및 §7 필수 검증, 제품 결함 해소와 제출 증거가 모두 확인되면 0B 완료 및 1단계 착수 가능 판정을 사용자에게 보고하고 자동화를 중지한다. 원격 병합·배포·1단계 구현은 자동으로 수행하지 않는다.
- 필수 권한/연결 정보 부재나 범위·정책 변경이 필요한 경우만 사용자의 결정을 요청한다. 도구 실행 완료 배지는 제품 완료 판정이 아니다.
