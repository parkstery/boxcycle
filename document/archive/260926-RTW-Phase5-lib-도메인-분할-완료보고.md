## 3. 세 미결을 실측으로 결론냈다

Phase 4 완료보고 §9 가 남긴 미결 셋이다. **추정이 아니라 의존 그래프로** 답했다.

### ① Trail 은 Ride 의 하위가 아니다

**`trail/` → `ride/` 직접 import 가 0건.** Trail 은 주행보다 먼저 존재하는 **맥락**이고
(`atTrailheadIdle`), Ride 의 형제다.

다만 조건이 붙는다 — `trail/repo` 가 Ride 의 정책·스키마를 import 하면 화살표가 `trail/` 에서
`trail/repo/` 로 **옮겨간 것**일 뿐 결합은 그대로다. 그래서 repo 는 **Trail 이 소유한 좁은
읽기 모델만** 반환하고, 게이트가 `trail/repo → ride/**` 도 위반으로 센다.

### ② Conquest ↔ Route — 끊지 않고 뒤집었다

경로 생성이 Claim 을 읽는 것은 **제품 요구 그 자체**다(`distanceAutoRouteHttp.ts:503`
「출발점 주변 Claim만 읽어 신규도로·자기중복으로 순위(탈락 아님)」). 끊으면 기능이 사라진다.

코어가 `ClaimReader` 계약을 선언하고 Conquest 가 구현하며 `…Http` 가 조립한다.
**실측해 보니 코어는 이미 `claimedCellIds` 를 입력으로 받고 있었다** — 방향은 옳았고,
진짜 위험은 다른 데 있었다(§4).

### ③ Firebase — 도메인 안도 밖도 아니다. 두 층이다

`firestore*.ts` 25개는 인프라가 아니라 **Repository** 였다. 이미 도메인 로직을 **수입**하고
있었다(`firestoreRides → rideRecordPolicy` 등, 되짚어 올라가는 화살표 30건 이상).

```
lib/firebase/        순수 인프라 — app · converters · functionsEmulatorUrl
lib/<도메인>/repo/    도메인을 아는 저장소
```

양자택일(「전부 몰기」 vs 「도메인 안」)이 틀린 질문이었다.

## 5. 순환은 폴더 이동이 끊어주지 않았다

감사 보고서 §8 은 「도메인 폴더로 나누면 순환 4쌍이 자연 해소된다」고 적었다.
**두 번 확인했고 두 번 다 사실이 아니었다.**

- 실측 순환은 **3쌍**(1쌍은 Phase 3 에서 이미 해소)
- 저장소 25개를 도메인 폴더로 옮긴 **직후에도 3쌍 그대로**였다

끊은 것은 **타입의 위치**였다. 세 순환 모두 한쪽은 **타입만**, 반대쪽은 **함수**를 가져갔다.

| 순환 | 실체 | 해소 |
|---|---|---|
| `trailAccessPolicy ↔ …Instance ↔ …OpenTrailListings` | 정책이 저장소에서 **타입**을 가져옴 | `trail/trailTypes` 로 타입을 내림 |
| `rtdbTrailMotion ↔ …LivePublicationRides` | 저장소끼리 **타입**을 주고받음 | 〃 |
| `activityWorldLod ↔ rideSyncPolicy` | **양쪽 다 오배치** — `haversineMeters` 는 지리 계산, LOD 상수 re-export 는 **소비자 0** | `geo` 로 모으고 re-export 삭제 |

> 저장소는 종전 이름으로 re-export 하되 **`lib/` 안의 소비자는 타입 모듈을 직접** 보게 했다.
> 호환 re-export 를 경유하면 순환이 그대로 살아남는다.

## 6. 같은 오배치가 다섯 번 나왔다

「이 값이 왜 여기 있지」가 계속 반복됐다. 패턴이 하나다 — **어떤 모듈이 필요로 했기 때문에
그 모듈 옆에 놓였고, 그래서 아래 층이 위 층을 올려다보게 됐다.**

| 무엇이 | 어디 있었나 | 어디로 | 없앤 것 |
|---|---|---|---|
| `haversineMeters` (사본 3개) | `rideSyncPolicy` · `routeGeometryMidpoint` | `geo` | 순환 ①의 절반 |
| `ACTIVITY_WORLD_POLL_*` | `rideSyncPolicy` | `activity` | `activity → ride` |
| `PEER_INTERP_*` 등 전송 상수 7개 | `rideSyncPolicy` | `peerMotion` | `peerMotion → ride` |
| `sanitizeTrailId` · `DEFAULT_TRAIL_ID` | `trail/repo/firestoreTrail` | `trail/trailId` | `peerMotion`·`ride → trail/repo` |
| **`lastSeenAtToMillis`** | `trail/repo/firestoreTrail` | **`firebase/converters`** | 네 도메인의 저장소가 Trail 저장소를 import 하던 것 |

마지막은 감사 §8 의 목표 구조가 `lib/firebase/converters.ts` 를 적어 둔 바로 그 자리다 —
Timestamp 를 밀리초로 바꾸는 일에 Trail 은 아무 상관이 없다.

> ⚠️ **옮기는 일에 재작성을 섞을 뻔했다.** `lastSeenAtToMillis` 를 「깔끔하게」 다시 쓴 초안이
> 원본의 **nanoseconds 합산**과 **`< 1e12` 는 초 단위** 해석을 빠뜨렸다. 타입도 시험도
> 통과했을 것이고 **presence 시각만 조용히 달라졌을** 것이다. 원본을 그대로 옮겼다.

## 8. 이동은 LLM 이 아니라 codemod 로 했다 (결정 D8)

이번 위험은 정적 리팩터가 못 보는 곳에 몰려 있었다 — **동적 `import("../firebase")` 6건**,
문자열 Mapbox layer id, 런타임 상수 순환. 검산자가 `tsc` 로 완전한 작업에 LLM 을 쓸 이유가 없다.

`scripts/move-lib-files.mjs`(이동 전 specifier 해석 → `git mv` → 새 상대경로 재계산) +
`scripts/repair-lib-imports.mjs`(중단 복구 — basename 유일 후보만, 후보가 여럿이면 멈춘다).

**codemod 가 다섯 가지를 놓쳤고 전부 보강했다.**

| 놓친 것 | 증상 |
|---|---|
| 같은 specifier 가 한 파일에 두 번 | 두 번째 치환을 「실패」로 오판해 **이동 도중 멈춤** |
| 부수효과 `import "x"` (`from` 없음) | `import "../../lib/disableMapboxTelemetry"` 가 깨짐 |
| `/index.ts` 꼬리를 길이 빼기로 절단 | `index.ts`(8자) − `/index.ts`(9자) → **`./index.t`** |
| `.mjs` 의 짝 `.d.mts` | 선언만 남아 **암묵적 any**(`tsc` 가 잡음) |
| 문자열 경로 참조 | `readFileSync("lib/…")` · `ssrLoadModule(…)` · **정규식 단언**(`lib\/…`) — `tsc` 가 못 잡고 **시험만 ENOENT** |

## 12. 다음 세션에 남기는 규율

1. **파일을 옮기기 전에 방향을 선언한다.** 이동은 위반을 줄이지 않는다 — 위치만 바뀐다.
2. **순환은 「어느 쪽이 상위인가」가 아니라 「그 타입이 왜 거기 있는가」로 끊긴다.**
3. **게이트를 세우면 깨뜨려 확인한다.** 그리고 그 확인을 자동화한다 — 손으로만 하면 안 하게 된다.
4. **검산이 제품의 나쁜 상태에 기대면 안 된다.** 고치면 죽는 검산은 검산이 아니다.
5. **우회로가 있으면 결함은 영영 안 보인다.** e2e 가 가짜 토큰을 갈아끼우고 있었다.
6. **「없다」고 할 땐 어디를 찾았는지 적는다.** 수집 범위가 곧 판정의 일부다.
7. **옮기는 일에 재작성을 섞지 않는다.**
8. **도구의 출력을 자르지 않는다.**
