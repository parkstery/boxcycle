## 1. 문제

입문 Basic 1/2/3 의 geometry 가 좌표 4개짜리 **허구 직선**이었다. 지도 위에서 건물·도로를
가로지르고(Basic 1·3), 바다 위를 지났다(Basic 2). 어느 것도 실제 도로망 위가 아니었다.

추가로 확인된 정합성 붕괴:

| # | 함정 | 확인 결과 |
|---|---|---|
| 1 | `basicIntroHubRouteGeometries.ts` 의 뉴욕·로마 seed 2건이 앱에서 미사용 | 사실. `BASIC_COURSES` 와 무관한 고아 파일이었음 |
| 2 | 그 2건은 524m·543m 로 500m 조건에도 실패 | 사실. 또한 `profile: "walking"` 이라 cycling 조건에도 미달 |
| 3 | functions allowlist 와 web 의 세 ID 불일치 | 사실. 교집합 **0** (`basic-intro-nyc/rome` vs `basic-mountain/coastal/mountain`) |
| 4 | `ensureBasicCoursesSeeded` 가 기존 문서를 건너뜀 | 사실. 게다가 `firestore.rules` 가 `routePublications` create 를 `isRouteReviewer()` 로, update 를 `presenceEnabled`/`updatedAt` 로만 허용하므로 **클라이언트는 geometry 를 애초에 만들 수도 고칠 수도 없다** |
| 5 | ID·geometry 불일치 시 presence 대표점이 다른 경로를 봄 | 사실. Functions `computeRepresentativePoint` 가 `routePublications` 를 읽음 |

## 2. 선택한 실도로 경로 3개

모두 **Mapbox Directions API v5 / `cycling` / `overview=full` / GeoJSON** 단일 응답을 그대로 고정했다.
사람이 지도 위에 좌표를 찍거나 두 점을 직선으로 잇지 않았다.

| # | publication ID | 제목 | 도로 (Directions steps) | API 거리 | **좌표 재계산 거리** | 좌표 수 | 소요 |
|---|---|---|---|---|---|---|---|
| 1 | `basic-intro-seoul-namsan` | Basic 1 · 서울 남산공원길 | 남산공원길 | 414 m | **413.2 m** | 42 | 120 s |
| 2 | `basic-intro-paris-pont-neuf` | Basic 2 · 파리 퐁뇌프 | Rue de Nevers → Pont Neuf → Quai des Orfèvres | 448 m | **447.8 m** | 28 | 124 s |
| 3 | `basic-intro-nyc-central-park` | Basic 3 · 뉴욕 센트럴파크 | West Drive | 453 m | **452.9 m** | 36 | 102 s |

- **500m 이하는 nominal 이 아니라 좌표로 증명한다** — 위 "좌표 재계산 거리"는 seed 좌표열을
  haversine 으로 다시 적분한 값이며, 생성기·검증기 양쪽이 이 값으로 게이트한다.
- 출발·도착은 Directions 가 도로에 스냅한 좌표(`waypoints[].location`)로 고정했다. 따라서
  재실행 시 `waypoints[].distance` (스냅 오차)가 **0.003 ~ 0.563 m** 로, 끝점이 도로 위 실좌표임이 증명된다.
- 파리 경로는 센 강을 **퐁뇌프 다리 위**로 건넌다(물 위 허구 아님). 뉴욕 경로는 Winterdale Arch →
  Balcony Bridge 사이의 센트럴파크 순환로만 탄다.

### 증거

`document/archive/260816-입문-실도로-경로-증거/`

| 파일 | 내용 |
|---|---|
| `evidence.json` | provider·profile·요청 URL(토큰 제거)·요청 시각·**응답 SHA-256**·출발/도착 좌표·스냅 거리·API 거리/시간·좌표 재계산 거리·좌표 수·bounds·도로명 |
| `<id>.directions.json` | Directions API 원본 응답 (토큰 제거 후 보존) |
| `<id>.png` | Mapbox Static Images — 실제 도로 위에 경로선이 얹힌 스크린샷 |

토큰은 코드·로그·증거 어디에도 남기지 않았다. 산출 문자열은 전부 `scrubToken()` 을 통과하며,
증거 폴더·생성물 전체에 대한 토큰 문자열 검색 결과 **일치 0건**이다.

## 3. ID 결정 — 기존 유지가 아니라 신규 route ID 로 교체

**결정: 새 publication ID 3개를 만들고, 기존 3개는 폐기(archived, 삭제 아님)한다.**

근거:

1. **기존 ID 가 거짓말을 한다.** `basic-coastal-1_0km` / `basic-mountain-1_5km` 는 이름 자체에
   "해안 1.0km" · "산악 1.5km" 를 박아 두었다. 실제 경로는 서울 남산·파리·뉴욕의 400~453m 다.
   ID 를 유지하면 이름과 내용이 영구히 어긋난다.
2. **거리를 ID 에 박는 실수를 반복하지 않는다.** 새 ID 는 `basic-intro-<도시>-<장소>` 로,
   거리를 담지 않는다. geometry 를 다시 뽑아도 ID 가 낡지 않는다.
3. **Ontology 준수** — 신규 식별자에 `course`/`courseId` 를 만들지 않았다. `publication` 계열이며,
   기존 레거시 식별자의 일괄 rename 은 하지 않았다(스코프 규칙).
4. **seed skip 함정의 근본 회피** — 새 ID 는 프로덕션에 문서가 없으므로 "기존 문서라 건너뜀"이
   구조적으로 발생하지 않는다. 그럼에도 리비전 게이트를 별도로 넣었다(§4).

기존 `basic-mountain-0_5km` · `basic-coastal-1_0km` · `basic-mountain-1_5km` 는 **자동 삭제하지 않는다.**
Admin CLI 에 `--archive-legacy` 를 명시할 때만 `status: "archived"` 로 내리며, 문서는 남는다.

## 4. 정합성 — web / Functions / Firestore

```
scripts/gen-basic-intro-routes.mjs            (생성기 · 유일한 좌표 출처)
  ├─> apps/web/src/lib/basicIntroHubRouteGeometries.ts   ← web geometry SoT
  │     └─> firestoreCourses.ts : BASIC_COURSES · BASIC_SHARED_HUB_IDS · BASIC_SHARED_HUB_SUMMARIES
  │           └─> App.tsx · overlay 7종 · presence  (전부 BASIC_SHARED_HUB_IDS 하나만 import)
  └─> functions/src/basicIntroHubSeeds.ts               ← functions SoT
        ├─> publicationPresenceCore.ts : BASIC_SHARED_HUB_IDS (하드코딩 제거)
        └─> seedBasicIntroPublicationsCore.ts : Firestore Admin 시드
```

- web 쪽 overlay·presence 소비자 7개 파일은 모두 `BASIC_SHARED_HUB_IDS` 를 import 하므로
  한 곳만 바꾸면 전부 따라온다. 하드코딩 중복은 Functions 한 곳뿐이었고, 이제 생성물로 대체했다.
- 두 SoT 파일의 ID 집합 일치는 검증기 C7 이 강제한다.

### seed skip 함정 해소

`ensureBasicCoursesSeeded` 는 이제 문서 존재 여부가 아니라 `basicSeedRevision` 을 본다.
리비전이 다르면 다시 쓴다. 다만 프로덕션 rules 상 클라이언트는 이 쓰기를 수행할 수 없으므로,
**실제 프로덕션 정합은 Admin CLI 의 몫이다** — 이 사실을 코드 주석에 명시했다.

### Admin 시드/마이그레이션

```
npm run admin:seed-basic-intro-publications -- --dry-run
npm run admin:seed-basic-intro-publications -- --archive-legacy --dry-run
```

- idempotent: 문서 없으면 create, `basicSeedRevision` 이 낡으면 update, 같으면 unchanged.
- **어떤 문서도 삭제하지 않는다.** 레거시는 `--archive-legacy` 일 때만 `status: archived`.
- 쓰기 전 좌표 재계산 길이를 자가 검산한다(2점 미만·0m·500m 초과면 그 항목만 error 로 기록).

## 7. production migration 필요 여부

**필요하다. 단, 이 작업에서는 코드와 dry-run 절차까지만 했다 — 실제 실행은 Chief 승인 대상이다.**

- 새 ID 3건은 프로덕션에 존재하지 않으므로 `create` 가 발생한다. 클라이언트는 rules 상 create 를
  할 수 없으므로, Admin CLI 를 돌리지 않으면 프로덕션 `routePublications` 에 세 문서가 없다.
- 문서가 없을 때의 영향: **앱 주행은 정상**(로컬 `BASIC_COURSES` 로 로드). 다만 Functions 의
  presence 대표점(`computeRepresentativePoint`)이 geometry 를 못 찾아 동행 표시가 비게 된다.
  따라서 동행 기능까지 살리려면 migration 이 필요하다.
- 권장 순서: `--dry-run` → 결과 확인 → 승인 → 실행 → `--archive-legacy --dry-run` → 승인 → 실행.
- 기존 publication 삭제는 하지 않는다(코드에 삭제 경로 자체가 없다).

## 8. 이견·미해결

1. **`--archive-legacy` 미실행 시 옛 3건이 퍼블릭 카탈로그에 남는다.** `listPublishedPublicCourses`
   는 `status == "published"` 인 `routePublications` 를 전부 훑는다. 입문 목록(`BASIC_SHARED_HUB_SUMMARIES`)
   에는 안 뜨지만 퍼블릭 카탈로그에는 뜬다. archive 실행 전까지 남는 알려진 상태다.
2. **`profile` 은 `cycling` 유지했으나 남산공원길·West Drive 는 실제로 자전거 통행 규칙이 구간별로 다르다.**
   Directions `cycling` 이 통행 가능으로 판정한 결과를 그대로 썼고, 별도 현지 규칙 검증은 하지 않았다.
3. **`scripts/gen-basic-intro-routes.mjs` 의 이전 버전(뉴욕·로마 walking 2건 생성)은 폐기하고 덮어썼다.**
   그 산출물이던 `basicIntroHubRouteGeometries.ts` 의 옛 seed 2건도 함께 사라졌다. 앱에서 미사용이었으므로
   회귀 영향은 없다.
4. **탐색용 probe 스크립트는 커밋하지 않았다.** 후보 좌표 탐색 과정은 이 보고서 §2 에만 남는다.
