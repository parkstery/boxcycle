## 1. 무엇을 풀었나

**Cursor가 보고를 끝내면 Chief의 「확인해」 입력 없이 Claude 감리가 스스로 시작되고 판정이 남는다.**

착수 시점의 상태는 이것이 아니었다. 감리 스크립트는 있었지만 사람이 미리 watcher 터미널을 켜 둔 동안에만 반응했고, 결과는 Chief가 운영하는 Claude Sync 감리 대화와 **무관한 별도 산출물**이었다. 즉 자동화가 아니라 「수동 실행 가능한 스크립트」였다.

## 2. 최종 흐름

```
Cursor 보고완료 (INSTRUCTION 상태 = 보고완료)
  → watcher 가 감지 · 안정화 대기(지문이 90초 연속 동일)
  → 영속 pending 큐에 이벤트 기록                    (프로세스 경계, 유실 없음)
  → RTW Channel 서버가 실행 중 Claude Sync 세션에 주입
  → 화면에 <channel source="rtw" event_id="…"> 도착
  → 세션이 스스로 rtw_ack → 감리 수행 → rtw_verdict
  → done 저장. 대상 저장소는 무변경
```

감리를 **별도 프로세스로 돌리지 않는다.** 채널은 이벤트만 전달하고, 감리는 Chief가 쓰던 그 대화 세션 자신이 수행한다. 그래서 감리자의 정체성·프로토콜·이전 지시 이력이 그대로 살아 있다.

## 4. 도중에 틀렸던 판단 3건

이 작업의 실질은 **내가 틀린 것을 실측으로 잡아낸 과정**이었다. 기록해 둔다.

### 4.1 `--resume` 을 「실행 중 세션 기동」으로 착각

O-2 에서 `claude --resume` 으로 기존 감리 세션을 깨울 수 있다고 제시했다. 실제로는 **별도 프로세스가 같은 transcript 를 이어 쓰는 것**이고, 열려 있는 화면은 아무 일도 없이 대기한다. 같은 세션을 동시에 resume 하면 이력이 뒤섞인다.

→ Chief 지적으로 폐기. Channels(공식 수단)로 대체했고, `--emit-channel` 과 `--sync-session` 을 코드에서 **상호 배타**로 막았다.

### 4.2 Channels 가 없다고 단정

`claude --help` 에 서브커맨드가 없다는 이유로 「이 버전에 Channels 는 없다」고 판단했다. 공식 문서를 먼저 확인하지 않은 성급한 단정이었다. Channels 는 실재했고, 정확히 이 용도의 공식 수단이었다.

### 4.3 watcher 를 「교체했다」고 보고

작업 래퍼를 종료하면 프로세스도 죽는다고 가정했다. 실제로는 node 자식이 살아남아 **두 watcher 가 동시에** 돌았다. 결과적으로 lock 소유권 방어가 실환경에서 검증되는 계기가 됐지만(한쪽이 282초 내내 `busy`), 보고 자체는 틀렸다.

→ 이후 프로세스 목록으로 개수를 세는 절차를 넣었고, 채널 서버에 heartbeat 를 붙여 `doctor` 가 **0개·1개·중복**을 구분하게 했다.

## 5. 실측이 드러낸 결함과 수정

| 발견 경위 | 결함 | 수정 |
|---|---|---|
| 첫 실제 E2E | `verdict=WARNING` 인데 `findings: []` — 사유 없는 판정이 성공으로 저장됨 | 사유 없는 BLOCK·WARNING 거부. `PASS` 는 반대로 finding 금지 |
| S4-1R 실제 감리 | 감리 한 번이 **216.8분** (건강한 실행은 4분 37초) | 실행 상한 45분. 초과는 실패로 기록 |
| 코드 검토(Codex) | 회수·release 가 소유권 확인 없이 경로를 `unlink` — 남의 lock 을 지움 | 소유권 토큰 + `rename` 기반 원자적 회수. 내용이 다르면 되돌림 |
| 코드 검토(Codex) | timeout 후 `close` 가 안 오면 Promise 가 영영 안 끝남 | 상한+유예 뒤 `close` 와 무관하게 강제 종결 |
| S4-1R 1차 시도 | 감리 도중 커밋이 들어와 실행이 폐기됨 | 안정화 게이트 — 지문이 90초 연속 동일해야 시작 |
| **실제 운영 사고** | **ACK 후 세션이 끊겨 3시간 49분간 verdict 없음** | ACK 에도 lease. 초과 시 이전 ACK 무효화 후 재전달, 시도 소진 시 에스컬레이션 |

마지막 항목이 가장 중요하다. `pumpOnce` 가 `if (event.ackedAt) continue` 였다 — **ACK 를 「끝났다」로 취급**했다. ACK 는 「받았다」일 뿐이다. 프로세스·lock·heartbeat 는 모두 정상이었고 죽은 것은 세션 안의 **한 응답**이라, 기존 방어선 어느 것도 잡지 못했다.

## 6. 지켜진 경계

| 경계 | 방식 |
|---|---|
| 대상 저장소 무변경 | 감리 전후 지문(HEAD·status·diff·미추적 내용) 대조. 어긋나면 실행을 **실패로 폐기** |
| Sync 지시서 무수정 | 상태 전환은 개발 담당의 일. 우리는 관측만 한다 |
| 판정 자동반영 없음 | `inbox/`·`done/` 에 놓을 뿐, 작업선에 반영하지 않는다 — 설계된 하드 스톱 |
| 후속 actor 자동 실행 없음 | 코드에 경로 자체를 만들지 않았다 |

실제로 S4-1R 1차 시도는 **감리 도중 대상이 바뀌자 스스로 폐기**됐다. 이는 결함이 아니라 방어가 동작한 것이다 — 움직이는 트리를 감리해 놓고 성공으로 적었다면 그 판정이 어느 커밋에 대한 것인지 말할 수 없다.

## 8. 2단계는 취소했다

자동 Cursor 실행(2단계)은 제어면까지 만들고 시험 24건이 통과했으나 **Chief 결정으로 취소**했다. 실제로 Cursor 를 실행한 적은 한 번도 없다. 코드와 확정된 환경 사실은 `rtw-orchestrator/archive/phase2-auto-cursor-취소-20260816/` 에 보관했다.

되살릴 때 쓸 수 있는 사실: WSL 불필요(네이티브 Windows 설치 존재) · 명령은 `agent` · 무인 인자는 `-p --output-format text --workspace <target> --trust --force` · `--worktree` 는 대상 고정을 깨므로 금지 · `.cmd` 는 `node.exe + index.js` 로 우회 · 위험 차단은 전역 deny 목록이 담당.

## 9. 남은 위험 (해결되지 않음)

1. **ACK lease 20분은 실측 2점 기반 추정치다.** 실제로 230분 걸린 감리가 관측됐다 — 그 상태에서 이 로직이 떠 있었다면 20분 시점에 재전달해 **중복 감리**가 났을 것이다. 값 조정이나 진행 중 heartbeat 도구가 필요하다.
2. **ACK 후 단절 복구는 실환경에서 한 번도 돌지 않았다.** 단위 시험 5건으로만 고정돼 있다. 실제로 멈췄던 이벤트는 원래 세션이 230분 만에 스스로 이어서 끝냈다.
3. **채널은 research preview** 다. 조직 정책으로 막히면 이벤트가 **조용히 버려지고** 서버는 오류를 받지 못한다 — ACK 부재로만 알 수 있다.
4. **단일 세션 규율이 운영 조건이다.** 창이 둘이면 중복 감리가 된다. `doctor` 가 경고하지만 강제하지는 못한다.
5. **watcher·세션 수명주기는 여전히 수동이다.** 자동 시작·재시작·알림은 범위 밖으로 두었다.
