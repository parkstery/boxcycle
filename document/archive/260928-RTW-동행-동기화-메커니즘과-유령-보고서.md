## 1. 한 장 요약

- **튐**: 고쳤다. 원인 넷을 찾았고 마지막에 **출구 한도**로 덮었다. chief 판정 「튄다고 할 정도 아닌 작은 진동」.
- **유령**: **절반 고쳤다.** Stop 은 양쪽 모두 정상. **브라우저 강제 종료**는 불규칙하게 남는다.
  - 근본 원인은 **Firestore 에 「연결이 끊기면 지워라」가 없다**는 것 — 앱 코드만으로는 완전히 못 막는다(§5.3).
- **계측 도구**를 남겼다. 다음 사람은 추측 대신 콘솔 두 줄로 시작한다(§7).

## 2. 데이터가 흐르는 길

### 2.1 채널 두 개 — 용도가 다르다

| | RTDB `trailMotion` | Firestore `livePublicationRides` |
|---|---|---|
| 주기 | **10Hz** (`PEER_MOTION_PUBLISH_INTERVAL_MS=100`) | 약 1Hz |
| 용도 | **동행 라이더를 그린다** | 관전·인원수·활동 집계 |
| 연결이 끊기면 | **`onDisconnect().remove()` 가 지운다** | **아무 일도 일어나지 않는다** |
| 쓰기 | `set()`, 겹쳐 보내기 2개까지 | 단일 슬롯 |

> 이 표의 **마지막 줄이 유령의 뿌리다.** 두 채널의 수명 관리가 근본적으로 다르다.

### 2.2 화면에 그리는 길 **셋** — 서로 다른 코드다

하나를 고쳤다고 나머지가 고쳐지지 않는다. 실제로 그래서 같은 증상을 **두 번** 고쳤다.

| 무엇 | 어디 | 기준 |
|---|---|---|
| **동행 라이더 본체** | `PeerMotionRegistry` → `syncPeerDomMarkers` | 침묵 15초(§5.4) |
| Trailhead 관전 점 | `useWorldLivePublicationRideMapOverlay` | `...RowPeerVisible` 15초 |
| Trail 안 관전 점 | `useTrailLivePublicationRideSpectatorOverlay` | `...RowPeerVisible` 15초 |

발행 → 수신 → 화면:

```
주행 tick 100ms
  └ publishLiveLocationFanout
      ├ enqueueMotionPublish → motionPublishFlight(겹쳐 2) → RTDB set()
      └ enqueueRoutePublish  → Firestore set()
                                    ↓
            PublicationSharedPresence (구독 2종)
                                    ↓
                    syncPeerMotionFromPresence
                    (RTDB 우선, 없으면 Firestore 폴백)
                                    ↓
                        PeerMotionRegistry.ingest
                                    ↓
              rAF: pruneInactive → step → buildRenderFeatures
                                    ↓
                             DOM 마커 setLngLat
```

## 3. 보간이 하는 일 — 그리고 무엇이 틀렸었나

### 3.1 지금의 파이프라인

```
도착 간격 EMA ──×2.2──→ 목표 지연 (160ms~3s)
                              ↓
재생 시계 (실시간으로 흐르고, 목표 쪽으로 ±10%만 당김)
                              ↓
타임라인 = 송신시각 + 시계오프셋(최근 최소값)
                              ↓
   재생시점을 감싸는 두 스냅샷 사이를 보간 (없으면 1.2초까지 외삽)
                              ↓
         출구 한도 — 제 속도의 2.5배까지만 따라감 (15m 초과는 즉시)
```

### 3.2 네 가지 결함 (전부 오류를 내지 않았다)

| # | 무엇이 틀렸나 | 증상 |
|---|---|---|
| 1 | 지연이 **160ms 고정**인데 도착 간격은 약 200ms | 보간이 아니라 **「외삽 후 스냅」**으로 동작. 외삽 프레임이 도착 1000ms 에서 **83.4%** |
| 2 | 시간축이 **도착 시각** | 망 지터가 그대로 속도 지터. 몰려 온 두 패킷 사이를 순간이동 |
| 3 | 재생 시점을 `지금 − 지연` 으로 매 프레임 재계산 | **1번을 고치자 생긴 결함.** 지연이 바뀔 때마다 화면이 통째로 이동 |
| 4 | 시계 오프셋이 내려갈 때 재생 시계를 안 옮김 | 버퍼 전체가 타임라인 위에서 이동 → 그만큼 건너뜀 |

**1번이 「간격을 좁혀야만 나아지던」 이유다.** 보간에 기대는 설계였는데 보간이 돌지 않았다.

### 3.3 합성 실측 (등속 5.00 m/s 송신 → 화면 속도)

| 도착 간격 | 처음 | 1·2·3 후 | 4+한도 후 |
|---|---|---|---|
| 200ms | −0.40 ~ 6.67 | 4.35 ~ 8.12 | **4.50 ~ 5.50** |
| 1000ms | **−42.56 ~ 49.22** | 3.95 ~ 10.00 | **4.50 ~ 5.50** |

음수는 동행이 **뒤로 가는** 것이다. 재현: `cd apps/web` → `npm run probe:peer-interp`

### 3.4 실주행 실측 (chief 두 창, `[peerSmooth]`)

```
avg=1.41  min=-10.57  max=34.36  back=0.8%  gap=147ms delay=323ms  (1,815프레임)
avg=2.13  min= -2.96  max=51.62  back=0.5%  gap=128ms delay=281ms  (5,497프레임)
```

평균·간격·지연은 정상인데 **0.5~0.8% 의 프레임만 통째로 튀었다**(최대 186 km/h).
60fps 에서 2~3초에 한 번 — 이것이 chief 가 끝까지 보던 「작은 튐」이다.

> **교훈**: 모의 계측은 평범한 지터만 흉내 냈다. 실제 실패는 **드물고 크다**.
> 합성 시험은 「2초 끊겼다 복귀」 같은 **최악을 손으로 만들어야** 재현된다(§8).

### 3.5 왜 원인을 더 쫓지 않고 한도를 걸었나

원인이 여럿이고(시계 오프셋·버퍼 밀림·외삽에서 보간으로 전환) 하나씩 쫓으면 늘 하나가 남는다.
**출구 한 곳**에 한도를 걸면 무엇이 원인이든 화면에서 보이지 않는다.
위치를 버리는 게 아니라 다음 프레임들에서 따라잡는다.

주의 — 한도는 **증상을 덮는다.** 남은 원인은 여전히 거기 있고, `[peerSmooth]` 의
`back` 이 0 이 아니면 그 흔적이다. 근본을 파려면 한도를 잠시 풀고 재야 한다.

## 4. 전송 쪽에서 고친 것

**겹쳐 보내기**(`MOTION_MAX_IN_FLIGHT=2`) — 종전에는 앞 쓰기가 끝나야 다음을 보내서,
100ms 마다 보내려 해도 **왕복 시간(약 200ms)에 묶였다.** 보내려던 10Hz 가 실제 5Hz 였다.

- 도착 간격 약 200ms → **약 130ms**, 표시 지연 0.44초 → **약 0.25~0.32초**
- 순서는 안전 — RTDB 는 한 클라이언트의 쓰기를 보낸 순서대로 적용하고, 받는 쪽도 역행 패킷을 버린다
- **전송량이 는다.** 비용 손잡이는 `PEER_MOTION_PUBLISH_INTERVAL_MS`(ride 소유)다.
  보간이 도는 지금은 넓혀도 튀지 않는다 — 그 둘을 혼동하지 말 것

**정리 순서** — 겹쳐 보내면 「내가 끝났다 = 날아가는 게 없다」가 깨진다.
하나가 끝나도 다른 하나가 날아가는 중인데 노드를 지우면 **늦게 도착한 쓰기가 지운 노드를 되살린다.**
`inFlight === 0` 일 때만 정리한다. (e2e `peer-sync-s4m1` **M6** 이 이 회귀를 잡았다)

## 5. 유령 — 아직 안 끝났다

### 5.1 관측 사실 (chief, 2026-09-28)

| 상황 | 참여자가 나감 | 개설자가 나감 |
|---|---|---|
| **Stop 클릭** | 15초 내 사라짐 | 15초 내 사라짐 |
| **브라우저 강제 종료** | 대개 15초 내 · 불규칙 | **1분 이상 남음** |

> chief 요약: 「Stop 은 일관성이 있다. **브라우저를 강제 종료했을 때 신호를 명시적으로
> 끊지 못한 채 유령을 만들고 있다.**」 — 정확한 진단이다.

### 5.2 Stop 이 멀쩡한 이유

Stop 은 **행을 지우고 나간다.** RTDB 노드 삭제와 Firestore 행 삭제를 명시적으로 한다.

### 5.3 강제 종료가 남는 이유 — 구조적이다

- **RTDB**: `onDisconnect().remove()` 가 걸려 있다(`ensureMotionOnDisconnect`, trail+uid 당 1회).
  다만 **서버가 소켓 끊김을 알아챌 때까지 시간이 걸리고**, 그 시간이 일정하지 않다.
  → 「불규칙하게 사라지거나 버틴다」의 설명.
- **Firestore**: **onDisconnect 에 해당하는 것이 없다.** 행은 마지막 `lastSeenAt` 인 채 그대로 남는다.
  서버가 이 행을 건드리는 Function 도 없다(확인함).
  → RTDB 가 사라진 뒤 **Firestore 폴백**으로 계속 그려질 수 있다.

**즉 클라이언트 코드만으로는 완전히 막을 수 없다.** 지금 한 것은 「안 지워진 행을 **받는 쪽에서 무시**」하는 방어다.

### 5.4 지금 서 있는 방어선 셋

| # | 무엇 | 기준 | 어디 |
|---|---|---|---|
| 1 | 관전 **점** 숨김 | 15초 (`PEER_LIVE_RIDE_STALE_MS`) | 두 오버레이 |
| 2 | 라이더 **본체** 침묵 판정 | 15초 | `PeerMotionRegistry` |
| 3 | 송신 시각을 못 읽을 때 | **45초** (`NO_SRC_SILENT_MS`) | 같음 |

**2번의 판정 근거는 「거리」가 아니라 「보내고 있는가」다.** 신호 대기로 멈춘 사람도 좌표는
계속 보내므로, 거리로 판정하면 멈춘 사람을 쫓아낸다. 시계는 비교하지 않고 **송신 시각이
바뀌는 것을 마지막으로 본 내 시각**을 쓴다(순수 상대 비교라 시계 차이와 무관).

지우기만 하면 다음 배달에 다시 태어나므로 **ingest 에서 낡은 행을 되살리지 않는다.**

### 5.5 왜 개설자만 1분 넘게 버티나 — 미결

가설 셋. 아직 어느 것인지 모른다.

1. 개설자 쪽 Firestore 행의 `lastSeenAt` 을 읽을 수 없어(`serverAtMs=0`) **45초 기준**이 적용된다
2. 개설자의 RTDB `onDisconnect` 가 늦게 발화한다(소켓 종료 방식 차이)
3. 개설자가 **Trailhead 에 있을 때**와 **주행 중일 때** 도는 코드가 달라 prune 이 안 돈다

→ **`[peerAlive]` 한 줄이면 갈린다**(§7.2). 다음에 팔 때 여기부터 시작한다.

### 5.6 제안하는 해결책

| 안 | 내용 | 장단 |
|---|---|---|
| **A. 서버 sweeper** (권장) | 스케줄 Function 이 `lastSeenAt` 낡은 `livePublicationRides` 행을 주기적으로 삭제 | 근본 해결. `trailInstanceLifecycle` 에 이미 비슷한 틀이 있다. 비용은 주기에 비례 |
| **B. RTDB 를 유일한 생존 근거로** | 화면 표시는 RTDB presence 만 믿고 Firestore 는 집계 전용 | 구조가 가장 깔끔. Firestore 폴백을 버리므로 RTDB 미설정 환경에서 동행이 안 보인다 |
| **C. 받는 쪽 기준 강화** (지금) | 침묵 15/45초로 무시 | 이미 함. **행은 계속 남아 읽기 비용을 먹는다** |
| **D. Firestore TTL** | 문서 TTL 정책으로 자동 삭제 | 최소 해상도가 커서 화면 반응성엔 못 쓴다. 비용 청소용으로는 유효 |

**권장: A + C.** C 로 화면을 즉시 지키고, A 로 행 자체를 치운다.
B 는 구조적으로 가장 깔끔하지만 폴백을 버리는 결정이라 결정 로그가 필요하다.

## 7. 계측 도구 — 추측하기 전에 이것부터

실행: `cd C:\20.HDev\boxcycle` → `npm run dev` → 두 창 · **Ctrl+Shift+R** · 둘 다 주행

### 7.1 매끄러움 — 콘솔 필터 `peerSmooth`

```
[peerSmooth] xOTFTZ  avg=1.41 min=-10.57 max=34.36  back=0.8%  gap=147ms delay=323ms
```

`back` 이 0%가 아니면 동행이 뒤로 간 것이고 그게 튐이다.
`back=0` 인데 눈에 튀면 **동행 위치가 아니라 카메라**를 의심한다(내 라이더는 화면 중앙 고정).

### 7.2 왜 안 사라지나 — 콘솔 필터 `peerAlive`

```
[peerAlive] xOTFTZ  silent=3.2s  mark=yes  active=yes  기준=15s  마지막ingest=0.1s 전
```

- `mark=NO` → 판정 자체를 못 하고 있다
- `mark=내용만` → 송신 시각을 못 읽어 45초 기준이 적용 중
- `silent` 이 계속 작다 → **누군가 아직 보내고 있다**(행이 갱신되는 중)

### 7.3 사슬 추적 — 필터 `peerSyncChain`

`pt=1·2` 발행 → `pt=3` RTDB 쓰기 완료 → `pt=4` 수신 → `pt=5` 반영 → `pt=6·7` 렌더 → `pt=10` 관전 외삽

기본 1초 간격. 폭주하면 `?peerSyncLogMs=10000`. 콘솔 필터에 `-peerSyncChain` 을 넣으면 제외된다.

### 7.4 합성 계측

`cd apps/web` → `npm run probe:peer-interp`

## 8. 다음 사람을 위한 경고

- **「튐」과 「유령」을 섞지 마라.** 보간과 연결 종료는 다른 문제다.
- **화면에 그리는 길이 셋**이다(§2.2). 하나를 고쳐도 나머지는 그대로다.
- **240초 기준을 맵에 쓰지 마라.** 멤버 목록용이다. 맵은 15초.
- **사보타주가 통과하면 제품이 옳은 게 아니라 시험이 못 겨눈 것이다.**
  이 작업에서만 **네 번** 겪었다. 무작위 지터로는 드물고 큰 실패를 재현하지 못한다 —
  「2초 끊겼다 복귀」·「늦던 신호가 갑자기 빨라짐」처럼 **최악을 손으로 만들어라**.
- **조용한 계측은 고장난 계측과 구분되지 않는다.** 빈 표·항상 0인 카운터·갱신 안 된 계기로
  세 번 헛돌았다. 계기는 「나는 지금 왜 조용한가」를 말해야 한다.
- **도구 출력을 자르지 마라.** e2e 실패를 `tail -30` 으로 받아 원인 JSON 을 잃고 재실행했다.
- **e2e 전에 `npm run dev` 를 꺼라.** 5000 포트를 물고 있으면 webServer 타임아웃으로 죽는다.
