## 1. 한 줄 요약

주행 중 라이더와 네임태그가 앞뒤로 톡톡 진동하던 현상은 **카메라 쪽 원인 두 가지**가 겹친 것이었다.
카메라가 라이더를 **지연 추종**했고 그 지연이 **프레임 간격에 따라 변했으며**, 코너에서는
**지도 중심을 잡는 방향과 화면을 회전시키는 방향이 서로 다른 값**이었다.

---

## 2. 증상 — 표현이 두 번 바뀌었다

```
최초 보고    "라이더가 진동한다"
1차 정정     "라이더가 아니라 화면 자체가 톡톡 튄다"
2차 정정     "맵과 지명은 안 움직인다. 라이더와 네임태그만 전후로 왔다갔다 한다"   ← 정확
```

**2차 정정이 결정적이었다.** 「화면이 흔들린다」와 「화면 위 물체가 흔들린다」는 원인 집합이
겹치지 않는다. 전자는 렌더·카메라 자체의 문제이고, 후자는 **두 좌표계의 상대 관계**다.
1차 정정의 전제로 세 라운드를 조사했으나 배제만 나왔다.

증상 조건: 거리 1 m ~ 5.5 m 밀착 구도 · 속도 5 km/h. 40 m 등 원거리 구도에서는 보이지 않았다.

---

## 3. 원인

### 3-1. 원인 ① — 위치 지연이 프레임 간격에 따라 변동

`apps/web/src/components/map/rideCameraFollow.ts`

```
alphaPos   = dampAlpha(dtSec, CAMERA_POSITION_TAU_SEC)     τ = 0.1 s
nextCenter = lerp(curCenter, cameraCenterTarget, alphaPos)

dampAlpha(dt, τ) = 1 − exp(−dt/τ)      ← dt 에 의존한다
```

카메라 중심이 라이더를 고무줄처럼 지연 추종한다. 정상 상태 지연은 `v × τ` 다.

```
5 km/h = 1.389 m/s × 0.1 s ≈ 0.139 m
```

여기까지는 일정한 offset 이라 눈에 띄지 않는다. 문제는 **`alphaPos` 가 프레임 간격에 의존**한다는 것.

```
프레임이 짧으면 (8 ms)   alpha 0.077   덜 따라잡음 → 라이더가 화면에서 앞으로
프레임이 길면  (25 ms)   alpha 0.221   많이 따라잡음 → 라이더가 화면에서 뒤로
```

브라우저 프레임 간격은 항상 흔들린다. 따라서 **지연 거리가 매 프레임 오르내리고,
라이더는 그만큼 앞뒤로 진동한다.**

**왜 지도는 안 흔들렸나** — 지도는 카메라 변환으로 그려지므로 카메라 기준에서 항상 자기 자신과
일치한다. 라이더와 네임태그는 **실제 좌표**에 그려진다. 어긋나는 것은 이 둘의 상대 위치뿐이다.

**왜 확대에서만 보였나** — 0.139 m 가 40 m 구도에서는 1 px 미만이지만 1~5.5 m 구도에서는 수십 px 다.

### 3-2. 원인 ② — 중심 방향과 화면 회전이 다른 값

수정 전 계산 순서:

```
① baseHeading                                  원본 방향
② nextCamera = getCameraForFollowMode(...)     offsetBearing = 원본 방향 + 180
③ framing = computeRideFollowFraming({
       offsetBearing: nextCamera.offsetBearing  ← **원본** 으로 중심을 잡는다
   })
④ 그 뒤에 nextBearingPrimary → nextBearing 스무딩 → **지도에는 이 값이 적용**된다
```

```
직선   원본 방향 == 스무딩 방향 → 어긋날 것이 없다 → 무증상
코너   원본 방향이 즉시 꺾여 중심이 옆으로 훅 이동하는데
       화면 회전은 천천히 따라간다 → 그 차이만큼 라이더가 화면에서 튄다
```

**이 원인은 원인 ①을 제거한 뒤에야 드러났다.** ①만 껐을 때 사용자 관측이
「직선 톡 없음 · 코너만 톡」으로 갈렸고, 그것이 ②의 존재를 가리켰다.

## 4. 수정 (`e446913`)

```
① bearing 스무딩(nextBearingPrimary → nextBearing)을 framing **앞으로** 옮겼다
② 중심 방향을 지도에 실제 적용되는 bearing 에서 파생시켰다
     offsetForFraming = normalizeCompass(nextBearing + 180)
③ 중심 lerp 계수를 1 로 두어 위치 지연을 없앴다
```

**스무딩 상수는 하나도 바꾸지 않았다.** `CAMERA_POSITION_TAU_SEC` · `CAMERA_BEARING_TAU_*` ·
`CAMERA_BEARING_MAX_DPS_*` 전부 그대로다. 값 조정이 아니라 **어느 값을 쓰느냐**의 문제였다.

보존한 것:

```
offsetBearing 이 null 인 경로(north·기본 분기, distanceM 0) — 치환하지 않음
free 모드 — 함수 진입 즉시 return
첫 프레임 resetCameraSmoothing · curCenter 폴백 — 순서 변경에도 유지
```

**비교 스위치** (DEV 전용, 기본 상태에서는 배지 없음)

```
__rtwTick.aligncam(false)   옛 동작 (지연 추종 + 원본 방향 중심)
__rtwTick.aligncam(true)    현행 복귀
```

## 5. 원인이 아니었던 것 — 다시 파지 마라

세 라운드를 여기에 썼다. 배제 근거가 실측으로 남아 있다.

| 후보 | 배제 근거 |
|---|---|
| LOD·활동 레이어 재동기(100 ms) | U-2 에서 제거(emit 190→0 · moveToTop 886→0)했으나 증상 유지 |
| 위치 표본이 계단식 | `virtualDistanceRef` 가 rAF 마다 `v×dt` 연속 적산 — 계단 아님 |
| bearing 이 계단식 | 60 m 앞을 60 샘플로 평균 — 정점 하나당 1/60 만 변함, 불연속 없음 |
| zoom 진동 | 전 구간 24.837241~24.837267 로 사실상 상수 |
| 앱 rAF ↔ Mapbox 렌더 위상 어긋남 | `lagFrames` 677 개 전부 0 · render:write = 1:1 |
| 라벨 재배치 · `map.stop()` · GLB 레이어 | 사용자가 DEV 스위치로 하나씩 꺼 본 결과 전부 무관 |

## 6. 검증

톡의 유무는 정지 화면으로 증명되지 않는다. **판정은 실제 주행 중 사용자 육안**으로 했다.

```
조건    5 km/h · 좌측 팔로우 · 거리 5.5 m
① 지연만 제거      직선 무증상 · 코너 진동 → 원인 ② 존재를 지목
② 방향까지 정렬    직선·코너 모두 무증상 → **종결**
③ 비교 스위치      aligncam(false) 로 옛 동작 복귀 시 증상 재현 확인
```

계측 하네스로는 판정하지 않았다 — 헤드리스가 12~22 fps 라 프레임 현상 자체가 재현되지 않는다.
이 사실 자체도 U-2·U-3 에서 실측으로 확인했다.

## 8. 교훈

**시각 증상 조사는 계측 코드를 짜기 전에 기준계부터 확정한다.**
배경(지도)이 움직이는가, 전경(모델·마커)이 움직이는가, 둘의 간격이 변하는가.
사용자에게 「A 가 B 에 대해 움직입니까」로 물으면 정지 화면 두 장으로도 대개 갈린다.
전제가 틀리면 아무리 정밀하게 계측해도 배제만 쌓인다 — 여기서 세 라운드를 태웠다.

**게이트가 축퇴값으로 자동 통과하지 않는지 먼저 검산한다.**
U-1 에서 라이더 화면 bbox 의 높이가 정확히 0 이라 「안전 영역 안」 판정이 자동으로 참이 됐다.
높이 0 인 상자는 어떤 영역에도 들어간다. 판정 직전에 측정 자체의 유효성을 확인하는 단계를 둔다.
