## 1. 한 줄 결론

동행(peer) 라이더가 화면에서 앞뒤로 튀는 증상은, **S4-15 의 11.45 Hz 실패 trace 한 건에서 볼 때 경위도를 화면 좌표로 바꾸는 투영 단계에서 처음 관측된다.** 15라운드에 걸쳐 계측 체인을 세우고 후보를 배제해 여기까지 왔다.

**「카메라·투영으로 확정」이 아니다.** 확정된 것은 아래 한 문장뿐이다.

```
11.45 Hz 로 기록된 S4-15 trace 에서, 왕복이 처음 나타나는 단계는 projected 였다
```

원인 파라미터(bearing·center·pitch·zoom)는 **전부 미확정**이고, 60 fps 재검증도 **미완료**다
(11.45 Hz 는 60 fps 의 1/5 로, 더 빠른 진동은 계측되지 않았거나 aliasing 되었을 수 있다 — §9 W-1).

## 2. 증상과 재현 조건

### 증상 (Chief 실주행 관찰 — 이것이 기준)

```
동행 주행 중 상대 라이더가 앞뒤로 톡톡 튄다
내 라이더는 매끄럽다
단독 주행에서는 나타나지 않는다
```

**「내 라이더가 흔들린다」로 문제를 바꿔 읽지 않는다.** 이 혼동으로 여러 라운드를 소모했다.

```
카메라        좌측
속도          약 5 km/h
두 라이더     시각적으로 나란히 붙은 근접 상태
탭            양쪽 모두 visible
구간          8초 단발이 아니라 증상 구간 확보
```

이 조건은 **S4-15 에서 처음으로 창 전체에서 성립**했다(§4).

## 3. 지금까지 좁혀진 범위 (모두 S4-15 trace 기준 · 미확정)

```
① local rAF 거리          정상   역행 0
② peer 패킷 dist/serverAt  정상   역행 0
③ peer displayDistM        정상   역행 0 (단조 전진)
──────────────────────────────────────────── S4-14 trace 에서 여기까지는 왕복 없음
④ getPointOnRouteByDistance → lngLat    정상   반전 0
⑤ map.project(lngLat) → 화면 좌표       ★ 이 trace 에서 왕복이 처음 나타난 단계
⑥ peer/self DOM 상대좌표                ⑤ 를 그대로 따라감
```

**S4-14** 가 「displayDistM 이후 ~ 최종 DOM」으로 구간을 좁혔고, **S4-15** 가 그 안에서 **투영 단계를 최초 관측 지점으로 지목**했다. 위 「정상/무죄」 판정은 모두 **이 한 건의 11.45 Hz trace 안에서만** 성립한다. 60 fps 에서도 같은지는 확인되지 않았다.

## 4. S4-15 계측 결과 (최초 관측 지점 · 원인 미확정)

### Chief 조건 성립

| 항목 | 값 |
|---|---|
| 프레임 수 | 93 |
| 두 라이더 간격 | 2.033 ~ 2.336 m · 중앙값 **2.185 m** |
| 창 전체 근접 유지 | `closeWholeWindow: true` |
| 같은 속도 유지 | `sameSpeedWindow: true` — local 5 km/h 고정, peer 1.39 m/s 고정(변동 0) |

다섯 차례 시도 끝에 근접·같은 속도가 창 전체에서 성립했다.

### 단계별 왕복(반전) 계측

| 단계 | 대상 | 반전 횟수 | 최대 크기 | peak-to-peak |
|---|---|---|---|---|
| ④ | peer `lngLat.lng` | **0** | 1.17e-6 | 5.98e-5 |
| ④ | peer `lngLat.lat` | **0** | 1.63e-6 | 8.80e-5 |
| ④ | self `lngLat.lng` | **0** | 8.41e-7 | 5.96e-5 |
| ⑤ | peer `projected.x` | **26** | **7.882 px** | **26.18 px** (first idx 8) |
| ⑤ | peer `projected.y` | 0 | 0.263 px | 1.73 px |
| ⑤ | self `projected.x` | 0 | 8.0e-7 px | 5.9e-6 px |
| ⑤ | projected **상대** x | 12 | 7.882 px | 26.18 px (first idx 8) |
| ⑥ | DOM **상대** x | 12 | 7.976 px | 26.49 px (first idx 9) |

`displayDistM` 단조성: 역행 **0**. `vsDisplay` 오차 6.1e-8 — displayDistM → lngLat 변환 자체는 정확하다.

### 판정

```
④ lngLat 완전히 깨끗         →  이 trace 에서 경로 거리 → 좌표 변환은 왕복을 만들지 않았다
⑤ projected 에서 처음 왕복    →  이 trace 의 최초 관측 지점
⑤ 7.88 px → ⑥ 7.98 px        →  DOM 은 투영 결과를 거의 그대로 옮긴다 (증폭 0.09 px)
```

`branchPeer = "카메라·투영"` · `branchSelf = "미분기"`

**이 분기값은 판정기가 「이 trace 에서 처음 더러워진 단계」를 적은 것이지, 원인 확정이 아니다.**
11.45 Hz(87 ms) 기록이므로 그보다 빠른 성분이 앞 단계에 있었다면 잡히지 않는다.

### self 의 반전 0 을 「카메라 무죄」로 읽으면 안 된다

카메라는 self 를 따라가므로 **self 는 항상 화면 중앙 부근에 고정**된다. 카메라가 흔들리면 self 도 같이 흔들려 **상쇄**된다. self 는 구조적으로 카메라 변동을 드러낼 수 없는 위치에 있다. 반대로 **peer 는 중심에서 떨어져 있어 카메라 파라미터의 미세 변동이 거리에 비례해 증폭**된다.

### bearing 가설 — 자릿수 검산

```
화면상 peer-self 거리   2.185 m × 83.44 px/m ≈ 182 px      (pxPerM 은 S4-12 실측)
S4-14 카메라 bearing    peak-to-peak 1.426° = 0.0249 rad
증폭 추정               182 × 0.0249 ≈ 4.5 px
S4-15 관측              7.88 px
```

**같은 자릿수다.** bearing(회전) 흔들림이 유력 후보지만, **이번 데이터로 확정된 것은 아니다.** center·pitch·zoom 과 갈라야 한다.

## 8. 반드시 지켜야 할 전제

### 8-1. 싱크 정확도는 퇴보 불가 (Chief 확정)

개발 초반에 **브로드캐스팅 간격을 넓히고 보간으로 메우는** 접근을 이미 시도했고, 그 결과 **A 화면에서는 A 가 1등, B 화면에서는 B 가 1등**으로 보일 만큼 싱크가 어긋났다. 이를 줄이려고 간격을 좁힌 것이 지금의 구조이고, 그것이 Firestore 비용 문제로 이어졌다.

```
현재 싱크 정확도는 「완전 해결은 아니어도 인정할 수 있는 수준」이다
이 수준이 퇴보해서는 안 된다
간격 확대 + 보간으로 단순 회귀하는 안은 옛 문제의 재발이다
둘이 충돌한다면 완전히 새로운 접근을 찾아야 한다
```

### 8-2. 비용선과 증상선의 분리

**우선순위는 비용 실험이 아니라 동시 주행 peer 튐 해결이다.** 적응 발행 + 흡수는 Firebase 비용 연구선으로 **따로 보존**하고 현재 증상과 섞지 않는다.

### 8-3. 관성 관점 (Chief 제기 · 유효한 방향으로 보존)

자전거는 속도(관성)를 가지므로 **1초 이하의 짧은 순간에 톡톡 튀는 움직임 자체가 물리적으로 불가능하다.** 움직임을 느끼지 못하게 만드는 문제를 「자전거의 속도」 관점에서 따질 수 있고, 이는 read 폭증 문제와도 연결된다. 제품에는 이미 실측 기반 가감속 포락선이 있다.

```ts
// apps/web/src/lib/rideSpeedRamp.ts (사용자 확정 2026-07-14)
RIDE_SPEED_ACCEL_KMH_PER_SEC = 20 / 7.5   // 0.741 m/s²
RIDE_SPEED_DECEL_KMH_PER_SEC = 20 / 3     // 1.852 m/s²
```

단, S4-15 trace 에서는 **거리 단계가 이미 매끄러운데 투영 단계에서 튀었다.** 그 범위 안에서는 관성 보간만으로 해결되지 않는다. 다만 원인이 확정되지 않았으므로 이 방향을 폐기하지도 않는다.

## 10. 다음 단계 (전부 미확정 · 착수 시 이어갈 지점)

### 10-1. 카메라 파라미터 4분기

**새 계측이 거의 필요 없다.** ⑦ 로 이미 `center · bearing · pitch · zoom` 을 같은 프레임에 기록하고 있다. 각 파라미터의 변동으로 **예상되는 화면 이동량을 계산해 실측 7.88 px 와 대조**한다. 다만 **11.45 Hz trace 로 이 분기를 확정할 수 있다고 전제하지 않는다** — 10-2 와 함께 해야 한다.

```
bearing   회전 — 중심에서 먼 점일수록 반경에 비례해 증폭. 산수상 1순위 (§4)
center    평행이동 — self 도 같이 움직여 상대좌표에서는 상쇄되는 쪽
pitch     기울기 — 원근이 바뀌어 거리에 따라 다르게 움직인다
zoom      배율 — 중심 기준 확대·축소
```

### 10-2. W-1 동시 처리

11 Hz 기록으로는 60 fps 에서의 실제 진동 폭을 볼 수 없다. **단일 브라우저 조건**으로 한 번 더 캡처해야 한다.

### 10-3. 금지 사항 (유지)

```
어느 파라미터인지 확정되기 전에는 보간 상수·마커 로직·카메라 코드를 수정하지 않는다
캡처 로그는 「회귀 replay」가 아니라 「실패 trace」로 표기한다 (kind: fail-trace-not-replay)
새 노브·상수·예측 알고리즘을 먼저 지시하지 않는다
```
