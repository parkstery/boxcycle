## 1. 목적

실내 자전거 앱 RTW에서 **혼자 1분 주행**과 **같은 Trail 2인 동시 1분 주행**이 Firestore에 남기는 트래픽 차이를, 결제 개요(일 합계)가 아니라 **분 단위 시계열**로 비교한다.

질문:

1. 2인은 1인 대비 읽기·쓰기가 얼마나 커지는가?
2. 비용 신호의 주범이 **쓰기(하트비트)** 인가 **읽기/리스너** 인가?
3. 이후 최적화를 어디에 걸어야 하는가?

캡처 시점의 슬라이딩 60분 합계:

| 지표 | 값 |
|------|-----|
| 읽기 | **1.9만** |
| 쓰기 | **2.2천** |
| 삭제 | **65** |
| 스냅샷 리스너 최다 | **79** |
| 활성 연결 최다 | **7** |

읽기:쓰기 ≈ **8.6 : 1** — 청구·체감 모두 **읽기 우세**.

| **08:19–08:20** | **363** | **118** | 1 | **1인 주행 창과 일치** |

## 4. 비교 분석

### 4.1 1인 vs 2인 (분당 대표값)

| | 1인 (08:19–08:20) | 2인 본구간 (08:24–08:25) | 배수 |
|--|--:|--:|--:|
| 읽기/분 | 363 | 1,200 | **×3.3** |
| 쓰기/분 | 118 | 252 | **×2.1** |
| 읽기+쓰기/분 | 481 | 1,452 | **×3.0** |

2인 직전 분(08:23–08:24: 읽기 1.4천·쓰기 280)은 **합류·구독 개설**이 겹쳐 본구간보다도 읽기가 크다.  
→ **2인 비용의 상당 부분은 “달리는 중”뿐 아니라 “붙는 순간”에 발생**한다.

### 4.2 조용 구간 대비

| | baseline (08:21–08:22) | 1인 | 2인(08:24) |
|--|--:|--:|--:|
| 읽기/분 | 45 | 363 (**×8**) | 1,200 (**×27**) |
| 쓰기/분 | 1 | 118 | 252 |

1분 주행만으로도 조용 상태 대비 읽기가 한 자릿수 배, 2인은 **수십 배**로 뛴다.

### 4.3 슬라이딩 합계를 쓰지 않은 이유

재측정 중 T0→T1에서 60분 합계 읽기·쓰기가 **감소**했다.  
원인은 절약이 아니라 **창에서 이전 08:05 피크가 빠졌기 때문**.  
따라서 **전후 누적 델타 비교는 기각**하고, **분당 호버 + 주행 ISO 시각 정렬**을 정본으로 둔다.

### 4.4 구조적 함의

1. **읽기 ≫ 쓰기** — `liveCourseRides` 주기 write뿐 아니라 **스냅샷 리스너·쿼리 증폭**이 청구를  Mil다.
2. **연결 수(≤7) ≪ 리스너(피크 79)** — 탭/클라이언트가 적을수록도 **문서·컬렉션 구독 개수**가 읽기를 폭발시킨다.
3. **2인 ≈ 쓰기는 약 2배, 읽기는 약 3배+** — 동행은 write 복제보다 **상호 구독·presence·activity 읽기** 비용이 더 민감하다.
4. **08:05 초대형 피크**는 1차 측정(실패 재시도·겹친 세션)과 일치 — 측정 규율(분리·quiet)이 없으면 분석이 오염된다.

## 6. 권장 후속

1. **코드 측**
   - 동행 시 `onSnapshot` 범위·개수 감사 (연결당 리스너 상한).
   - `liveCourseRides` / Trail member / routeActivity 구독이 2인에서 어떻게 겹치는지 경로 맵.
   - 합류 순간 one-shot `get` vs 장기 listener 재검토.
2. **계측 측**
   - 동일 프로토콜로 3회 반복해 분당 표 분산 확인.
   - 가능하면 Cloud Monitoring으로 동일 창 API 추출(호버 수동 의존 제거).
3. **제품 측**
