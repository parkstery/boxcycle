## 1. 목표와 실행 원칙

사용자가 RTW를 **“운동하면 내 길이 남고, 다음에 그 길을 이어 달리는 앱”**으로 이해하고 자발적으로 다시 사용하는지 검증한다. 핵심 판타지 「Ride = Claim」을 결과 화면 → 다음 접속 → 주행 중 경험 순으로 드러낸다.

2026-09-07 사용자 요청은 실행 계획과 1단계 지시서 작성이다. 이 문서는 향후 코딩의 범위·순서를 정한다. 작성 시점에 제품 코드 변경·배포·사용자 모집은 수행하지 않았다. 시장 점유·매출·재방문 개선은 아직 검증되지 않은 가설이다.

- 기존 다음 주행 카드·재개·Claim 파이프라인을 재사용한다. 구현된 기능을 새 시스템으로 대체하지 않는다.
- 각 단계의 수용 기준과 회귀 검증이 통과한 뒤 다음 단계로 진행한다. 기간은 담당자 1명 기준 추정이며 확정 일정이 아니다.
- 현재 단계는 [0A 계약 보완 → 0B 필요한 구조 수정](ops/ride-relay/260907-Ride-결과계약-0단계-작업지시서.md)이다. 0B 검증 후 기존 1단계에 착수한다. 2단계 이후는 방향과 게이트이며, 착수 전에 별도 상세 지시서를 작성한다.
- 기존 인정 수치·Trust Tier·무료/유료 정책·완주 기준·용어는 각 SoT를 따른다. Journey라는 신규 제품명·모델은 이번 계획에서 확정하지 않는다.

## 2. 코드에서 확인한 출발점

| 기존 자산 | 확인한 코드 | 이번 계획에서의 취급 |
|---|---|---|
| 모든 유효 Ride의 결과 시트 | `apps/web/src/components/ride/RideSummarySheet.tsx` | 1단계 주 작업면. 지금은 오늘 거리 중심이며 새 도로는 선택적 한 줄 |
| 종료 스냅샷·실제 종료 anchor | `apps/web/src/hooks/useRideEndAndPersistence.ts`, `lib/rideEndResult.ts` | 재개 offset을 뺀 세션 구간을 재사용. 로컬 recordId와 서버 rideId 연결을 보강 |
| 새 도로 표시 | `apps/web/src/App.tsx`의 `conquestSummaryLine` | 현재 계정 누적값과 baseline의 차이. 결과 시트에는 해당 Ride의 서버 집계값을 연결할 필요 |
| 서버 인정 결과 | `functions/src/conquestOnRideCreated.ts` | `rides/{rideId}.conquestResult.newMeters`가 존재. 클라이언트에서 새 인정 계산을 만들지 않음 |
| 내 도로망 구독·궤적 | `apps/web/src/hooks/useConquest.ts`, `lib/firestoreConquest.ts` | 이미 로드한 데이터 재사용. 결과 시트를 위해 전체 재조회하지 않음 |
| 다음 주행·재개 | `components/ride/NextRideCard.tsx`, `lib/nextRideTarget.ts` | 2단계에서 첫 화면의 위계를 높임. 기존 파생 규칙 유지 |

이 표는 소스 열람 결과이며 실행 시험 결과가 아니다. 상태보드의 완료 표시를 새 검증 결과로 간주하지 않는다.

## 3. 단계별 실행 순서

| 단계 / 예상 기간 | 사용자에게 생기는 변화 | 구현 범위 | 다음 단계 진입 조건 |
|---|---|---|---|
| **0A. 결과 계약 보완 / 범위 확인 후 산정** | 후속 화면에 전달할 결과의 의미가 확정된다 | 기존 조사 재사용, ID·거리 변환·상태 전이·실패 계약, 수정 판정 | 계약·회귀 fixture·수정 범위 확정 |
| **0B. 필요한 구조 수정 / 0A에서 산정** | 기존 화면에서 결과와 재개가 일관되게 동작한다 | Ride 동일성, 종료 스냅샷, 해당 Ride 집계, 필요한 거리 변환 보정 | 0단계 C1~C14 검증 및 후속 API 인계 |
| **1. 도로망 성취 결과 / 0B 이후 재산정** | 종료 직후 이번에 달린 길과 인정된 새 도로를 이해한다 | 검증된 결과 모델을 사용한 세션 궤적 미리보기, 결과 시각 위계, 기존 다음 행동 보존 | 1단계 수용표 전 항목 PASS. 집계 지연·재주행·재개·계정 전환 회귀 통과 |
| **2. 다음 접속의 목적 / 3~5 개발일** | 내 도로망과 이어 달릴 대상이 첫 화면에서 보인다 | 기존 NextRideCard 우선 노출·가독성, 적절한 초기 지도 범위, 데이터 없는 첫 사용자에게 기존 입문 코스 진입 제공 | 새로고침·다른 날 접속·완주·삭제 경로·legacy에서 올바른 CTA. 시작 게이트 유지 |
| **3. 주행 중 변화와 선택 정리 / 3~5 개발일** | 달리는 중에도 자신의 진행을 읽고 조작을 덜 한다 | 라이브 궤적/진행률 위계, 주행 중 불필요한 편집 UI 접기, 기존 추천 코스 제목·목적지 표현 개선 | 센서 준비→Go→주행→종료→재개 전체 흐름과 좁은 화면 통과 |
| **4. 사용성·재방문 실험 / 준비 2~3일 + 관찰 4주** | 작은 대상 집단이 자기 기기로 반복 사용한다 | 측정 배선, 호환 조합 안내, 테스트 사용자 모집안, 고정 주제·시간의 동행 운영안 | 실제 사용자 행동과 이탈 원인으로 확대·수정·중단 판단 |
| **5. 공유·유료 가치 검증 / 4단계 근거 후 산정** | 누적 성취를 보관·공유할 이유가 생긴다 | 실내 주행 표기와 공개 범위를 갖춘 지도 공유/내보내기, 기존 유료 정책 안의 제공안·가격 실험 | 실제 결제 및 사용자별 지도·서버·지원 비용 확인 |

0~3단계 전체를 1~2주로 확약하지 않는다. 종전 1단계 3~5일 추정은 철회하고 0A에서 구조 수정 범위를 확인한 뒤, 0B 완료 시 UI 작업량을 재산정한다.

## 4. 범위와 기존 작업의 관계

- [다음 주행 기존 지시서](ops/ride-relay/260829-다음-주행-이어달리기-작업지시서.md)의 파생 후보·진행률 단조 보존·Go 게이트 계약을 유지한다.
- [폰 실사용 결함 4A](ops/route-relay/260903-폰-실사용-결함3건-4A-작업지시서.md)의 이어가기 값 승계가 대상 브랜치에서 재현되면 2단계 선행 결함으로 추적한다. 해결되지 않은 상태를 새 디자인 완료로 덮지 않는다.
- [센서 표면 정리 6A](ops/route-relay/260905-화면정리-센서칩-RouteDock-6A-작업지시서.md)는 3단계와 겹친다. 착수 시 실제 반영 여부를 확인하고 같은 UI를 두 번 이동하지 않는다.
- 카메라는 기존 상공 기본값, 궤적은 기존 BlueViolet와 굵기·glow 구분을 유지한다. 앞선 자문의 기울어진 시점 제안은 검증 후보이며 이번 채택 사항이 아니다.
- 도시 전체 정복률, 새로운 목적지 판정 시스템, AI 추천, 전면 3D 교체, 랭킹·토큰 경제·센서 프로토콜 확장은 이 계획의 선행조건이 아니다.
- 추천 코스는 실제 geometry·기존 Publication을 확인한 소수로 시작한다. 임의의 ‘20분 도착’ 약속과 도시 커버리지 %를 만들지 않는다.

## 5. 사용자 검증 설계

초기 대상 가설은 **연결 가능한 실내 자전거/센서를 갖고, 기록 경쟁보다 가벼운 반복 운동을 원하며, 지도·여행·수집에 관심 있는 사용자**다. 검증한 센서·OS·브라우저 조합을 안내한 뒤 20명 안팎으로 시작한다. 모집·메시지 발송은 별도 실행 요청 때 수행한다.

| 측정 | 정의 | 해석 |
|---|---|---|
| 첫 사용 성공 | 모집 인원 중 도움 없이 입력 준비와 첫 유효 Ride 종료까지 완료한 인원 | 연결 실패와 화면 이해 실패를 분리 |
| 첫 성취 이해 | 결과를 본 후 ‘오늘 거리’와 ‘새 도로’ 차이를 자기 말로 설명 | 호감 점수보다 가치 전달 확인 |
| 다른 날 재사용 | 첫 유효 Ride 이후 다른 현지 날짜에 다시 유효 Ride를 남긴 인원 | 동일 날 반복 테스트와 구분 |
| 4주차 재사용 | 최초 사용일 기준 22~28일에 유효 Ride가 있는 인원 / 전체 모집 인원 | 연결 실패자도 분모에서 빼지 않음. 첫 성공자 기준 수치도 병기 |
| 자발적 재사용 | 직전 개인 독려 없이 발생한 재사용 | 운영자 독려·정기 행사·자발적 사용을 별도 기록 |
| 사용 이유 | 재방문자와 이탈자에게 지도·완성 목표가 실제 동기인지 확인 | 기능을 좋아한다는 답과 반복 행동을 구분 |

측정 구현은 기존 Ride 기록으로 가능한 항목부터 재사용한다. 추가 이벤트 후보는 `ride_summary_viewed`, `ride_summary_resolved`, `next_ride_selected`이며 이 이름은 향후 구현안이다. 외부 분석 도구 도입 전에 저장 위치·보유 기간·접근 권한을 정한다. 좌표·주소·이메일은 이벤트에 넣지 않는다. uid/rideId도 필요한 최소 범위에서 처리한다.

임시 판단 기준: 20명 중 4주차 자발적 사용 8명 이상, 복수의 사용자가 ‘길을 이어 완성하려고’ 재방문했다는 행동·설명 근거가 있으면 확대 검토한다. 업계 벤치마크나 성공 보장이 아니다. 미달이면 연결/진입 실패를 먼저 고치고, 충분히 경험한 사용자도 돌아오지 않으면 기능 확장보다 핵심 약속을 재검토한다.

## 6. 개발팀장의 완료 보고

각 단계는 변경 파일, 수용표, 실행 명령·종료 코드·skip 수, 화면 증거, 남은 결함을 제출한다. 완료 보고는 `document/archive/`에 날짜 접두어로 작성한다. 상태보드는 실제 코드 반영 이후 해당 기호만 갱신한다. 1단계의 구체적인 계약은 연결된 지시서를 따른다.
