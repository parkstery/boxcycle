## 1. 이 계획이 답하려는 것

원안의 문제 제기는 **“어디를 달려야 하지?”** 다. 첫 사용자에게 100% 자유 선택을 주면 시작점이 없고, Street View를 쓰지 않기로 한 이상 지도만으로는 특정 장소에 대한 호기심이 생기지 않는다.

원안의 답 — **Recognition → Ride → Claim → Explore → Choose** — 은 채택한다. 이는 상태보드 §3.5의 「목표 계층화 표면 원칙」(첫 화면은 오늘의 작은 목표, 세계 점령률은 뒤로, 07-12 채택)과 같은 방향이며, 지금 💭로 비어 있는 온보딩 표면의 구체안이다.

다만 **원안의 구현 분량 추정은 과대하다.** 원안 Phase 1이 새로 만들자고 한 것의 상당 부분이 이미 제품에 있고(§2), 반대로 원안이 비중을 두지 않은 표면 작업이 실제 가설 검증 변수(§3.1)다. 이 문서는 그 교정본이다.

### 1.1 실행 원칙

- 구현된 기능을 새 시스템으로 대체하지 않는다. `distanceAutoRoute`·`NextRideCard`·입문 코스·Conquest 집계를 **재사용**한다.
- 측정할 수단이 없는 판정 항목은 만들지 않는다. 축퇴값(항상 같은 값)으로 게이트가 자동 통과하는 구조를 금지한다.
- 각 단계는 수용 기준과 회귀 검증이 통과한 뒤 다음으로 간다. 기간은 담당자 1명 기준 **추정**이며 확약이 아니다.
- 용어·인정 수치·tier 정책·완주 기준은 각 SoT를 따른다. 신규 제품명은 [Ontology §2](260714-RTW-Ontology.md) 등재 전에는 코드·UI에 쓰지 않는다(§4).

## 3. 원안에서 바꾸는 것 (근거 포함)

### 3.1 위치 권한은 첫 화면에 두지 않는다

원안 §5는 “첫 실행 시 GPS → 국가 → 지역 → 도시”, §6은 “권한 거부 시 수동 선택”이다. 두 절이 사실상 다른 첫 화면을 말한다. **§6으로 통일한다.**

- 첫 화면은 권한 요청 없이 **`[지역 선택]` + `[현재 위치]`** 두 버튼. 권한 프롬프트는 사용자가 `[현재 위치]`를 누를 때만 띄운다.
- 근거: ① 앱은 폰 가로 전용·실내 사용이라 GPS 정밀도의 제품 이득이 작다 ② 첫 화면 권한 프롬프트는 첫 이탈 지점이 된다 ③ 지금 코드에 GPS 경로가 전혀 없어 실패 모드(거부·타임아웃·부정확·HTTPS 제약)를 전부 새로 떠안는다.
- 위치는 지역 단위로 일반화해 사용한다(원안 §5 말미와 동일). 좌표는 분석 이벤트에 넣지 않는다([260907 §5](260907-RTW-도로망-성취경험-실행계획.md)).

### 3.2 첫 Ready Ride는 5~10 km가 아니라 기본 3 km · 사용자 선택

원안 §9는 첫 목표를 5~10 km로 잡았다. 그러나 현재 프로덕션 입문 코스는 **400 m대**다. 첫 주행에서 검증해야 할 것은 지구력이 아니라 **“달리면 내 길이 남는다”의 1회 완결**이며, 첫 세션이 길수록 첫 Claim 도달률이 떨어진다.

- 첫 Ready Ride 기본값 **3 km**, 선택지 **2 / 5 / 10 km**. 5~10 km는 2회차 이후 기본값으로 옮긴다.
- 입문 코스(400 m대)는 폐기하지 않는다. **「내 지역에서 시작」(Ready Ride)** 과 **「입문 경로로 시작」(기존 3경로)** 을 같은 카드의 두 선택지로 둔다. 어느 쪽이 첫 주행 완료율이 높은지는 LF-4에서 관측한다.

### 3.3 자체 도로 그래프(Edge/Node)를 만들지 않는다

원안 §8·§20은 도로망을 그래프로 적재해 Edge를 조합하는 구조다. **미채택**한다.

- 우리는 Mapbox Directions 응답을 경로 진실로 쓰는 구조이고, 자체 그래프는 OSM 원데이터 수집·갱신 파이프라인을 요구한다. “전 세계 어디서나”라는 요구와 가장 비싸게 충돌한다.
- 같은 결과는 **후보 스윕 확장**으로 얻는다: 방위 자동 선택 + 폐합(출발=도착) + 스코어 항목 추가. 이미 `AUTO_ROUTE_DISTANCE_FACTORS`·`AUTO_ROUTE_BEARING_OFFSETS_DEG`가 그 형태다.
- 재검토 조건: 후보 스윕으로 폐합 성공률이 목표에 미달하고, 프로바이더 호출 예산(현 13회)을 늘려도 개선되지 않을 때. 그때 별도 결정 로그를 거친다.

### 3.4 v1 Route Score는 **측정 가능한 5개**로 제한한다

원안 §11의 항목 중 상당수는 Directions 응답만으로 판정 근거가 없다.

| 원안 항목 | v1 채택 | 사유 |
|---|---|---|
| 거리 적합성 | ✅ | `scoreRouteDistanceError` 기구현 |
| 주행 가능성 | ✅ | `profile: cycling` 라우팅 성공 여부로 대리 |
| 지역성(출발점 이격) | ✅ | 출발점–경로 거리로 계산 가능 |
| 신규 도로 비율 | ✅ | `conquest/{uid}` 겹침으로 계산 가능 |
| 과도한 반복(중복 구간) | ✅ | 자기 겹침 길이 비율 — [5A](ops/route-relay/260904-자동Route-중복구간-정복손실-5A-작업지시서.md)와 동일 항목 |
| 복잡한 교차로 · 막다른 길 · 주행 부적합 도로 · 경로 다양성 · 주행 단순성 | ❌ 미측정 | 현 데이터로 판정 근거 없음. 항상 같은 값이 되어 **게이트를 자동 통과**시킨다 |

미측정 항목은 문서에서 지우지 않고 **「미측정」으로 표시**해 둔다. 판정 코드에는 넣지 않는다.

### 3.5 Mission 체계(원안 Phase 3)는 보류한다

Mission 1/2/3이 하려는 일(가까운 곳 → 넓은 범위 → 미주행 도로)은 기구현된 **`NextRideCard`(다음 주행·이어 달리기)** 의 파라미터 변경으로 더 싸게 달성된다. 미션 상태·완료·해금이라는 새 상태 기계의 비용 대비 이득이 작다.

대신 원안 Phase 4(Claim 연동)를 **앞당긴다.** `conquestResult.newMeters`가 이미 서버에 있어 「안 달린 길 우선」은 지금 스코어 한 항목이다.

### 3.6 Route Token — 당분간 무제한 (2026-09-24 Chief)

첫 Ready Ride 에 토큰을 물릴지 묻는 질문에 Chief 는 **「적정 부여·소모를 다시 고민해야 하니 현재
시점에서는 모두 무제한」** 으로 답했다. 따라서 이 계획에서 토큰은 **변수에서 제외**한다.

- 생성 비용은 `config/routeTokenEconomy.generateCostBase = 0`. `spendRouteGenerateToken` 이
  `cost === 0` 에서 차감을 건너뛰는 분기를 이미 갖고 있으므로 **새 우회로를 만들지 않는다**
- 토큰 시스템 코드는 **삭제하지 않는다**(원장·적립·온보딩 지급 유지). 한 값으로 껐다 켠다
- **출시 전 복원 대상**이며, 복원은 「원래 값으로 되돌리기」가 아니라 **재설계 후**다
- tier quota(수량 한도)는 별개 축이다 — 이번 결정 범위가 아니다

### 3.7 첫 화면 카메라는 「아는 곳을 인식할 수 있는 스케일」 (2026-09-24 Chief)

LF-1 캡처에서 S0(지역 미정) 첫 화면이 **10m 줌의 이름 없는 골목**이었다. Recognition 을 목표로 한
화면의 첫인상으로 맞지 않는다. 지역을 고르기 **전에도** 시·구·동 라벨이 읽히는 스케일로 연다.

판정 기준은 줌 숫자가 아니라 **폰 가로(740×300)에서 라벨이 읽히는가** 다 — LF-1 이 지역 확정 후
줌 13 을 같은 기준으로 채택했다. 기존 NextRideCard 앵커 점프·주행 카메라·Quick Camera 와
경합시키지 않는다. 첫 화면 한 번의 초기값 문제이지 카메라 시스템 변경이 아니다.

### 3.8 Recognition의 전달 매체는 스코어가 아니라 표면이다

원안은 §12 Locality Score(계산)에 무게를 실었지만, 실내 주행에서 “여기 내가 아는 곳인데”를 만드는 것은 **초기 카메라·지명 라벨·카피**다. 로컬리티 점수가 아무리 정교해도 화면이 저축척으로 열리면 Recognition은 발생하지 않는다. LF-1(표면)을 LF-2(생성기)보다 **먼저** 한다.

## 4. 용어 — 착수 전 처리 필요

**결정(2026-09-23, Chief):** 「Ready Ride」를 **사용자 노출 명칭으로 쓴다.** [Ontology §2.2](260714-RTW-Ontology.md)에 등재 완료.

- 표기는 **영문 그대로 「Ready Ride」**, 한국어 문장에서는 조사를 붙인다 — 「Ready Ride를 시작」·「내 지역 Ready Ride」. 한글 음차(레디 라이드)·번역어를 병행하지 않는다.
- **데이터 모델은 만들지 않는다.** Ready Ride의 그릇은 **Route**(필요 시 SavedRoute로 저장)다. 따라서 쿼터·완주 판정·Claim 처리는 기존 Route/SavedRoute 규칙을 그대로 따르며, 새 컬렉션·새 상태 기계를 추가하지 않는다.
- **인접 표면과 구분이 필요하다(LF-1 카피 작업의 제약):** 추천 코스(목록에서 고름) · 입문 코스(고정 3경로) · **Ready Ride**(한 건이 제시됨)는 서로 다르다. 첫 화면에 셋이 동시에 뜨면 선택지 과잉이 되므로 §3.2·Q2의 배치를 따른다.
- 나머지 원안 용어 `Free Ride`·`Mission`·`Local First Ride`는 **등재하지 않는다** — 내부 문서 용어로만 쓰고 UI에 노출하지 않는다(Mission은 §3.5로 보류 상태).
- 원안 §3의 Claim 정의(“소유·점령이 아니라 주행으로 확보한 길”)는 Ontology §2.4와 일치한다 — 그대로 유지한다.
- 금지어 확인: 원안에 `Room`·`Lobby`·`course`는 없다. 통과.

## 6. 성공 지표

원안 §21을 채택하되, 지금 산출 가능한 것과 아닌 것을 구분한다.

| 지표 | 정의 | 현재 산출 가능성 |
|---|---|---|
| ① 첫 Ready Ride 시작률 | 첫 화면 도달 중 Go까지 간 비율 | 이벤트 신설 필요 |
| ② 첫 주행 완료율 | 시작 중 유효 Ride 종료까지 간 비율 | 기존 Ride 기록으로 근사 가능 |
| ③ 72시간 내 2번째 유효 주행률 | [260907 §5](260907-RTW-도로망-성취경험-실행계획.md)의 「다른 날 재사용」과 정합 | 기존 Ride 기록으로 산출 가능 |
| ④ 자유 경로 전환율 | Ready Ride 사용자가 직접 경로 설정으로 넘어간 비율 | 이벤트 신설 필요 |
| ⑤ 신규 도로 Claim 비율 | Ride의 `conquestResult.newMeters` / 총 거리 | **기존 서버 집계로 즉시 산출 가능** |

총 주행거리는 성공 지표로 쓰지 않는다(원안과 동일).

## 7. 하지 않을 것

원안 §22를 유지하고 다음을 추가한다.

1. AI가 경로를 창작하게 하지 않는다 (원안과 동일).
2. 전 세계 도시 코스를 사람이 미리 제작하지 않는다 (원안과 동일).
3. **자체 도로 그래프를 만들지 않는다** (§3.3 — 추가).
4. **측정 근거가 없는 스코어 항목을 판정에 넣지 않는다** (§3.4 — 추가).
5. **첫 화면에서 위치 권한을 요청하지 않는다** (§3.1 — 추가).
6. **입문 코스를 제거하지 않는다** (§3.2 — 추가).
7. 새 데이터 모델(Ready Ride 전용 컬렉션)을 만들지 않는다 (§4 — 추가).
