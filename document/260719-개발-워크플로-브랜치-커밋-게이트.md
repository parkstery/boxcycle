| 항목 | 내용 |
|------|------|
| 문서 유형 | **운영 규칙** — 브랜치 전략·커밋/푸시 타이밍·품질 게이트 |
| 작성 | 2026-07-19 |
| 배경 | 하나의 브랜치에 109커밋이 여러 기능(카메라·GLB·맵·퍼블릭 경로·용어)으로 뒤섞여 쌓임 → 코드 리뷰 불가·리팩토링 위험. 자동화 장치 부재(husky·hooks·CI 전무). |

> **한 줄 원칙**: 커밋은 **작게 자주**(품질 게이트가 지킴), 푸시는 **덩어리 단위**(타입 게이트가 지킴), 브랜치는 **짧게** 살고 `main2`로 돌아온다.

---

## 1. 브랜치 전략 — `main2`를 개발 base로

`main`은 건드리지 않는 **최종 안정선**으로 둔다. 실제 개발은 **`main2`** 위에서 진행한다.

```
main            ← 최종 안정선. 모든 개발 완료 시점에 main2 를 한 번에 병합.
 └── main2       ← 개발 base(기둥). 여기서 브랜칭하고, 여기로 merge.
      ├── feat/rider-brake-anim     ← 짧게 살고 merge 후 삭제
      ├── feat/conquest-layer
      └── refactor/route-publication
```

규칙:

- **모험적·독립적 작업은 `main2`에서 브랜칭**한다. 브랜치명은 `feat/…` `fix/…` `refactor/…` `chore/…`.
- 작업이 끝나면 **`main2`로 merge**하고 브랜치를 **삭제**한다(`git branch -d`). 실패한 실험은 `-D`로 버린다.
- 브랜치는 **짧게**(수 시간~며칠) 산다. 브랜치가 여러 기능을 담기 시작하면 이미 실패 — 그게 이번 109커밋 사태의 원인.
- **`main2` → `main` 병합은 "모든 개발 완료" 한 시점에 한 번**. 그전까지 main은 손대지 않는다.

왜 병합을 미루나: 현재 `main2`가 사실상 기둥 역할을 하고 있고 main과 격차가 커서, 지금 억지로 쪼개 main에 밀어넣는 것은 위험·무익. `main2`를 개발선으로 승격시키는 게 현실적.

**코드 리뷰는 `main2 ← 기능 브랜치` diff 단위**로 한다. main 대비 전체 diff는 리뷰 대상이 아니다.

## 2. 커밋·푸시 타이밍

이전 커서 방식("작은 수정마다 커밋, 덩어리마다 푸시")을 규칙으로 고정한다.

| 시점 | 행동 | 이유 |
|---|---|---|
| 작은 수정 하나 완료 | **커밋** | 워킹트리에 여러 기능이 누적되는 걸 원천 차단. `add -p` 수술 불필요해짐 |
| 기능/의미 단위 완료 | **푸시** | 원격 백업 + 리뷰 가능 단위 형성 |
| 하루 작업 종료 | **푸시** | SSD 고장·폴더 손상 대비 백업 (혼자 개발이어도 GitHub는 백업 수단) |

커밋 메시지는 Conventional Commit: `feat(scope): …` `fix(scope): …` `docs:` `refactor:` `chore:`.

**핵심**: 커밋을 자주 하면 커밋 정리가 "절차"로 내려가 하위 모델(Haiku/Sonnet)로도 안전. 워킹트리를 방치하면 정리가 "판단"이 되어 상위 모델이 필요해진다 — 모델 등급을 낮추는 진짜 방법은 **상태를 단순하게 유지**하는 것.

## 3. 품질 게이트 (자동화)

의존성 없는 **순정 git hook**. `core.hooksPath = githooks`로 활성화. **강제는 게이트만** — 커밋 자체를 자동으로 눌러주진 않는다(의미 없는 대량 커밋 방지).

| 훅 | 검사 | 대상 | 비용 |
|---|---|---|---|
| [githooks/pre-commit](../githooks/pre-commit) | **eslint** | 스테이징된 변경 파일만 | ~1–2s (가벼움, 자주 커밋 가능) |
| [githooks/pre-push](../githooks/pre-push) | **tsc --noEmit** | 이번 push로 나가는 변경이 닿은 워크스페이스 | ~12s (푸시 때만) |

설계 의도: typecheck(12초)를 pre-commit에 넣으면 "작게 자주 커밋"이 깨진다 → **커밋엔 lint만, 푸시엔 typecheck**. 커밋은 가볍고, 원격엔 타입 깨진 코드가 안 나간다.

**활성화 (clone 후 1회, 리포당 1회)**:

```bash
git config core.hooksPath githooks
```

**우회 (예외 상황 한정)**: `git commit --no-verify` / `git push --no-verify`. WIP 커밋을 잠깐 남길 때만. 상시 우회는 게이트를 무력화하니 금지.

향후: 여럿이 붙거나 배포가 잦아지면 GitHub Actions(PR에서 lint+build) 추가 검토 — 지금은 로컬 게이트로 충분.

## 4. 요약 체크리스트

- [ ] 새 작업 → `main2`에서 `git switch -c feat/…`
- [ ] 작은 수정마다 → `git commit` (pre-commit lint 자동)
- [ ] 기능 완료 → `git push` (pre-push typecheck 자동) → `main2`로 merge → 브랜치 삭제
- [ ] 워킹트리에 두 기능이 섞이기 시작하면 → 멈추고 먼저 커밋
- [ ] 전체 개발 완료 시 → `main2` → `main` 한 번 병합
