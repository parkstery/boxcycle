## 0. 실행 주체 방침 (2026-08-12 개정 — 이 문서의 나머지보다 우선한다)

**오케스트레이터는 Claude가 직접 설계·구현·시험한다.** 초판에 있던 「Claude가 지시서를 쓰고 Cursor가 오케스트레이터를 구현한다」는 전달 구조는 **폐기됐다.**

- 오케스트레이터 코드·테스트·E2E 검증의 실행자는 Claude다. 구현을 넘기기 위한 Cursor 수신용 지시서는 작성하지 않는다.
- Cursor 실행을 오케스트레이터가 자동으로 트리거하지 않는다. actor 자동 실행은 이 문서의 어느 단계에서도 승인되지 않았다.
- 이 개정은 **오케스트레이터 개발**에만 적용된다. `sync-relay`·`cyclefit-relay` 같은 **제품 작업선의 역할 분담은 그대로**이며, 감리 대상 REPORT를 누가 썼는지와 무관하게 감리 계약은 동일하다.
- 본문의 「개발 구현·개발 담당」은 **제품 작업선의 개발 역할**을 가리키는 일반 명사이며, 특정 외부 도구를 지정하지 않는다.

## 1. Claude에게 맡기는 책임

Claude는 RTW 오케스트레이션 시스템의 **설계·계획·지시·감리 책임자**다.

- Chief의 목적을 운영 계약과 수용 기준으로 바꾼다.
- 기존 1단계 PoC를 독립적으로 조사하고 유지·폐기·재사용 범위를 결정한다.
- 오케스트레이터 코드와 테스트를 **직접 구현**한다(§0).
- 자신의 구현 결과와 실제 E2E를 스스로 시험하고, 증거를 Chief가 재현할 수 있게 남긴다.
- 중요한 운영 선택과 위험은 Chief에게 결정 카드로 올린다.

Codex는 구현자가 아니다. Codex는 Chief의 자문과 Claude 산출물의 독립 검토에만 참여한다.

## 2. 가능성에 대한 기준 판정

오케스트레이션 자체는 기술적으로 가능하다. Claude CLI와 Codex CLI 모두 비대화식 actor로 호출할 수 있고, 상태·hash·lock·재시도·로그를 관리하는 결정론적 프로그램도 일반적인 기술로 구현할 수 있다.

그러나 다음 두 문장을 구분해야 한다.

> 파일 변화가 보이면 Claude를 한 번 호출할 수 있다.

> 시스템이 종료·재시작·중복 이벤트·actor 실패를 견디면서 Chief의 추가 조작 없이 작업을 이어간다.

현재 1단계는 첫 번째를 시험한 PoC다. Chief가 원하는 것은 두 번째다. 따라서 단위 스크립트의 성공을 오케스트레이션 완료로 보고하지 마라.

## 3. Chief가 원하는 실제 결과

Chief의 목적은 watcher 터미널을 관리하는 것이 아니다. 다음 업무 전달을 반복해서 수동 수행하지 않게 하는 것이다.

```text
Claude 지시·계획
→ Chief가 필요한 승인·결정
→ 개발 구현
→ 개발 REPORT 완료
→ Claude 자동 감리
→ 감리 판정에 따른 다음 상태
→ 필요한 경우 개발 재작업
→ Chief 최종 검토
```

장기적으로는 Claude의 지시·제안과 최종 감리 결과를 Codex가 읽기 전용으로 자동 검토하는 게이트도 포함한다.

자동화의 성공 기준은 “AI가 호출됐다”가 아니다. **산출물과 상태가 다음 책임자에게 정확히 넘어가고, 실패했을 때 멈춘 이유와 다음 행동이 드러나는 것**이다.

## 4. watcher를 바라보는 원칙

watcher는 별도로 설치하는 고유 제품명이 아니다. 현재 PoC에서는 `scripts/claude-report-audit.mjs`의 `watch` 명령이 주기적으로 파일을 확인하는 foreground 감시 프로세스다.

새 설계에서 watcher는 아키텍처가 아니라 **이벤트 감지 구현 후보 중 하나**다.

- 파일시스템 이벤트를 사용할 수 있다.
- 주기적 catch-up scan을 사용할 수 있다.
- 개발 완료 hook이나 명시적 event enqueue를 사용할 수 있다.
- Windows 작업 스케줄러·서비스·supervisor가 runner를 관리할 수 있다.

어떤 방식을 선택할지는 Claude가 운영 모델을 먼저 정의한 뒤 결정한다. 다만 결과는 다음 조건을 만족해야 한다.

1. Chief가 작업마다 별도 watcher 명령을 실행하지 않는다.
2. 터미널을 닫아도 자동화가 함께 사라지지 않는다.
3. Windows 재시작 또는 runner 재시작 뒤 미처리 작업을 다시 발견한다.
4. watcher가 잠시 죽어도 영구적으로 이벤트를 잃지 않는다.
5. watcher가 죽거나 멈추면 Chief가 알 수 있다.

실시간 파일 이벤트만 믿지 말고, 재시작 시 상태 저장소를 기준으로 미처리 작업을 다시 찾는 **catch-up 경로**를 반드시 둔다.

## 5. 구현 전에 먼저 확정할 운영 계약

Claude는 코딩을 시작하기 전에 아래 계약을 문서화하고 Chief에게 설명해야 한다.

### 5.1 작업과 artifact

- 작업을 식별하는 단위는 무엇인가?
- 지시서·REPORT·감리서·Codex 의견의 정본은 무엇인가?
- REPORT가 쓰이는 중간 상태와 완성 상태를 어떻게 구분하는가?
- artifact가 수정되면 새 attempt인가, 기존 attempt의 갱신인가?

### 5.2 event와 상태

- 어떤 사건이 다음 상태를 만든다고 인정하는가?
- 현재 책임자가 Claude·개발 담당·Codex·Chief 중 누구인지 어떻게 표시하는가?
- 대기·실행 중·완료·재작업·실패·Chief 결정 필요를 어떻게 구분하는가?
- 허용되지 않은 상태 전이는 어떻게 차단하는가?

### 5.3 실행과 복구

- actor timeout과 종료 코드를 어떻게 처리하는가?
- 재시도 횟수·간격·최종 중단 조건은 무엇인가?
- 프로세스 강제 종료·PC 재부팅·부분 출력 뒤 어디서 이어가는가?
- stale lock을 어떤 근거로 회수하는가?

### 5.4 중복과 일관성

- 동일 event를 여러 번 감지해도 결과가 한 번만 반영되게 하는가?
- 실행 중 REPORT가 바뀌면 어느 hash를 감리한 것으로 기록하는가?
- 감리 결과와 대상 지시서·REPORT·Git 기준점이 항상 연결되는가?

원칙은 **event 감지는 중복될 수 있지만 effect는 artifact hash와 expected state로 멱등하게 만든다**는 것이다.

## 6. 1차 구축 범위

전체 시스템을 한 번에 만들지 마라. 첫 완료 범위는 아래 한 구간으로 고정한다.

```text
개발 REPORT 완성(상태 = 보고완료)
→ 운영 중인 runner가 미처리 REPORT 발견
→ Claude 읽기 전용 감리
→ 구조화된 판정과 AUDIT 저장
→ Chief가 결과·실패 상태를 확인
```

이 단계에서는 다음을 하지 않는다.

- Claude가 제품 코드를 직접 수정
- Codex가 코드·문서를 직접 수정
- 자동 커밋·push·merge·deploy
- 제품 방향·UX·데이터 모델·인증·비용 정책의 자동 승인
- 제품 구현을 Orchestrator가 임의로 재지시
- 후속 actor(Cursor 포함) 자동 실행 — 어떤 형태로도 배선하지 않는다
- 여러 actor를 한 번에 연결한 전체 자동 루프

기존 `sync-relay` 제품 작업과 오케스트레이터 개발도 분리한다.

## 7. 1차 완료를 인정할 수용 기준

Claude는 숫자 한도를 조사해 명시하되, 최소한 다음 시나리오를 실제 actor E2E로 통과시켜야 한다.

1. **정상 경로** — REPORT 완성 후 Chief의 추가 명령 없이 Claude 감리가 시작되고 현재 REPORT에 대응하는 AUDIT가 생성된다.
2. **부분 작성 방지** — REPORT 작성 중에는 감리가 시작되지 않는다.
3. **중복 방지** — 같은 artifact를 여러 번 감지하거나 runner를 재시작해도 같은 감리가 중복 생성되지 않는다.
4. **수정 감지** — REPORT가 유효하게 바뀌면 새 hash에 대해 새 감리가 수행된다.
5. **동시성 차단** — 같은 task의 감리가 동시에 두 개 실행되지 않는다.
6. **actor 실패** — Claude 인증 실패·timeout·비정상 종료·스키마 오류가 성공으로 기록되지 않고 재시도 또는 BLOCKED로 남는다.
7. **runner 복구** — runner 강제 종료와 Windows 재시작 뒤 미처리 REPORT를 다시 발견한다.
8. **stale lock 복구** — 죽은 프로세스가 남긴 lock 때문에 영구 정지하지 않는다.
9. **읽기 전용 증명** — Claude 감리 전후 제품 코드와 지시서·REPORT가 변경되지 않았음을 기계적으로 확인한다.
10. **관측 가능성** — Chief가 정상 대기, 감리 중, 완료, 재시도 중, 중단을 구분할 수 있다.
11. **오래된 AUDIT 방지** — 화면이나 문서에서 현재 REPORT와 이전 AUDIT를 혼동할 수 없다.

단위 테스트와 fake actor PASS만으로는 완료가 아니다. 실제 Claude CLI를 포함한 E2E 증거가 필요하다.

## 8. runner 수명주기 결정

Claude는 다음 선택지를 실측해 비교하고 하나를 권고한다.

- 사용자 로그인 시 자동 시작되는 장기 실행 runner
- Windows 작업 스케줄러가 주기적으로 `once`를 실행하는 구조
- 별도 service/supervisor가 runner를 감시하는 구조
- 개발 완료 동작이 event를 명시적으로 enqueue하고 별도 runner가 소비하는 구조

비교 기준은 설치 난이도보다 다음이 우선이다.

- 재부팅 복구
- 누락 없는 catch-up
- 중복 방지
- 오류 가시성
- 권한 최소화
- 제거·비활성화 용이성
- Chief가 매 작업마다 수행해야 하는 조작 수

한 번의 명시적 설치·등록 절차는 허용할 수 있다. 그러나 그 절차와 자동 시작 조건을 숨기지 말고 Chief에게 먼저 설명하고 승인받아라.

## 9. actor 권한과 안전 경계

### Claude 감리 actor

- 읽기 전용이어야 한다.
- 지시서·REPORT·Git diff·보존 증거를 대조한다.
- 테스트를 새로 실행할 권한을 줄지 여부는 감리 정책에서 별도 결정한다.
- 파일 수정·commit·push·외부 통신은 금지한다.

### Codex 자문 actor

공식 OpenAI 문서상 `codex exec`는 스크립트·CI·scheduled job에서 비대화식으로 사용할 수 있고, 읽기 전용 sandbox와 기계 판독 출력을 지원한다. 따라서 장기 목표의 Codex 자동 검토 게이트는 기술적으로 가능하다.

다만 자동 Codex는 현재 Chief와 대화 중인 Codex 세션의 기억을 자동으로 이어받지 않는다. 매 실행에 다음을 명시적으로 제공해야 한다.

- `AGENTS.md`
- 자문역 프로토콜
- 해당 task의 지시·제안·REPORT·Claude 감리
- 관련 HANDOFF와 Git 기준점
- 원하는 구조화 출력 스키마

Codex actor는 명시적인 read-only sandbox로 실행하고, 산출물 원문을 직접 수정하지 않는다.

### Orchestrator

- actor의 판단 내용을 대신 만들지 않는다.
- 상태 전이·입력 hash·프로세스·결과 스키마·이벤트 로그만 관리한다.
- 제품 결정이나 감리 판정을 자체 규칙으로 추론하지 않는다.

## 10. 관측·알림 원칙

자동화는 실패를 숨기면 안 된다. 최소한 다음 상태가 서로 다른 메시지와 기록으로 남아야 한다.

- REPORT 미완성 대기
- REPORT 완성·감리 대기
- Claude 실행 중
- 감리 완료와 판정
- 재시도 예정
- 인증·권한·스키마·timeout 실패
- runner 비정상 또는 heartbeat 만료
- Chief 결정 필요

터미널을 열어야만 상태를 알 수 있는 구조는 최종 운영안으로 승인하지 않는다.

## 11. 단계별 확대 원칙

### 단계 A — 운영 계약과 fixture

상태·event·artifact·권한·복구·완료 기준을 확정하고 실제 actor 없이 상태 머신을 검증한다.

### 단계 B — Claude 자동 감리 1차 완성

개발 REPORT → Claude 감리 → AUDIT 저장 구간을 실제 Claude CLI와 운영 runner로 검증한다.

### 단계 C — Codex 읽기 전용 검토

Claude 지시·제안과 Claude 감리 결과를 별도 `codex exec`가 검토하도록 연결한다. Chief의 결정 지점은 유지한다.

### 단계 D — 구현 actor와 재작업 loop

충분한 통제 증거가 쌓이고 **Chief가 별도로 승인한 뒤에만** 구현 actor 실행과 지시 범위 내 재작업을 연결한다. 현재 방침(§0)에서 이 단계는 열려 있지 않다.

### 단계 E — 다중 task·알림·상시 운영

task별 worktree, 다중 relay, 장기 보존, Windows 자동 시작, 사용자 알림을 운영 기준으로 마무리한다.

각 단계는 이전 단계의 실제 E2E가 통과하기 전 시작하지 않는다.

## 12. Chief가 직접 결정해야 하는 항목

Claude는 아래 선택을 임의로 확정하지 말고 선택지·권고·비용·위험을 짧은 결정 카드로 제시한다.

- 재부팅 후 자동 시작 수준까지 v1에 포함할지
- 작업 스케줄러와 장기 실행 runner 중 운영 방식
- Claude/Codex 호출 실패의 최대 재시도와 대기 시간
- runtime 기록의 보존 기간과 저장 위치
- 자동 재작업을 허용할 결함 범위
- Chief 알림 수단
- 제품 코드가 dirty한 상태에서 감리를 허용할지
- 장기적으로 별도 PC·CI runner로 이전할지

## 13. Claude의 첫 산출물

이 가이드를 받은 Claude는 곧바로 코딩에 들어가지 말고 먼저 다음을 제출한다.
